# 第 4 章｜文件读取：参数解析与窗口构造

本章学习任务：理解 read 的参数校验、文件访问和窗口构造，分析缺失文件与输出截断的处理。

## 04.1 基本概念

程序通过文件路径定位读取目标，当前工作目录提供相对路径的解析起点。Session 和生效的文件 Provider 一起推导出 `README.md` 对应的实际地址。后端系统遵循统一的文件接口约定：该接口定义了读取操作及返回数据的格式，具体后端环境负责处理本机或远端等不同场景下的路径计算与文件提取。

工具的参数契约限制了输入字段的名称、类型与取值。schema 定义了基本数据结构，比如路径是字符串、行号是数字；解析函数负责检验具体数值、填充缺省配置，将这些数据转化为执行体接受的内部输入格式。读取窗口负责暂存当前挑选出的文本行，并随同总行数与截断标志一起返回，模型依靠这些信息判断后续是否需要继续读取。

流式文件读取采用分批提交文本给窗口构造器的方法，防止大文件一次性占据大量内存。模型的流式响应同样按批次输出生成的文本，两种机制分别处理文件输入与模型输出。最终的读取结果受限于行数、单行字符数和总输出字节数上限，并在结果中标注实际留存的数据区间。第 18 章会展示结构化读取结果转换成模型文本及界面元数据的完整过程。

字节是衡量数据存储与传输的基本单位。UTF-8 编码将字符映射为字节序列，单个汉字通常由多个字节组成。随后模型的 tokenizer 会将文本再次编码为 token。计算文件字节数、统计文本行数以及估算模型 token 数各有独立的规则，工具的输出容量限制与模型自身的上下文余量由不同的机制分开管理。

工具执行前需经过通用准入检查；放行后依次进行参数解析、读取方式选择及窗口构建。调用请求被安全策略拦截，与执行时遇到文件不存在错误，分属截然不同的两个校验阶段。

## 04.2 沿一个任务看完整流程

设想一份有五行的 README 文件，工具传入参数包括路径 README.md、offset 取 2、limit 取 2。调用发起后先由 ToolRuntime 完成准入校验；放行之后，defineTool 的包装函数验证输入符合 schema 定义，接着 read 执行体确认路径非空并且行号参数为正整数。这些合法的外部输入随之转换为内部属性 filePath、offset 与 limit。底层文件服务解析目标地址并获取文件元数据，再根据文件大小决定执行一次性读取还是流式读取；窗口构造器从中截取第二和第三行，该截取过程同时受到其他预设输出上限的约束。

当请求缺失 offset 参数时，程序默认从第 1 行开始读取；缺失 limit 参数时，采用当前环境配置的默认行数限制。若传入 0、负数或超出配置上限的 limit 值，程序会进入参数错误处理分支。文件大小无法获知时，程序固定走流式读取路径，以此防止某些后端因体积不明而提前将任意大小的文件整体载入缓存。

读取结果产生后，ToolRuntime 负责验证并将其渲染为特定输出，驱动程序随即将该工具结果追加记录。随后发起的下一次请求会接收到本次构建的读取窗口，模型根据窗口提供的起始行号及文件总行数信息评估是否发起后续续读。

## 04.3 关键机制与设计取舍

### 一次读取的材料变化

![F04A：读取参数怎样变成文件片段](../figures/F04A.png)

图 04A 演示了从输入路径和行范围信息进入文件服务，到构建行窗口、渲染模型文本，最后记录结果的完整步骤。通用准入环节先判定是否允许分派任务，后续的工具执行阶段再承担具体的参数核验及文件读取工作。

`read` 工具接收 `file_path` 以及可选的 `offset` 和 `limit` 参数，起始行号规定从 1 算起。参数的 schema 结构指明了各字段的名称、数据类型以及是否必填等属性；函数 `parseReadArgs` 会过滤空路径、验证行号和读取行数全为正整数，在此期间一并应用配置好的大小上限与缺省默认值。

### 启动注册与调用执行

系统启动期间，文件工具插件会获取其依赖的各项服务，并通过调用 `applyReadTool` 完成工具定义的注册，附带提供相应的使用指导说明。该定义集合内包含功能描述、参数声明、执行逻辑以及输出展示契约。在这个初始化阶段，程序不会去读取用户指定的任何具体文件。

发生实际调用时，请求会先接受通用工具准入审查，依据安全策略决定是否准许执行，此部分的详细规则在第 11 章介绍。通过审查后，包装函数负责校验 schema 结构，`read` 执行体处理具体参数解析，随后借助 `resolveRegularReadTarget` 取得目标路径与文件特征信息。目标文件体积较小时采用一次性整读，一旦大小未知或触及预设阈值便切换至流式读取。`buildWindow` 函数依照给定的行区间、单行长度控制与总字节数上限截取相应文本，同时不间断地扫描后续剩余输入，以便计算出确切的总行数。这个处理结果让模型能够同步获知“当前截取了哪几行文本”以及“原文件总共包含多少行”。

上下文对象中的 `ctx.fs` 依托当前 profile 选定的文件 Provider 予以实现。本机 Provider 负责解析和访问宿主系统路径，SSH Provider 处理远端环境路径；`read` 逻辑依赖同一套抽象接口与它们交互。读取到的结果接着被拆分为供应给模型的文本数据以及用于界面渲染的元数据，关于这两条数据流的合并呈现逻辑详见第 18 章。

### 行、字符和字节

行数限制、单行字符长度与全局输出字节数三项指标共同约束工具的返回体积。超出长度的单行会被预先截断，程序再核算其 UTF-8 字节数以判定是否允许放入窗口。模型拿到这份文本材料后会独立进行 token 编码操作，因此读取 100 行文本所消耗的 token 数量需要依据实际字符内容单独测算。

违规参数会在发起文件读取前触发错误返回。遇到路径失效或指定目标不属于普通文件类型的情况，目标解析阶段会抛出异常，并由通用结果处理链条转化为规范的工具错误。当已读内容触及字节数上限时，窗口随即终止吸纳新的行内容，但依然扫描剩余数据以统计总行数，最后在返回的成功结果里打上截断标记。

### 分析示例：读到哪些行

假定教学文件共计 120 行，调用请求从第 41 行起获取 30 行，同时假设运行期间未触发字节或单行长度的提前截断。算上起始行计算终点即 41＋30−1＝70，因此程序返回第 41 到 70 行的数据，窗口后仍有 50 行尚未返回给调用方。

复算记录：[C4 · 行窗口计算](../examples/calculation-results.json)。

假如关键信息位于文件的第 100 行，调用者需要继续请求后续的行窗口。假若碰上字节数上限导致内容提前在第 60 行终止收集，实际返回区间就锁定在 41 到 60 行；下一次续读应当从第 61 行起步。模型侧每次均需根据返回结果中明确给出的行范围采取行动。

有大小上限的窗口控制了返回文本的体积，方便追踪数据来源，代价则是调用者需要具备识别信息截断及发起续读的能力。一次性整体读取会率先加载全部文本，流式读取则按数据批次输送给窗口构造器；这两条执行路径始终受制于同一组预设的输出上限。

![F04B：完整文件与有限返回窗口](../figures/F04B.png)

图 04B 展示了 120 行文件的三段划分：前 40 行为窗口前的忽略内容，本次处理并返回第 41 至 70 行，第 71 到 120 行保留给未来续读。返回正文内附带的行范围字段指明了当前结果的实际覆盖区域。

### 常见误解

“read 成功等于全文进入上下文”：必须核对行窗口、截断标识及实际返回正文。执行成功与内容完整性属于不同的结果属性。

“模型能直接执行参数里的任意路径”：任何调用都要先通过工具准入评估，再受到文件服务解析与执行边界的约束，不能绕过这些层级。

“行数限制就是 token 预算”：计量单位互不相同，文本材料的数量统计与模型的 token 消耗计算需要独立进行。

## 04.4 源码研读

### E04A · 参数默认值与错误分支

阅读任务：观察 parseReadArgs 完整代码。调用者将模型提交的外部参数连同配置上限一同传入；本次研读需关注程序如何区别处理缺省参数值和不合法的取值。

#### 实现详解

`parseReadArgs` 将 `read` 的外部参数转换为执行体使用的内部输入。外部请求使用 `file_path`、`offset` 和 `limit`；包装函数先检查字段结构与类型，本函数再校验具体值并补齐缺省项。`maxLimit` 来自插件配置，既是未指定 `limit` 时的默认行数，也是本次窗口允许请求的最大返回行数。

路径先经过非空检查：函数对 `file_path` 调用 `trim()`，检查去除首尾空白后的字符串长度，拒绝空字符串和纯空白路径。这个检查不改写路径。返回对象仍使用原始 `file_path` 字符串，只将属性名改为内部的 `filePath`；后续文件服务负责实际路径解析。

行参数分别处理缺省值和显式值。`offset` 未提供时取 1，表示从第一行开始；`limit` 未提供时取 `maxLimit`。显式提供的值必须是有限的正整数，因此 0、负数、小数及非有限数字均会报错。`limit` 通过正整数检查后还要与 `maxLimit` 比较，超过上限就拒绝。`offset` 的参数检查不依赖文件总行数，实际是否越界由读取及窗口构造阶段根据文件内容判断。

例如配置 `maxLimit=100`，调用只提供路径 README.md 和 `limit=2`，内部输入就是 `filePath=README.md`、`offset=1`、`limit=2`。`limit=0` 在正整数检查时失败，`limit=101` 在上限检查时失败。全部参数通过后，执行体才解析目标、获取文件信息并读取。缺省值、参数错误和文件访问错误分别在对应阶段处理，便于判断一次调用在哪一步停止。

代码类型：**真实源码摘录**。证据编号 [E04A](../evidence-index.md#e04a)；下表的数字是原文件行号。

```ts
export function parseReadArgs(args: { file_path: string; offset?: number; limit?: number }, maxLimit: number): ReadInput {
  if (args.file_path.trim().length === 0) throw new Error('file_path must be a non-empty string')
  const offset = args.offset === undefined ? 1 : parsePositiveInteger(args.offset, 'offset')
  const limit = args.limit === undefined ? maxLimit : parsePositiveInteger(args.limit, 'limit')
  if (limit > maxLimit) throw new Error(`limit must be less than or equal to ${maxLimit}`)
  return { filePath: args.file_path, offset, limit }
}
```

### E04B · 大小信息决定文本获取方式

阅读任务：代码处于 read 执行体内部，前置参数解析已完成。target 存储后端确立的具体目标，info 携带文件元数据，caps 限定读取边界，exec.signal 提供操作取消信号，ctx 作为上下文对象输送各项服务。有关 outcome 的计算及最终结果呈现由后续正文详细讲解。

#### 实现详解

`read` 执行体取得合法参数后，先确定文本的获取方式，再从文本中构造返回窗口。它调用 `resolveRegularReadTarget`，由当前文件 Provider 解析路径并确认目标是可读取的普通文件。返回的 `target` 表示后端可访问的目标，`info` 提供文件信息，包括可选的大小；`target.displayPath` 用于结果中的路径显示。

文件大小已知且严格小于 `streamMinSize` 时，程序用 `readText` 一次取得完整文本，再包装为单个文本批次。文件大小达到阈值，或后端没有提供大小时，程序改用 `streamText` 按批次提供文本。未知大小采用流式路径，避免先缓存一个无法确定体积的完整文件。两种接口都接收 `exec.signal`，将本次调用的取消信号传递给文件后端。

两种获取方式随后统一进入 `buildWindow`。窗口按 `offset` 跳过起始行之前的内容，最多保存 `limit` 行，并用 `maxLineLength` 和 `maxBytes` 分别限制单行长度与输出字节数。流式路径提供多个文本批次，整读路径提供包含完整文本的单个批次。构造器处理跨批次的行边界，即使窗口已满或达到字节上限，也继续扫描剩余输入，以统计准确的文件总行数。获取方式决定文本怎样到达，窗口规则决定哪些内容最终返回。

例如文件有 120 行，请求从第 41 行取 30 行，且其他上限没有提前截断，结果保存第 41—70 行并报告总行数 120。若字节上限使保存停在第 60 行，窗口返回第 41—60 行，仍统计完整文件的行数。执行体据此构造规范值并记录本次文件观察；输出契约再生成模型文本与界面元数据。模型根据实际返回范围判断是否需要从第 61 行继续读取。

代码类型：**真实源码摘录**。证据编号 [E04B](../evidence-index.md#e04b)；下表的数字是原文件行号。

```ts
      const { target, info } = await resolveRegularReadTarget(ctx, exec, input.filePath)

      // Stream when the file is large OR size is unknown, so a size-less backend
      // never buffers an arbitrarily large file.
      const chunks = info.size === undefined || info.size >= caps.streamMinSize
        ? await ctx.fs.streamText(target, exec.signal)
        : [await ctx.fs.readText(target, exec.signal)]
      const window = await buildWindow(
        chunks,
        { offset: input.offset, limit: input.limit, maxLineLength: caps.maxLineLength, maxBytes: caps.maxBytes },
        target.displayPath,
      )
```

## 04.5 理解检查与讲解问答

### 问题 1 · offset=2、limit=2 是否代表文件只有两行？

讲解：传入 offset=2 规定从第 2 行起读，limit=2 控制最大返回行数为两行。原始文件整体行数由返回信息内的总行数字段单独传达。

### 问题 2 · 未提供 limit 与提供 limit=0 一样吗？

讲解：缺省时使用配置默认值；0 不满足正整数条件，会产生参数错误。

### 问题 3 · 未知大小的文件为什么走流式路径？

讲解：此策略旨在避免强行缓存体积未知的巨型文件，并顺势安排窗口构造器通过分批接收机制截取限定范围的输出。
