# 第 1 章｜从一句话到一个结果：DeepSeek Harness 究竟做什么

本章学习任务：沿读取 README 的案例，说明谁接纳任务、谁调用模型、谁读取文件、谁保存结果；区分工具提议、接纳回执与任务完成。

## 01.1 基本概念

计算机程序是一组交给计算机执行的步骤；数据是步骤处理的信息，例如一段任务文字或一份文件内容。大语言模型（Large Language Model，LLM）接收材料、生成文字或工具调用建议。运行模型的服务与管理本地文件的程序是不同的参与者。模型提出读取建议，文件服务实际读取，再把结果交给模型用于后续回答。

Agent 在本书中指能够围绕任务反复获取材料、调用模型并使用工具的运行单元。Harness 组织这些步骤，DeepSeek Harness 是本书研究的具体项目。Tool 是由程序实现的一项操作，像 `read` 读取文本；模型看到的是工具的名称、用途和参数说明。参数是告诉操作“这次处理什么”的输入，例如文件路径；结果是操作返回的信息，例如第 1—20 行文字。

Session 保存一次持续交互的身份和记录。日志是按发生顺序保存的记录集合；Session 事件日志因此能回答“先发生了什么，随后发生了什么”。消息是供对话使用的内容；事件是“某件事已经发生”的记录，例如开始一次工具调用。消息内容参与对话，轮次开始、工具调用等事件记录运行过程。Inbox 保存已经接纳、尚待领取的输入；它把下一轮输入与下一步输入分开保存，由驱动在对应时点领取。

请求是向另一方提出的操作要求，例如“为这个 Session 接纳一段文字”。请求标识用来识别同一次提交，防止重复排队。客户端发起请求并接收结果，例如网页界面；Host 提供并处理项目能力。入口先返回接纳回执，后台任务随后继续运行。

附件是随文字一同提交的文件或图像等材料；只有文字时不需要附件。后文会解释附件如何进入请求。

上下文是本次请求提供给模型使用的材料，例如任务文字、行为规则和已读到的文件。system prompt 是用于向模型表达系统行为规则的那部分文字；模型根据这段文字生成回答；文件访问由工具链和文件服务控制。

这条流程有六位参与者：用户、接纳入口、Agent 驱动、LLM 服务、ToolRuntime 和 Session。接纳入口收下任务，驱动安排步骤，LLM 服务调用模型，ToolRuntime 组织工具执行，Session 保存过程与结果。

对照短源码还会用到几个基础词：函数封装一组可调用步骤，变量给值取名，对象把相关字段放在一起，属性是对象的一项字段，返回值是函数交给调用者的结果，类型说明值应有什么形状。第 2 章会用真实写法展开它们。

## 01.2 沿一个任务看完整流程

先看成功路径：用户要求“读取 README，概括项目用途和三项功能”。用户提交一句话，入口建立消息并排入 Inbox，返回“已接纳”。驱动领取输入，组装第一次模型请求；模型提出读取建议。工具服务记录调用，按安全规则判断是否放行，这一步称为准入。获准后，文件服务读取文本。工具结果进入 Session，第二次请求才有这些文字可用。模型生成总结，驱动记录轮次结束，界面显示结果。

| 时点 | 谁处理 | 输入与变化 | 已知结论 |
| --- | --- | --- | --- |
| 提交 | 接纳入口 | 输入文字变成待处理消息 | 接纳成功，不代表已读文件 |
| 第一次请求 | 驱动与模型 | 用户目标和工具说明变成读取提议 | 提议还没有执行 |
| 工具阶段 | 工具与文件服务 | 路径变成有大小上限的文本片段或错误结果 | 查调用与结果才能确认读取 |
| 第二次请求 | 驱动与模型 | 历史新增工具结果 | 总结可以依据获取的材料 |
| 收尾 | 驱动、记录与界面 | 记录结束原因并显示产物 | 显示最终总结和结束原因 |

入口先检查是否有文字或附件，两者都没有就拒绝接纳。接纳以后若文件不存在，工具返回错误，后续请求可据此解释资料不足或选择其他目标。模型请求失败时，驱动先记录失败，再由恢复策略决定是否重试；工具阶段等待成功响应。这个案例的主循环包含两次相互依赖的请求：第一次提出读取，第二次使用读取结果。主循环就是驱动反复执行“请求模型—执行工具—再请求”的过程。

## 01.3 关键机制与设计取舍

### 先看材料怎样流动

![F01A：请求、文件读取和回答之间的材料流动](../figures/F01A.png)

图 01A 按箭头展示成功路径：接纳任务、模型提出 read、文件服务返回窗口、下一次请求使用结果，再生成总结。第一次请求负责提出读取，第二次请求负责利用读到的文本。

1. 用户提交任务，入口把消息放入 Inbox，返回接纳回执。
2. 驱动组装第一次请求。模型提出 Tool Call，指定 read 和参数 `{ file_path: "README.md" }`。花括号里的“名称—值”组合称为对象，这里保存本次读取的路径。
3. ToolRuntime 完成准入，执行包装函数检查参数，再由文件服务读取目标。
4. 工具结果记录到 Session；驱动组装第二次请求，把已获取的文件窗口交给模型。
5. 模型根据这些文字生成总结，驱动记录轮次结束，界面显示结果。

### 把正常路径与失败放在一起

![F01B：接纳结果与任务进展的两个观察范围](../figures/F01B.png)

图 01B 左侧是入口接纳，右侧是后台任务。左侧结束于输入排队，右侧继续经历模型请求、工具执行和轮次结束；文件不存在、模型限流等错误出现在后续运行中。

`accepted: true` 是入口接纳本次输入的回执。文件读取和模型生成随后各自产生结果。读取 README.md 时若文件不存在，工具服务构造带错误信息的 `ToolResult`，驱动把它加入历史。下一次模型请求便能根据这个错误说明资料不足，或调整读取目标。

排查错误时，沿处理顺序检查：先查入口是否接纳，再查驱动是否启动，再查模型是否返回合规 Tool Call，最后查工具执行状态与终态事件。

### E01A · 接纳时的身份与来源

阅读任务：位置是 prompt 已通过前面的输入检查之后。已知请求有 Session 标识和请求标识，本段观察怎样定位 Agent、识别重复输入并建立来源对象；后续附件、排队和接纳返回不在此节选中。

代码类型：**真实源码摘录**。证据编号 [E01A](../evidence-index.md#e01a)；下表的数字是原文件行号。

```ts
    const agent = await this.resolveAgent(request.sessionId)
    if (hasPromptRequest(agent, request.requestId)) return { accepted: true }
    const source: MessageSource = {
      kind: 'user',
      rpcId: request.requestId,
      ...(clientTimeZone === undefined ? {} : { clientTimeZone }),
    }
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 329 | const 保存一次结果，await 等待 resolveAgent | 按请求的 Session 标识获取本次接收输入的 Agent 对象。 |
| 330 | if 判断条件，return 提前结束方法 | 已识别的 requestId 不再排入一次，返回已有接纳确认。 |
| 331 | 冒号声明类型，花括号开始对象 | source 将保存本次用户消息的来源字段。 |
| 332 | 字符串属性 kind | 将来源类别记为 user，区别于其他消息来源。 |
| 333 | 点号读取属性，属性赋值 | 把入口的请求标识记成 rpcId，供后续关联使用。 |
| 334 | 三点号展开对象，三元表达式选择分支 | 未提供时区不增加字段；提供时加入规范化的时区值。 |
| 335 | 结束对象字面量 | source 建立完成，后续创建用户消息时使用它。 |


执行推演：已识别的请求标识直接得到接纳回执；新标识则继续建立用户消息的来源信息，随后进入附件处理、排队和回执返回。

### E01B · 记录工具提议，而不是宣布完成

阅读任务：这是 executeToolCalls 使用的调用记录辅助函数。参数已经包含 Session、轮次、步骤和一个工具调用块。本段观察保存哪些关联信息以及返回什么。

代码类型：**真实源码摘录**。证据编号 [E01B](../evidence-index.md#e01b)；下表的数字是原文件行号。

```ts
function appendToolCall(session: Session, turn: number, step: number, block: ToolCallBlock): SessionSeq {
  const event = session.append('tool/call', { turn, step, callId: block.id, name: block.name, arguments: block.arguments })
  return event.seq
}
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 263 | function 定义函数，冒号给参数与返回值标注类型 | 调用者交入本次工具调用所属的 Session 和推进位置。 |
| 264 | const 接收方法返回的事件，对象简写使用同名参数 | 把调用身份、名称、参数和所属 turn/step 追加到 Session 记录。 |
| 265 | return 读取事件的 seq | 返回刚创建的序号，供结果与调用关联。 |
| 266 | 右花括号结束函数 | 记录辅助函数到此结束，真实工具动作在调用者的后续路径中。 |


执行推演：当前日志有 9 项时，新调用得到序号 9。函数返回该序号，供后续结果关联；调用者接着推进工具执行，存储写入由 Session 的监听器另行处理。

## 01.5 理解检查与讲解问答

### 问题 1 · 入口返回 accepted 后，能说已经读完 README 吗？

讲解：不能。这里只确认输入已接纳。还要经过领取、模型提议、准入与读取，才有文件结果。

### 问题 2 · 模型给出了三点总结，怎样检查它依据了文件？

讲解：先找到 read 的调用记录和成功结果，确认返回的行范围覆盖总结所用的材料，再逐项对照总结与原文。这样才能把总结中的结论追到实际读取结果。

### 问题 3 · 第一次模型请求与第二次请求的材料有什么差别？

讲解：成功案例的第二次请求增加了读取结果。它依赖前面的真实执行，不是独立重复同一份输入。
