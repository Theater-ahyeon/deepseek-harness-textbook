# 第 1 章｜DeepSeek Harness 的架构与任务流程

本章学习任务：理解任务接纳、模型调用、工具执行与 Session 记录的分工，区分各阶段的输入和结果。

## 01.1 基本概念

程序由可执行的指令构成，数据则是指令要处理的信息，例如任务文本与文件内容。大语言模型（Large Language Model，LLM）读取输入，接着生成文本或提供工具调用建议。模型服务负责处理生成过程，文件服务用来访问文件；工具链执行模型建议后，返回的文本才能成为后续回答的依据。

Agent 是一个持续运行的单元，它围绕任务不断组装上下文、调用模型和使用工具。Harness 提供这套过程的运行机制，本书重点分析的具体实现即为 DeepSeek Harness。Tool 指代程序实现的操作，比如负责读取文本的 `read`。工具定义向模型告知其名称、用途及参数含义；调用参数说明本次操作的目标，工具结果则带回执行所得的信息，比如文件第 1—20 行的内容。

Session 用于维持持续交互的身份，并记录一条事件日志。日志按先后顺序保存消息、轮次边界和工具调用等事件。消息存放对话文本，过程事件记录任务走到哪一步；后续的模型请求会使用从这段日志派生出的消息历史。Inbox 属于 Agent，用于存放已接纳但没领取的输入，它分别维护了下一轮和下一步的消息队列，供驱动在对应边界提取。

请求代表调用方希望服务去做的操作，比如向某 Session 提交文字。请求标识用于识别重复提交，避免同一次请求重复排队。网页等客户端负责发起请求与接收结果，Host 提供服务的调用接口。提交入口返回接纳回执后，任务本身会在后台继续推进。

附件是随同消息提交的文件或图片等资料。如果请求只有纯文本，可以省略附件；附件的处理与传输细节在后续章节中探讨。

上下文是本次请求交给模型阅读的所有材料，涵盖任务说明、行为规则和获取到的文件等。system prompt 负责向模型陈述系统级别的行为规则；模型以此为要求生成回复；具体的文件访问权则由工具链与文件服务负责把控。

这条工作流涉及用户及五类组件：接纳入口、Agent 驱动、LLM 服务、ToolRuntime 和 Session。接纳入口验证并接收输入，驱动负责调度，LLM 服务请求模型，ToolRuntime 管理工具执行，Session 记录状态与结果。

后续源码讲解会涉及以下概念：函数将步骤封装以供调用，变量用于绑定值，对象把相关属性归拢在一起，返回值是函数向调用方提供的结果，类型用来约束和描述值的结构。第 2 章将结合代码详述这些概念。

## 01.2 沿一个任务看完整流程

以“读取 README，概括项目用途和三项功能”为例，成功的路径由提交任务开始。入口建立对应的消息并放入 Inbox 队列，随后向客户端返回接纳回执。驱动提取输入后准备第一次模型请求，模型根据目标返回了读取该文件的工具调用。ToolRuntime 记录下这次调用并检验准入条件；判定获准后，文件服务去读取真实文本。读回的内容随后存入 Session，变成了第二次模型请求上下文的一部分。模型依据这份文本完成总结，驱动记录当前轮次结束，最终客户端界面展示该总结结果。

| 时点 | 谁处理 | 输入与变化 | 已知结论 |
| --- | --- | --- | --- |
| 提交 | 接纳入口 | 输入文字变成待处理消息 | 接纳成功，不代表已读文件 |
| 第一次请求 | 驱动与模型 | 用户目标和工具说明变成读取提议 | 提议还没有执行 |
| 工具阶段 | 工具与文件服务 | 路径变成有大小上限的文本片段或错误结果 | 查调用与结果才能确认读取 |
| 第二次请求 | 驱动与模型 | 历史新增工具结果 | 总结可以依据获取的材料 |
| 收尾 | 驱动、记录与界面 | 记录结束原因并显示产物 | 显示最终总结和结束原因 |

入口首先检查请求里有没有文字或附件，若两者皆无就会拒绝接纳。接纳之后，如果指定的文件不存在，工具将返回错误，后续的请求就能根据此错误告知资料不足，或者换一个目标读取。模型请求失败时，驱动先记录失败，再由恢复策略决定是否重试。成功的助手消息提交后，驱动根据其中的工具调用与停止条件决定是否进入工具阶段。这个案例的主循环包含了两次彼此依赖的请求：第一次提出读取提议，第二次使用读取到的结果。主循环就是驱动反复执行“请求模型—执行工具—再请求”的运转过程。

## 01.3 关键机制与设计取舍

### 请求与结果的数据流转

![F01A：请求、文件读取和回答之间的材料流动](../figures/F01A.png)

图 01A 通过箭头展现了成功路径：接纳任务、模型提议 read、文件服务返回文本窗口、下一次请求带上该结果，最终生成总结。第一次请求用来提出读取，第二次请求用来消费读出的文本。

1. 用户提交任务，入口将消息排入 Inbox，并给出接纳回执。
2. 驱动构造第一次模型请求。模型返回 Tool Call，指定使用 read 和参数 `{ file_path: "README.md" }`。花括号包裹的“名称—值”组合即对象，此处保存了待读取的路径。
3. ToolRuntime 验证准入，运行包装函数校验参数，再交由文件服务读取目标文件。
4. 工具结果被记录进 Session 日志；驱动组装第二次请求，把拿到的文件窗口传给模型。
5. 模型基于这些文字产出总结，驱动记录轮次结束，最终界面上呈现该结果。

### 接纳与后台执行的分工

![F01B：接纳结果与任务进展的两个观察范围](../figures/F01B.png)

图 01B 左侧展现入口接纳，右侧展现后台任务。左侧在输入排队后结束，右侧则接着处理模型请求、工具执行和轮次结束；诸如文件不存在、模型遭限流等错误，均在后续运行阶段浮现。

`accepted: true` 只表明入口接纳了当前输入。文件读取情况与模型生成的文本稍后才各自得出结果。比如读取 README.md 遇到文件不存在时，工具服务会构造携带错误详情的 `ToolResult`，由驱动把它追加到历史里。下一次模型请求便可根据该错误向用户解释资料不足，或调整目标。

排查故障时，应顺着处理顺序推进：先确认入口是否接纳，再看驱动是否启动，接着看模型有没有给出合规的 Tool Call，最后核查工具执行状态与最终事件记录。

## 01.4 源码研读

<a id="e01a"></a>

### E01A · 接纳时的身份与来源

阅读任务：以下节选处于 prompt 输入校验环节之后。请求已携带 Session 标识与请求标识，代码依此定位目标 Agent、过滤重复输入，并构建消息来源对象。随后的流程将处理附件、把消息排队并交回接纳回执。

#### 实现详解

一次 prompt 请求需要把客户端提交的内容传递给指定 Agent，同时留存本次提交的身份。请求自带两个作用不同的标识：sessionId 指明接收输入的 Session，requestId 标记客户端的本次提交动作。入口先凭借 sessionId 获取 Agent 对象，往后的查重、排队与附件绑定都围绕它展开。比如两名用户向不同 Session 提交相同文字，依然属于两次独立输入。

获取 Agent 之后，入口要确认当前 requestId 是否曾经出现。核对范围涵盖 Agent 的两类 Inbox 队列以及 Session 里登记的用户消息：尚未领取的输入可在队列中识别，已经领取并登记的用户消息可在历史中查询。若发现对应记录便直接给出 accepted 回执，以免重复排队。此处只对比请求身份，同一段文字换成新 requestId 就是全新提交。若客户端因网络不稳重发相同请求，该机制能确保已有的接纳记录继续生效。

新请求随后创建 MessageSource，即附属于用户消息的来源信息。kind 字段把它记为用户输入，rpcId 留存 requestId，使后续的正式消息能与客户端本地的 pending 条目关联。客户端时区此前已做过格式化与有效性校验；提供了有效时区才会写入对象，没提供则维持缺省。来源对象负责存放提交时的元数据，任务文字与附件另外安排在消息内容里组织。

该阶段完结后，入口继续检验图像能力、解析文件凭据并接纳附件，再创建出用户消息。steer 模式将消息送至下一步，普通提交通过 followup 排进下一轮；等附件绑定完成，入口就返回 accepted。以“读取 README”为例，此时确认的是输入已排入队列且身份可追踪，之后再由驱动提取消息、调用模型并执行读取。请求回执与后期的任务事件共同组成了客户端观察单次提交的全链路轨迹。

代码类型：**真实源码摘录**。证据编号 [E01A](../evidence-index.md#e01a)；下表的数字是原文件行号。

```ts

    if (hasPromptRequest(agent, request.requestId)) return { accepted: true }
    const source: MessageSource = {
      kind: 'user',
      rpcId: request.requestId,
      ...(clientTimeZone === undefined ? {} : { clientTimeZone }),
    }
```

| --- | --- | --- |

| 331 | 冒号声明类型，花括号开始对象 | source 将保存本次用户消息的来源字段。 |

### E01B · 工具调用的关联记录

阅读任务：appendToolCall 是 executeToolCalls 里用来登记记录的辅助函数。它的输入参数包括 Session、turn、step 以及工具调用块；该函数负责把调用信息追加写入 Session 的内存日志，并交回一个事件序号供之后的结果关联使用。

#### 实现详解

模型提出工具调用后，执行器先建立调用记录，供后续结果关联。appendToolCall 接收四组信息：所属 Session、当前 turn、当前 step，还有模型生成的 ToolCallBlock。调用块持有本次调用的 id、名称和参数；轮次与步骤标明了它位于任务推进的哪一环节。同一轮里多次调用 read 时，凭借身份与推进位置便能区分具体是哪一次。

辅助函数将这些字段构造成 tool/call 事件交予 Session.append。Session 为事件进行快照并校验，把它追加到内存日志中，再通知观察者。调用方由此拿到包含 seq 的事件对象，seq 代表新记录在当前日志里的位置。若原日志已有 9 项（位置 0—8），本次调用就占用位置 9。其余消息与过程事件也会占据位置，因此 seq 反映当前 Session 中各类事件的登记顺序。

函数把 seq 返回给执行器，待执行器产出工具结果时就传入此位置。结果事件通过关联字段指回原调用，并保留调用 id、turn 与 step。无论是成功读取、准入拒绝还是取消跳过的结果，都能通过这套方式解释：哪一次提议促成了何种结论，结论又属于什么步骤。界面展示或查询历史时，无需凭工具名称盲目配对。

以模型提议 read 为例，调用事件率先进入 Session，此后执行器才去准备准入和派发。获准且文件存在时，文件服务交回窗口内容，接着登记与原调用绑定的结果；若被拒绝则立刻生成拒绝结果。Session 的存储监听器会另行安排把记录写入文件，appendToolCall 返回时建立的仅是调用发生的内存事实。顺着“调用记录—准入与执行—结果记录”去观察，便可复原一次调用的全流程。

代码类型：**真实源码摘录**。证据编号 [E01B](../evidence-index.md#e01b)；下表的数字是原文件行号。

```ts
function appendToolCall(session: Session, turn: number, step: number, block: ToolCallBlock): SessionSeq {
  const event = session.append('tool/call', { turn, step, callId: block.id, name: block.name, arguments: block.arguments })
  return event.seq
}
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 263 | function 定义函数，冒号给参数与返回值标注类型 | 调用者交入本次工具调用所属的 Session 和推进位置。 |
| 264 | const 接收方法返回的事件，对象简写使用同名参数 | 把调用身份、名称、参数和所属 turn/step 追加到 Session 记录。 |
| 265 | return 读取事件的 seq | 返回刚创建的序号，供结果与调用关联。 |
| 266 | 右花括号结束函数 | 记录辅助函数到此结束，真实工具动作在调用者的后续路径中。 |


执行推演：假定当前日志已有 9 项记录，新增调用拿到序号 9。函数将此序号返回，以便与后续结果相连；调用者随即推进实质的工具执行，至于落盘存储则由 Session 的监听器另行负责。

## 01.5 理解检查与讲解问答

### 问题 1 · accepted 回执确认了哪个处理阶段？

讲解：accepted 回执确认入口已经接纳输入。文件读取结果在驱动领取消息、模型提出调用、通过工具准入并执行读取之后产生。

### 问题 2 · 如何核对总结与实际读取内容的对应关系？

讲解：应该先定位 read 的调用记录与成功结果，确认读回的行号范围涵盖了总结所依赖的内容，随后逐项对比总结文本与原内容。这样就能将总结里的结论溯源到具体的读取产物。

### 问题 3 · 两次模型请求的上下文有什么差异？

讲解：在这条成功路径中，第二次模型请求新增前一步获得的文件窗口，模型据此生成总结。两次请求通过工具读取结果形成数据依赖。
