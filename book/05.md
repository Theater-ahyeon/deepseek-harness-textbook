# 第 5 章｜Session 与日志：发生过的事怎样保存和还原

本章学习任务：说明事件怎样从当前 Session 进入记录和存储；区别 append、flush、重放与派生视图，判断崩溃时哪些事实已有持久证据。

## 05.1 基本概念

Session 事件日志按顺序记录消息、工具调用和运行边界。终端调试输出属于另一条输出通道。序号说明事件在 Session 中的位置；时间记录发生时刻，序号决定事件顺序和连续性。

快照是在某个时刻获取的一份数据副本；冻结让已经建立的对象不能再被直接改写。派生是从事实计算另一种数据，例如从消息类事件形成模型历史。投影是按特定问题整理状态，例如当前有哪些待办。快照保留某个时刻的数据，派生生成新的数据形式，投影持续维护某项业务状态。

可序列化表示数据能够按约定转成可保存或传输的形式，例如对象中的字符串与数字可形成 JSON，带任意函数的运行对象则不能直接当作同样的事实数据。冻结是限制对象修改，不是把它写到存储。缓存是保存已经算过的结果供后续复用，例如消息派生结果；原始记录变化后要使相关缓存失效。

持久化把运行内存中的资料交给能够在退出后保留它的存储。JSON 是表示对象、数组等值的文本格式；JSONL 每行保存一个 JSON 记录。追加事件首先改变 Session 内的历史，并通知订阅者；JSONL Provider 把写入排队。flush 等待存储 Provider 排空缓冲并完成写入。Session.append 更新内存日志，存储 writer.append 才执行持久写入。

Session 恢复还原已经记录的对话和运行过程；文件当前内容由文件服务读取，外部进程状态由进程 Provider 查询。

## 05.2 沿一个任务看完整流程

设 Session 已有 0—8 号事件，新工具调用追加为 9 号。Session 先创建数据副本，检查事件与 Surface 规则，再加入内存日志并通知观察者。Surface 是参与组装模型请求的消息序列，下一节展开它的维护方式。JSONL 写入者接到通知后安排存储，界面观察者则更新显示状态；同一条事件分别驱动这两项工作。

| 检查点 | 处理结果 | 后续工作 |
| --- | --- | --- |
| append 返回 | Session 追加并发布事件 | 实时存储缓冲继续写入 |
| 消息派生返回 | 从当前 Surface 形成消息数组 | 模型使用这份历史组织请求 |
| flush 成功 | 存储监听器完成排空和持久化等待 | 调用者继续关闭或后续处理 |

重新打开 Session 时，存储 Provider 读取可支持的数据格式，恢复逻辑事实；投影再按这些事实恢复业务视图。格式迁移与运行恢复不同：迁移让旧表示能被当前代码理解，恢复则处理先前中断的运行状态。外部终端的连接与进程状态由对应 Provider 重新确认。

## 05.3 关键机制与设计取舍

### 一份事实，多个消费方

![F05A：Session 事实派生消息、状态和持久记录](../figures/F05A.png)

图 05A 由 Session 事件分出三个用途：模型历史按 Surface 派生，界面和状态投影消费过程事件，存储监听器排队写入持久记录。

持久日志保存已追加的底层过程事件，模型消息则由当前 Surface 派生。Surface 是参与组装下次模型请求的消息节点序列，规定哪些消息按什么顺序进入请求。Surface 管理器根据事件维护这份序列。生成途中的流式文本片段仍是临时观察；循环正式提交助手消息后，该消息才成为可交给持久化 Provider 处理的记录。提交使消息进入 Session 内存日志，flush 则等待存储写入完成。

### append 怎样建立一个事实

`Session.append` 先创建可序列化的数据副本，再构造带序号和时间的冻结条目。可序列化表示数据能按约定转换成保存格式。接着，方法校验事件字段，并检查 Surface 约束：这条事件是否符合当前消息序列的更新规则。两项校验通过后，事件进入日志并发布。副本与冻结共同防止调用者后来修改原对象时改变已记录的历史。

随后 Session 发布该事实，消费方依各自接口更新或排队处理。消息派生 `deriveMessages` 遍历当前 Surface 中的消息节点，生成新的消息数组。状态投影则按注册的事件消费规则维护可查询状态。消息视图处理消息节点，状态投影处理各自关心的过程事件。

DSH 的 JSONL Provider 为每个 Session 管理一条写入通道，称为写入句柄。它监听 `session/event`，将新条目排入后台缓冲；收到 `session/flush` 后，先等待缓冲排空，再等待 writer.flush 完成。Session 通过事件通知存储，存储组件负责实际文件读写。

### 投影和持久化屏障

投影可理解为“按用途整理事实”。给定同一份订单记录，可以整理出当前状态，也可以整理出明细清单；软件里同理。Session 投影同样按各自的事件规则更新结果。

JSONL 的持久化链分为两层：实时监听器先把事件放进缓冲，writer.append 再按序写入文件并调用文件同步。session/flush 先等待 drainLive 排空实时缓冲，再等待 writer.flush；尚未写入事件的空 Session 会在此创建并同步头记录。文件追加或同步失败时，存储层关闭追加句柄，再把文件截回本批写入前的长度并同步，随后抛出原错误。若回退也失败，就用 AggregateError 同时报告写入错误与回退错误。成功回退后，本批可以按未推进的游标重试。

### 分析示例：日志行数为什么不是对话数

教学片段有一条用户消息、两条助手消息和一条工具结果，另有一条工具调用、两项轮次边界和四项步骤边界，共 11 个列出的事件。这里得到的消息数是 4，工具调用数是 1，日志片段事件数是 11；三个值回答不同问题。

复算记录：[C5 · 消息与事件计数](../examples/calculation-results.json)。

统计对话消息时筛选消息事件；统计工具调用时筛选 tool/call；统计运行轨迹时再纳入轮次、步骤、请求信息和用量。回放按这些事件还原对应模型响应。

### 写入时间线与故障判断

![F05B：Session 追加与存储完成的等待边界](../figures/F05B.png)

图 05B 对比 append 返回和 flush 等待。append 完成 Session 内追加与通知，flush 等待存储监听器排空并完成写入；后台写入从接到通知时就可以开始。

回到读取任务：用户输入、助手工具提议、工具调用、工具结果、助手总结和轮次边界依次进入事件序列。消息视图组织后续请求，页面更新显示，存储 Provider 写入文件。页面已经显示而写入失败时，问题出在存储链；刷新后临时文字消失时，先查它是否曾被提交为助手消息，再查对应事件是否写入文件。

### 常见误解

“日志里每一项都发给模型”：消息派生只处理相应的消息节点，过程边界另有用途。

“可从日志还原，所以视图必须与原日志相同”：派生视图可以按用途选择、组合和更新；压缩会在第八章进一步改变当前 Surface。

“页面显示了，所以已经保存到磁盘”：界面与存储分别消费事件。查看存储写入和 flush 的结果，才能确定对应记录是否已保存。

### E05B · 后台写入与持久化等待

阅读任务：这两项监听由 JSONL 存储组件注册。回调在收到相应 Session 事件时执行；不是注册当场立即写入。重点区分 enqueueLive 与等待 drainLive/flush。

代码类型：**真实源码摘录**。证据编号 [E05B](../evidence-index.md#e05b)；下表的数字是原文件行号。

```ts
    ctx.on('session/event', (session: Session, event) => {
      this.writers.get(session.id)?.enqueueLive(event, (error) => {
        ctx.logger.warn(`session-persistence: background write for session "${session.id}" failed (buffered events retained): ${String(error)}`)
      })
    })
    ctx.on('session/flush', (session: Session) => {
      const writer = this.writers.get(session.id)
      if (writer === null || writer === undefined) return undefined
      return (async () => {
        await writer.drainLive()
        await writer.flush()
      })()
    })
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 535 | on 注册事件回调，箭头函数接收 Session 与事件 | 订阅 Session 新事实，稍后发生事件才进入函数体。 |
| 536 | 可选调用与回调参数 | 有对应 writer 才排入实时写入队列，并设置失败处理。 |
| 537 | 模板字符串和 warn 调用 | 后台写入失败时记录 Session 与错误，提示缓冲事件仍保留。 |
| 538 | 结束 enqueueLive 的错误回调 | 失败处理定义结束，不是把错误转成成功写入。 |
| 539 | 结束新事件监听器 | 登记的监听器继续等待后续事件。 |
| 540 | 注册另一项监听 | session/flush 是要求等待持久化边界的事件。 |
| 541 | const 获取 Map 中的 writer | Map 是按键查值的集合；这里按当前 Session 身份找到它的存储写入者。 |
| 542 | if 与 return | 没有 writer 时本监听不承担刷新工作。 |
| 543 | async 箭头函数立即调用并返回 Promise | 把内部异步排空任务交给等待 flush 的调用者。 |
| 544 | await 排空实时缓冲 | 先等待已经排入的实时事件处理完。 |
| 545 | await 等待刷新 | 再等待写入者完成其刷新契约。 |
| 546 | 结束函数并立即调用 | 向外返回这次等待任务。 |
| 547 | 结束 flush 监听器注册 | 之后 Session 服务可收集并等待这些刷新监听者。 |


执行推演：新事件发出后，如果有写入者则排入后台缓冲；后台失败会记录警告并保留缓冲事件。显式 flush 的处理获取同一写入者，先排空实时缓冲，再等待刷新。

## 05.5 理解检查与讲解问答

### 问题 1 · append 返回以后，能宣布已经完成磁盘持久化吗？

讲解：不能。追加首先完成 Session 内记录与发布，后台写入有单独的 flush 等待边界。

### 问题 2 · 为什么事件与聊天消息数量不同？

讲解：事件包括生命周期和状态记录，只有相应消息节点参与消息派生。

### 问题 3 · 恢复 Session 后，原来的外部终端一定恢复了吗？

讲解：Session 恢复对话记录和运行事实；终端进程保存在执行环境中，需要由进程 Provider 确认它是否仍在运行、连接是否可用。
