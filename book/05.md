# 第 5 章｜Session 事件日志、投影与持久化

本章学习任务：追踪事件从内存日志进入存储与派生视图的过程，解释 append、flush 和 Session 恢复。

## 05.1 基本概念

Session 事件日志按登记顺序记录消息、工具调用和运行边界。终端调试输出使用另一条通道。序号表示事件在当前 Session 日志中的位置，用于检查顺序与连续性；时间戳记录事件建立的时刻。

快照保存特定时刻的数据副本，冻结限制对象及其内部数据被修改。派生根据已有事实生成新的数据形式，例如从消息事件构造模型历史；投影按事件规则持续维护可查询状态，例如最新的待办列表。快照与冻结用于保留稳定数据，派生与投影分别负责构造视图和维护业务状态。

可序列化数据可以按约定转换为存储或传输格式。例如，包含字符串和数字的对象可表示为 JSON，带有函数等运行时成员的对象需要另行处理。冻结保护内存对象，持久化负责写入存储。缓存复用已经计算的派生结果，原始记录变化后使相关缓存失效。

持久化将内存数据写入程序退出后仍可保留的存储。JSON 用文本表示对象、数组等值，JSONL 每行保存一条 JSON 记录。Session.append 更新内存日志并通知订阅者，JSONL Provider 将事件排入缓冲，再由 writer.append 追加到文件。flush 提供显式等待点，等待缓冲排空及存储层刷新。

恢复 Session 指的是还原之前记录的对话和运行过程。当前的文件内容由文件服务负责读取，外部进程的存活状态则交给进程 Provider 去查询。

## 05.2 沿一个任务看完整流程

设 Session 已有 0—8 号事件，新工具调用取得序号 9。Session 先创建数据副本，验证事件字段和 Surface 更新规则，再追加到内存日志并通知观察者。Surface 是参与模型请求组装的消息节点序列，下一节介绍其维护方式。JSONL 写入者收到通知后安排存储，界面观察者更新显示，同一条事件分别驱动这两项工作。

| 检查点 | 处理结果 | 后续工作 |
| --- | --- | --- |
| append 返回 | Session 追加并发布事件 | 实时存储缓冲继续写入 |
| 消息派生返回 | 从当前 Surface 形成消息数组 | 模型使用这份历史组织请求 |
| flush 成功 | 存储监听器完成排空和持久化等待 | 调用者继续关闭或后续处理 |

重新打开 Session 时，存储 Provider 读取支持的数据格式，恢复逻辑事实；投影再据此重建业务视图。格式迁移让旧数据表示能被当前代码理解，运行恢复处理先前中断的运行状态。外部终端连接与进程状态由对应 Provider 重新确认。

## 05.3 关键机制与设计取舍

### 一份事实，多个消费方

![F05A：Session 事实派生消息、状态和持久记录](../figures/F05A.png)

图 05A 展示了 Session 事件被分发用于三个独立方向：模型历史依据 Surface 派生而来，界面和状态投影读取并消费过程事件，存储监听器则将事件排入队列以写入持久记录。

持久日志用于保存底层过程事件，模型消息则从当前 Surface 派生。Surface 是参与组装下次模型请求的消息节点序列，规定哪些消息按什么顺序进入请求，由 Surface 管理器根据事件维护。生成途中的流式文本仍是临时观察；主循环正式提交助手消息后，它才进入 Session 内存日志并交由持久化 Provider 处理。存储监听器随后安排写入，flush 等待存储完成。

### append 怎样建立一个事实

`Session.append` 会首先为输入建立一份可序列化的数据副本，然后构造出一个带有序号和时间的冻结事件条目。这里所说的可序列化，意味着数据能够按照约定转换成文件保存格式。接下来，该方法会校验各个事件字段，同时检查 Surface 约束，也就是确认这条新事件是不是符合当前消息序列的更新规则。只有在这两项校验都通过之后，事件才会被放入日志中并向外发布。副本机制和冻结操作共同协作，防止调用者后续修改原始对象影响到已记录的历史。

Session 发布新事实后，消费方按各自接口更新状态或排队处理。deriveMessages 遍历当前 Surface 的消息节点，生成新的消息数组；状态投影按已注册的事件消费规则维护可查询状态。消息视图处理消息节点，状态投影处理各自关心的过程事件。

DSH 的 JSONL Provider 为每个受管理的 Session 维护一条写入通道，称为写入句柄。它监听 session/event，将新事件排入后台缓冲；收到 session/flush 后，先等待 drainLive 排空缓冲，再等待 writer.flush。Session 通过事件通知存储，存储组件负责文件读写。

### 投影和持久化屏障

Session 投影通过具体的事件规则来更新状态，提供给不同的消费方进行查询。举例来说，待办投影会根据待办变更事件更新出最新的列表，而运行状态投影利用生命周期事件来推断当前所处的阶段。同一份记录日志足以同时支持多种不同的投影，它们各自提取并保存业务需要的数据。

JSONL 持久化分为两层：实时监听器先缓冲事件，writer.append 再按序写入文件并调用文件同步。session/flush 先等待 drainLive 排空实时缓冲，再等待 writer.flush；尚未写入事件的空 Session 会在此创建并同步头记录。文件追加或同步失败时，存储层关闭追加文件句柄，将文件截回本批写入前的长度并同步，随后抛出原错误。回退也失败时，用 AggregateError 同时报告写入错误与回退错误。成功回退后，未推进的游标允许本批重新写入。

### 写入时间线与故障判断

![F05B：Session 追加与存储完成的等待边界](../figures/F05B.png)

图 05B 对比 append 返回与 flush 的等待边界。append 完成 Session 内事件追加和通知；后台写入从收到通知时便可开始，flush 等待存储监听器排空缓冲并完成刷新。

在一个标准流程里，用户的输入内容、助手给出的工具提议、发起的工具调用、返回的工具结果、助手的总结文本以及轮次边界，都会按顺序进入到事件序列中。消息视图借此组织下一次的请求，界面据此更新展示状态，存储 Provider 则将其写进磁盘文件。如果发现界面已经显示更新但文件写入失败了，可以判定故障发生在存储链条；而当页面刷新后发现生成的临时文字丢失了，此时需优先排查那段文本是否已正式提交为助手消息事件，同时也要确认它是否顺利写到了文件里。

### 常见误解

“日志里每一项都发给模型”：消息派生只处理相应的消息节点，过程边界事件用于记录运行状态。

“可从日志还原，所以视图必须与原日志相同”：派生视图按用途筛选、组合和更新。第 8 章介绍压缩如何改变当前 Surface。

“页面显示了，所以已经保存到磁盘”：界面与存储分别消费事件。存储写入和 flush 的结果决定对应记录是否已保存。

### E05A · 事件对象建立与验证

阅读任务：以下代码节选自 Session.append 方法，并且此时已经获取了输入数据的可序列化副本。在此应重点观察序号分配、时间获取、数据副本组合以及事件校验；至于后续加入日志、向外发布通知以及返回事件，则属于后面的代码逻辑。

#### 实现详解

Session.append 将调用方数据变成稳定、有序且符合事件规则的事实。进入本段前，事件正文和可选的 Surface 元数据已经生成可序列化快照；无法转换的数据提前报错。事件使用这些快照，调用方之后修改原对象不会改变已记录的内容。

事件对象包含类型、序号、时间、正文，以及需要时附加的 Surface 更新信息。seq 取当前日志长度：已有 9 项时，新序号为 9。time 记录本条事件建立的时刻，连续性按 seq 检查。surfaceOp 说明消息怎样更新 Surface，sourceEventSeqs 关联派生内容的来源事件。deepFreeze 冻结这些字段及嵌套数据，形成稳定的内存条目。

对象建立后通过两层验证：事件数据验证检查该类型要求的字段，Surface 管理器检查当前消息序列的更新规则，例如替换区域是否合法。验证先于 log.push，失败时事件没有进入日志，长度也不增加。TypeScript 的类型声明帮助组织代码，运行期字段与 Surface 约束由这些实际验证检查。

验证通过后，append 将事件加入内存日志，使事件快照缓存失效，再通知观察者并返回事件。追加 read 调用时，序号供工具结果关联，冻结保护参数，通知让界面更新并让存储组件安排写入。内存追加与文件保存分阶段推进，flush 负责等待存储完成。事件因此按“提交数据—建立记录—通知消费方”的顺序流转。

### E05B · 后台写入与持久化等待

阅读任务：本段落展示了 JSONL 存储组件如何注册两项核心事件监听。当 session/event 事件到达时，它负责将新事件排入后台缓冲队列；而当 session/flush 事件到达时，则负责等待缓冲排空并完成最终的刷新。注册方法负责保存这些回调函数，待具体的事件产生时才会触发对应回调执行。

#### 实现详解

JSONL Provider 通过事件监听接入 Session，为每个受管理的 Session 保存写入句柄。session/event 回调按 session.id 查找 writer，有对应句柄时调用 enqueueLive，将事件排入实时缓冲，再由写入通道追加到文件。界面观察者可以同时更新显示。

实时写入在后台推进，失败时错误回调记录警告，尚未完成的缓冲事件继续保留。日志指出哪个 Session 写入失败，后续排空仍可处理保留的事件。写入句柄负责顺序、追加位置和失败回退，监听器负责将事件路由到相应通道。

session/flush 提供显式等待点。找到 writer 后，回调返回异步操作：先等待 drainLive 写完实时缓冲，再等待 writer.flush 完成存储刷新。Session 的 flush 流程收集并等待这些结果，将成功或失败交给调用方。没有写入句柄时，这个 Provider 返回 undefined，本次没有对应通道参与等待。

以 read 结果为例，结果先进入 Session 内存日志，再排入 writer 缓冲。界面可能已经显示文件窗口，文件追加仍在进行；关闭或其他需要确保保存完成的路径等待 flush，先排空缓冲，再等待刷新。任一步失败都会传回调用方。沿“事件发布—缓冲入队—后台追加—显式排空与刷新”观察，可以定位显示与保存之间的进度差。

代码类型：**真实源码摘录**。证据编号 [E05B](../evidence-index.md#e05b)；下表的数字是原文件行号。

```ts
    ctx.on('session/event', (session: Session, event) => {
      this.writers.get(session.id)?.enqueueLive(event, (error) => {
        ctx.logger.warn(`session-persistence: background write for session "${session.id}" failed (buffered events retained): ${String(error)}`)
      })
    })
    ctx.on('session/flush', (session: Session) => {
      const writer = this.writers.get(session.id)
      if (writer === null || writer === undefined) return undefined
      return (async () => {
        await writer.drainLive()
        await writer.flush()
      })()
    })
```

## 05.5 理解检查与讲解问答

### 问题 1 · append 执行返回是否代表磁盘持久化已完成？

讲解：append 返回时已完成 Session 内记录与事件发布，后台写入可能正在推进。flush 提供等待缓冲排空和存储完成的边界。

### 问题 2 · 为什么事件与聊天消息数量不同？

讲解：事件还涵盖生命周期与状态记录，派生模型历史时只有相关的消息节点才参与进去。

### 问题 3 · 恢复 Session 后，原来的外部终端一定恢复了吗？

讲解：Session 恢复对话记录和运行事实。终端进程位于执行环境中，进程 Provider 需要确认它是否仍在运行、连接是否可用。
