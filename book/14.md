# 第 14 章｜Web Client：任务提交与状态同步

本章学习任务：理解任务提交与持续跟随，分析 pending 协调、事件序号、快照和状态同步。

## 14.1 基本概念

网页交互依赖两条主要信息流：用户向 Host 发出操作指令，Host 将后续变化送回页面。远程调用（RPC）向执行环境提交任务，它返回的是任务的接纳结果。持续跟随链路则让页面在任务执行期间不断获取新变化。

请求尚未完成时，客户端通过本地回显显示用户输入，提供即时反馈。这些输入暂存于 pending 状态，待 Host 接纳后才转为正式记录。程序利用 requestId 关联这两种表示，协调状态更新并避免视图中重复显示输入。

快照给出某个游标位置的已知状态，作为后续更新的基线。持久事件用 seq 标示历史位置，助手临时流传递尚在生成中的变化。follow 在准备快照前登记监听与缓冲，保留这段准备期间新增的事件。

Host 的 follow 服务按序号顺序发送事件：遇到旧序号直接略过，符合预期的下一项正常发送；若发现事件序号存在缺口，则报错并结束当前数据流。在客户端，历史来源管理和控制流重连将分别处理历史消息与状态更新。

## 14.2 沿一个任务看完整流程

用户发送消息后，客户端率先创建 pending 记录以回显输入。附件处理完毕，客户端发出携带 requestId 的 prompt 请求，Host 接纳后返回回执。持续跟随流随后带回正式的用户消息，客户端依靠 requestId 将 pending 条目与正式记录对齐，避免消息重复显示。

基线是已知时点的完整状态，增量是此后发生的变化。程序通过订阅确立后续事件的接收关系，使用缓冲保存待处理事件，并由监听器响应事件通知。快照与增量相互配合，持续刷新客户端的 Session 镜像。

系统沿另一条链路获取快照与后续变化。如果预期下一序号是 41，但缓冲收到了 39、41、43：早于预期的 39 被作为重复记录略过；41 被正常消费，预期序号随之更新为 42；随后到达的 43 揭示了序号缺口，无法当作 42 继续处理。Host 跟随生成器因此抛出 gateway/internal 错误。

页面刷新后，客户端重新获取快照并接收后续变化。已提交的助手消息从 Session 记录恢复；正在生成的内容通过已启用的助手临时流观察。页面没有更新时，可沿提交、接纳、跟随、客户端状态和视图订阅逐项定位。

## 14.3 关键机制与设计取舍

### 两个方向

![F14A：上行提交与下行跟随的两条链](../figures/F14A.png)

图 14A 左侧展示了上行的任务提交链路，右侧则是下行的持续跟随链路。prompt 请求返回输入的接纳结果，follow 流则负责提供初始快照、持久事件以及启用的助手临时流，客户端依据这些数据不断更新页面。

### 发送路径

Session 交互控制器提取编辑器的内容，调用 `beginSubmission` 创建本地的 pending 条目，让用户的输入立即显示在界面上。控制器随后处理附件并发出网络请求；Host 的接纳结果和消息记录会通过另外的通道返回。

创建本地记录时，程序会生成 requestId，并在附件序列化完成后，由 Client Session 的 `prompt` 把同一个标识传给 Host 命令控制器。后续的跟随流将带回该条目对应的正式记录，客户端利用该标识协调 pending 状态与正式消息，消除界面的重复显示。如果提交出现失败，则按照失败状态处理本地的 pending 条目。

### 跟随路径与网络基础

snapshot 提供游标所在位置的状态，后续的订阅从该位置起恢复接收事件。游标起到了记录事件消费进度的作用。RPC 主要负责发送操作请求并接收回执，持续流则专门传递任务执行期间的状态变化。

为了防止在准备快照的间隙丢失新产生的变化，`SessionHistoryController.follow` 会先安装事件监听并开启缓冲，再去发出快照并处理缓冲队列里的后续事件。持久事件与助手临时流在这里分开处理；其中临时流仅在请求指明开启相应能力时才会提供。

Host 使用预期序号对缓冲事件做校验，略过旧事件，遇到缺口时抛出错误。客户端负责消费收到的事实变化，据此维护本地的 Session 状态，ChatView 组件则订阅这些状态更新，重新显示受影响的节点。

### 分析示例：序号去重与缺口

以教学快照为例，假设游标位于 40，后续预期的序号是 41。缓冲中依次有 39、41、43：因为 39 早于当前消费位置，程序会将其跳过；正常消费 41 之后，预期序号向前推进至 42；随后到达的 43 揭示了中间的缺失事件，随即触发缺口处理逻辑。

复算记录：[C14 · 预期序号](../examples/calculation-results.json)。

这个例子中的 39、41、43 都来自 Host 的事件缓冲。当预期应当是 42 却收到了 43，Host 会抛出 gateway/internal 错误并结束当前的流。客户端中的 `resync` 专门负责历史来源地址的替换：先关闭旧来源，再重新 open 新的历史窗口。投影状态则交由另一条控制流负责管理与重连。事件连续性检查、历史来源替换与状态重连机制各自对应了这些不同的实现环节。

### 刷新后重建视图

![F14B：快照与后续事件组成可观察视图](../figures/F14B.png)

图 14B 演示了完整过程：Host 先安装监听和缓冲，随后发送快照并检查后续事件序号；最后客户端依据接收的数据更新状态、驱动视图。快照确立了观察基线，持续事件则在此基线上不断推进。

当 README 还在读取时刷新浏览器，页面通过获取新快照和后续事件重建视图。原先依靠本地回显呈现的输入仅具有 pending 状态；它们必须在 Host 接纳并记录后，才能在新的历史读取中作为正式用户消息出现。

本地回显使输入立即显现，requestId 将其与 Host 的接纳记录关联；快照和后续事件则持续更新聊天视图。

### 常见误解

“提交函数返回成功就是最终回答”：它的契约仅是任务被接纳；后续连续过程仍通过跟随链传递。

“刷新会把所有临时片段逐字恢复”：临时流的保存方式与持久事实不同。

“有序号就一定无损恢复”：序号只负责检查事件连续性，具体的恢复还需由实际协议与客户端执行路径共同完成。

## 14.4 源码研读

<a id="e14a"></a>

### E14A · 跟随时发现重复与缺口

阅读任务：这是跟随消费循环内部的代码节选。item 是当前缓冲的事件，nextOffset 是下一个等待消费的位置。yield 用于把当前结果交给流的消费者，调用后还可继续生成下一项。

#### 实现详解

Host 的 follow 先提供快照，再从缓冲队列处理后续变化。nextOffset 表示等待的持久事件位置，初始值由快照游标加 1 得到。本段专门处理 Session 事件；助手临时流使用不同的条目和序号，已在此前分支处理。持久历史的连续性通过 Session 的 seq 属性校验。

当前事件序号小于 expectedSeq 时，它已经位于快照覆盖或此前消费过的位置，循环跳过此项。先监听、后快照的过程可能让同一事件同时出现在基线和缓冲中，跳过旧项可避免重复交付。序号等于 expectedSeq 时，代码先将 nextOffset 增加 1，再转换事件并通过 yield 交给消费者。

事件序号大于 expectedSeq 时，Host 抛出 gateway/internal，错误中写明缺失序号，当前 follow 随之终止。缺失的中间事实可能影响客户端状态，因此不能继续按连续事件交付。外层 finally 撤销事件与助手临时流监听，移除取消处理，完成本次订阅收尾。

例如快照游标为 40，预期到达 41。缓冲若先给出 39，Host 略过；拿到 41 下发后，预期推进到 42；随后若收到 43，就报告缺少 42。客户端根据快照和增量更新 Session 镜像，驱动视图刷新。历史来源地址替换与投影控制流重连各自对应单独的客户端流程，本段逻辑仅负责检查和交付本次跟随流内的连续持久事件。

代码类型：**真实源码摘录**。证据编号 [E14A](../evidence-index.md#e14a)；下表的数字是原文件行号。

```ts
        const expectedSeq = SessionSeq(nextOffset)
        if (item.event.seq < expectedSeq) continue
        if (item.event.seq !== expectedSeq) {
          throw new RemoteError('gateway/internal', `session event stream skipped seq ${String(expectedSeq)}`, {})
        }
        nextOffset = SessionLogOffset(nextOffset + 1)
        yield entryFor(item.event)
```

| 226 | const 与序号包装 | 把当前消费位置转成期待的 Session 事件序号。 |
| 227 | 小于比较和 continue | 跳过已经早于期待位置的重复或旧事件。 |
| 228 | 不等比较 | 事件序号高于预期位置时，判定流中存在缺口。 |

## 14.5 理解检查与讲解问答

### 问题 1 · 本地出现输入气泡是否证明服务器已接纳？

讲解：提交前客户端先创建 pending 条目以立刻显示输入。网络提交返回的回执确认了操作被接纳，持续跟随流随后带回 Host 的正式记录，客户端再把 pending 条目同正式记录进行对齐。

### 问题 2 · 预期 42 却收到 43，能否继续当作连续事件？

讲解：Host 预期 42 却收到 43，会报告缺失事件并结束当前 follow。客户端的 resync 在历史来源地址替换时关闭旧来源、重新 open；投影状态通过另一条控制流管理重连。这两项流程各有触发条件，Host 的缺口检查本身不会补齐缺失事件。

### 问题 3 · 提交回执和持续跟随为什么分开？

讲解：提交行为发起操作并获得接纳，持续跟随负责传回后续执行进度；它们的完成时段和数据契约各不相同。
