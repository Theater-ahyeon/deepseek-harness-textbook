# 第 14 章｜Web Client：任务提交与状态同步

本章学习任务：理解任务提交与持续跟随，分析 pending 协调、事件序号、快照和状态同步。

## 14.1 基本概念

网页交互至少有两条信息流：用户向宿主提交任务，宿主把后续变化送回页面。远程调用（RPC）让页面请求另一执行环境执行操作；它这次返回的是接纳结果。持续跟随则让页面在任务推进期间获取变化。

本地回显在请求完成前显示用户输入，提供即时交互反馈。输入此时保存在客户端 pending 状态，Host 接纳后生成正式记录。requestId 关联这两种表示，使客户端能够协调状态并避免重复显示。

快照描述某个位置的已知状态，游标指出后续消费从哪个位置推进。持久事件有序号，助手临时流是尚在生成中的变化。跟随过程在准备快照前安装监听与缓冲，可以保留准备期间发生的事件。

Host 的 follow 按序号发送事件：略过旧事件，发送符合预期的下一项，发现缺口则报错并结束这次流。客户端的历史来源管理与控制流重连分别处理历史和状态，下一节说明两条路径。

## 14.2 沿一个任务看完整流程

用户发送消息后，客户端先创建 pending 记录并显示输入。附件处理完成后，客户端发出带 requestId 的 prompt 请求，Host 接纳后返回回执。后续跟随流提供正式用户消息，客户端根据 requestId 协调 pending 与正式记录，避免重复显示。

基线是已知时点的完整状态，增量是此后发生的变化。订阅登记后续事件的接收关系，缓冲保存尚待处理的事件，监听器响应事件通知。快照与增量结合，持续维护客户端的 Session 镜像。

另一条链路获取快照与后续变化。假设下一预期序号是 41，而缓冲收到 39、41、43：39 为过去的重复记录被略过；41 正常消费后预期更新为 42；43 暴露序号缺口，无法作为 42 消费。Host 跟随生成器因此抛出 gateway/internal 错误。

页面刷新后，客户端重新获取快照，再接收后续变化。已提交的助手消息从 Session 记录恢复；正在生成的文字通过启用的助手临时流观察。页面不更新时，沿提交、接纳、跟随、客户端状态和视图订阅逐项定位。

## 14.3 关键机制与设计取舍

### 两个方向

![F14A：上行提交与下行跟随的两条链](../figures/F14A.png)

图 14A 左侧是上行提交，右侧是下行跟随。prompt 返回输入接纳结果，follow 提供初始快照、持久事件和启用的助手临时流，客户端据此更新页面。

### 发送路径

Session 交互控制器从编辑器取出内容，用 `beginSubmission` 创建本地 pending 条目，立即显示用户输入。随后处理附件并发出请求；Host 的接纳与消息记录通过另一条通道返回。

本地记录创建时生成 requestId，附件序列化完成后，Client Session 的 `prompt` 将同一标识送往 Host 命令控制器。后续跟随流带回对应记录，客户端据此协调 pending 条目与正式用户消息，避免重复显示。提交失败时，则按失败状态处理本地条目。

### 跟随路径与网络基础

snapshot 提供游标位置的状态，后续订阅从该位置继续接收事件。游标记录事件消费进度。RPC 负责操作请求与回执，持续流负责传递任务执行期间的状态变化。

`SessionHistoryController.follow` 在准备快照前安装事件监听与缓冲，再发出快照并处理缓冲后续。这避免把快照准备期间的变化简单丢掉。持久事件与助手临时流分别处理；临时流只有在请求开启相应能力时提供。

Host 用预期序号检查缓冲事件，旧事件略过，缺口抛错。客户端消费收到的事实并维护 Session 状态，ChatView 订阅状态变化，重新显示相应节点。

### 分析示例：序号去重与缺口

教学快照游标为 40，后续预期序号为 41。缓冲依次包含 39、41、43：39 早于消费位置，予以跳过；消费 41 后，预期序号推进到 42；随后到达的 43 暴露了缺失事件，触发缺口处理。

复算记录：[C14 · 预期序号](../examples/calculation-results.json)。

这里的 39、41、43 来自 Host 的事件缓冲。预期 42 却收到 43 时，Host 报告 gateway/internal 并结束该流。客户端 `resync` 用于历史来源地址替换：关闭旧来源，再重新 open 历史窗口。投影状态由另一条控制流管理重连。事件连续性、历史来源替换和状态重连分别对应这些实现。

### 常见误解

“提交函数返回成功就是最终回答”：其契约仍然是接纳；连续过程走跟随链。

“刷新会把所有临时片段逐字恢复”：临时流与持久事实的保存方式不同。

“有序号就一定无损恢复”：序号能检查连续性，恢复还要由实际协议与客户端路径完成。

### E14A · 跟随时发现重复与缺口

阅读任务：这是跟随消费循环内的节选，item 是当前缓冲事件，nextOffset 是下一个需要的位置。yield 是把一项结果交给流的消费者，后续可再继续生成下一项。

代码类型：**真实源码摘录**。证据编号 [E14A](../evidence-index.md#e14a)；下表的数字是原文件行号。

```ts
        const expectedSeq = SessionSeq(nextOffset)
        if (item.event.seq < expectedSeq) continue
        if (item.event.seq !== expectedSeq) {
          throw new RemoteError('gateway/internal', `session event stream skipped seq ${String(expectedSeq)}`, {})
        }
        nextOffset = SessionLogOffset(nextOffset + 1)
        yield entryFor(item.event)
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 226 | const 与序号包装 | 把当前消费位置转成期待的 Session 事件序号。 |
| 227 | 小于比较和 continue | 跳过已经早于期待位置的重复或旧事件。 |
| 228 | 不等比较 | 事件序号高于预期位置时，判定流中存在缺口。 |
| 229 | throw 构造远程错误 | 报告缺失序号并中断当前跟随流。 |
| 230 | 结束 if | 连续事件才能进入后面推进。 |
| 231 | 赋值和加 1 | 消费当前位置以后，期待下一项。 |
| 232 | yield 调用转换函数 | 把当前事实转成协议条目交给跟随消费者。 |


执行推演：Host 预期 41 时略过 39，收到 41 后发送该项并将预期推进到 42；随后收到 43，就抛出 gateway/internal，结束跟随。客户端的历史来源地址替换由 resync 关闭旧来源并重新 open，投影状态由独立控制流维护。

## 14.5 理解检查与讲解问答

### 问题 1 · 本地出现输入气泡是否证明服务器已接纳？

讲解：客户端提交前会建立 pending 条目，让输入立即显示。提交回执确认入口接纳，随后跟随流带回 Host 记录，客户端再把 pending 条目与正式记录协调。

### 问题 2 · 预期 42 却收到 43，能否继续当作连续事件？

讲解：Host 预期 42 却收到 43，会报告缺失事件并结束跟随。客户端有两项相关机制：历史地址替换时，resync 关闭旧来源并重新 open；投影控制流独立管理重连。Host 的缺口检查负责发现不连续，resync 负责替换历史来源。

### 问题 3 · 提交回执和持续跟随为什么分开？

讲解：提交表达操作并返回接纳，跟随传回后续过程；两者完成时间与数据契约不同。
