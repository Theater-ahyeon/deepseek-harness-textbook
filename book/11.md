# 第 11 章｜工具准入、审批与执行约束

本章学习任务：追踪准入策略、审批、guard、参数校验与执行顺序，区分拒绝、取消和执行错误。

## 11.1 基本概念

工具调用能否进入执行体由准入流程决定。前置策略给出允许、拒绝、取消或要求审批的判定；若需审批，则由审批服务提供本次结果；随后通过守卫检查额外限制。`allowed-once` 意味着许可仅对本次审批有效，后续调用需再次经历准入。

守卫执行单调约束：它只能新增拒绝，若前置判定已拒绝则维持原样。当守卫返回 `undefined` 时，表示未提出额外否决，调用依原准入决定继续。实际的资源访问受执行环境限制，文件、网络与操作系统沙箱行为由相应 Provider 与配置规范。

一次调用应分别观察调用记录、执行状态和最终结果。前置拒绝时，框架直接构造拒绝结果，工具体不会执行；进入执行体后抛错时，此前完成的外部动作按实际情况保留。后置处理决定模型收到的内容，这些观察点用于区分未执行与执行后失败。

准入策略、审批服务、单调守卫与执行环境均具备独立的控制接口以供扩展。排查故障时应根据记录确认发生阶段，前置拒绝、审批不通过、执行报错与结果处理异常分别对应各自的日志信息。

## 11.2 沿一个任务看完整流程

当模型要求读取某路径时，循环首先登记此调用事实。接着 ToolRuntime 创建执行上下文 exec 描述该次操作，并进入前置链。若被拒绝会直接构造拒绝结果；如需审批，服务先记录 asked，在等待应答后记录 decided。获准后系统继续检验单调守卫，通过时分派层重新解析可执行工具，调用其包装函数。包装函数完成 schema 验证，才开始 read 的读取操作。

假设有四项请求：前置拒绝、审批拒绝、获准且成功、获准并在执行体内报错。总请求数为 4，实际进入工具执行体的有 2 项，成功结果有 1 项。最后那项报错前完成了哪些操作，需根据执行体内的代码顺序进行追踪。

工具执行返回后，结果规范化流程将返回值整理为统一结构，再由后置策略决定最终发给模型的内容。若策略替换了结果文本，模型将接收修改版本；但此前完成的读取或外部修改依然保留。单次调用怎样推进，可通过调用记录、准入决定与执行结果共同还原。

## 11.3 关键机制与设计取舍

### 工具执行前后的处理链

![F11A：准入、可选审批、守卫、执行和结果处理](../figures/F11A.png)

图 11A 呈现的主线包含调用记录、前置决定、可选审批与守卫检查、工具执行，以及结果处理与记录环节。拒绝支线会直接跳过 execute 执行体，把拒绝结果交由后续步骤处理。

### 从调用到最终结果

循环最先记录工具调用，随后 ToolRuntime 创建执行上下文并检查取消状态。策略插件在 `tools/pre-execute` 链上判定返回允许、拒绝、取消或要求审批，该链末端默认返回 allow。面临审批请求时，服务向应答方发起询问、记录事件然后回传结论；用户常通过交互界面应答，自动化桥接程序亦可提供机器应答。如果前置决定予以允许，ToolRuntime 继续检验单调守卫。单调是指守卫只可否决或原样放行，无法将拒绝状态转为授权。

进入分派流程后，注册表重新解析对应的可执行工具，把调用方与外层封装的取消信号加以融合，随后调用真实的 `execute`。执行体返回的对象会经过成功结果构造流程；而抛出的异常则转换为工具错误。此后执行后置处理、内容约束与结果通知，循环再按次序记录交由模型的结果。

审批服务在开放轮次中写入 `approval/asked` 与 `approval/decided`。开放轮次代表已开始且未结束的 turn，使询问与结论归属同一轮任务。`allowed-once` 只允许本次审批关联的调用。当要求审批却缺失审批服务、调用 Agent 或可用通道时，serviceAsk 直接返回拒绝。

### 三种边界分别回答什么

准入策略负责为当前调用生成判定决定，审批服务收集确认结论，执行环境则限制真实的资源访问。沙箱及文件系统守卫在执行层面实施边界限制；审批机制与这些资源约束各自独立配置，在单次调用中按次序生效。

通过 profile 选取审批策略与执行 Provider，可将决策流程与资源约束装配进工具链。分析权限行为时，必须同时查验前置决定、审批记录、后续 guard 以及执行后端的详细配置。

### 分析示例：请求数与执行数

教学批次有四项已记录工具请求：一项前置拒绝，一项审批拒绝，一项允许且执行成功，一项允许但执行体抛错。请求数为 4，进入执行体的调用数为 2，成功结果数为 1。被拒绝的两项未进入工具体，框架仍可将拒绝构造为错误结果。

复算记录：[C11 · 请求与执行计数](../examples/calculation-results.json)。

工具结果的 isError 属性是错误标志。前两项在执行前遭拒绝，后两项进入了执行体；最后一项报错前产生过哪些动作，需检查执行体代码。准入记录说明是否放行，结果记录表明调用以何种状态结束。

遇到拒绝时应查前置决定与审批记录；执行体内抛错时查阅文件服务或进程结果；输出阶段报错则检查结果校验与渲染流程。

### 读取任务的拒绝与结果替换

![F11B：策略、一次审批与执行环境的不同职责](../figures/F11B.png)

图 11B 并列呈现三种控制：前置策略提供处理决定，审批服务取得确认结论，执行环境约束真实资源访问。审批通过后，调用仍要接受单调守卫与环境约束。

假定 read 已读出文件，随后的后置策略将结果文本替换。模型后续请求会使用替换后文本，但文件读取动作已然发生。后置处理仅修改返回内容，外部资源的修改或撤销必须由相应的执行服务处理。

### 常见误解

“审批允许即绕开所有限制”：实际后续 guard 与执行环境依然保留各自的约束边界。

“全部错误都是执行前拒绝”：执行体报错、任务取消以及后置结果处理均会生成错误结果。

“存在调用记录等于操作已完成”：调用记录说明操作被提出，执行状态说明是否进入工具体，最终结果说明调用怎样结束。三个观察点需要分别确认。

## 11.4 源码研读

<a id="e11a"></a>

### E11A · 准入链与可选询问

阅读任务：这是 prepareExecution 创建执行上下文后的节选。exec 描述当次调用，carrier 确定了服务派发范围；请观察前置决定与审批分支的处理，后续守卫和实际分派未包含在本段落中。

#### 实现详解

ToolRuntime 在工具执行前创建 exec 对象，记录该次调用的 Agent、参数、身份以及取消状态。本段逻辑发生在执行上下文成功建立且初次取消检验通过之后。scopeTarget 依照当前工具服务与请求 Agent 选取派发范围，让准入策略能够沿着本次调用的插件环境运行。

`tools/pre-execute` 是一条支持等待的前置处理链。各个策略接收 exec，综合工具名称、参数和环境因素产出 allow、deny、cancel 或 ask 决定。处理链末端提供默认的 allow，介入者依据规则更新结果或直接退出。waterfall 执行完毕后，gate 会保存整条链作出的最终裁决，而真实的工具体尚未进行分派。

当 gate 为 ask 时，ToolRuntime 调用 serviceAsk 以等待审批服务，进而获取最终决策与审批的取消状态。若缺少有效的审批条件，此询问路径直接形成拒绝结果。其他的 gate 则被包装为统一格式，同时将 approvalCancelled 设为 false，表明该分支未涉及审批取消。此字段独立于决策值保存，协助后续流程分清调用层取消和审批期间的取消。

运行时随后检查取消、拒绝原因和 guard。前置允许的调用仍可被 guard 否决，通过检查才进入分派；工具包装函数校验参数 schema 后才运行 execute。读取 README 时，allow 路径通过守卫后执行读取，deny 路径构造拒绝结果，ask 路径取得一次审批再确定后续出口。策略与交互审批由此形成统一的准入决定。

代码类型：**真实源码摘录**。证据编号 [E11A](../evidence-index.md#e11a)；下表的数字是原文件行号。

```ts
      const carrier = scopeTarget(this, exec.agent)
      const gate = await this.ctx.waterfall(
        carrier, 'tools/pre-execute', exec,
        () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
      )
      const askResolution = gate.kind === 'ask'
        ? await this.serviceAsk(exec, gate)
        : { decision: gate, approvalCancelled: false }
```

| 1505 | await waterfall | 等待前置处理链给出本次准入决定。 |
| 1506 | 调用实参 | 指定范围、事件名和执行上下文，处理者据此判断。 |

### E11B · 一次审批怎样留下关联记录

阅读任务：以下是审批服务获取到可记录 Session 后的常规路径。req 携带了工具及本次调用信息；阅读重点在于同一个审批标识如何把 asked 和 decided 串联起来。至于取消和失败处理，要结合 decide 方法及调用方契约来理解。

#### 实现详解

审批服务为需要确认的工具请求记录询问与结论。request 先要求 Session 有尚未结束的 turn，使两条审批事件归属当前任务。randomUUID 生成本次审批 id，用于配对询问和决策；callId 标识被询问的工具操作，用于关联工具调用。两种标识分别承担审批配对和调用关联。

服务先追加 `approval/asked`，记录审批 id、工具名以及请求提供的 callId 和 reason。观察方据此了解任务正在等待的确认。随后 await decide，先检查取消和有效策略，再通过 `approval/request` 链取得应答。never 策略直接拒绝；无人应答、应答抛错或返回不合法值时，结论归为 unavailable；取消则以 cancelled 收尾。

取得 outcome 后，服务用同一 id 追加 `approval/decided`，再将结论返回 ToolRuntime。`allowed-once` 是授予本次许可的结论，后续调用重新进入准入流程。记录先于返回，因此调用方使用结果时，Session 已保存询问与决策事实。若事件 append 在提交前失败，方法抛错，不能沿正常路径返回结论。

一次文件修改需要审批时，Session 先出现 asked，界面展示工具与询问原因；用户允许后，同一 id 的 decided 保存结论，工具链继续检查守卫并执行。用户在等待中取消时，decide 返回 cancelled，迟到的应答无法覆盖已结束的等待。用审批 id 配对两条记录，再以 callId 关联工具调用，就能说明操作为何获准、拒绝或取消。

代码类型：**真实源码摘录**。证据编号 [E11B](../evidence-index.md#e11b)；下表的数字是原文件行号。

```ts
    const id = ApprovalRequestId(randomUUID())
    session.append('approval/asked', {
      id,
      toolName: req.toolName,
      ...req.callId !== undefined ? { callId: req.callId } : {},
      ...req.reason !== undefined ? { reason: req.reason } : {},
    })
    const outcome = await this.decide(req, session)
    session.append('approval/decided', { id, outcome })
    return outcome
```

| 225 | 调用 append 并开始对象 | 记录一次 approval/asked 事实。 |
| 226 | 对象属性简写 | 保存审批身份。 |
| 227 | 属性读取 | 保存被询问的工具名称。 |
| 228 | 条件展开 | 有调用标识时加入，以便关联具体工具请求。 |

## 11.5 理解检查与讲解问答

### 问题 1 · 审批允许一次以后，守卫还能拒绝吗？

讲解：能。审批允许一次并不会绕开后续的守卫与执行环境限制。

### 问题 2 · 结果 isError 是否证明没有外部动作？

讲解：isError 仅标记单次调用以错误状态收尾。若阻断发生在准入阶段，工具执行体并未运行；若报错出现在执行体内部，那么抛错前已执行的读写或远端请求仍按真实的进度予以保留。

### 问题 3 · 后置处理删掉结果文字，能否撤销此前读取？

讲解：后置处理仅修改反馈给模型的结果内容。之前的读取操作已由底层文件服务实际完成，撤销该外部动作必须由执行服务提供相应的处理操作。
