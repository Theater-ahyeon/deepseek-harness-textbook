# 第 19 章｜Cordis 与 Spatiotemporal Composability

本章围绕资源登记、依赖变化与插件卸载这三个问题，讲解 Cordis 的 Spatiotemporal Composability。我们会先通过定时器和工具注册来理解基本机制，然后将这些做法与论文中的定义及生命周期规则相联系。

这里提到的论文是 *A Programming Paradigm for Spatiotemporal Composability*，作者为 Yifan Shi、Wei Zhang、Tianyi Cui，本文采用 arXiv:2608.25512 的 v1（2026-08-26）。代码实现基于固定项目快照中的 `@deepseek-ai/cordis` 4.0.4。接下来先介绍论文模型，随后展示 Cordis 4.0.4 的实现方式。

## 19.1 组件替换与资源释放

假设我们在装入文件工具插件时执行了两项操作：一是注册 read 工具，二是监听文件观察事件。这样模型就能调用该工具，其他组件也能接收通知。如果后来配置发生变化，需要替换为另一份实现。此时若仅从列表中删去插件名称，旧的监听器仍可能继续接收事件，旧工具也可能滞留于注册表中；当新实现装入再次登记时，就会导致重复响应或旧对象依然被访问。

因此，组件的生命周期需要同时管理能力的启用和贡献的撤销。effect 表示操作对状态带来的改变，比如注册了一个监听器；disposer 是用来释放这项贡献的函数，比如移除刚才注册的监听器；而 inverse 则描述与操作对应的逆向动作，用于让状态恢复到操作前的样子。

此外，read 插件的运行还依赖文件服务。当文件服务的提供者撤销该服务时，作为消费者的插件需要重新评估自身依赖，此时它会退出当前实例或等待新服务出现。服务名称用来标识一项可以被解析的能力，依赖声明则列出了装入插件前必须具备的入口条件。

论文将上述两个问题结合起来探讨：在时间维度上，组件做出的贡献应当如何撤回；在空间维度上，组件又该如何在当前的 Context 中获取依赖，并随着环境的变化进行重新装配。这就是 Spatiotemporal Composability：涵盖时间方向的撤回机制与空间方向的依赖组合。此处的空间维度，指的是服务之间的组织和解析关系。

## 19.2 可逆操作与恢复见证

假设系统当前状态 S 是一个工具集合，在装入组件 A 之前集合内容为 `{read}`。接着，执行操作 f 将集合变为 `{read, search}`。此时，f 还需要提供一个逆操作 g。如果 g 仅负责移除 A 刚才注册的 search 工具，那么就会满足 `g(f(S)) = S`。这个等式要求逆操作必须让系统恢复到本次操作发生之前的输入状态。

这里的“状态”是数学模型中的数据，“函数”是把旧状态变成新状态的规则。witnessed effect function 返回新状态及逆操作，并附带逆操作恢复本次输入状态的见证；Definition 8 给出这项等式条件。实现中的 ctx.effect 保存 disposer，由组件作者提供满足恢复条件的释放逻辑。

disposer 通过闭包保留资源身份。闭包由函数及其引用的外层变量构成，例如清理函数捕获本次定时器的 timer 句柄，卸载时据此停止对应定时器。作者在资源获取时登记释放函数，让获取与撤销保持明确对应。

释放动作由组件作者编写。定时器的 disposer 必须保存本次 timer 句柄并调用 clearInterval；只打印“已清理”不会停止调度。论文 §5.1.1 将逆操作正确性交给作者，Cordis 负责登记与调用。§6.1 进一步区分资源获取与对外发送：连接句柄可以关闭，已经发送的数据仍可能由外部系统持有。文件写入、邮件发送等动作应按服务能力安排延迟提交或补偿，并针对业务采用的观察关系检查恢复与独立性。

## 19.3 逆操作的组合与释放顺序

如果组件先申请了资源 A，随后又基于 A 创建了资源 B。那么在释放时，程序需要先清理 B，再清理 A，这样才能在清理 B 时仍然保有它所需要的依赖 A。LIFO（Last-In-First-Out，后进先出）正好描述了这一处理顺序：越晚创建的依赖资源，越早被撤销。

论文的设计是将每一步返回的逆操作都连接在已有恢复动作的前面，从而形成反向组合。effect iterator 会驱动装入过程逐步向前推进；迭代器在每一步给出下一项操作，并指明装入是否结束。借助这种机制，运行时可以在步骤之间记录当前进度、检查目标状态，从而决定是继续执行装入还是转入撤离流程。

论文的反向组合、单个 ctx.effect 内的多步恢复、Fiber 上多个 effect 的释放，采用不同组织方式。Fiber._unload 用 Promise.all 等待同层任务，多个异步 disposer 会重叠运行。两项清理有严格依赖时，应在同一个 disposer 中依次 await，先撤销 B，再撤销 A。

框架在执行释放时，会捕获并记录每一项释放任务中出现的错误，而其他清理任务仍会继续推进。在排查问题时，开发者可以根据错误记录定位所属的组件实例和具体的释放位置，从而弄清清理动作在何处中断。

## 19.4 环境要求：coeffect、服务键与依赖

coeffect 用来描述组件在执行时需要从环境中获取哪些支持，例如文件服务；而 effect 则描述执行过程会对状态带来哪些改变，比如注册了一项工具。服务 key 作为一种标识，被用来识别和解析特定的能力。提供者会在对应的 key 下发布能力，消费者声明自己需要该项能力，随后 Context 会根据当前的作用范围，将 key 解析为具体的服务实现。

在理解一个组件的结构时，我们可以依次观察它声明了哪些依赖、提供了什么服务，以及具体的装入行为。插件通过声明来描述所需依赖，通过服务提供操作来登记自身能力，而 Fiber 则负责管理本次装入过程所产生的各类资源。

举例来说，若插件 T 依赖 tools 和 fs。其中 tools 允许它登记工具，fs 使其能够执行文件读取。只有当这些依赖条件都成立时，运行时才会推进该插件实例的装入。若 fs 的提供者撤销了该服务，运行时会通知依赖它的消费者重新评估目标状态；消费者此时需要退出当前的装配进度，或者等待环境再次满足所需条件。

响应式依赖使环境变化触发实例重新评价目标状态，依赖注入通过统一接口解析提供者。实例创建连接、监听器或后台任务后，作者或相应注册 API 需要把资源及其 disposer 登记到资源管理接口；实例卸载时，框架调用这些已登记的释放动作。

## 19.5 Fiber 与生命周期：目标变化时怎样收尾

Fiber 表示组件的一次运行实例，并管理其生命周期。每个 Fiber 保存自己的配置、依赖状态和释放动作。同一组件可以装入多个实例，分别使用不同的 Context 或配置，各自维护资源与状态；分析清理时应明确所属实例。

论文 §4 采用抽象状态和转换规则分析装入、已激活、撤离等过程。论文中的 Reloading 包含了推进装入的情形；它用四类抽象状态表达转换规则；而代码实现的 FiberState 枚举对运行时状态做了进一步区分。实现与官方教程还提供了 PENDING、FAILED、DISPOSED 等状态，用来表示依赖未满足、装入失败与实例终结。

如果在等待建立连接时配置发生变化，惯性原则要求必须先完成当前的装入步骤，把结果与 disposer 交付给框架后，再决定是继续推进还是执行撤回。这种做法确保了占用的资源能及时进入清理记录。若外部操作迟迟不返回，这一步就会一直等待；因此组件需要在资源操作中加入超时或取消处理。

在依赖撤离阶段，还涉及提供者和消费者的顺序。因为消费者的清理动作往往需要向提供者归还资源。论文使用守卫演算，通过等待关系防止资源被过早回收，并形式化地讨论了“提供者存活时间必须长于其消费者”的条件。

Reflect.provide 的 disposer 先从公共服务存储撤销入口，再通知相关消费者，等待这些 Fiber 的当前生命周期工作达到稳定状态，最后删除本实例保留的服务入口。该 disposer 内部按此顺序等待；Fiber 同层的其他 disposer 仍会并发执行。需要等消费者退出后才可释放的资源，应与该等待组织在同一受控流程中。

| 阶段 | 发生什么 | 需要核对什么 |
| --- | --- | --- |
| 依赖可用 | 消费者可以开始当前装配 | 声明与实际解析是否一致 |
| 提供者撤去入口 | 新解析不能把它当作普通可用服务 | 是否通知了相应消费者 |
| 消费者收尾 | 处理仍属于旧实例的资源 | 清理是否还需提供者 |
| 提供者资源释放 | 撤去自身登记的贡献 | 是否按真实依赖组织等待 |

## 19.6 操作独立性与安全卸载

交换律的意思是：先执行 A 再执行 B，与先执行 B 再执行 A 能够得到相同的结果。假设操作 A 登记它自己的键 a，操作 B 登记另一个键 b。如果它们都只是修改各自独立的集合元素，最终的整体集合是不受顺序影响的。但如果两项操作都在修改一个对顺序敏感的中间件列表（即请求依次穿过的一系列处理环节），执行的先后就可能改变请求实际经过的规则。

Definition 42 要求两项迭代的正向、撤回及相关变换满足独立性，并保持对方返回的逆操作与后续迭代。检查两次注册能否交换顺序，只验证了部分条件；还要检查卸载 A 时，B 的贡献和后续运行是否保持。

举个释放方式存在缺陷的例子：A 在注册前把当前的整个工具集合保存为副本，随后 B 注册了另一项工具；到了 A 需要卸载时，它直接用之前保存的旧副本覆盖当前的集合。这种做法就会把 B 合法添加的贡献一并抹除。正确的释放逻辑应当只识别并移除当前实例自身注册的条目。当面临重名、覆盖、排序逻辑或者操作共享资源的情况时，还必须额外核实替换与撤销动作是否破坏了独立性。

这也就说明了为什么论文会特别讨论服务提供者的责任：提供者所发布操作的数据表示方式，直接决定了其他组件能否做到独立撤回。因此，服务提供者在设计注册机制与撤销规则的初期，就必须妥善处理这些独立性条件。

## 19.7 观测等价与证明条件

观测等价指的是，按指定的合法观察方式进行检查，系统前后没有出现影响契约的差异，就认为它们是等价的。比如对工具集合来说，并不要求它的内存地址、分配顺序或运行时缓存逐字节一致。观察关系由理论模型来界定；而像网络请求或外部设备写入，自身就带有另外的可观察状态。

论文 §3.3 利用观察关系来界定状态相等的用途，随后 §3.4 讨论了独立性与恢复机制。相应的证明也是如此展开：先定义状态、操作及观察方式；再写下可逆和依赖条件；最后证明满足条件的系统能够以何种方式组合与撤回。

Theorem 73 假设依赖先行关系无环、迭代长度有统一有限上界、整个序列涉及的实例名称有限，且每一步遵守生命周期规则。无环表示依赖箭头不会绕回同一组件。满足这些前提时，论文证明没有规则层死锁，并能在有限步骤内达到静止状态，即不再有待推进的生命周期步骤。

例如组件 A 等待 B，而 B 反过来等 A，这构成了依赖环，违反了 Theorem 73 的无环前提。这个例子也说明，依赖图和步骤长度本身就是推进定理的组成部分。

## 19.8 服务作用域与模块热重载

ctx.isolate(name, label) 为指定服务名设置解析标签，并返回派生 Context。缺省 label 时创建新 Symbol，使子范围可以提供并解析另一项实现；传入相同 label 时，多个范围共享该服务解析空间。建立标签不创建服务实现，各 Context 仍在同一 JavaScript 宿主中共享进程资源。

### E19A · 作者提供资源释放逻辑

阅读任务：以下是官方 Cordis 教程中 heartbeat 插件的 effect 代码片段。请观察定时器句柄是如何被传递给释放函数的，以及 Cordis 框架是如何接收到这项清理动作的。

#### 实现详解

官方教程通过 heartbeat 插件展示了资源获取与释放应当如何成对登记。装入插件时程序调用 ctx.effect，并传入获取资源的函数。该函数在执行时创建定时器，每 200 毫秒输出 tick，同时把得到的 timer 句柄存在当前执行的局部变量里。这个句柄标识了本次创建的定时器，后面的清理函数依赖它定位资源。

获取函数随后返回另一项函数，作为 disposer 交给 Cordis。返回时只交付释放逻辑，定时器继续运行；Cordis 将它登记到所属 Fiber。释放函数的闭包保留 timer，使获取函数结束后，清理仍能访问本次资源的句柄。

当插件卸载时，框架会提取并调用已登记的 disposer。它首先执行 clearInterval(timer) 停止本次的定时器，然后输出 heartbeat cleaned up，供教程中观察清理的发生。如果同一插件被多次装入，各实例都会拥有独立的 timer 与闭包；卸载其中一个时，程序沿对应登记只清理那份资源。触发热重载时，机制同样沿这条生命周期路径撤销旧实例贡献，再推进新实例。

这把责任分成了相连的两部分：作者编写正确的获取及释放操作，Cordis 负责保存对应关系并在实例退出时调用。论文提及的恢复条件要求逆操作能够让系统回到输入状态；在此具体恢复由 clearInterval 完成。类似地，注册 read 或监听事件时，也必须保留本次登记的身份，使释放时只撤销这单次贡献。资源创建、句柄捕获、登记与卸载调用共同组成了可追踪的生命周期。

代码类型：**仓库官方教程示例**。证据编号 [E19A](../evidence-index.md#e19a)；下表的数字是原文件行号。

```ts
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => {
      clearInterval(timer)
      console.log('heartbeat cleaned up')
    }
  })
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 20 | effect 接收函数并开始资源获取 | 把本次定时器生命周期登记给所属插件。 |
| 21 | const、setInterval 与回调 | 保存定时器句柄，每 200 毫秒调用日志回调。 |
| 22 | return 返回另一个函数 | 把释放动作作为值交给 Cordis，以后卸载时才调用。 |
| 23 | clearInterval 调用 | 作者使用已捕获的 timer 句柄停止该计时器。 |
| 24 | 日志调用 | 在实际清理时给出教程观察输出。 |
| 25 | 结束返回的释放函数 | 本次逆操作定义完成。 |
| 26 | 结束资源获取函数与 effect 调用 | 框架获得并登记释放函数。 |


执行推演：装入时创建定时器，effect 记录回调返回的释放函数。卸载时框架会调用作者写下的 clearInterval；框架本身没有从 setInterval 自动推导代码的能力。

### E19B · 服务名称作用域隔离

阅读任务：Context.isolate 为 name 参数指定的服务名称设立专用的解析标签。可选参数 label 能让不同的 Context 共享相同的服务作用域，返回值是带有新解析表的派生 Context。

#### 实现详解

Context.isolate 主要用于为指定服务名建立派生的解析范围。Context 内部的隔离表保存了“服务名到 Symbol 标签”的关系，后续对该服务的读写都依据标签来选择实现。方法接收 name，指明对哪项服务使用新范围；可选参数 label 决定是否复用已有标签。方法最终返回派生 Context，调用方可在其下挂载插件或提供服务。

执行中，方法先创建继承当前隔离表的新表，接着只对参数 name 设置标签。查找其他未修改的服务时，这张新表会沿着继承链路取得父范围的标签，因此局部改动不影响其他名称。建立新表也不会改写原 Context 里的隔离表，父范围依然维持它原本的解析关系。

若调用时缺省 label，每次 Symbol(name) 都会生成全新的唯一身份；所以哪怕两次传入的 name 相同，标签也不一样。如果显式传入相同的 Symbol，多个派生 Context 就能使用该共用标签，从而共享该项服务的解析空间。例如为 fs 创建两项新标签，能在两个子范围提供不同的文件服务；复用同一 label 则把它们接到同一个 fs 解析范围。

extend 把新表放入派生 Context，后续服务读取与提供按这张表解析。该方法只建立标签映射，不创建文件 Provider 或启动子进程。各 Context 仍共享宿主；profile 与插件装配决定标签下提供哪项实现，文件和进程服务负责资源访问。区分服务名、解析标签和实际实现，就能理解局部范围如何替换同名能力。

### E19C · 同层资源释放并发等待

阅读任务：下面的代码节选自 Fiber._unload 中的资源释放阶段。_disposables 保存当前 Fiber 拥有的释放函数，代码利用 Promise.all 等待所有的异步清理完成，且每项任务都有独立异常记录。随后的流程负责清理 store 并更新实例的生命周期状态。

#### 实现详解

Fiber._unload 释放当前插件实例已登记的资源，再清理实例存储并推进状态。它先从 _disposables 取出整组动作并清空登记集合，让本次卸载处理确定的一组资源。释放动作由作者或注册 API 提供，再由框架通过 runDisposable 实际调用。

代码把各项释放映射成异步任务，再用 Promise.all 等待整组完成。任务可以重叠执行，结束顺序由各自等待决定。例如移除监听器先结束，关闭网络连接还在等待，整个卸载仍须等连接清理返回。某项一直不结束时，整组等待也无法完成，因此资源操作内需要相应超时或取消处理。

在此流程中，每项任务都处于独立的 try/catch 块里，并通过 composeError 组合完整的诊断信息。在调用释放动作前，代码先经过一个异步等待边界，随后记录本次错误位置；一旦失败，就会结合外层调用信息写入日志。某项释放报错后，其自身的处理路径结束，其他释放任务仍然继续收尾。这里使用的 Promise.all 汇总的正是这批带有独立错误处理的任务。

等所有任务完成后，后续代码会清空该实例的 store，再根据目标状态决定它是保持未激活还是重新装入。对于有严格先后依赖的清理操作，应将它们写在同一个 disposer 内依次执行 await：例如先停止仍会访问连接的后台任务，结束后再关闭连接。如果在同层登记两个独立的 disposer，启动时不会保证前一项彻底结束后再开始后一项。整个过程中的资源集合、独立错误记录与整组并发等待，共同展示了一次卸载是如何从释放走向状态更新的。

        }, this._runner.getOuterStack)
      } catch (reason) {

    }))

## 19.10 理解检查与讲解问答

**问题 1：既然框架能够调用释放函数，为什么这不代表能保证释放正确？**

讲解：登记把 disposer 与所属 Fiber 联系起来，卸载时框架调用它。作者必须在定时器 disposer 中使用本次句柄调用 clearInterval，才能停止资源。论文的见证条件要求恢复对应输入状态；Cordis 提供登记和调用机制，作者实现具体恢复动作。

**问题 2：同层如果有两个异步释放函数，能否仅靠它们的登记顺序，就保证第一个结束后第二个才开始？**

讲解：无法保证。_unload 会将同层的释放函数映射成异步任务，再使用 Promise.all 汇总等待。晚启动的任务也能先结束。如果清理动作存在先后依赖，应把它们写进同一个 disposer 中依次执行 await。

**问题 3：把插件放入 ctx.isolate 之后，能否运行不可信代码且无须其他隔离？**

讲解：ctx.isolate 仅调整了服务名称的解析标签，派生出的 Context 依旧与原 Context 共享宿主进程。要运行不可信组件，程序必须独立设计执行层的隔离、桥接接口以及资源访问限制。

**追问：怎样向他人准确地概括 Cordis 的价值？**

Cordis 把插件组织成声明依赖、登记资源、响应环境变化并释放贡献的运行实例。Context 解析服务，Fiber 管理实例状态，effect 保存资源与 disposer 的对应关系。论文说明这些机制所需的可逆性和独立性条件，源码展示装入、撤离及依赖通知的具体步骤。
