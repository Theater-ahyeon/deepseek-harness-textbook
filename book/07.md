# 第 7 章｜Skill 发现与按需加载

本章学习任务：追踪 Skill 的目录发现、入口检查与正文读取，区分工作方法与工具执行权限。

## 07.1 基本概念

Skill 将任务方法与相关资源组织为一份可加载的定义，例如技术报告的整理流程。目录摘要给出名称和用途，正文说明操作步骤与具体要求。模型先根据摘要发现候选，再按任务需要读取正文。

Skill 服务负责发现、列出和读取定义，`skill` 工具提供按名称获取正文的模型入口。调用标志分别控制用户调用和模型调用，各入口依据相应标志检查许可。因此，名称可见说明候选能够被发现，是否可加载还取决于当前入口的调用条件。

加载 Skill 后，正文进入模型上下文，指导模型组合已有工具。文件读取、网络请求和内容发布仍经过工具注册、准入规则与执行环境。用户显式指定 Skill 与模型调用 skill 工具分别采用各自的读取路径。

排查模型未按 Skill 步骤执行的问题时，需要依次确认三个事实：目录中是否包含名称，读取是否获取完整定义，正文是否进入本次请求。这三个阶段都得到验证后，再分析正文中的任务方法是否清楚。

## 07.2 沿一个任务看完整流程

假设目录包含 report-skill，摘要说明它用于整理技术报告。模型根据摘要匹配任务需求，并调用 Skill 读取工具。工具以当前工作目录、Agent 范围和取消信号查询目录，找到名称后检查模型调用许可，通过检查才获取完整定义。

目录中的定义若已移除，名称查询会失败；名称仍可见但禁止模型调用时，工具返回入口限制错误。成功读取后，框架将正文整理为模型材料，后续请求据此使用 Skill 提供的方法。

用户显式调用采用用户入口的许可检查。符合条件时，框架建立来源标记为 Skill 调用的指令消息；未知名称和不符合条件的文本保留为普通文字。正文中的方法随后通过模型推理与工具调用落实。

## 07.3 关键机制与设计取舍

### 先知道名称，再获取正文

![F07A：目录发现、指定读取与 Skill 正文](../figures/F07A.png)

图 07A 沿着模型调用路径展开：发现候选、发布摘要、选中名称、检查模型调用许可与获取正文。取得的正文会作为工具结果被记录下来，随后再进入下一次模型请求中。

### 注册表与 Provider 分别负责什么

`SkillRegistry` 管理当前范围内的 Provider 与候选，文件系统 Provider 负责目录发现和文件读取。`list` 返回摘要列表，`get` 按名称选择候选。不同 scope 层的同名项由较近层覆盖较远层；同一层内再按 Provider 优先级、Provider 登记顺序和本地顺序选择。注册表将选中候选的定位信息交回对应 Provider 读取，并校验完整定义，消费方因此可以使用不同的 Provider 实现。

在执行前置步骤时，工具插件会将当前 Agent 可调用的 Skill 目录写成一条持久提示消息。这份目录带有名称和说明，而正文留待需要时读取。当目录发生改变，插件会发布替换消息；如果发现过程未能完成，旧有的目录就会保留下来。当模型调用 `skill` 之后，执行体便去核对名称、可见摘要以及模型调用标志，通过后再获取完整定义并交出正文。

用户直接调用由前置步骤检查直接用户消息首行的 `/<name>`。名称存在且允许用户调用时，正文作为指令注入本步消息；模型调用 `skill` 则将正文记录为工具结果，供后续步骤使用。两条路径的生效时点由消息来源与调用标志决定。

### 按需加载与工具权限

按需加载在任务需要时获取 Skill 内容。正文提供工作方法，工具注册决定可调用能力，准入链判断本次调用是否允许，执行环境限制实际资源访问。这些控制在 Skill 加载后继续生效。

目录摘要帮助模型选择 Skill，正文给出操作步骤、参数与限制。例如“用于文档整理”说明用途，具体整理方法需在读取正文后确定。Provider 读取失败、名称消失或当前入口禁止调用时，工具返回对应错误。

### 分析示例：按需材料量

教学目录包含三个 Skill，正文分别占 2000、3000、5000 字节，目录摘要合计 600 字节。只加载第一个 Skill 时，目录与正文共 2600 字节；全部加载时共 10600 字节，差额为 8000 字节。两种方案均携带同一目录，计算忽略其他请求材料。

复算记录：[C7 · Skill 材料用量](../examples/calculation-results.json)。

按需方案省去未选中 Skill 的正文，同时增加查找与读取操作。评价时应记录材料量、加载次数和任务结果。摘要的准确性、候选选择与正文版本共同影响加载的方法是否符合任务需求。

### 回到项目说明整理

![F07B：全部正文与只取所需正文的材料对照](../figures/F07B.png)

图 07B 的左侧展示了携带同一目录及三个 Skill 全部正文的情况，总共占 10600 字节；右侧只携带了目录与第一个正文，总计 2600 字节，中间差的正好是另外两份未使用正文的 8000 字节。

在此过程中，Skill 的正文负责指导报告结构，而 read 工具的返回结果提供实际的项目事实。模型最后把这两种信息结合起来，生成一份包含数据来源和条件限制的总结报告。

### 常见误解

“目录列出一百个 Skill，上下文就包含一百份全文”：目录与正文采用不同契约，应查看实际读取了哪些正文，以及本次请求携带哪些材料。

“任何页面出现 /Skill 名称都会触发”：直接调用只扫描符合来源条件的用户消息，并检查用户调用标志，外部材料中的同名文本不会自动触发。

“既然 Skill 已经加载完毕，就能避开原有的工具准入”：Skill 只是改变了传入的材料和工作方法，真实的准入控制仍然处在第十一章所述的工具链条里面。

## 07.4 源码研读

### E07A · 读取正文前的可见性和入口检查

阅读任务：这是 Skill 读取工具执行体中的代码节选。args.name 传入了请求寻找的名称，exec 提供了 Agent 环境与取消信号；阅读时请重点区分其中的目录查询、模型调用条件检查与获取正文环节。后续如何构造返回结果不在本段展示之内。

#### 实现详解

当模型调用 skill 工具时，系统需要把名称解析成当前 Agent 可读取并有权调用的完整定义。工具首先检查名称格式，接着建立 lookup 查询条件：工作目录取自 Agent 所在 Session，scope 指向当前 Agent，signal 用于传递本次调用的取消信号。后续的目录发现和正文读取都会沿用这套条件，从而顺着当前 Agent 的插件装配和工作区环境去解析候选。

工具先调用 skills.list 拿到摘要目录，然后从中寻找与 args.name 一致的条目。若目录里没有此名称，程序会报告未知或不可用；找到摘要后，还会进一步检查它是否允许被模型调用。有些 Skill 即使可见，也仅允许用户显式调用，这类候选在模型入口会被拒绝。在此处，摘要同时承担了提供发现信息和限制入口策略的职责，而正文尚未进入结果。

摘要检查通过后，工具调用 skills.get 获取完整定义。两次异步查询之间，Provider 状态或文件可能变化，因此 get 返回空时仍需报告不可用。节选后的代码再次检查完整定义的模型调用标志，通过后才将名称、Provider、可选资源基址和 content 组织成结果。资源基址定位正文引用的材料，content 保存方法说明。

以 report-skill 为例，摘要中不存在该名称时，流程停止于名称查找；摘要存在但仅允许用户调用时，流程停止于入口检查；摘要许可且完整定义有效时，工具返回正文。正文经过输出渲染和工具结果记录，进入后续模型请求并指导报告结构。文件读取继续经过原有工具链与准入规则，四个阶段依次为候选发现、入口许可、完整读取和上下文使用。

## 07.5 理解检查与讲解问答

### 问题 1 · 看到 Skill 摘要以后，正文是否已经可用？

讲解：这个时候还没有。摘要只用来帮助选择候选，必须等读取工具取得完整定义后，才能真正形成正文材料。

### 问题 2 · Skill 可见但不允许模型调用，会怎样？

讲解：读取入口会主动检查调用条件，不能因为名称出现在目录里就直接放行。

### 问题 3 · Skill 能否自行提高工具权限？

讲解：Skill 不能自行提高工具权限。它提供方法与说明，真实工具调用仍经过自身的准入规则和执行限制。
