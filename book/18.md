# 第 18 章｜综合案例：read 工具的接入与呈现

本章学习任务：串联 read 的注册、参数校验、执行、结果渲染和客户端呈现，分析各层失败的影响。

## 18.1 基本概念

扩展点是框架允许新增能力的位置，例如工具注册接口。接口契约既规定输入输出，也规定怎样处理生命周期、取消和结果。一个新能力复用这些位置，才能进入现有流程；插件通过 profile 挂载并注入依赖，工具定义才进入运行中的注册表。

规范值是执行体返回的结构化数据，供输出契约检查。schema 定义结构，render 生成模型内容，presentationMeta 提取可持久化的展示元数据。模型使用渲染文本，客户端根据原始事件与 meta 派生卡片数据。

真实 read 工具通过已选文件服务获取有界文本，再构造路径、行范围和总行数等结果。模型从渲染文字获取资料，界面从保存的展示元数据重建读取卡片。持久记录保存模型内容和展示元数据；界面恢复时读取这份记录。

本章将启动装配、参数校验、工具准入、文件读取、结果记录与界面呈现串联为同一条调用链。新增工具通过现有扩展接口接入各环节，复用统一的控制与记录机制。

## 18.2 沿一个任务看完整流程

read 的接入始于 profile 装载文件工具插件。插件声明依赖并注册工具，模型调用提交 file_path、offset 和 limit。ToolRuntime 创建参数 JSON 快照并完成准入；defineTool 的 execute 包装函数随后检查 schema，read 执行体通过 parseReadArgs 补齐缺省值、校验行范围，再调用文件服务读取目标并构造窗口。

执行结果形成规范对象，输出 schema 检查形状，render 生成模型材料，顶层工具调用的 presentationMeta 提取可保存的窗口资料。通用链处理最终结果，循环将 content 和 meta 写入 tool/result。后续模型请求使用 content，Web Client 从原始调用、结果和 meta 生成卡片。

| 出错位置 | 影响 |
| --- | --- |
| 参数解析 | 还未按这些参数读取 |
| 准入拒绝 | 真实执行体不运行 |
| 读取执行 | 需要检查文件服务错误与取消 |
| 结果契约 | 已读取也可能不能形成合法结果 |
| 顶层 presentationMeta 生成 | 执行结果转成工具错误，进入后续结果处理 |
| 客户端卡片数据不匹配 | readCardModel 返回 null，工具行显示原始输出 |

新增工具时，依次实现注册、输入检查、执行、输出渲染和资源释放；专用卡片通过展示契约接入。

## 18.3 关键机制与设计取舍

### 通过扩展接口接入运行链

![F18A：读取工具注册后复用既有准入与结果链](../figures/F18A.png)

图 18A 按工具接入生命周期展开：确认契约、挂载插件、注册定义、复用 ToolRuntime、记录结果、卸载注册。read 的执行逻辑位于已有运行链中。

### 参数、规范值、模型文本和展示元数据

read 的外部参数是 `file_path`、`offset` 和 `limit`，解析后得到 `filePath`、`offset` 和 `limit`。前者是调用接口的命名，后者供执行逻辑使用：路径是字符串，起始行和最大行数是数字。解析完成后，执行体用这份内部输入读取文件。

执行体返回路径、起始行、行列表和总行数等规范 JSON 值。`output.schema` 检查结构，`output.render` 把该值转成模型面对的文本；`presentationMeta` 抽取可持久化的窗口数据，使支持读取卡片的界面能够重建行号和语言信息。规范值用于执行契约，模型文本供后续请求使用，展示元数据保存窗口事实。page 和 follow 传输原始 Session 事件；客户端再从事件提取卡片数据。

执行体通过所选文件服务读取，并检查取消与输出上限。schema 检查结构，解析逻辑检查具体值。插件的 `name` 标识实现，`inject` 声明依赖，`apply` 在依赖可用时注册工具。卸载时撤销注册，专用卡片则由客户端插件提供。

### 原指南与真实工具各怎样参考

官方最小工具示例说明 defineTool、execute 与 render 的关系，并使用 Node 文件读取展示一个最小形态。实际 tool-fs 使用 DSH 文件服务，由所选 Provider 解析路径；文件观察与执行守卫通过独立插件参与调用。

Web Client 的展示链从原始事件开始。Conversation 通过 callId 关联调用与结果，ToolCallTree 通过工具名称选择 tool.call.toolview 中的 renderer。这个按名称选择组件的入口称为 keyed slot。read 对应 ReadRow，它调用 readCardModel，从原始参数、结果文本与持久 meta 构造 React 组件的 props，即组件使用的输入数据。

readCardModel 先确认这是已结算、成功的顶层 read，再检查参数、meta 中的路径与行号、每行文本，以及模型结果的文件文本格式。通过后生成路径标签、行列表、总行数与语言信息；不符合时返回 null，工具行保留原始输出。没有专用 renderer 时，ToolCallTree 选择 GenericToolCard。

Host 的 presentCall 和 presentResult 是为本地消费方保留的纯转换接口。内置 Web Client 使用自己的卡片模型；page 和 follow 传输原始事实，Host 无需在读取历史时再次计算网页卡片。[展示链核验](../evidence-index.md#s03)列出这条路径的实现入口。

### 分析示例：什么证据支持“能读文件”

沿同一次 read 检查六项行为：参数解析、空路径拒绝、文件读取、行窗口构造、输出校验和客户端卡片派生。输入决定前两项，执行轨迹说明读取过程，content 与 meta 分别支持模型材料和界面展示。

输出 schema、render 或顶层 presentationMeta 抛错时，ToolRuntime 将本次返回转成工具错误。结果已经记录以后，客户端的卡片模型只读取并校验事实：数据不符合卡片要求时显示原始输出，已有模型内容保持原样。执行结果的构造与卡片的派生分别发生在 Host 和 Client。

复用通用工具链让文件工具专注获取和表达材料，代价是必须实现已有 schema、结果、准入和生命周期约定。模型文本与专用卡片分别处理，也避免为了界面格式污染模型材料。

### 全书机制回到一个任务

![F18B：目标材料、执行事实与产品验证的三组职责](../figures/F18B.png)

图 18B 用三组职责回顾全书：目标与材料、执行与事实、产品与验证。一次总结任务由这些部件合作完成，read 的输出在 Session、模型请求和界面中各有对应形式。

遇到材料过长，检查压缩后是否保留任务约束；模型失败，检查 attempt 与恢复决定；工具拒绝，检查准入结果；子任务参与，检查初始材料和返回产物。这些机制共同决定总结依据什么资料，以及失败发生在哪里。

### 常见误解

“一段类型定义就是可用插件”：类型不完成挂载、执行或运行验证。

“工具注册后自然有网页专用卡片”：工具行为与客户端呈现分别需要契约。

“更多能力必定更好”：新增接口还带来理解、控制与维护成本，应对准真实任务。

          offset: value.offset,

## 18.5 理解检查与讲解问答

### 问题 1 · 规范值、模型文本与展示元数据各自有什么用途？

讲解：规范值供契约检查和内部处理，模型文本供模型推理，展示元数据供保存与卡片重建。

### 问题 2 · 专用卡片失败是否意味着模型一定没收到文本？

讲解：Host 将规范结果渲染成模型文本，并为顶层调用保存窗口 meta。Web Client 从原始事件派生卡片；readCardModel 不接受当前数据时，工具行显示原始输出，模型仍使用已保存的文本。

### 问题 3 · 新增工具只写 execute 是否足够？

讲解：不够。还要完成注册、参数与输出契约、准入配合、取消和资源生命周期。
