# 第 18 章｜综合案例：read 工具的接入与呈现

本章学习任务：串联 read 的注册、参数校验、执行、结果渲染和客户端呈现，分析各层失败的影响。

## 18.1 基本概念

框架在扩展点（如工具注册接口）接纳新增能力。接口契约除了约束输入输出，也规定取消行为、生命周期及结果处理。新能力复用这些约定方可进入现有流程；程序通过 profile 挂载插件并注入依赖，工具定义随即加入运行时的注册表。

规范值指执行体返回的结构化数据，用于输出契约检查。schema 校验数据结构，render 将其转为模型内容，presentationMeta 从中提取供持久化使用的展示元数据。后续模型使用渲染文本，客户端依靠原始事件与 meta 派生界面卡片。

具体的 read 工具借助目标文件服务获取有界文本，随后构造路径、行范围和总行数等返回结果。模型读取渲染生成的文字资料，界面根据保留的展示元数据还原读取卡片。持久化记录包含模型内容与展示数据；界面刷新时直接读取这份记录。

本章把启动装配、参数校验、工具准入、读取文件、记录结果和界面呈现串成一条调用链。新增工具通过既有扩展接口衔接各个环节，并共享框架统一的控制与记录机制。

## 18.2 沿一个任务看完整流程

read 接入从 profile 装载文件工具插件起步。插件声明自身依赖并注册工具定义，接着模型发起调用并提供 file_path、offset 及 limit 参数。ToolRuntime 生成参数 JSON 快照并执行准入检查；defineTool 的 execute 包装函数负责检查 schema，read 执行体用 parseReadArgs 补齐默认值并校验行范围，再依靠文件服务读取目标并构造窗口。

执行结果被包装成规范对象，输出 schema 校验其数据形状，render 负责生成模型材料，顶层调用的 presentationMeta 从中提取可保存的窗口信息。通用工具链负责处理这一结果，循环将 content 与 meta 记入 tool/result。后继模型请求消费 content，Web Client 根据原始调用、结果与 meta 生成界面卡片。

| 出错位置 | 影响 |
| --- | --- |
| 参数解析 | 还未按这些参数读取 |
| 准入拒绝 | 真实执行体不运行 |
| 读取执行 | 需要检查文件服务错误与取消 |
| 结果契约 | 已读取也可能不能形成合法结果 |
| 顶层 presentationMeta 生成 | 执行结果转成工具错误，进入后续结果处理 |
| 客户端卡片数据不匹配 | readCardModel 返回 null，工具行显示原始输出 |

开发者新增工具时，需依次实现注册、输入检查、执行、输出渲染与资源释放；专用卡片由展示契约完成接入。

## 18.3 关键机制与设计取舍

### 通过扩展接口接入运行链

![F18A：读取工具注册后复用既有准入与结果链](../figures/F18A.png)

图 18A 按照工具的接入生命周期展开：确认契约、挂载插件、注册定义、复用 ToolRuntime、记录结果以及卸载注册。read 工具的具体执行逻辑融入在既有运行链中。

### 参数、规范值、模型文本和展示元数据

read 对外接收 `file_path`、`offset` 和 `limit`，解析后以 `filePath`、`offset` 和 `limit` 供执行逻辑使用。这里的变化是字段命名与输入检查：路径必须是字符串，起始行和最大行数必须是数字；缺省值由解析逻辑补齐。解析完成后，执行体用这份内部输入读取文件。

执行体最后返回含路径、起始行、行列表及总行数的规范 JSON 值。`output.schema` 负责校验该结果结构，`output.render` 将此值转作模型阅读的文本；`presentationMeta` 提取支持持久化的窗口数据，让兼容读取卡片的界面能还原行号与语言。规范值满足执行契约，模型文本供后继请求读取，展示元数据记录窗口事实。page 和 follow 负责传输原始 Session 事件；客户端从中提取卡片数据。

执行体通过所选文件服务读取数据，并检查取消信号与输出上限。schema 校验结构，解析逻辑检查具体值。插件的 `name` 标识实现，`inject` 声明依赖，依赖可用后由 `apply` 注册工具。卸载时撤销注册，专用卡片由客户端插件提供。

### 原指南与真实工具各怎样参考

官方最小工具示例演示了 defineTool、execute 及其 render 的关联，并借助 Node 原生文件读取给出了最小形态。实际项目中的 tool-fs 调用 DSH 文件服务，靠选定的 Provider 解析指定路径；文件观察器与执行守卫也作为独立插件接入这次调用中。

Web Client 展示链路的起点是原始事件。Conversation 依靠 callId 把调用和结果配对，ToolCallTree 依据工具名字去 tool.call.toolview 选择 renderer 组件。这种依靠名字分发组件的机制称为 keyed slot。read 逻辑对应 ReadRow，该组件调用 readCardModel 函数，利用原始参数、结果文本和持久化 meta 组装 React 组件需要的 props，也就是组件接收的输入数据。

readCardModel 会先确认这是已结算且成功的顶层 read 调用，随后校验参数、meta 记录的路径和行号、各行文本，并核验模型结果文本的文件格式。校验通过后，函数生成路径标签、行列表、总行数及语言信息；若数据不匹配则返回 null，此时工具行仅显示原始输出结果。如果缺乏专用的 renderer，ToolCallTree 则启用 GenericToolCard。

Host 端的 presentCall 与 presentResult 函数是专供本地消费方使用的转换接口。内置的 Web Client 依靠自有的卡片模型处理渲染；由 page 和 follow 接口传输原始数据，Host 并不在读取历史记录时重复计算网页卡片内容。[展示链核验](../evidence-index.md#s03)整理了此路径的具体实现入口。

### 分析示例：什么证据支持“能读文件”

沿单次 read 调用可检查六项环节：参数解析、空路径拒绝、文件读取、行窗口构造、输出校验及客户端卡片派生。外部输入触发前两项行为，执行轨迹呈现文件读取过程，生成的 content 和 meta 分别供模型阅读材料与界面展示使用。

只要输出 schema、render 或顶层 presentationMeta 抛出异常，ToolRuntime 就把本次结果转换为工具错误。当结果存入记录后，客户端卡片模型仅读取并验证这些事实：若内容不满足卡片要求，界面直接显示原始输出，已生成的模型内容维持原状。执行结果的构造位于 Host 端，而卡片派生发生在 Client 端。

通用工具链承担准入与结果处理，使文件工具专注获取和表达材料。接入工具仍需遵循既有 schema、结果和生命周期契约。模型文本与专用卡片分别处理，使界面格式无需混入模型材料。

### 全书机制回到一个任务

![F18B：目标材料、执行事实与产品验证的三组职责](../figures/F18B.png)

图 18B 划分三组职责来回顾全书概念：目标与材料、执行与事实、产品与验证。一次普通的总结任务需要这些部件协作完成，read 工具产生的输出在 Session 事件、模型请求和前端界面里都有各自的呈现形式。

材料过长时，去检查压缩操作后是否保留了任务约束；模型出现失败时，审查 attempt 记录与恢复决定；当工具拒绝执行，排查具体的准入结果；子任务参与进来后，检查其初始材料及返回产物。这些机制组合起来决定了系统依照什么资料进行总结，同时指出了潜在的失败位置。

### 常见误解

“一段类型定义就是可用插件”：单纯的类型声明无法替代挂载过程、实际执行或运行时的校验工作。

“工具注册后自然有网页专用卡片”：工具的运行行为与客户端界面的渲染呈现，各自受不同的契约约束。

“更多能力必定更好”：提供新接口的同时会增加理解、控制和维护成本，应当围绕真实任务设计。

## 18.4 源码研读

<a id="e18a"></a>

### E18A · 卡片资料从规范值派生

阅读任务：这里展示 read 输出定义里的 presentationMeta 函数属性。传入的 value 是读取完毕的规范值，_args 是该场景中未使用的参数。请观察程序怎样构造出可序列化的展示对象；将结果渲染为模型文本的 render 则是同一输出定义的另一项职责。

#### 实现详解

read 执行体读取文件并构造完毕窗口后，向外返回包含显示路径、起始行、逐行文本及总行数的规范值 value。工具输出定义负责两项工作：由 render 将该值渲染成模型文本；用 presentationMeta 提取界面恢复所需的结构化资料。本段代码实现了后一条逻辑，由于读取数据已就位，函数仅依赖实际结果组织展示元数据。

元数据保留 path 和 offset，再遍历 value.lines，为每行建立仅含 number 与 text 的新对象，最后写入 totalLines。消费方据此取得行号与文字：offset 是窗口起点，lines 给出实际保留的行，totalLines 是完整文件的总行数。即使返回窗口受到字节上限限制，这些字段仍可描述本次覆盖的范围。

函数使用 langFromPath 按路径推测语言，能识别时补充 lang 字段，无法识别则省略。界面可凭此决定语法高亮方式，而逐行文字始终来自本次真实读取内容。入参的 _args 未被使用，展示资料必须从实际结果 value 派生，以避免把请求的行数错误当成实际返回的行数。

例如从 README 第 41 行请求 30 行，结果只保留到第 60 行，meta 就保存 offset=41、20 条带实际编号的行，以及文件总行数。ToolRuntime 为顶层调用取得元数据，驱动将它与 content 一起写入 tool/result。Web Client 校验原参数、结果和 meta，再派生卡片。页面刷新后使用保存的资料重建同一窗口，无须再次读取当前文件；模型文本与卡片由此共享读取事实，各自保留所需形式。

代码类型：**真实源码摘录**。证据编号 [E18A](../evidence-index.md#e18a)；下表的数字是原文件行号。

```ts
      presentationMeta: (_args, value) => {
        const lang = langFromPath(value.path)
        return {
          path: value.path,
          offset: value.offset,
          lines: value.lines.map(({ number, text }) => ({ number, text })),
          totalLines: value.totalLines,
          ...lang === undefined ? {} : { lang },
        }
      },
```

## 18.5 理解检查与讲解问答

### 问题 1 · 规范值、模型文本与展示元数据各自有什么用途？

讲解：规范值用于契约检查及内部逻辑处理，模型文本专门交由模型推理使用，而展示元数据则负责持久化保存和界面卡片重建。

### 问题 2 · 专用卡片失败是否意味着模型一定没收到文本？

讲解：Host 将规范结果渲染成模型文本，为顶层调用保存窗口 meta。Web Client 根据原始事件派生卡片；readCardModel 不接受当前数据时，工具行显示原始输出，模型仍使用已经保存的文本。

### 问题 3 · 新增工具只写 execute 是否足够？

讲解：完整工具接入还包括注册、参数与输出契约、准入、取消处理和资源生命周期管理。execute 负责其中的执行逻辑。
