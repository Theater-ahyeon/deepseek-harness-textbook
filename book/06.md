# 第 6 章｜提示词组装与项目指令

本章学习任务：理解提示贡献、项目指令与历史的组装规则，追踪作用域选择、去重和请求冻结。

## 06.1 基本概念

模型请求的上下文通常包含系统规则、工具说明、历史消息和当前输入。提示词向模型说明任务目标与行为要求，其中 system prompt 提供系统规则。工具结果、项目指令和用户消息从各自的入口加入请求，组装过程依据来源决定采用哪些材料以及如何排列。

程序在注册阶段留存插件提交的提示段与动态上下文，并在请求组装时读取当下可用的内容贡献。当前请求的输入由三项规则共同决定：作用域划定内容对哪些 Agent 可见，同名选择规则敲定所用版本，排序规则负责排列内容的先后次序。

项目指令阐述特定工作区及文件路径应当遵循的规则。发起模型请求前，项目指令插件先挑出对应的规则文件，将其内容封装为指令消息，再与等待处理的输入一同并入当前步骤。Session 历史记录则由 Surface 派生而来，随后与上述新材料合并。

请求冻结为本次调用创建独立、稳定的数据副本。新消息、压缩与插件变更影响后续请求的组装，已发出的请求继续使用原副本。运行期间到达的引导消息，在下一步骤被领取后进入后续请求。

## 06.2 沿一个任务看完整流程

假设用户要求“总结 README，但保留实验性功能的限制”，该目标体现为一条来源清晰的消息。此时 system prompt 贡献交代具体的行为规则，工具贡献解释 read 操作如何调用，历史记录补充早前收集到的素材；接着工作区指令根据当前的路径范围附加额外约束。

组装器判断出当前作用域内可见的提示贡献后，再依序处理同名项及排列顺序问题。前置指令处理阶段负责清理掉无用的待处理指令，同时把当前需要的指令添进本步骤的消息批次。用户消息只在初次尝试时登记，重试时不再重复该操作；当请求创建完毕，它会拿到一份独立的配置副本。

在请求执行时新补充的“只总结正式功能”要求，会先存入 next-step 队列。由于当前请求绑定了既定的数据副本，只有等到下个步骤提取新消息时，才会重新组装上下文。后期的压缩处理可能会修改历史 Surface，但在途的请求仍会维持原有内容。在排查材料缺失问题时，应当分别核对可见提示贡献、前置消息、历史 Surface 以及最后的完整请求。

## 06.3 关键机制与设计取舍

### 材料有不同的入口

![F06A：提示贡献、项目指令与历史分别进入请求](../figures/F06A.png)

图 06A 所示的三路材料汇入当前步骤请求：SystemPrompt 负责组装提示贡献，项目指令转化为前置消息，Session 历史记录通过 Surface 派生生成。这三部分内容都各自保持原本的来源标记与排布规则。

system prompt 说明工具用法与运行约束。运行时上下文补充当前时间、工作目录等环境信息。项目指令提供工作区规则，用户消息提出任务目标，工具结果保存执行返回的材料。保留各类材料的来源，便于排查冲突、遗漏和重复。

### 从贡献到请求冻结

各插件利用 `SystemPrompt.section` 登记具名提示段，通过 `context` 登记动态上下文，每条贡献都带有特定的作用域。当出现同名项时，程序优先选取距离当前 Agent 较近的作用域版本，接着按服务指定的次序排列。完整的提示段另外配备自身的选择规则。SystemPrompt 服务依据这些规则拼接当前步骤的提示词。

驱动程序在步骤准备期提取输入，执行 `assemble` 完成提示词组装并产出当前运行时上下文，随后转入 `agent/pre-step` 前置处理链。该处理链按既定顺序运行，由此决定步骤是否继续及其采用的消息批次。项目指令插件会先等待相关的投影加载完毕，再结合工作区与触及路径挑选出规则文件。触及路径代表工具调用时已经接触过的文件路径，用来判定该应用哪份目录规则。选出的规则随之转化为上下文消息，并放入当前批次中。

进入步骤后，框架准备模型调用，记录所需的系统消息、首次进入的用户消息和请求信息，再派生并冻结请求。冻结保护本次调用的材料，使外部对共享对象的修改不会改变请求内容；下一步骤重新组装消息与上下文。

### 顺序与作用域的基础

每一项提示贡献在参与组装时，均依赖其名称、作用域和顺序参数。名称负责识别同名的条目以便挑选出有效版本，作用域负责圈定它的可见范围，顺序则用于确定最后的排布位置。显式地定义这三个属性，可保证各个插件提交的材料在一致的规则下顺利组合。

消息内容与来源共同参与请求组装：项目指令来自规则文件，用户需求来自提交入口，工具结果来自执行链。框架依据这些来源组织材料。一段文字包含“系统提醒”，不会改变它原有的消息类别。

### 分析示例：重复材料占了多少空间

某次教学请求包含了 800 字节工具指导、600 字节项目规则、200 字节用户需求以及 2400 字节历史，原始体积总计 4000 字节。当另一个插件又添加了一份完全一样的 600 字节项目规则后，整体体积便达到 4600 字节，增幅为 15%。

该算例的数据保存在[计算输入](../examples/metrics-input.json)中，`calculations.py` 读取这些数据，依次求出基础总量、加入重复规则后的总量及相对增幅。[计算记录](../examples/calculation-results.json)中的 `C6_baseline_bytes`、`C6_augmented_bytes` 和 `C6_increase_percent` 对应这三个结果。

重复的规则不仅推高了请求体积，还加大了来源识别的难度。因此，项目指令借助 sameContextPayload 方法来核对等价消息，而 SystemPrompt 依据名称和作用域参数来筛选提示贡献。一旦锁定重复项，就能在各自的组装入口将其去除，从而减轻后续压缩流程面临的冗余负担。

### 在下一步加入项目约束

![F06B：重复规则前后的材料体积](../figures/F06B.png)

图 06B 展示了重复材料造成的体积变动情况：原基础请求为 4000 字节，额外混入一份 600 字节的规则后，总长度变为 4600 字节，整体增加 15%。图表左右两侧分别对比了内容的组成板块与具体字节数。

驱动准备模型调用时检查取消信号。工具成功访问文件后，项目指令插件根据调用结果收集触及路径。当前步骤结束时，插件排队更新对应指令；下一步前置链等待更新完成，再把本次需要的规则消息加入请求。

### 常见误解

“所有项目指令都直接变成 system prompt”：前置步骤将项目指令转成指令消息，与本步输入合并；SystemPrompt 服务单独组装 system prompt。

“更长的提示词必定更可靠”：篇幅反映材料体积。检查提示词时，需要核对规则是否冲突、重复，以及执行结果是否符合要求。

“冻结一次请求就冻结整个 Session”：冻结保护本次请求的材料。下一步仍会读取新消息、工具结果和更新后的 Surface 状态。

## 06.4 源码研读

<a id="e06a"></a>

### E06A · 项目指令进入本步消息

阅读任务：这段代码出现在前置指令处理计算出 desired 之后。变量 desired 表示本步骤需要新插入的指令消息；pending 代表有待清理的旧指令；decision 存放正在准备阶段的消息批次；messages 则是本次领取的输入内容。请重点留意等价消息去重和消息插入位置的逻辑；关于指令文件如何发现，请回顾本章前文的讲解。

#### 实现详解

项目指令插件在 agent/pre-step 链中，将工作区规则加入本步消息。进入本段前，它已取得其他前置处理形成的 decision，等待相关投影更新，并计算出 desired 指令消息。decision.messages 是当前准备采用的消息数组，messages 保存本次从 Inbox 领取的输入，pending 是 Inbox 中等待更新的项目指令消息。

步骤被拒绝，或首次进入轮次却没有输入时，前面的分支会保留或更新待处理指令。当前分支允许继续，插件先从 Inbox 移除 pending 中的旧指令，避免重复排队。随后检查 desired：没有新指令，或当前批次已包含等价内容时，直接返回原 decision。等价判断比较上下文内容，防止同一份规则重复进入消息批次。

需要插入新指令时，插件在 decision.messages 中找到最后一条属于本次领取批次的消息，将 desired 插在它后面。直接输入因此在项目规则之前，驱动追加的运行时上下文在规则之后。例如“用户要求、运行时上下文”变为“用户要求、项目指令、运行时上下文”。如果没有匹配的领取项，查找返回 -1，插入位置就是数组开头。

插入操作创建新数组，返回对象保留 decision 的其他字段，只替换 messages。后续请求组装使用这份批次，本段没有直接发送模型请求。读取 README 产生的触及路径可以影响此前的规则选择；这里负责对选定规则去重，并放入指定位置，让下一步模型同时获得任务、目录约束与运行环境材料。

代码类型：**真实源码摘录**。证据编号 [E06A](../evidence-index.md#e06a)；下表的数字是原文件行号。

```ts
    for (const message of pending) agent.inbox.remove(message.id)
    if (desired === undefined || decision.messages.some(message => sameContextPayload(message, desired))) {
      return decision
    }
    // Fold the context right after the claimed batch, so the direct prompt
    // precedes it and the driver-appended runtime context follows it.
    const lastClaimedIndex = decision.messages.findLastIndex(message => messages.includes(message))
    const entered = decision.messages.toSpliced(lastClaimedIndex + 1, 0, desired)
    return { ...decision, messages: entered }
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 332 | for...of 遍历 pending 并调用 remove | 先从 Agent Inbox 移除不再保留的待处理指令消息。 |
| 333 | if、逻辑或与 some 检查 | 没有新指令或已经有等价内容时，不重复插入。 |
| 334 | return 返回既有决定 | 本分支保持当前批次不变。 |
| 335 | 结束 if 分支 | 只有需要新增内容的情况继续。 |
| 336 | 原注释说明插入相对位置 | 指令放在领取输入之后。 |
| 337 | 原注释说明后续追加的运行材料 | 直接输入在前，驱动后补的运行上下文在后。 |
| 338 | findLastIndex 与 includes | 在决定的消息数组里找到最后一条属于领取批次的输入。 |
| 339 | toSpliced 建立新数组 | 在该位置之后插入 desired，不原地改写旧数组。 |
| 340 | 展开对象并替换 messages | 返回新的前置决定，供本步请求组装使用。 |


执行推演：若 desired 内容早已包含在此次批次里，程序直接返回原有决定；如果需添加新指令，就在数组内查找到最后一条已领取的输入，将 desired 紧跟在其后插入，最后返回包含新数组的批次对象。

## 06.5 理解检查与讲解问答

### 问题 1 · 项目指令一定进入 system prompt 吗？

讲解：项目指令通过前置步骤转换成消息，然后并入当前步骤材料；system prompt 则由 SystemPrompt 服务单独组装。这两条路径生成的内容，会在系统准备模型请求时汇合。

### 问题 2 · 引导消息到来后，已经发出的请求会改变吗？

讲解：已经发出在途的请求只使用早前冻结的数据副本。新到达的消息必须等到下一次提取输入边界，才能并入后续发起的新请求中。

### 问题 3 · 重试为什么不重复登记用户消息？

讲解：首次尝试登记完成后，内存中已有对应的 Session 事实。若重试时依然执行登记，便会把同一个用户输入变成两份重复的历史记录。
