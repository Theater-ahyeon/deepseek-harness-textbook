# 第 6 章｜提示词与项目指令：下一次模型输入怎样形成

本章学习任务：追踪目录中的指令怎样被发现、组合与加入模型请求；解释指令的适用范围，以及文字规则与执行权限的区别。

## 06.1 基本概念

一次模型请求不是只发送用户刚打出的那句话。上下文指这一次推理能够使用的材料，包括行为规则、当前输入、历史内容和工具说明。提示词是作为材料发送给模型的文字指示；system prompt 是其中用于表达系统规则的部分，用户消息、项目指令和工具结果各自保留来源。

注册是先把某项贡献交给管理者保存，组装才是在请求需要时取出可见贡献形成材料。作用域回答贡献对谁可见；同名覆盖回答同一位置有多个版本时选择谁；排序回答不同贡献按什么顺序出现。这三件事分别决定请求内容。

项目指令描述工作区和当前文件路径相关的规则。每次模型请求前，项目指令插件先选择规则文件，将内容整理成指令消息，再与待处理输入一起进入本步。历史则从 Session 的 Surface 派生，随后与这些新材料汇合。

请求冻结为正在执行的请求固定数据副本。新输入、插件变化或压缩仍可影响下一次组装，但不能倒回去改已经提交的这一份请求。这解释了为什么引导消息要等下一步骤生效。

## 06.2 沿一个任务看完整流程

以“总结 README，但保留实验性功能的限制”为例，用户目标是一条来源明确的消息。system prompt 贡献说明行为规则，工具贡献说明 read 怎样调用，历史提供先前已经获取的材料；工作区指令再依据当前范围补充约束。

组装器先决定哪些贡献在当前作用域可见，再解决同名项和顺序问题。前置指令处理会清掉不再需要的待处理指令，并把这次需要的指令放入本步消息批次。用户消息在首次尝试登记，重试不再重复登记它；请求创建后获取独立配置副本。

若请求执行期间用户补充“只总结正式功能”，这句话先进入下一步输入。当前请求仍使用原来的固定材料；下一步骤重新领取并组装，才有新要求。若之后发生压缩，后续历史视图可能变化，但已经在途的请求仍不变。检查材料缺失时，应分别查可见贡献、前置消息、历史 Surface 和实际请求，而不是只在某个大字符串里找一句话。

## 06.3 关键机制与设计取舍

### 材料有不同的入口

![F06A：提示贡献、项目指令与历史分别进入请求](../figures/F06A.png)

图 06A 的三路材料汇入本步请求：SystemPrompt 组装提示贡献，项目指令形成前置消息，Session 历史按 Surface 派生。它们分别保留自己的来源和排列规则。

system prompt 通常描述运行方式和工具使用等约束。运行时上下文提供当时环境材料，例如当前时间、工作目录或刚读取过的文件路径。项目指令描述工作区规则。用户消息提出当前目标，工具结果给出已获取事实。知道每类材料从哪里来，才能检查冲突、遗漏与重复。

### 从贡献到请求冻结

插件用 `SystemPrompt.section` 注册具名提示段，用 `context` 注册动态上下文。每项贡献带有作用域。同名项先选择当前 Agent 更近的作用域，再按服务规定的顺序排列。完整提示段另有自己的选择规则。SystemPrompt 服务根据这些规则组装本步提示词。

驱动在前置步骤领取输入，调用 `assemble` 得到组装结果，并把运行时上下文投影成适合本步的材料。随后进入 `agent/pre-step` 链。这是一串按顺序执行的前置检查关卡，决定本步是否继续，以及哪些消息进入本次请求。项目指令插件在这条链上等待相关投影就绪，再按工作区与触及路径整理指令。触及路径就是本次任务接触过的文件路径，用来确定要加载哪些目录下的规则文件。插件把选中的指令整理成上下文消息，插入将要进入步骤的批次。

进入步骤后，框架准备模型调用，记录需要的系统消息、首次进入的用户消息和请求信息，再派生并冻结请求。冻结意味着这次请求的内容不能被稍后修改的共享对象悄悄改变，下一步重新组装消息和上下文。

### 顺序与作用域的基础

贡献类似多个人填写同一份请求资料，但合并规则由系统决定。每项至少要有身份、范围和位置：身份帮助替换或去重，范围决定谁可见，位置决定有序组装。

消息同时保存内容与来源。项目指令来自规则文件，用户需求来自提交入口，工具结果来自执行链。框架按这些来源组织消息；一段文字里出现“系统提醒”，不会改变它原有的消息类别。

### 分析示例：重复材料占了多少空间

教学请求包含工具指导 800 字节、项目规则 600 字节、用户需求 200 字节、历史 2400 字节，共 4000 字节。某插件又加入完全相同的项目规则 600 字节，新总量为 4600 字节，增加 15%。

多一份相同规则没有提供新事实，还可能使来源难以辨认。合并前先识别同名项、作用域与历史中的既有材料，比盲目压缩整个请求更有针对性。项目指令用 sameContextPayload 判断等价消息，SystemPrompt 则按名称和作用域选择贡献。两条路径各自去重。

### 在下一步加入项目约束

![F06B：重复规则前后的材料体积](../figures/F06B.png)

图 06B 比较重复材料的体积：基础请求 4000 字节，重复一份 600 字节规则后变成 4600 字节，增加 15%。两侧比较的是内容组成和字节数。

驱动准备模型调用时检查取消信号。工具成功访问文件后，项目指令插件按调用结果收集触及路径。当前步骤结束时，插件排队更新对应指令；下一步前置链等待更新完成，再把本次需要的规则消息加入请求。

### 常见误解

“所有项目指令都直接变成 system prompt”：项目指令在前置步骤中形成指令消息，再与本步输入组合；SystemPrompt 服务另行组装 system prompt。

“更长的提示词必定更可靠”：长度只描述材料体积。冲突、重复和是否被正确执行仍要检查。

“冻结一次请求就冻结整个 Session”：冻结保护本次材料；下一步可读取新消息、工具结果或新的 Surface 状态。

### E06A · 项目指令进入本步消息

阅读任务：位置是前置指令处理已经算出 desired 之后。desired 是这一步要插入的指令消息；pending 是待清理指令，decision 保存准备中的消息批次，messages 是已领取输入。重点观察去重和插入位置；指令文件的发现过程见本章前面的讲解。

代码类型：**真实源码摘录**。证据编号 [E06A](../evidence-index.md#e06a)；下表的数字是原文件行号。

```ts
    for (const message of pending) agent.inbox.remove(message.id)
    if (desired === undefined || decision.messages.some(message => sameContextPayload(message, desired))) {
      return decision
    }
    // Fold the context right after the claimed batch, so the direct prompt
    // precedes it and the driver-appended runtime context follows it.
    const lastClaimedIndex = decision.messages.findLastIndex(message => messages.includes(message))
    const entered = decision.messages.toSpliced(lastClaimedIndex + 1, 0, desired)
    return { ...decision, messages: entered }
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 332 | for...of 遍历 pending 并调用 remove | 先从 Agent Inbox 移除不再保留的待处理指令消息。 |
| 333 | if、逻辑或与 some 检查 | 没有新指令或已经有等价内容时，不重复插入。 |
| 334 | return 返回既有决定 | 本分支保持当前批次不变。 |
| 335 | 结束 if 分支 | 只有需要新增内容的情况继续。 |
| 336 | 原注释说明插入相对位置 | 指令放在领取输入之后。 |
| 337 | 原注释说明后续追加的运行材料 | 直接输入在前，驱动后补的运行上下文在后。 |
| 338 | findLastIndex 与 includes | 在决定的消息数组里找到最后一条属于领取批次的输入。 |
| 339 | toSpliced 建立新数组 | 在该位置之后插入 desired，不原地改写旧数组。 |
| 340 | 展开对象并替换 messages | 返回新的前置决定，供本步请求组装使用。 |


执行推演：desired 已经包含在批次时，返回原决定；需要新指令时，找到最后一条已领取输入，把 desired 放在它之后，返回新的批次对象。

## 06.5 理解检查与讲解问答

### 问题 1 · 项目指令一定进入 system prompt 吗？

讲解：项目指令由前置步骤形成消息，并加入本步材料；system prompt 则由 SystemPrompt 服务组装。两条路径在准备请求时汇合。

### 问题 2 · 引导消息到来后，已经发出的请求会改变吗？

讲解：不会倒改在途请求。新消息在相应领取边界影响后续请求。

### 问题 3 · 重试为什么不重复登记用户消息？

讲解：首次尝试登记后已有这份 Session 事实，再次登记会把一个输入变成重复历史。
