# 第 3 章｜Agent 循环、Inbox 与工具调度

本章学习任务：追踪输入从 Inbox 进入 turn、step 和 attempt 的过程，解释并发执行与有序提交。

## 03.1 基本概念

一轮（turn）代表驱动处理一批输入的完整过程。轮次可以包含一个或多个执行步骤（step）；前置拒绝或空首输入也可能使轮次没有进入模型步骤。尝试（attempt）对应步骤内的一次模型请求。例如，先读取 README 文件再总结内容，可作为同轮次内的两个步骤。如果请求失败且恢复策略允许重试，后续新请求依然归属当前步骤，此时 attempt 计数增加，turn 与 step 维持原值不变。

系统在特定时刻持有的待处理消息、轮次编号及驱动阶段统称为状态。事件发生导致这些数据更新，驱动依此调度状态流转。若路径支持取消操作，代码会检查收到的取消信号，中断未开始的工作并安排已启动任务收尾。

Inbox 维护着 `next-turn` 与 `next-step` 两类等待项。`followup` 输入存放于前者，`steer` 存放于后者。当驱动进入下一步时，会取走所有 next-step 待处理项；若逢新一轮开启，再额外取出一条 next-turn 附加在材料末尾。这样安排使得后加入的引导能优先得到处理，排队较早的普通任务仍在等待。取出输入后，程序执行前置判断，条件符合才会发起模型请求。

处理阶段划分为输入接纳、消息领取、模型请求、工具执行与轮次结束。评估任务进展时，各阶段产生的事件和结果需关联至其所属轮次。

## 03.2 沿一个任务看完整流程

假设 A 和 C 皆为普通任务，B 作为当前轮次的补充要求。此时 A 已处于本轮执行中，C 正在等待下一轮次，而 B 通过引导入口排入了下一步骤。

| 边界 | next-step 待处理 | next-turn 待处理 | 领取结果 |
| --- | --- | --- | --- |
| 本轮请求执行中 | B | C | 不改已经发出的请求 |
| 本轮下一步骤 | B | C | 领取 B，C 继续等待 |
| 下一轮开始 | 空 | C | 领取下一轮的一项普通输入 |

驱动记录轮次启动后，对下一步骤执行前置判断。若条件不符被拒绝，轮次会以 blocked 状态结束，且不产生模型步骤；判断通过后才组装并发送请求。若请求成功且无工具调用，步骤即告完成；若附带工具调用，程序会执行工具并留存结果，接着依循结论决定进行下一步或是终止。当尝试失败时，后续动作受恢复策略控制：仅当错误恢复链（详见第 9 章）返回 retry（重试）时，同一步骤内才会发起再次尝试，否则按失败处理。以包含两个步骤且首步重试一次的任务为例：期间共计经历一个 turn、两个 step 以及三次模型请求，产生三次 attempt。

## 03.3 关键机制与设计取舍

### 三层边界

![F03A：轮次、步骤与模型尝试的嵌套关系](../figures/F03A.png)

图 03A 外层方框代表一轮任务，内层方框标示两个步骤。由于第一步经历了失败与重试共计两次尝试，第二步经历了一次成功尝试，该轨迹总计由一个 turn、两个 step 以及三个 attempt 构成。

turn、step 与 attempt 独立记录任务在不同层面的推进情况。前置拒绝会使整个轮次跳过模型步骤；读取并总结的操作可分为两个步骤完成；步骤内的请求失败后允许发起重试。当成功消息完成提交后，驱动从中解析出工具调用。如果尝试失败，尚未成功完成的输出内容称为 partial，程序会将其转入失败记录及恢复流程。

### Inbox 怎样与驱动合作

Inbox 负责存放还未被取走的输入。`followup` 存放于下一轮列表并触发唤醒请求；`steer` 存放于下一步并触发唤醒；`inject` 同样加入下一步，交由随后的驱动操作去获取。采用不同入口决定了输入何时进入后续流程，同时影响驱动的启动时机。

系统空闲时，附带唤醒请求的输入将启动驱动。若此时已有驱动处于运行中（即活跃活动），新到达的输入会在指定边界由该驱动提取。在系统维护期间，产生的唤醒请求暂存于 `wakeRequested` 属性，待维护收尾时判断是否启动驱动。如果当前活动接到了取消信号，`send` 方法将本应唤醒的输入重新路由至 `next-turn`，使其在当前运行任务结束后再被处理。

按照常规流程，驱动先开启轮次、准备下一步，接着取走待处理消息以组装请求材料。前置判断会给出放行或拒绝的决定。获准进入后程序发出模型请求，如果成功结果包含工具调用，程序转向执行相应的工具批次，产生的结果追加至 Session 历史。随后驱动根据停止原因以及是否还有下一步输入，裁定继续推进还是结束。

### 工具执行能重叠，结果仍按模型顺序提交

现在对贯穿全文的案例稍加扩展以辅助教学：模型在单条消息内先后提出了读取 README 的调用 A，以及读取包信息的调用 B。此处需理清三个不同的顺序：模型提出调用的排列、真实执行完成的先后，以及工具结果写入 Session 的次序。真实执行的完成顺序可以不同，结果提交仍遵循模型提出调用的顺序。[S02](../evidence-index.md#s02) 可与本节介绍的执行器对照阅读。

执行器依照模型提议的次序生成调用计划，依次存储调用标识、工具名、已解析参数、所属 Agent 及取消信号。支持并发的调用会被放入具有容量上限的执行池；要求独占的调用则设立执行屏障，需等池中现有任务完毕才开始运行。执行池用于追踪进行中的调用，屏障限制各批次的启动先后。

开始处理各项调用时，程序先记录 tool/call 与对应的序号，随后等待前置准备。此环节可能直接给出拒绝结果，也可能通过校验分派实际操作。前置准备严格按次序开展，只有实际分派和工具内部运行会发生重叠。对于产生的拒绝结果，程序同样把它放入结果链的对应位置予以留存。

若 A 与 B 都允许并发，且执行池空间充裕，B 可能会先执行完毕。执行器把 B 的返回结果放在索引为 1 的暂存槽，此时提交游标依然停留在 A 所在的索引 0。待 A 执行结束，执行器才按照 A、B 的次序进行结果后处理、向 Session 历史追加记录，并将额外的上下文留给后续步骤使用。结果槽依据调用原本的位置保管返回数据，提交游标机制确保了最终的历史顺序同模型提议完全吻合。

| 时点 | A 的结果槽 | B 的结果槽 | 已提交到 Session 的工具结果 |
| --- | --- | --- | --- |
| 两项已开始 | 尚空 | 尚空 | 无 |
| B 先结束 | 尚空 | 已有结果 | 无，仍等待位置 0 |
| A 随后结束 | 已有结果 | 已有结果 | 按 A、B 顺序处理并追加 |
| 下一步准备 | 已按约定交接 | 已按约定交接 | 模型可使用有确定关联的结果 |

前文所述的提交将结果追加至 Session 历史，第 5 章会详细阐述这些事件的存储写入过程。结果提交后，执行器重新校验未启动项的执行模式。若某工具在执行期间变更了注册状态，余下的调用将依照新模式流转。工具产生的轮次结束提示汇总至外层驱动，以此作为判断继续执行下一步骤的依据。

执行遇到取消或调度失败时走向不同的处理分支。发生取消时，程序停止分派新动作，等待运行中的调用收尾，并按既定顺序完成交接；针对模型提出但尚未启动的工具调用，框架生成标明已跳过的合成结果。这类结果仅作为说明，不指向真实的工具行为。遭遇调度失败时，执行器等待已发出的动作收尾，随后把错误带回当前步骤。

坚持按序提交方便了历史记录与模型原始提议对齐，允许重叠执行则有效利用了独立工具运算时的等待期。为此，执行器配置了并发池、结果暂存槽以及提交游标。B 的执行虽然先结束，仍需等待排在前面的 A 完成提交。由于历史顺序维持原样，下一步的模型依然按起初的提议顺序获取结果数据。

### 队列与状态机的最小基础

队列的职责是存放那些仍待处理的输入，而状态机负责标记系统当前处于哪个运行阶段。当新消息排入队列时，进行中的请求继续使用已经组装的材料；只有当驱动推进到下一个领取节点，积压的待处理输入才会被组装进接下来的请求。

程序借助事件通知，向用户界面、日志记录等观察者广播队列或状态发生的变更。在 DSH（DeepSeek Harness 的简称）设计中，Inbox 产生变动时会先更新自身的可见状态，然后再发出监听通知。这使得接收方能够在收到通知时顺利获取最新的状态值。

系统主要依靠 `ReactLoopAgent` 充当核心运行驱动。它涵盖了 Inbox、turn、step 数据的管理，处理模型请求发送以及响应取消信号。网页端对应的 React 组件则提取这些运行状态用于界面展现。

### 分析示例：数一次有重试的读取任务

观察以下教学轨迹：程序开启一轮执行；第一步中的首回模型尝试失败，重试的第二次尝试成功且发出了 read 调用；随后工具返回文件片段内容；进入第二步，模型成功产出内容总结；最后该轮次结束。统计此案例可见：它总共包含 1 个 turn、2 个 step、3 次模型 attempt 以及 1 次工具调用。

复算记录：[C3 · 轮次与步骤计数](../examples/calculation-results.json)。

发生于第一步的重试位于同一个尝试循环内部，程序保留原有的 step 数据，且避免重新执行前置步骤或登记初始用户消息。这解释了为何 3 次 attempt 只产生 2 个 step。由工具结果推进引发的第二次模型步骤依旧从属于当前用户的输入任务，所以 turn 总数保持为 1。

通过拆分 turn、step 和 attempt 进行独立计数，观察者能够分辨额外的请求是源于任务环节的推进，还是由失败重试引发。

### 运行中插入新要求

![F03B：下一轮、下一步与是否唤醒的区别](../figures/F03B.png)

图 03B 的三个栏目展示了 followup、steer 与 inject 的不同流向。followup 被置于 next-turn 并发出唤醒请求，steer 被置于 next-step 且发出唤醒请求，而 inject 则排入 next-step，留待后续驱动活动发生时领取。

回到读取案例，驱动取得工具结果后准备下一步请求材料。如果在领取边界取得新的约束，总结请求就会包含这些约束。前置拒绝使轮次以 blocked 结束；取消则停止后续调度并安排在途操作收尾。cancel 默认清空 Inbox，调用方设置 keepInbox 时保留待处理输入，由后续驱动活动继续领取。

### 常见误解

常见误解包括“到达下一步的输入会立刻打断当前模型流”。next-step 指定下次领取输入的位置，当前请求继续执行。需要中断当前运行时，应发送取消信号。

工具的返回结果严格按模型调用次序留存。各工具的实际运行过程允许并发处理，但调用前的前置准备、运行完毕的结果后处理以及提交动作，均依照执行器限定的顺序推进。

“出现 turn/start 一定会消耗一次模型请求”同样是误解。如果遭遇前置判断拒绝或者最初输入为空，程序可能在进入实际模型步骤前就已经终止执行了。

## 03.4 源码研读

<a id="e03a"></a>

### E03A · 领取时组合两类待处理输入

阅读任务：下面展示的是 Inbox.claim 的完整方法。参数 target 用于判断当前领取是否恰逢新轮次边界，turn 标明本次领取归属的轮次编号。内部的 mutate 操作负责删除指定列表项并返回抽取的对应消息。代码重点揭示了两类待处理列表在提取时的差异。

#### 实现详解

Inbox.claim 将排队输入转换为供当前步骤使用的一批消息。Agent 驱动在准备阶段调用它，以 target 参数标识当前边界是否开启新轮次，用 turn 指定本次领取的归属。Inbox 内部维护 next-step 与 next-turn 两个队列：前者存放要在下一步加入的引导或注入，后者装载等待下一轮的普通任务。

执行提取时，程序先获取 next-step 内所有现有消息，并依序列入 claimed。mutate 调用在返回提取项的同时更新队列，取出的消息随即脱离待处理列表。若边界为 next-step，提取动作就此结束；若处在 next-turn 边界，程序额外从下一轮队列开头抽取一项并接在 claimed 末尾。即便普通队列有多项积压，本次也仅取一项。

此机制确保了本轮新增的约束能在下一步及时混入，同时使普通任务逐轮稳步推进。假定 next-step 含有 B 与 D，next-turn 含有 C 与 E：当筹备下一步时执行提取，将得到 B、D，剩下的 C、E 留置；而在新一轮边界提取时，结果为 B、D、C，仅留 E 给后续轮次。抽取的结果严格按目标边界与列表位置拼接，不能按各消息的提交时间做全局重排。

队列更新完成后，程序逐条派发 agent/inbox/claimed 事件，并携带消息及其所属 turn，让界面等观察者知晓输入去向。拼接好的 claimed 数组随后交给前置步骤，前置通过后才用来组装模型请求。完成领取代表消息进入步骤筹备期，不过前置逻辑依旧能选择拒绝放行。后抵达的输入暂存在队列中，等下次驱动触及边界时处理，现行发出的模型请求保留其初始材料。

代码类型：**真实源码摘录**。证据编号 [E03A](../evidence-index.md#e03a)；下表的数字是原文件行号。

```ts
  claim(target: InboxTarget, turn: number): UserMessage[] {
    const claimed = this.mutate('next-step', 0, this.nextStep.length, [], false)
    if (target === 'next-turn') claimed.push(...this.mutate('next-turn', 0, 1, [], false))
    for (const message of claimed) this.dispatch.emit('agent/inbox/claimed', { message, turn })
    return claimed
  }
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 109 | 方法接收边界和轮次，并返回消息数组 | 调用者是准备下一步骤的驱动。 |
| 110 | const 保存 mutate 返回值，length 表示列表项数 | 先取走当前全部 next-step 输入，保存为 claimed。 |
| 111 | if 比较 target，push 与展开追加数组成员 | 新轮次边界才再取一项 next-turn 输入，拼到领取批次后。 |
| 112 | for...of 遍历领取结果，emit 发出事件 | 发布每条消息所属轮次的领取通知，供界面等观察者更新状态。 |
| 113 | return 返回数组 | 前置处理可使用这批消息形成本步材料。 |
| 114 | 右花括号结束方法 | 领取动作完成，模型请求仍属于后续步骤。 |


执行推演：设 next-step 内存有 B，next-turn 内存有 C。当 target 是 next-step 时，方法提取出 B，C 继续留在队列；当 target 为 next-turn 时，方法提取全部的步骤输入，接着再抽取仅一项轮次输入。所有被取走的消息均会发出领取事件通知。

## 03.5 理解检查与讲解问答

### 问题 1 · C 先以 followup 排入，B 后以 steer 排入，谁先用于本轮下一步？

讲解：B 会在下一步骤边界被取走，C 必须留给下一轮。Inbox 预先按照消息指定的边界目标做好了分类，提取动作严格基于边界类型执行。凭借这种队列分离，晚提交的 B 得以在早到的 C 之前加入当前请求。

### 问题 2 · 一轮两步，第一步重试一次，一共有几次尝试？

讲解：一共发生三次尝试。第一步内部包含了两次，第二步经历了一次，但这些步骤全部归属同一个轮次。

### 问题 3 · inject 与 steer 的关键差别是什么？

讲解：这两类都会存入 next-step。区别在于 inject 存入后不触发唤醒，steer 存入后触发唤醒。因此在驱动空闲期间，由 inject 投递的输入暂时滞留于队列，依靠后来的唤醒动作才能推进。

### 问题 4 · 模型先提出 A、再提出 B，但 B 先完成，为什么 Session 可以先没有 B 的结果？

讲解：执行器先将先完成的 B 放置在索引为 1 的暂存槽内，游标继续停留在位置 0 等待 A。直至 A 完成，执行器才按序处理并把 A、B 提交追加。真实执行的快慢独立于向历史提交的次序；后续模型若要读取过往历史，它拿到的一定是根据提议顺序已确实追加完成的结果。
