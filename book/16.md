# 第 16 章｜测试、模型回放与行为验证

本章学习任务：理解按位置消费的模型回放，区分调用轨迹检查、请求断言与真实任务评价。

## 16.1 基本概念

测试把预期行为写成可检查的条件。断言规定程序必须满足的关系，例如失败模型尝试中提出的工具调用不得进入执行阶段。替身替换选定依赖，回放用预录响应代替模型生成，真实循环与工具链继续处理这些响应。

本项目的 LLM 回放机制会先为 Session 绑定响应脚本，再根据模型调用的先后位置挑选响应条目。新开启的 Session 会绑定下一份可用脚本，随后的每次模型调用都会依次消费脚本中的下一项响应。因为程序仅凭调用序号选择响应，所以请求字段是否合规，需要由测试中的独立断言来完成检查。

本章的脚本是一份录制 Session 的响应清单，每项对应一次模型调用。消费检查确认脚本是否绑定、条目是否全部使用；请求超出清单时，由响应生成器报告耗尽。请求内容、工具动作和最终产物分别用相应断言检查。

固定模型的输出可以排除一种变化来源，但这种方式不会固定操作系统文件、时间、并发调度与远端工具的所有行为。在回放期间具体使用哪种文件和工具实现，是由测试的 profile 与替身配置来共同决定的。

## 16.2 沿一个任务看完整流程

假设录制脚本包含两项响应：第 0 项提出 read 动作，第 1 项生成总结。当前 Session 发起第一次请求时会获取第 0 项，第二次请求获取第 1 项，随后游标变为 2。如果只发出一次请求，就会剩下未消费的条目；若发起第三次请求，就会面临脚本耗尽。这种消费检查能够帮助开发者察觉调用轨迹的变化。

位置回放按照调用序号返回响应。即使实际请求的上下文有误，第一次调用仍会消费第 0 项。因此，验证提示材料组装时，还要断言实际请求中的消息、工具定义和参数。

| 想验证的命题 | 合适观察 |
| --- | --- |
| 错误尝试没有执行工具 | 固定失败响应，并检查调用与执行 |
| 请求包含项目指令 | 检查实际组装的请求内容 |
| 新提示词使模型更少遗漏 | 使用新模型输出和统一任务评价 |
| 客户端没有重复气泡 | 检查客户端提交与历史合并状态 |

在修改了提示词之后，需要使用真实模型重新生成结果，并按照相同的任务标准进行比较；而回放机制则专门用于在固定响应的情况下，检查程序的实际运行行为。

## 16.3 关键机制与设计取舍

### 固定一个依赖，继续执行其他部分

![F16A：固定模型响应，运行真实循环并检查行为](../figures/F16A.png)

图 16A 展示了从录制日志派生响应脚本的过程。系统将脚本接入 LLM 边界，随后运行真实的循环与工具。测试过程会检查程序的实际运行行为，同时核实响应清单是否已被完整消费。

### 证据层怎样选择

单元测试检查局部函数，例如验证读取窗口逻辑；快照测试对比选定的输出内容；回放机制让固定的模型响应驱动真实的程序循环；API 端到端测试连接实际服务，运行完整的请求链路；性能实验则记录规定条件下的耗时与资源用量。在选择检查方式时，应先明确想要观察的具体行为。

`deriveReplayScript` 从事件恢复响应条目。录制缺少终结时，需要在 replay.override.json 中提供覆盖响应：完整 ReplayEntry 数组替换整份脚本，{ patches } 在能够成功派生的脚本上修改指定位置。`installLlmReplay` 加载脚本并按 Session 绑定消费位置。providers 非空时注册 ReplayAdapter，替换指定 Provider 的模型响应；没有配置或配置为空数组时，在 `llm/stream` 边界拦截，交由同一脚本应答。

回放的消费检查会确认每份脚本都已绑定实际 Session，并且所有条目都已用完。少发起一次请求会留下未消费的条目，多发起一次则会引发脚本耗尽错误。通过固定响应来排查工程故障时，这些检查能够有效发现调用轨迹上发生的变化。

### 断言、替身与覆盖范围

断言（assertion）用于写明需要检查的条件，替身（mock）则用来替代特定的依赖项。如果仅检查数组的长度是否为 2，那就只验证了数量；只有当检查元素内部的工具名称、参数和结果时，才真正验证了这些具体字段。回放机制只是固定了响应序列，实际需要检查什么内容完全由测试断言来决定。

一个故障测试应当明确给出触发条件与对应的观察点。例如，当构造一个失败的 finish 响应时，我们需要检查驱动程序是否记录了 attempt、是否执行了相应的工具。而在评价模型总结的质量时，则应使用任务集和新生成的产物，按相同标准来检查其中是否存在遗漏与错误。

### 分析示例：四个命题选四种检查

验证“行窗口只返回选定范围”可以使用窗口单元测试；验证“失败尝试没有执行工具”可以利用固定的失败响应驱动真实循环来观察；确认“实际服务能够完成协议请求”需要完整的 API 测试；若要评估“修改提示词后更少遗漏实验性声明”，则需要同等条件下的业务任务评价。

如果在评估提示词时采用固定输出的回放，由于输出内容已完全由脚本决定，我们将无法判断提示词对真实模型产生的影响。回放主要用于定位工程回归（即原本正常的行为在代码修改后遭到破坏），而评估真实模型的表现必须使用它新生成的输出结果。

考虑一份包含 3 次模型调用的录制数据。如果第 2 次调用缺失了 finish 块，`deriveReplayScript` 会抛出 “ended without a finish chunk” 错误，要求通过 replay.override.json 提供覆盖文件。若回放使用包含 3 项响应的完整脚本，但实际运行时仅发起 2 次请求，`assertConsumed` 会报告仅消费了 2/3 次的条目。针对录制 Session 的另一项检查是：若某份脚本从未绑定到实际运行的 Session，系统将报告 recorded script(s) never bound。前者负责检查条目的消费进度，后者负责检查脚本与 Session 的绑定状态。

图 16B 对比了三类检查：局部函数与固定响应回放、真实服务接口测试，以及业务任务评价。前两类主要检查程序行为与服务交互，业务评价则重点对比新生成的最终产物。

### 常见误解

“测试通过说明所有场景正常”：测试仅能覆盖其代码中给定的触发条件与断言逻辑。

“回放通过说明新模型更强”：使用固定输出的回放并没有检验新模型的实际生成行为。

“读到测试就等于测试通过”：代码描述预期行为，执行结果记录测试在给定环境中通过还是失败。

### E16A · 消费按位置推进

阅读任务：本段代码运行在 replay 已经依据 Session 找到或建立了绑定状态之后。变量 state 此时保存了该 Session 专属的脚本数组与当前游标；我们需要重点关注这一次选择模型响应的判断依据。而后续的异步生成器（一种配合 yield 关键字，可逐个产出值并暂停执行的函数，详见附录）则负责处理脚本耗尽等错误情况。

#### 实现详解

模型回放会为实际运行的每个 Session 绑定一份对应的响应脚本，再按照该 Session 内部的调用位置来消费条目。在进入这段代码前，replay 已经完成了绑定状态的查找；初次出现的 Session 会领取下一份可用录制脚本，此后的调用则继续沿用它自己的 entries 数组和 cursor 游标。因此，多个 Session 能够分别推进各自的响应序列。

本次调用首先保留了 boundState，并捕获当前已绑定的脚本数和录制脚本总数，这些数据将用于在后续报错时说明录制范围。随后，程序提取 cursor 的旧值作为 index 索引，同时将 cursor 的值增加 1，再利用 index 从 entries 数组读取具体的条目。当 cursor 为 0 时，程序选中第 0 项响应，下一次调用将选中第 1 项。因为位置游标在返回生成器之前已经完成推进，后续的响应消费就会沿着本次选中的 entry 正常进行。

提取的 entry 允许为空（undefined），因为程序实际发出的请求次数有可能超过了录制的条目总数。随后返回的异步生成器会负责检查未录制 Session 与脚本耗尽等异常，并抛出要求重新录制的错误信息；而对于合法的条目，它会进行必要的标识与消息处理，最终逐项产出响应内容。选择响应的核心依据始终是调用位置，而请求携带的完整上下文是否符合预期，需要由测试断言来执行检查。

例如，某份录制脚本包含“先提出 read，再生成总结”两项响应，那么实际的两次模型调用就会依次取得这两项。若只发生了一次调用，assertConsumed 检查会发现还存在未消费的条目；若发生了第三次调用，生成器就会报错提示脚本耗尽。即使首次请求缺失了项目规则，位置选择机制仍能获取到第 0 项响应，因此在验证提示词组装时，测试还必须额外断言实际的 messages 数组、工具定义与携带的参数。响应回放与请求断言相互配合，分别完成了运行轨迹和输入内容的验证。

代码类型：**真实源码摘录**。证据编号 [E16A](../evidence-index.md#e16a)；下表的数字是原文件行号。

```ts
    const boundState = state
    const seenSessions = nextScript
    const totalScripts = scripts.length
    const index = boundState.cursor++
    const entry: ReplayEntry | undefined = boundState.entries[index]
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 1064 | const 保存同一状态对象 | 后面的生成器使用本次已经绑定的 Session 状态。 |
| 1065 | const 保存数量 | 捕获目前已绑定的脚本数量，用于错误说明。 |
| 1066 | 读取数组 length | 保存录制脚本总数，便于报告未录制 Session。 |

执行推演：cursor 为 0 时，调用取 entries[0]，随后 cursor 变为 1；下次取 entries[1]。选择依据是调用位置，这些行不会根据请求内容（Payload）查找等价条目。

### E16B · 有路由时与无路由时的接入

阅读任务：回放脚本加载后，本段把模型替身接到请求边界。providers 是配置中的 Provider 清单，dispose 是以后撤销替身登记的释放函数。

#### 实现详解

在 installLlmReplay 载入脚本并建立 replay 函数后，程序需要把模型替身接入到应用的请求边界上。本段代码会根据 providers 的配置来选择具体的接入位置，当缺省时会采用空数组。这两种安装方式最终都将模型请求交给了同一个 replay 函数，而响应的挑选规则则继续遵循 Session 绑定与游标推进逻辑。

当 providers 数组非空时，代码会提取出各项 Provider 的 id，随后注册 ReplayAdapter。这个适配器负责提供测试配置中的 Provider 身份信息，并在相关路由尝试获取数据流时调用 replay。这一设计能让正常的模型路由检查与调用准备逻辑继续参与测试。注册行为只覆盖配置指定的 Provider 身份，其他路由仍由系统原有逻辑进行处理。

providers 缺省或为空数组时，代码在 `llm/stream` 登记监听器。模型请求到达此边界，监听器直接返回 replay(options)，不调用传入的后续处理函数 _next，由脚本提供响应。登记时只保存回调，实际请求到来才执行它。dispose 保存所选安装方式返回的释放函数，测试结束后用于撤销本次登记。

以 README 的回放测试为例，即使模型边界直接返回了预录的 read 提议，真实的 Agent 循环依然会解析这个调用、经过工具的准入规则、访问测试配置指定的文件服务，然后再去提取脚本里的总结响应。测试既可以按照 Provider 路由来安装适配器，也可以在流入口处接管响应；而文件、工具和 Session 的具体实现则由测试的装配逻辑另行挑选。固定模型输出使程序的运行轨迹易于复现，而断言则继续负责核查实际的执行过程与产物。

代码类型：**真实源码摘录**。证据编号 [E16B](../evidence-index.md#e16b)；下表的数字是原文件行号。

```ts
  const providers = config.providers ?? []
  const dispose = providers.length > 0
    ? ctx.llm.registerAdapter(providers.map(provider => provider.id), new ReplayAdapter(providers, replay))
    : ctx.on('llm/stream', (options: GenerateOptions, _next) => replay(options))
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 1101 | 空值合并与数组字面量 | 缺省目录采用空数组。 |
| 1102 | const 与长度判断 | 依据是否指定 Provider 目录选择安装方式。 |
| 1103 | map、箭头函数和适配器构造 | 提取 Provider 身份并注册对应回放适配器。 |
| 1104 | on 与回调 | 另一分支在流接口拦截，把请求交给同一 replay 函数。 |


执行推演：当 providers 非空时，程序会登记指定路由的适配器；当其为空时，则在 llm/stream 登记统一的拦截回调。对应路由的模型调用会被 replay 函数接管并返回响应；而工具执行和文件服务则继续采用测试配置所指定的实际实现。

## 16.5 理解检查与讲解问答

### 问题 1 · 两次回放调用都消费完了，是否证明请求材料正确？

讲解：位置消费主要检查第几次请求提取了第几项响应。如果需要验证输入材料的组装是否正确，还必须断言实际发出的请求中所包含的消息、工具名称与参数；这两类检查手段分别负责覆盖调用轨迹和请求的具体内容。

### 问题 2 · 固定回答以后能评价新提示词改善了多少吗？

讲解：不能。回答已经由脚本固定，评价提示词的影响需要新的模型输出。

### 问题 3 · 回放是否自动成为纯内存、无外部动作的测试？

讲解：回放替换模型响应序列，循环、工具和 Session 继续运行。测试配置使用真实文件 Provider 时，工具仍会访问测试工作区。
