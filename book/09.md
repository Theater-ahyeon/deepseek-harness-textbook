# 第 9 章｜模型流式响应与请求恢复

本章学习任务：追踪模型路由、请求准备和流式消费，解释失败结算、恢复决定与同一步骤内的重试。

## 09.1 基本概念

流式响应通过连续到达的片段传递模型输出，片段可以包含文本、工具调用、用量或结束状态。Provider 与模型路由确定本次服务，适配器将服务协议转换成统一接口。驱动持续消费片段；正常迭代结束后依据 finish 结算，消费过程抛错则进入异常处理。

限流限制服务在一段时间内接收的请求数量，超时表示等待超过规定边界。两者都可能使请求失败，恢复方式由对应策略决定。

重试是在失败后重新尝试。恢复策略决定某类失败能否重试以及重试前的准备；只有 agent/request-error 链返回 retry 时，循环才会开启下次尝试。失败尝试产生的临时内容可以显示，但不能作为成功的助手消息去执行里面的工具提议。

请求先解析模型路由与配置，再获取流并消费片段。流正常结束后检查 finish：成功则提交助手消息，错误或中止则记录失败尝试并询问恢复链。消费过程直接抛错时，catch 先结算已开始的尝试，再继续抛出；若尝试尚未开始则直接抛出。这条路径与 finish 携带失败状态的恢复入口分开。

当 finish.kind 为 max-tokens 时，表示已达本次请求的输出上限。循环先提交已生成的助手消息，再返回 max-tokens 结束原因，不进入此消息的工具执行阶段。此机制与因上下文过长而触发的压缩恢复分别处理。

## 09.2 沿一个任务看完整流程

如果第一次尝试在返回部分文本后以失败状态结束，界面仍可显示这些临时进展。驱动会记录这次失败，并将失败类型、Provider、重试策略与取消信号交给恢复链。当恢复链决定返回 retry 时，程序进入下一次尝试；若没有重试决定，则抛出相应的模型错误。

| 到达的内容 | 循环处理 | 能否进入工具执行 |
| --- | --- | --- |
| 正在生成的片段 | 更新临时流状态 | 先显示临时进展 |
| 失败尝试的工具提议 | 记录尝试失败并走恢复 | 不走成功工具阶段 |
| 成功终结的助手消息 | 建立消息并提取工具调用 | 再交给通用准入链 |

重试并非重新接纳用户的任务。已经记录的用户输入不应被再次追加，请求准备也维持着对应的配置语义。不过，每次重试都会重新准备调用，以便恢复处理能修改后续请求的配置。在此过程中，turn 与 step 保持不变，仅 attempt 数量增加。

## 09.3 关键机制与设计取舍

### 临时输出与最终事实

![F09A：流片段经过终结检查才成为提交消息](../figures/F09A.png)

图 09A 将临时输出与正式提交分开：流片段首先更新界面，再由 finish 决定成功、失败或取消，随后循环记录助手消息或失败尝试。只有完成且未触发 max-tokens 的消息，才会进入工具调用判断。

### 一次调用怎样绑定 Provider

LLM 服务的 `prepareCall` 按 provider 标识查找对应适配器，解析目标模型与配置，返回绑定此次调用的 prepared call。它保存被冻结的配置和重试策略，且只能分派一次。发生重试时需要重新准备调用，适配器负责把具体服务的响应转换为统一的流。

DeepSeek 适配器将响应转换成异步片段，并组合取消信号。空闲监测检查等待新片段的时间，超出阈值时产生超时错误；超时、取消与传输失败分别分类。结束时停止消费并尝试关闭迭代器。关闭过程的异常被忽略，以免覆盖已经结算的请求结果。

驱动用 `for await` 消费片段，每次处理片段前检查取消信号并推送临时输出。正常终结后生成并记录助手消息；符合请求恢复流程的失败先记录尝试，再经 `agent/request-error` 链决定是否重试。未获得 retry 时抛出 LlmError；已取消时由取消信号结束等待。

### 异步迭代与响应消费

Promise 用于获取一次异步操作的结果，而异步可迭代对象表示按顺序产生的一组值。`for await` 会等待下一个值，当前项处理完毕后再继续迭代。例如，流中依次送达文本甲、文本乙及结束信息，驱动将按照到达顺序逐个处理，并在消费结束后读取终结状态。

`for await` 循环等待后续片段，直到迭代器结束。随后驱动读取 finish 状态，以确定本次响应如何结算。取消信号在驱动与适配器间向下传递，各层一旦检查到已取消，便会立刻停止后续消费，并开始连接的清理工作。

### 分析示例：重试等待算在哪里

教学轨迹示例中，首次尝试用时 400 ms 后失败，程序退避等待 300 ms（退避指失败后先等待一段时间再重试的策略），第二次尝试用时 700 ms 并成功。不考虑其他开销，模型阶段总计 400＋300＋700＝1400 ms。其中请求尝试时间共 1100 ms，退避等待时间 300 ms，尝试总数为 2 次。

复算记录：[C9 · 请求与退避耗时](../examples/calculation-results.json)。

如果用户在退避等待期间发起取消，流程在第二次尝试前就会结束，此时仅有一次请求。重试机制能处理临时故障，但也会增加等待时间与模型用量；重试策略由 Provider 和恢复插件共同决定。

### 失败、取消与成功走不同出口

![F09B：同一步里的尝试、恢复与工具执行边界](../figures/F09B.png)

图 09B 的左侧展示了对于可重试失败的处理方式，右侧则列出了成功和取消的出口。系统在遇到失败时记录 attempt 然后等待恢复；如果是取消，若留有文本就提交 interrupted 消息，没有文本则仅记录 attempt。

在 README 任务中，如果第一次模型请求遇到失败，驱动会记录下该尝试，并依照恢复决定发起重试。当成功的响应提出了 read 调用后，流程便会转入工具执行环节；读取的内容被加入后续步骤的上下文中，模型再基于此生成总结。失败产生的输出保存在尝试记录内，只有成功消息携带的调用才会进入工具阶段。

### 常见误解

“每个 chunk 都是一条助手消息”：片段仅属于一次尝试过程中的暂态流，而最终的助手消息具备独立的提交边界。

“重试只是再次发送同一函数，在哪里都一样”：重试发起的位置，将决定是否会重复传递材料、引发工具副作用（即对外部世界产生的实际影响，如写文件）或产生其他重复提交。

“取消后保留了文本，所以任务成功”：应当检查 interrupted 标志与具体的结束原因，并根据这些信息另外进行产物判断。

### E09A · 配置复制与冻结

阅读任务：节选位于 prepareCall 的配置准备阶段。config 指定 Provider 与模型，registration 提供适配器。代码解析配置并建立独立冻结副本，模型生成请求与流消费位于后续执行阶段；准备模型能力信息本身也可能需要查询。

#### 实现详解

发起一次模型调用前，必须确定 Provider 的实现、目标模型、有效配置以及附加上下文。prepareCall 首先依据 config.provider 查找当前的适配器登记，然后等待适配器为指定模型准备相关信息。这项准备工作可能会查询模型能力，并接收取消信号；最终的模型输出流将通过随后返回句柄的 stream 操作来获取。

适配器返回的信息先规范为统一的模型描述，再用于解析配置。解析结合调用方设置与模型能力，确定适用的输出上限、推理设置等参数，附加 context 也来自解析结果。请求记录与实际分派因此使用同一组模型和配置依据。

配置数据随后经 structuredClone 建立独立副本，并由 deepFreeze 冻结。复制过程切断了与原配置对象的共享引用，冻结则确保准备好的资料不再被修改。如果存在附加的 context，也会采取同样的复制并冻结操作；若无则保持 undefined。即使调用准备完成后，页面更改了后续请求的参数，当前句柄仍维持已确定的配置，新参数留给未来的调用读取。

后续代码把冻结好的配置、重试策略与流入口组装成一个一次性句柄，同时绑定本次选中的适配器登记。假若准备与分派之间发生插件热重载，该句柄依旧沿用原有的登记信息，防止能力描述与具体执行代码产生版本错位；若尝试再次分派同一个句柄，则会触发报错。在驱动发起重试时，会重新准备新句柄，确保新的尝试能采用恢复流程调整过的配置。准备、冻结与一次性分派这三个环节，共同确立了每次模型请求的执行依据。

### E09B · 失败以后是否再尝试

阅读任务：当前代码位于失败已被登记且恢复链返回 action 的时间点。这段逻辑处在尝试循环的内部；finish 变量保存了本次尝试的失败终结信息。阅读重点在于理解不出现 retry 时的结束路径，以及 continue 语句会回到哪个循环起点。

#### 实现详解

这段代码位于当前步骤的模型尝试循环。此时流已消费结束，finish 标明尝试遭遇失败或中止；驱动已经追加了 assistant/attempt 记录，保存本次未能成功完成的流状态，随后等待 agent/request-error 恢复链处理。恢复链收到 Provider、失败详情、重试策略及取消信号，最终返回 action 以说明是否继续尝试。

恢复环节可能会等待退避或执行压缩，等待期间用户仍可取消。驱动在使用 action 前会再次检查 signal：如果检测到已取消，立即进入取消路径，即便恢复链返回了 retry，也不会启动下次请求。这确保取消状态在经历了恢复等待后仍然生效。

在未取消的状态下，驱动要求 action 必须明确为 retry。若没有返回值或返回了其他动作，程序均利用 finish.failure 中的消息、代码与详情构造 LlmError，交由上层结束当前步骤。若明确重试，便执行 continue 回到该步骤尝试循环的起点，重新准备并发起模型调用。重试沿用当前的 turn 和 step，仅增加一次 attempt，首次已登记的用户输入保持原有记录。

以第 1 步初次请求因限流错误结束为例：恢复链等待后允许重试，此时第二次请求依然隶属于第 1 步。当第二次请求成功并提出 read 调用，流程才转入工具调度。第一次失败流里的临时文字与工具提议仅留在尝试记录中，直接跳过成功助手消息及工具阶段。这一顺序设计将失败记录、恢复判定与新尝试串联，防止把未成功完成的响应当作可执行结论。

## 09.5 理解检查与讲解问答

### 问题 1 · 失败流里出现工具提议，是否应该执行？

讲解：不会进入成功助手消息的工具阶段。驱动首先记录失败，再按照恢复行动决定下一次尝试。

### 问题 2 · 每次请求失败都会重试吗？

讲解：不会。仅当恢复链返回 retry 决定，并且未被取消时，才会发起重试。

### 问题 3 · 临时文字已经显示，为什么后来还会失败？

讲解：片段到达表示生成正在推进。确认成功还要检查终结状态和后续处理是否完成。
