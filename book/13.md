# 第 13 章｜Subagent：拆分任务前先看上下文起点

本章学习任务：说明子 Session 的来源与继承材料，比较 fresh 和 fork；解释子任务完成、团队消息送达与共享文件冲突是不同问题。

## 13.1 基本概念

Subagent 是父任务启动的另一运行单元，负责一部分工作。父 Agent 交代目标、材料、可用能力和交付要求，子 Agent 完成分工，父 Agent 再检查并整合结果。

fresh 从不继承父历史的材料起点开始，fork 从已有历史的规定前缀开始。进程内 Provider 的 spawn 创建空历史子 Session，fork 截取父 Session 到最近已完成轮次为止的事件。前缀保留开头到该位置的全部记录；当前轮次新增资料由父 Agent 通过启动输入传给子任务。

Subagent Runtime 选择 Provider，检查选项与最大深度，再交给 Provider 创建运行。进程内 Provider 为子任务建立独立 Agent 和 Session，它们与父任务共享宿主进程。这里的 fork 指历史继承方式，子任务仍有自己的驱动和生命周期。

实验性团队功能再增加成员、任务板和消息投递记录。邮箱机制可以安排投递、确认与恢复，但不会因此给共享工作区加文件锁。两个成员修改同一文件，仍需要实际的协调或冲突检查。

## 13.2 沿一个任务看完整流程

父 Agent 在当前轮次刚读到一份 README，随后启动 fork Subagent。进程内 Provider 先查最近的 turn/end，只继承到已完成轮次；这份资料位于当前未结束轮次，因此不在继承前缀里。父 Agent 应把子任务必需材料明确交代，或选择适当的已完成起点。

| 起点 | 初始历史 | 父 Agent 应补什么 |
| --- | --- | --- |
| spawn | 不继承父事件历史 | 目标、材料和限制 |
| 本章进程内 fork | 最近完成轮次以前的事件前缀 | 当前轮次新增的必要材料 |
| 其他 Provider | 由其能力契约决定 | 依支持项建立交接 |

运行时检查 Provider、能力、最大深度和结构化输出选项；Provider 再创建运行句柄。父 Agent 获取子结果后对照原任务检查准确性、遗漏和冲突，然后汇合。团队消息有排队、投递和确认记录，恢复时可继续处理未确认项；共享文件修改另由任务分工和冲突协调处理。

## 13.3 关键机制与设计取舍

### 两种起点

![F13A：新 Session 与已完成历史前缀的对照](../figures/F13A.png)

图 13A 左侧是进程内 spawn：新建子 Session，任务材料显式传入。右侧是进程内 fork：复制父 Session 到最近 turn/end 为止的前缀；没有 turn/end 时种子为空。

### 从父工具调用到子运行

父 Agent 调用 Subagent 工具后，执行入口先取得实际调用 Agent，再处理模型选项和 Provider 请求。Runtime 管理启动、Provider 查找和契约检查。一次性任务调用 `start`；后台任务选用支持持续运行的 Provider 时，可调用 `startContinuable` 接纳输入并返回子 Session 身份。Runtime 检查能力和最大深度，后者限制子任务继续创建子任务的层数。检查通过后，Runtime 建立运行描述并交给 Provider。fresh 与 fork 选择初始材料，start 与 startContinuable 选择运行和交付方式。

进程内 spawn 将空种子交给 `startInProcessRun`，fork 则先截取父 Session 到最近 `turn/end` 为止的事件前缀。两种 Provider 复用这份创建流程，为子任务建立新的 Agent 和 Session；子 Agent 接收自己的任务输入，再运行自己的循环。没有已完成轮次时，fork 的种子为空。运行句柄提供结果、取消传递和资源释放。

持续运行的历史起点在创建时捕获，后续继续运行沿用子 Session 已有历史。Provider 的能力契约列明支持的选项，Runtime 在启动前按该契约检查。

### 并发、进程与历史

多个 Agent 和 Session 可以在同一进程内分别运行，各自保存 Inbox、历史与生命周期。进程内 spawn 和 fork 通过这些对象组织任务；进程、容器和操作系统资源由宿主与执行 Provider 管理。

拆分任务先确定职责，再准备材料。例如一个子任务提取功能，另一个核对限制，父 Agent 最后整合。当前轮次刚读到的 README 尚未进入 fork 的已完成历史前缀，父 Agent 要在启动输入中把这份材料传给子任务。

### 分析示例：拆分不只计算工作时间

教学单代理需要 1200 ms。拆成两个子任务，各 700 ms；假设允许重叠且确实同时开始，启动与交代开销 200 ms，汇合检查 250 ms，则简化总时间是 200＋max(700,700)＋250＝1150 ms，只减少 50 ms。

复算记录：[C13 · 并发耗时](../examples/calculation-results.json)。

若串行执行，则相同假设下为 1850 ms。若结果不一致还需额外处理。因此比较不仅要计执行区间，还要计材料、请求量与汇合质量。

### 选择任务起点

![F13B：拆分增加交代、执行和汇合三段](../figures/F13B.png)

图 13B 用三栏列出拆分任务的工作：父任务交代目标和材料，子任务运行并返回结果，父任务检查与汇合。时间分析应把这三段一起计入。

父 Agent 收集子结果，检查材料来源和相互矛盾，再形成最终总结。取消子任务时，Runtime 调用对应 Provider 的取消与清理路径，运行句柄返回收尾结果。

### 常见误解

“fork 复制了父 Agent 当前全部内容”：本 Provider 只取最近已完成轮次前缀。

“多个 Subagent 就是多个独立进程”：当前讨论的是进程内实现。

“一个生成、一个评审就一定更准”：评审输入、标准和责任仍需设计与实验验证。

### E13A · 进程内 fork 取到哪里

阅读任务：这是 completedTurnPrefix 完整辅助函数。parent 是父 Agent；重点观察事件边界，而不是猜测 fork 与操作系统进程复制相同。

代码类型：**真实源码摘录**。证据编号 [E13A](../evidence-index.md#e13a)；下表的数字是原文件行号。

```ts
function completedTurnPrefix(parent: Agent): SessionEvent[] {
  // oxlint-disable-next-line typescript/no-deprecated -- Existing Session history read; migration deferred.
  const events = parent.session.snapshotEvents()
  const lastEnd = events.findLast(e => e.type === 'turn/end')
  if (lastEnd === undefined) return []
  // seq === array index (the append contract), so slice up to and including it.
  return events.slice(0, lastEnd.seq + 1)
}
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 48 | function 和参数类型 | 从父 Agent 计算可继承的完成轮次前缀。 |
| 49 | 原 lint 注释 | 说明本处暂时采用现有历史读取接口，不是运行逻辑。 |
| 50 | const 保存快照 | 获取当前父 Session 的事件数组。 |
| 51 | findLast 和箭头判断 | 从末尾找最后一个 turn/end 事件。 |
| 52 | if 与提前 return | 没有完成轮次时不继承历史。 |
| 53 | 原注释解释序号关系 | 追加契约保证 seq 与数组下标对应，所以可用来切片。 |
| 54 | slice 的不包含结束位置规则 | 加 1 使边界事件也被保留，返回整个前缀而非摘要。 |
| 55 | 结束辅助函数 | Provider 随后用这份起点创建子 Session。 |


执行推演：事件中最后的 turn/end 为 20 号时，返回开头到 20 号的全部事件；21 号以后属于当前未完成部分，不在种子里。没有 turn/end 时返回空数组。

## 13.5 理解检查与讲解问答

### 问题 1 · 当前轮次刚获取的资料会自动进入进程内 fork 吗？

讲解：fork 使用最近一个已完成轮次之前的历史前缀，正在进行的轮次留在父 Session。若子任务需要当前轮次的读取结果，应在启动材料中明确传入。

### 问题 2 · fork 是否自动生成很短的摘要？

讲解：不会。前缀保留边界以前的事件，摘要属于另外的机制。

### 问题 3 · 团队邮箱能否解决同时修改同一文件的冲突？

讲解：邮箱协调消息的投递和确认。共享文件由文件服务修改，多个成员写同一路径时，应拆分修改范围、安排执行顺序，并在整合时检查冲突。
