# 第 13 章｜Subagent：任务拆分与历史继承

本章学习任务：比较 fresh 与 fork 的历史起点，分析子任务创建、结果汇合及共享工作区协调。

## 13.1 基本概念

Subagent 是父 Agent 为子任务创建的独立运行单元。父 Agent 在启动时提供目标、上下文材料、能力配置和交付要求；子 Agent 执行后返回结果，由父 Agent 核查并整合。

fresh 与 fork 的区别在于初始历史：fresh 不继承父任务历史，fork 继承其中一个前缀。进程内 Provider 的 spawn 创建空历史子 Session，fork 则复制父 Session 从起点到最近一次 turn/end 为止的事件，并包含这条结束记录。当前未完成轮次中新增的必要材料，需要通过启动输入传给子任务。

Subagent Runtime 先选择 Provider，检查选项与最大深度，再请求 Provider 创建运行。进程内 Provider 为子任务建立独立的 Agent 和 Session，父子任务仍在同一宿主进程中执行。fork 决定历史继承的方式，子任务的循环驱动与生命周期由自己的运行对象管理。

实验性团队功能在子任务之上增加成员、任务板和消息投递记录。邮箱管理投递、确认与恢复，共享工作区的文件修改则需要另行协调。两个成员同时修改同一文件时，应划分修改范围、安排执行顺序，或检查并解决冲突；邮箱机制本身不提供文件锁。

## 13.2 沿一个任务看完整流程

假设父 Agent 在当前轮次读取 README 后，立即创建 fork Subagent。进程内 Provider 会寻找最近一次 turn/end，只继承截至该事件的完整前缀。刚取得的 README 位于这条边界之后，子任务无法从种子中读到它。因此，父 Agent 应在启动输入中显式传入本次任务需要的文本。

| 起点 | 初始历史 | 父 Agent 应补什么 |
| --- | --- | --- |
| spawn | 不继承父事件历史 | 目标、材料和限制 |
| 本章进程内 fork | 最近完成轮次以前的事件前缀 | 当前轮次新增的必要材料 |
| 其他 Provider | 由其能力契约决定 | 依支持项建立交接 |

启动前，Runtime 检查 Provider、能力、最大深度和结构化输出选项，通过后由 Provider 创建运行句柄。父 Agent 收到结果，再对照原任务检查准确性、遗漏和冲突，完成汇合。团队消息记录排队、投递与确认过程，恢复时继续处理未确认项；共享文件修改通过任务分工和冲突协调处理。

## 13.3 关键机制与设计取舍

### 两种起点

![F13A：新 Session 与已完成历史前缀的对照](../figures/F13A.png)

图 13A 对照两种初始历史：进程内 spawn 创建新子 Session，并通过启动输入提供材料；进程内 fork 复制父 Session 截至最近 turn/end 的前缀。没有 turn/end 时，fork 也以空种子开始。

### 从父工具调用到子运行

父 Agent 调用 Subagent 工具后，执行入口先取得实际调用的 Agent，再处理模型选项与 Provider 请求。Runtime 负责启动、Provider 查找和契约检查。一次性任务使用 `start`；后台任务选择支持持续运行的 Provider 后，可用 `startContinuable` 接纳输入并返回子 Session 身份。最大深度限制子任务继续创建子任务的层数。检查通过后，Runtime 建立运行描述并交给 Provider：fresh 与 fork 决定初始材料，start 与 startContinuable 决定运行和交付方式。

进程内 spawn 以空种子进入 `startInProcessRun`；fork 先从父 Session 截取到最近 `turn/end` 为止的前缀。两种 Provider 复用同一创建流程，为子任务建立新的 Agent 和 Session。子 Agent 接收自己的输入，运行自己的循环。没有已完成轮次时，fork 的种子为空。运行句柄提供结果、取消传递和资源释放。

持续运行的历史起点只在创建时捕获一次，后续继续执行沿用子 Session 已有历史。Provider 的能力契约列出支持的选项，Runtime 在启动前据此检查。

### 并发、进程与历史

同一进程可以运行多个 Agent 和 Session，各自维护 Inbox、历史和生命周期。进程内 spawn 与 fork 通过这些对象组织并发任务；进程、容器及操作系统资源由宿主和执行 Provider 管理。

任务拆分首先要确定各子任务的职责与输入。例如，一个子任务提取功能，另一个核对限制，父 Agent 负责整合。当前轮次读取的 README 尚未进入 fork 的完成轮次前缀，需要随启动输入传入，使两个子任务使用相同的必要材料。

### 分析示例：执行、启动与汇合的总耗时

假设单 Agent 需要 1200 ms。将任务拆成两个各需 700 ms 的子任务，在允许并发且同时开始的条件下，再计入 200 ms 的启动与传参、250 ms 的汇合检查，总耗时为 200＋max(700,700)＋250＝1150 ms，比单 Agent 少 50 ms。

复算记录：[C13 · 并发耗时](../examples/calculation-results.json)。

相同假设下，串行执行需要 1850 ms；结果不一致还会增加处理时间。比较方案时，应同时计入执行区间、材料传递、请求量与汇合质量。

### 选择任务起点

![F13B：拆分增加交代、执行和汇合三段](../figures/F13B.png)

图 13B 将任务拆分分为三个阶段：父任务提供目标与材料，子任务执行并返回结果，父任务核查与汇合。耗时分析应覆盖这三个阶段。

父 Agent 汇集子结果，核查材料来源与相互矛盾，再形成最终总结。取消子任务时，由对应 Provider 执行取消与清理路径，运行句柄交回收尾结果。

### 常见误解

“fork 会复制父 Agent 当前的所有内容”：本章的进程内 Provider 仅继承截至最近一次 turn/end 的已完成历史前缀。

“多个 Subagent 就是多个独立进程”：进程内 Provider 为子任务建立独立运行对象，父子任务共享宿主进程。

“一个生成、一个评审就一定更准”：评审需要明确输入、标准和责任，并通过实验检验效果。

## 13.4 源码研读

<a id="e13a"></a>

### E13A · 进程内 fork 取到哪里

阅读任务：`completedTurnPrefix` 从 parent 所指父 Agent 的日志中计算可继承前缀，以最近 turn/end 为边界，保留截至该事件的 Session 历史。Provider 随后根据这份种子创建子 Agent。

#### 实现详解

进程内 fork 先为子 Agent 选择初始历史，`completedTurnPrefix` 负责提取这份种子。函数取得父 Session 当前事件数组的快照，再从末尾寻找最近的 turn/end。该结束事件标明最近一个已完成轮次的边界，让子任务从包含完整轮次结算的历史开始。

找到边界后，函数从数组第 0 项截取到该事件，并把结束事件一并保留。Session 的追加契约保证 seq 等于数组下标，而 slice 的结束位置不包含在返回范围内，因此使用 `lastEnd.seq + 1`。例如最近 turn/end 的 seq 为 20，返回位置 0—20，共 21 项；位置 21 及以后不进入这份种子。

没有 turn/end 时，函数返回空数组，子任务从空历史种子开始。存在已完成轮次时，种子包含从起点到边界的所有事件，包括消息、工具调用、结果与边界记录。位置切片保留这段前缀中的历史表示及其关联，后续创建流程据此建立新的子 Session。

假设父 Agent 在尚未结束的轮次中读取 README，随后创建 fork 子任务。读取结果位于最近 turn/end 之后，因而不在种子内；子任务需要这些资料时，父任务必须通过启动输入传入。Provider 随后在同一宿主进程中建立子任务的 Agent、Session 与循环。历史前缀决定继承内容，启动输入补充当前材料，独立运行对象负责子任务的执行与生命周期。

代码类型：**真实源码摘录**。证据编号 [E13A](../evidence-index.md#e13a)；下表的数字是原文件行号。

```ts
function completedTurnPrefix(parent: Agent): SessionEvent[] {
  // oxlint-disable-next-line typescript/no-deprecated -- Existing Session history read; migration deferred.
  const events = parent.session.snapshotEvents()
  const lastEnd = events.findLast(e => e.type === 'turn/end')
  if (lastEnd === undefined) return []
  // seq === array index (the append contract), so slice up to and including it.
  return events.slice(0, lastEnd.seq + 1)
}
```

| 49 | 原 lint 注释 | 说明当前历史读取接口的弃用警告处理及后续迁移安排。 |
| 50 | const 保存快照 | 获取当前父 Session 的事件数组。 |
| 51 | findLast 和箭头判断 | 从末尾找最后一个 turn/end 事件。 |
| 52 | if 与提前 return | 没有完成轮次时不继承历史。 |
| 53 | 原注释解释序号关系 | 追加契约保证 seq 与数组下标对应，所以可用来切片。 |
| 54 | slice 的不包含结束位置规则 | 加 1 使边界事件也被保留，返回整个前缀而非摘要。 |

执行推演：最近 turn/end 的序号为 20 时，函数返回第 0—20 项；第 21 项及以后的事件不进入种子，其中包括当前未完成轮次的新增记录。没有 turn/end 时返回空数组。

## 13.5 理解检查与讲解问答

### 问题 1 · 当前轮次刚获取的资料会自动进入进程内 fork 吗？

讲解：本章进程内 fork 继承截至最近 turn/end 的历史前缀，当前未完成轮次的新增记录仍留在父 Session。子任务需要本轮读取结果时，由父任务通过启动材料显式传入。

### 问题 2 · fork 是否自动生成很短的摘要？

讲解：fork 按原样保留边界以内的事件前缀，不生成短摘要。摘要由独立的压缩机制处理。

### 问题 3 · 团队邮箱能否解决同时修改同一文件的冲突？

讲解：邮箱协调消息投递与确认，共享文件通过文件服务修改。多个成员写同一路径时，需要划分修改范围、安排执行顺序，并在整合时检查冲突。
