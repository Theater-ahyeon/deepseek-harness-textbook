# 第 19 章｜Cordis 与 Spatiotemporal Composability

本章从资源登记、依赖变化和插件卸载三个问题出发，讲解 Cordis 的 Spatiotemporal Composability。先用定时器和工具注册理解机制，再把它们与论文的定义和生命周期规则对应起来。

论文是 *A Programming Paradigm for Spatiotemporal Composability*，作者 Yifan Shi、Wei Zhang、Tianyi Cui，本文采用 arXiv:2608.25512 的 v1（2026-08-26）。实现采用固定项目快照里的 `@deepseek-ai/cordis` 4.0.4。下面先解释论文模型，再说明 Cordis 4.0.4 的实现方式。

## 19.1 组件替换与资源释放

假设文件工具插件装入时做两件事：注册 read，监听文件观察事件。模型于是能够使用工具，其他组件也能收到观察通知。后来配置改变，要换成另一份实现。如果只把插件名字从列表删除，旧监听器可能继续接收通知，旧工具也可能留在注册表；重新装入又登记一次，便会出现重复响应或旧对象继续被访问。

组件生命周期同时管理能力启用与贡献撤销。effect 是操作对状态产生的改变，例如注册事件监听器；disposer 是释放该贡献的函数，例如移除本次注册的监听器；inverse 描述对应的逆操作，用于恢复操作前的状态。

read 插件还依赖文件服务。提供者撤销服务后，消费者要重新检查依赖，退出当前实例或等待新的服务。服务名称标识可解析的能力，依赖声明列出装入前需要可用的入口。

论文把这两个问题放在一起：时间方向上，组件的贡献怎样撤回；空间方向上，组件怎样在当前 Context 中获取依赖并随环境变化重新装配。这就是 Spatiotemporal Composability：时间方向上的可撤回与空间方向上的依赖组合。空间维度指服务的组织和解析关系。

## 19.2 可逆操作与恢复见证

设状态 S 表示工具集合，组件 A 装入前为 `{read}`，操作 f 将其变为 `{read, search}`。f 同时提供逆操作 g，g 只移除 A 注册的 search，于是 `g(f(S)) = S`。这个关系要求逆操作恢复本次操作对应的输入状态。

这里的“状态”是数学模型描述的数据，“函数”是从旧状态得到新状态的规则。论文的 witnessed effect function 不仅返回新状态，还返回一项逆操作，并要求逆操作确实恢复其对应输入；Definition 8 给出这项见证条件。witnessed 表示函数附带满足该等式的数学见证。实现中的 ctx.effect 保存 disposer，组件作者负责让它满足恢复条件。

disposer（释放函数）通过闭包保留资源身份。闭包由函数及其引用的外层变量组成，例如清理函数捕获本次创建的 timer 句柄，卸载时据此停止对应定时器。资源创建时登记释放函数，使资源获取与撤销始终保持明确对应。

释放动作由组件作者编写。以定时器为例，disposer 要记住创建时得到的 timer 句柄，并调用 clearInterval 停止它；只打印“已清理”不会停止定时器。论文 §5.1.1 将逆操作的正确性交给组件作者，Cordis 运行时负责登记和调用。文件写入、邮件发送等外部动作，则要由作者按对应服务的实际能力设计后续处理。

## 19.3 逆操作的组合与释放顺序

若组件先申请资源 A，再基于 A 创建资源 B，释放时应先清理 B，再释放 A，以保留 B 清理所需的依赖。LIFO（Last-In-First-Out，后进先出）描述这种顺序：后创建的依赖资源先撤销。

论文把每一步返回的逆操作接到已有恢复动作之前，形成反向组合。effect iterator 让装入逐步推进；迭代器每次给出下一项，并说明是否结束。运行时因此可以在步骤之间记录进度、检查目标状态，决定继续装入还是进入撤离。

论文的反向组合、一个 ctx.effect 内的多步恢复、Fiber 上多个 effect 的释放采用不同组织方式。当前 Fiber._unload 用 Promise.all 等待同层释放任务，多个异步 disposer 会重叠运行。有严格依赖的两项清理，应写在同一个 disposer 中依次 await：先撤资源 B，再撤资源 A。

框架捕获并记录单项释放错误，其他释放任务继续推进。排查时，可以从错误记录找到所属实例和释放位置，再检查该项动作停在了哪里。

## 19.4 环境要求：coeffect、服务键与依赖

coeffect 描述组件执行需要从环境获取什么，例如文件服务；effect 描述执行对状态造成什么改变，例如注册工具。服务 key 是用于识别和解析某项能力的名称或标识。提供者发布该键下的能力，消费者声明自己需要它，Context 根据当前范围解析到实际实现。

理解一个组件时，可以依次查看它声明的依赖、提供的服务和装入行为。插件声明描述依赖，服务提供操作登记能力，Fiber 管理这次装入产生的资源。

例如插件 T 需要 tools 和 fs。tools 让它登记工具，fs 让它实现读取。只有依赖条件成立，运行时才推进该实例的装入。fs 的提供者撤去服务时，运行时通知相关消费者重新评价目标状态；它们需要退出当前装配或等待新的满足条件的环境。

响应式依赖使环境变化触发实例的目标状态更新。依赖注入通过统一接口解析服务提供者。实例创建的连接、监听器和后台任务经资源管理接口登记，对应 disposer 随实例卸载被调用。

## 19.5 Fiber 与生命周期：目标变化时怎样收尾

Fiber 是组件的一次运行实例及其生命周期管理对象。每个 Fiber 保存自己的配置、依赖状态和释放动作。相同组件装入多次，可以有不同的 Context、配置、资源记录和状态；讨论清理时要指明是哪一个实例。

论文 §4 用抽象状态和转换规则研究装入、已激活、撤离等过程。论文中的 Reloading 包含推进装入的情形；论文用四类抽象状态表达规则；FiberState 枚举进一步区分运行时状态。实现与官方教程还区分 PENDING、FAILED、DISPOSED 等状态，用于表达依赖未满足、装入失败和实例终结。

装入正在等待连接建立时，配置可能改变。惯性原则要求先完成当前这一步，把结果与 disposer 交给框架，再决定继续装入还是撤回。资源由此及时进入清理记录。若外部操作迟迟不返回，这一步就一直等待；组件要在资源操作中配置超时或取消处理。

依赖撤离时还存在提供者与消费者的顺序问题。消费者的清理可能需要向提供者归还资源。论文的守卫演算通过等待关系限制过早回收，形式化讨论“提供者比它的消费者活得更久”的条件。

当前 Reflect.provide 的释放函数先从公共服务存储撤销入口，通知依赖实例，等待相关 Fiber，再清掉本实例保留的服务入口。这项 disposer 内部按上述顺序等待。Fiber 同层的其他 disposer 仍并发运行；需要消费者先退出才能释放的资源，应与该等待组织在同一受控释放流程中。

| 阶段 | 发生什么 | 需要核对什么 |
| --- | --- | --- |
| 依赖可用 | 消费者可以开始当前装配 | 声明与实际解析是否一致 |
| 提供者撤去入口 | 新解析不能把它当作普通可用服务 | 是否通知了相应消费者 |
| 消费者收尾 | 处理仍属于旧实例的资源 | 清理是否还需提供者 |
| 提供者资源释放 | 撤去自身登记的贡献 | 是否按真实依赖组织等待 |

## 19.6 操作独立性与安全卸载

交换律表示先做 A 再做 B，与先做 B 再做 A，得到同样结果。设 A 登记自己的键 a，B 登记另一个键 b。若两项操作都只改变自己的独立槽位，最终集合可以相同。若两项都修改一个顺序敏感的中间件（请求依次经过的一串处理环节）列表，先后就可能改变请求经过的规则。

Definition 42 要求正向、撤回以及相关变换都满足独立性，并保持对方返回的逆操作与后续迭代。检查两次注册能否交换，只覆盖其中一部分；还要检查卸载 A 时，B 的贡献和后续运行是否保持。

考虑一种有缺陷的释放方式：A 注册前保存整个工具集合，B 随后注册另一项工具，A 卸载时用旧副本替换当前集合。这样会连同 B 的合法贡献一起删除。释放逻辑应识别并移除本实例注册的条目。存在重名、覆盖、排序或共享资源时，还需检查替换与撤销规则是否保持独立性。

这解释了为什么论文讨论服务提供者的责任：它发布的操作采用怎样的表示，直接影响其他组件能否独立撤回。服务提供者在设计注册和撤销规则时，就要处理这些独立性条件。

## 19.7 观测等价与证明条件

观测等价表示按指定的合法观察方式，看不到会影响契约的差别。相同工具集合不要求内存地址、分配顺序或运行时缓存逐字节相同。观察关系由模型规定；网络请求和外部设备写入则有它们自己的可观察状态。

论文 §3.3 通过观察关系界定状态相等的用途，§3.4 再讨论独立性与恢复。证明按这样的顺序展开：先规定状态、操作和观察；写下可逆和依赖条件；再证明满足条件的系统可怎样组合与撤回。

Theorem 73 的推进结果假设依赖先行关系无环、迭代长度有统一有限上界、整个序列涉及的实例名称有限，并且每一步遵守生命周期规则。无环意味着依赖箭头不会从某个组件绕回它自己。在这些条件下，论文给出没有规则层死锁以及有限推进到静止状态（不再有待推进的步骤）的结论。

例如 A 等 B、B 又等 A，构成依赖环，已经不满足 Theorem 73 的无环条件。这个例子说明，依赖图和步骤长度是推进定理本身的组成部分。

## 19.8 服务作用域与模块热重载

ctx.isolate(name, label) 为指定服务名建立新的解析标签，得到派生 Context。默认新标签使该名称在子范围中可以解析到另一项实现；相同标签可以让多个范围共享该服务解析空间。这些 Context 仍处于同一 JavaScript 宿主中，共享进程资源。

图 19B 先看两个 Context，再看右侧服务实现。派生箭头表示建立子 Context，解析箭头表示按服务标签找到实现。Context 乙为指定服务名使用新标签，其他服务继续沿继承关系解析；两个 Context 共用同一个宿主进程。

第 13 章的子 Session 组织历史与任务，第 11 章的执行环境限制资源访问，Context 的作用域组织服务解析。论文 §6.3 为不可信组件提出独立受限进程或容器等执行隔离，与这里的服务标签分工不同。

HMR 是 Hot Module Replacement，即热模块替换。项目的更新机制根据模块关系决定局部替换还是完整重载。当前 boot/hmr 检测到外部依赖变化时会走 fullReload（完整重载）并调用 loader.exit（结束当前进程以完成重载）。局部替换通过 disposer 释放旧贡献，完整重载则由 loader.exit 交给退出路径。

### E19A · 作者提供资源释放逻辑

阅读任务：这是仓库官方 Cordis 教程中 heartbeat 的 effect 片段。观察定时器句柄怎样进入释放函数，以及 Cordis 怎样获得这项动作。

#### 实现详解

官方教程用 heartbeat 插件说明资源获取与释放怎样成对登记。插件装入时调用 ctx.effect，并传入一个获取资源的函数。这个函数创建定时器，每 200 毫秒输出一次 tick，将得到的 timer 句柄保存在当前调用的局部变量中。句柄标识本次创建的定时器，后面的清理函数依靠它定位资源。

获取函数随后返回另一项函数，作为 disposer 交给 Cordis。这个返回动作只交付释放逻辑，定时器继续运行；Cordis 将 disposer 记入所属 Fiber 的资源集合。释放函数通过闭包保留 timer，所以获取函数结束后，后续清理仍能访问正确句柄。

插件卸载时，框架调用已登记的 disposer。它先用 clearInterval(timer) 停止本次定时器，再输出 heartbeat cleaned up，供教程观察清理确已发生。同一插件的其他实例各有自己的 timer 和闭包，卸载一份实例时沿对应登记清理这份资源。热重载使用同样的生命周期路径撤销旧实例贡献，再推进新实例。

这个例子把责任分成两个相连的部分：组件作者提供正确的获取与释放操作，Cordis 保存对应关系并在实例退出时调用。论文中的恢复条件要求逆操作恢复相应输入状态；这里的具体恢复由 clearInterval 实现。注册 read 或事件监听时，也需要保留本次登记的身份，使释放只撤销这份贡献。资源创建、句柄捕获、disposer 登记与卸载调用共同构成可追踪的生命周期。

代码类型：**仓库官方教程示例**。证据编号 [E19A](../evidence-index.md#e19a)；下表的数字是原文件行号。

```ts
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => {
      clearInterval(timer)
      console.log('heartbeat cleaned up')
    }
  })
```

| --- | --- | --- |
| 20 | effect 接收函数并开始资源获取 | 把本次定时器生命周期登记给所属插件。 |
| 21 | const、setInterval 与回调 | 保存定时器句柄，每 200 毫秒调用日志回调。 |
| 22 | return 返回另一个函数 | 把释放动作作为值交给 Cordis，以后卸载时才调用。 |
| 23 | clearInterval 调用 | 作者使用已捕获的 timer 句柄停止该计时器。 |
| 24 | 日志调用 | 在实际清理时给出教程观察输出。 |
| 25 | 结束返回的释放函数 | 本次逆操作定义完成。 |
| 26 | 结束资源获取函数与 effect 调用 | 框架获得并登记释放函数。 |

### E19B · 服务名称作用域隔离

阅读任务：Context.isolate 为 name 指定的服务名称设置解析标签。可选 label 用于让多个 Context 共享同一服务作用域，返回值是携带新解析表的派生 Context。

#### 实现详解

Context.isolate 为指定服务名建立派生的解析范围。Context 内的隔离表保存“服务名到 Symbol 标签”的关系，服务读写按标签选择实现。方法接收 name，指定哪项服务使用新的范围；可选 label 决定是否复用已有标签。返回值是派生 Context，调用方随后可在它下面挂载插件或提供服务。

方法先建立继承当前隔离表的新表，再只为 name 设置标签。查找其他服务时，新表仍沿继承关系取得父范围的标签，所以局部改动不影响其他名称。设置新表也不改写原 Context 的隔离表，父范围继续使用原来的服务解析关系。

缺省 label 时，每次 Symbol(name) 都生成新的唯一身份，即使两次的 name 相同，标签仍不同。显式传入同一个 Symbol 时，多个派生 Context 使用同一标签，可以共享这项服务的解析空间。例如为 fs 分别创建两项新标签，可以在两个子范围提供不同文件服务；复用同一 label 则把它们接到同一个 fs 解析范围。

extend 将新表放进派生 Context，服务名称的读取和提供由后续操作沿这张表解析。这个方法自身只建立解析标签，没有创建文件 Provider 或启动子进程。各 Context 仍位于同一宿主中；profile 与插件装配决定每个标签下实际提供的实现，文件与进程服务负责资源访问。把服务名、解析标签和实际实现分开，就能理解插件树为什么可以在局部范围替换同名能力。

代码类型：**真实源码摘录**。证据编号 [E19B](../evidence-index.md#e19b)；下表的数字是原文件行号。

```ts
  isolate(name: string, label?: symbol) {
    const shadow = Object.create(this[symbols.isolate])
    shadow[name] = label ?? Symbol(name)
    return this.extend({ [symbols.isolate]: shadow })
  }
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 121 | 方法、可选参数与 symbol 类型 | 指定哪个服务名称使用独立解析标签。 |
| 122 | Object.create | 创建继承父服务作用域表的新表，保留其他名称的解析关系。 |
| 123 | 下标赋值与空值合并 | 为指定名称使用已有标签，或创建唯一 Symbol 值作为新标签。 |
| 124 | return、extend 与计算属性 | 返回带新作用域表的派生 Context。 |
| 125 | 结束方法 | 隔离针对服务解析；物理执行边界需要另外的机制。 |


执行推演：不提供 label 时为指定服务建立新 Symbol 标签，其他继承关系仍保留；传相同 label 可加入同一服务作用域。没有创建进程、容器或文件权限边界。

### E19C · 同层资源释放并发等待

阅读任务：节选位于 Fiber._unload 的资源释放阶段。_disposables 保存当前 Fiber 的释放函数，Promise.all 等待各项异步清理，每项有独立的异常记录。后续流程清理 store 并更新实例状态。

#### 实现详解

Fiber._unload 负责释放这个插件实例登记的资源，再清理实例存储并推进生命周期状态。本段先从 _disposables 取出整组释放动作，同时清空登记集合，让这次卸载处理明确的一组资源。每个释放动作都由作者或注册 API 提供，框架通过 runDisposable 实际调用它。

代码把每一项映射成异步任务，再用 Promise.all 等待整组收尾。各任务之间能够重叠推进，结束顺序由实际等待决定。例如移除监听器很快完成，关闭网络连接需要等待，前者可以先结束；整个卸载仍等待连接清理返回。若某项释放一直不结束，统一等待也无法完成，因此资源操作内部要具备相应的超时或取消处理。

每项任务有独立的 try/catch，并通过 composeError 组织诊断信息。调用释放动作之前先经过一个异步等待点，再记录本次错误位置；失败时结合外层调用信息写入日志。某项释放报错后，它的处理路径结束，其他释放任务继续收尾。这里使用的 Promise.all 汇总的是这些带独立错误处理的任务。

所有任务结束后，后续代码清空 store，再按目标状态决定保持未激活或重新装入。具有严格依赖的清理应在同一个 disposer 中按顺序等待：例如先停止仍会访问连接的后台任务，再关闭连接。同层两个 disposer 分别启动时，不会因为登记顺序就保证前一项完全结束。实例资源集合、独立错误记录和整组等待共同说明一次卸载怎样从开始走到状态更新。

代码类型：**真实源码摘录**。证据编号 [E19C](../evidence-index.md#e19c)；下表的数字是原文件行号。

```ts
  private async _unload() {
    await Promise.all(this._disposables.clear().map(async (dispose) => {
      try {
        await composeError(async (info) => {
          await Promise.resolve()
          info.error = new Error()
          await runDisposable(dispose)
        }, this._runner.getOuterStack)
      } catch (reason) {
        this.ctx.logger.error(reason)
      }
    }))
```

## 19.10 理解检查与讲解问答

**问题 1：框架能够调用释放函数，为什么不等于保证释放正确？**

讲解：登记把 disposer 与当前 Fiber 联系起来，卸载时框架调用它。以定时器为例，作者必须在 disposer 内调用 clearInterval，并传入本次创建的句柄。论文的见证条件要求恢复原状态；运行时的登记与调用实现资源管理，具体恢复动作由作者完成。

**问题 2：同层两个异步释放函数，能否只靠登记顺序保证第一个完全结束后第二个才开始？**

讲解：_unload 将同层释放函数映射成异步任务，再用 Promise.all 汇总等待。后启动的任务可以先结束。有先后依赖时，在同一个 disposer 中依次 await。

**问题 3：把插件放入 ctx.isolate 后，能否运行不可信代码而无须其他隔离？**

讲解：ctx.isolate 调整服务名称的解析标签，派生 Context 与原 Context 仍共享宿主进程。不可信组件的运行需要独立设计执行隔离、桥接接口与资源访问限制。

**追问：怎样向别人准确讲述 Cordis 的价值？**

Cordis 把插件组织成声明依赖、登记资源、响应环境变化并释放贡献的运行实例。Context 解析服务，Fiber 管理实例状态，effect 保存资源与 disposer 的对应关系。论文解释这些机制需要满足的可逆性和独立性条件，源码给出装入、撤离与依赖通知的具体执行方式。
