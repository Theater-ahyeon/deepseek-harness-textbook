# 第 16 章｜测试、模型回放与行为验证

本章学习任务：理解按位置消费的模型回放，区分调用轨迹检查、请求断言与真实任务评价。

## 16.1 基本概念

测试将预期行为表达为可检查的条件。断言规定必须满足的关系，例如失败模型尝试中的工具提议不得进入执行阶段。替身替代选定依赖，回放则用预录制响应替代模型生成，所选的真实循环和工具链继续处理这些响应。

本项目的 LLM 回放按 Session 绑定响应脚本，再按调用位置选择条目。新 Session 绑定下一份脚本，每次模型调用消费下一项响应。响应选择的依据是调用序号，请求字段的正确性由测试中的独立断言检查。

脚本在本章指一个录制 Session 的响应清单，每个条目对应一次模型调用。消费检查发现脚本没有绑定或条目没有用完；请求次数超出清单时也会报错。消费检查验证调用次数与脚本绑定。请求内容、工具动作和最终产物分别用对应断言检查。

固定模型输出减少一种变化来源，不固定操作系统文件、时间、并发调度和远端工具的全部行为。回放时使用哪些文件和工具，由测试 profile 与替身配置决定。

## 16.2 沿一个任务看完整流程

设录制脚本有两个响应：第一项提出 read，第二项生成总结。当前 Session 第一次请求获取第 0 项，第二次获取第 1 项，游标变成 2。只发一次请求时有条目未消费；第三次请求时脚本耗尽。消费检查帮助发现轨迹变化。

位置回放按调用序号返回响应，即使请求上下文存在错误，第一次调用仍会消费第 0 项。验证材料组装时，需要同时断言实际请求中的消息、工具定义和参数。

| 想验证的命题 | 合适观察 |
| --- | --- |
| 错误尝试没有执行工具 | 固定失败响应，并检查调用与执行 |
| 请求包含项目指令 | 检查实际组装的请求内容 |
| 新提示词使模型更少遗漏 | 使用新模型输出和统一任务评价 |
| 客户端没有重复气泡 | 检查客户端提交与历史合并状态 |

修改提示词以后，用真实模型重新生成结果，再按同一任务标准比较；回放用于检查固定响应下的程序行为。

## 16.3 关键机制与设计取舍

### 固定一个依赖，继续执行其他部分

![F16A：固定模型响应，运行真实循环并检查行为](../figures/F16A.png)

图 16A 从录制日志派生响应脚本，把脚本接到 LLM 边界，再运行循环和工具。测试检查实际行为，同时检查响应清单是否完整消费。

### 证据层怎样选择

单元测试检查局部函数，例如读取窗口；快照测试比较选定输出；回放让固定模型响应驱动真实循环；API 端到端测试连接实际服务，走完整请求链；性能实验记录规定条件下的时间和用量。选择检查方式时，先明确要观察哪个行为。

`deriveReplayScript` 从事件中恢复响应条目。遇到缺失终结的录制，需要在 replay.override.json 中明确提供覆盖响应，让回放使用明确指定的响应。整个 ReplayEntry 数组替换完整脚本；{ patches } 则在可成功派生的脚本上修改指定位置。`installLlmReplay` 加载脚本，按 Session 绑定消费位置；接入有两种方式：配置 providers 时注册 ReplayAdapter，在模型 Provider 层面直接顶替真实模型；否则在 `llm/stream` 边界拦截，请求即将发出时截获并改由脚本应答。

回放的消费检查确认每份脚本都绑定到实际 Session，并且条目全部用完。少一次请求会留下未消费条目，多一次请求会使脚本耗尽。用固定响应定位工程故障时，这些检查可以发现调用轨迹变化。

### 断言、替身与覆盖范围

断言（assertion）写出要检查的条件，替身（mock）替代某项依赖。检查数组长度为 2，只验证数量；检查元素中的工具名、参数和结果，才验证这些字段。回放固定响应序列，断言决定测试实际检查什么。

一个故障测试需要给出触发条件与观察点。例如，构造失败 finish，检查驱动是否记录 attempt、是否执行工具。评价模型总结质量则使用任务集和新生成的产物，按相同要求检查遗漏与错误。

### 分析示例：四个命题选四种检查

“行窗口只返回选定范围”可以用窗口单元测试；“失败尝试没有执行工具”可以用固定失败响应驱动真实循环；“实际服务能够完成协议请求”需要 API 测试；“修改提示词后更少遗漏实验性声明”需要同条件的业务任务评价。

若把最后一项改成固定输出回放，输出内容已经由脚本决定，无法评价提示词对真实模型的影响。回放便于定位工程回归（回归：原本正常的行为在修改后被破坏），真实模型评价则使用新输出。

再看一份含 3 次模型调用的录制。第 2 次缺少 finish 时，`deriveReplayScript` 抛出 “ended without a finish chunk”，要求提供 replay.override.json 覆盖文件。若改用完整的 3 项响应脚本，而实际只发起 2 次请求，`assertConsumed` 报告只消费了 2/3 次。另一项检查针对录制 Session：某份脚本从未绑定实际 Session 时，报告 recorded script(s) never bound。前者检查条目消费，后者检查 Session 绑定。

### README 故障怎样复现

![F16B：不同检查的对象与盲区](../figures/F16B.png)

图 16B 比较三类检查：局部函数与固定响应回放、真实服务接口、业务任务评价。前两类检查程序行为和服务交互，业务评价比较新生成的产物。

“总结遗漏功能限制”需要通过任务材料和模型产物定位，再用新生成的结果比较修改效果。固定回放检查工程路径，真实模型输出检查提示与上下文对产物的影响；两类验证分别对应明确的待测行为。

### 常见误解

“测试通过说明所有场景正常”：测试只覆盖给定条件与断言。

“回放通过说明新模型更强”：固定输出没有检验新模型行为。

“读到测试就等于测试通过”：阅读测试说明预期行为，实际执行结果记录该环境下的通过与失败。

### E16A · 消费按位置推进

阅读任务：本段在 replay 已依据 Session 找到或建立绑定状态之后。state 保存该 Session 的脚本数组和游标；重点看这次选择响应的依据。后续生成器（可逐个产出值并暂停的函数，配合 yield，见附录）负责脚本耗尽等错误。

#### 实现详解

模型回放为实际运行的每个 Session 绑定一份响应脚本，再按该 Session 的调用位置消费条目。进入这段代码前，replay 已查找绑定状态；首次出现的 Session 领取下一份录制脚本，后续调用沿用自己的 entries 和 cursor。多个 Session 因而分别推进各自的响应序列。

本次调用先保留 boundState，并捕获已绑定脚本数与脚本总数，供后面的错误消息说明录制范围。随后取 cursor 的旧值作为 index，再把 cursor 增加 1，用 index 读取 entries。cursor=0 时选择第 0 项，下一次选择第 1 项。位置在返回生成器之前已经推进，后面的响应消费沿本次选中的 entry 继续。

entry 允许为空，因为实际请求次数可能超过录制条目数。返回的异步生成器检查未录制 Session 和脚本耗尽情况，并给出要求重新录制的错误；合法条目经过必要的标识与消息相关处理，再逐项产出响应。选择哪一项的核心依据仍是调用位置，请求中的完整上下文是否符合预期要由测试断言检查。

例如一份脚本录制“先提出 read，再生成总结”两项响应，实际两次模型调用依次取得这两项；只调用一次时，assertConsumed 发现还有条目未消费；第三次调用时，生成器报告脚本耗尽。即使首次请求漏了项目规则，位置选择仍能取得第 0 项，因此验证提示组装时，还要检查实际 messages、工具定义和参数。响应回放与请求断言合作，分别检查轨迹和输入内容。

代码类型：**真实源码摘录**。证据编号 [E16A](../evidence-index.md#e16a)；下表的数字是原文件行号。

```ts
    const boundState = state
    const seenSessions = nextScript
    const totalScripts = scripts.length
    const index = boundState.cursor++
    const entry: ReplayEntry | undefined = boundState.entries[index]
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 1064 | const 保存同一状态对象 | 后面的生成器使用本次已经绑定的 Session 状态。 |
| 1065 | const 保存数量 | 捕获目前已绑定的脚本数量，用于错误说明。 |
| 1066 | 读取数组 length | 保存录制脚本总数，便于报告未录制 Session。 |
| 1067 | 后缀自增 | 先取旧游标作为 index，再把本 Session 游标增加 1。 |
| 1068 | 方括号按下标取值，联合类型允许 undefined | 选择当前位置响应；越界由后续生成器报错。 |


执行推演：cursor 为 0 时本次取 entries[0]，随后 cursor 变为 1；下次取 entries[1]。这些行没有按请求内容（Payload）查找等价条目。

### E16B · 有路由时与无路由时的接入

阅读任务：本段在回放脚本已经加载后安装模型替身。providers 是回放配置的 Provider 目录，dispose 是以后移除替身的释放函数。

#### 实现详解

installLlmReplay 载入脚本并建立 replay 函数后，需要把替身接到应用的模型边界。本段按照 providers 配置选择接入位置，缺省时采用空数组。两种安装方式最终都把模型请求交给同一 replay 函数，响应选择继续遵循 Session 绑定与游标推进规则。

providers 非空时，代码提取各项 id，再注册 ReplayAdapter。这个适配器提供测试配置中的 Provider 信息，并在对应路由获取流时调用 replay，因而可让正常模型路由和调用准备继续参与测试。注册只覆盖给出的 Provider 身份，其他路由仍由其自身登记处理。

没有配置 providers 时，代码在 llm/stream 上登记监听器。请求到达这个流边界时，监听器直接返回 replay(options)，不继续调用传入的 _next，因此由脚本提供模型响应。注册监听器时只是保存回调，实际模型调用到来时才执行它。dispose 保存相应安装方式返回的释放函数，测试结束后可撤销本次替身登记。

以 README 回放测试为例，模型边界返回预录制的 read 提议，真实 Agent 循环仍解析调用、经过工具准入、访问测试配置指定的文件服务，再取得脚本中的总结响应。测试既可以按 Provider 路由安装适配器，也可以在流入口接管响应；文件、工具和 Session 的实现由测试装配另行选择。固定模型输出使程序轨迹易于复现，断言继续检查实际执行与产物。

代码类型：**真实源码摘录**。证据编号 [E16B](../evidence-index.md#e16b)；下表的数字是原文件行号。

```ts
  const providers = config.providers ?? []
  const dispose = providers.length > 0
    ? ctx.llm.registerAdapter(providers.map(provider => provider.id), new ReplayAdapter(providers, replay))
    : ctx.on('llm/stream', (options: GenerateOptions, _next) => replay(options))
```

| 原文件行号 | 写法 | 在这段流程中的作用 |
| --- | --- | --- |
| 1101 | 空值合并与数组字面量 | 缺省目录采用空数组。 |
| 1102 | const 与长度判断 | 依据是否指定 Provider 目录选择安装方式。 |
| 1103 | map、箭头函数和适配器构造 | 提取 Provider 身份并注册对应回放适配器。 |
| 1104 | on 与回调 | 另一分支在流接口拦截，把请求交给同一 replay 函数。 |


执行推演：providers 非空时登记路由适配器；为空时登记 llm/stream 拦截回调。对应路由的模型调用由 replay 返回；工具和文件服务继续采用测试配置中的实现。

## 16.5 理解检查与讲解问答

### 问题 1 · 两次回放调用都消费完了，是否证明请求材料正确？

讲解：位置消费检查第几次请求使用了第几项响应。要检查材料组装，还要断言实际请求中的消息、工具名和参数；两项检查分别覆盖调用轨迹与请求内容。

### 问题 2 · 固定回答以后能评价新提示词改善了多少吗？

讲解：不能。回答已由脚本决定，评价提示词影响需要新的模型输出。

### 问题 3 · 回放是否自动成为纯内存、无外部动作的测试？

讲解：回放替换模型响应。循环、工具和 Session 继续运行；若测试配置使用真实文件 Provider，工具仍会访问测试工作区。
