第 1 章｜DeepSeek Harness 的架构与任务流程

本章学习任务：理解任务接纳、模型调用、工具执行与 Session 记录的分工，区分各阶段的输入和结果。

01.1 基本概念

程序由可执行的指令组成，数据是指令处理的信息，例如任务文本或文件内容。大语言模型（Large Language Model，LLM）根据输入生成文本或工具调用建议。模型服务负责生成，文件服务负责访问文件；读取建议经过工具链执行后，返回的文本才能用于后续回答。

Agent 是围绕任务反复构造上下文、调用模型并使用工具的运行单元。Harness 提供支撑这一过程的运行机制，DeepSeek Harness 是本书分析的具体实现。Tool 是程序实现的操作，例如读取文本的 read。工具定义向模型公开名称、用途和参数说明；调用参数指定本次操作的目标，工具结果返回执行所得的信息，例如文件第 1—20 行的文本。

Session 维护持续交互的身份与事件日志。日志按发生顺序记录消息、轮次边界和工具调用等事件。消息承载对话内容，过程事件描述任务的执行状态；后续模型请求使用从日志派生的消息历史。Inbox 保存已接纳、尚待领取的输入，分别维护下一轮和下一步的消息队列，由驱动在对应边界领取。

请求指定调用方希望服务执行的操作，例如向某个 Session 提交文本。请求标识用于识别重复提交，避免同一输入重复排队。网页等客户端负责发起请求和接收结果，Host 提供项目的服务接口。提交入口返回接纳回执后，后台任务继续运行。

附件是随消息提交的文件、图像等材料。纯文本请求可以省略附件；附件的处理与传输流程将在后续章节展开。

上下文是本次请求提供给模型使用的材料，例如任务文字、行为规则和已读到的文件。system prompt 是用于向模型表达系统行为规则的那部分文字；模型根据这段文字生成回答；文件访问由工具链和文件服务控制。

这条流程涉及用户与五类系统组件：接纳入口、Agent 驱动、LLM 服务、ToolRuntime 和 Session。接纳入口校验并接收输入，驱动调度步骤，LLM 服务调用模型，ToolRuntime 管理工具执行，Session 记录过程与结果。

源码讲解涉及以下基础概念：函数封装可调用的步骤，变量绑定值，对象组织相关属性，返回值是函数向调用方提供的结果，类型描述值的结构与约束。第 2 章结合项目中的实际写法逐项解释。

01.2 沿一个任务看完整流程

以“读取 README，概括项目用途和三项功能”为例，成功路径从提交任务开始。入口构造消息、排入 Inbox，并返回接纳回执。驱动领取输入后构造第一次模型请求，模型返回读取文件的工具调用。ToolRuntime 记录调用并检查准入；调用获准后，文件服务读取文本。读取结果进入 Session，成为第二次模型请求的上下文。模型据此生成总结，驱动记录轮次结束，客户端显示结果。

01.3 关键机制与设计取舍

请求与结果的数据流转

图 01A 按箭头展示成功路径：接纳任务、模型提出 read、文件服务返回窗口、下一次请求使用结果，再生成总结。第一次请求负责提出读取，第二次请求负责利用读到的文本。

  3. ToolRuntime 完成准入，执行包装函数检查参数，再由文件服务读取目标。
  4. 工具结果记录到 Session；驱动组装第二次请求，把已获取的文件窗口交给模型。
  5. 模型根据这些文字生成总结，驱动记录轮次结束，界面显示结果。

01.4 源码研读

E01A · 接纳时的身份与来源

阅读任务：节选位于 prompt 的输入校验之后。请求已包含 Session 标识和请求标识，代码据此定位 Agent、识别重复输入并构造消息来源对象。后续流程继续处理附件、消息排队和接纳回执。

实现详解

一次 prompt 请求要把客户端提交的内容交给特定 Agent，同时保留这次提交的身份。请求中有两个用途不同的标识：sessionId 决定接收输入的 Session，requestId 标识客户端的这一次提交。入口先根据 sessionId 获取 Agent，后续的重复检查、消息排队和附件绑定都围绕这个对象进行。例如，两位用户分别向不同 Session 提交相同文字，仍是两次独立输入。

获取 Agent 后，入口检查这个 requestId 是否已出现。检查范围包括 Agent 的两类 Inbox 队列，以及 Session 中已经登记的用户消息：尚未领取的提交可以在队列中识别，已经领取并登记的提交可以在历史中识别。找到对应记录就直接返回 accepted 回执，避免重复排队。比较的是请求身份，相同文字配上新的 requestId 仍会作为新提交处理。客户端因网络问题重发同一个请求时，这项检查让已有接纳记录能够继续使用。

新请求随后建立 MessageSource，也就是随用户消息保存的来源信息。kind 将它标为用户输入，rpcId 保存 requestId，使后续正式消息能够与客户端的本地 pending 条目关联。客户端时区此前已经过规范化和合法性检查；提供了有效时区才写入来源对象，缺省时保留字段缺省状态。来源对象保存提交元数据，任务文字和附件另在消息内容中组织。

这一阶段完成后，入口继续校验图像能力、解析附件凭据并接纳附件，再创建用户消息。steer 模式把消息送往下一步，普通提交通过 followup 排入下一轮；附件绑定提交成功后，入口返回 accepted。以“读取 README”为例，此时确定的是输入已排队且具备可追踪身份，随后由驱动领取消息、调用模型并执行读取。请求回执与后续任务事件共同构成客户端观察一次提交的完整路径。

E01B · 工具调用的关联记录

阅读任务：appendToolCall 是 executeToolCalls 使用的记录辅助函数。输入包含 Session、turn、step 和工具调用块；函数把调用信息追加到 Session 内存日志，并返回用于关联结果的事件序号。

实现详解

模型提出工具调用后，执行器需要先建立一条能够追踪的调用记录，再把它与后续结果关联。appendToolCall 接收四组信息：所属 Session、当前 turn、当前 step，以及模型给出的 ToolCallBlock。调用块保存本次调用的 id、工具名称和参数；轮次与步骤说明它出现在任务推进的哪个位置。同一轮里多次调用 read 时，调用身份和推进位置能区分每一次读取。

辅助函数将这些字段作为 tool/call 事件交给 Session.append。Session 对事件作快照和校验，追加到内存日志，再通知观察者。调用者因此得到包含 seq 的事件对象，seq 是这条记录在当前 Session 日志中的位置。例如日志原有 9 项，位置为 0—8，本次调用就取得位置 9。其他消息和过程事件也占用日志位置，所以 seq 反映完整事件序列中的顺序。

函数把 seq 返回给执行器，执行器在产生工具结果时再传入这个位置。结果事件通过关联字段指回原调用，同时保留调用 id、turn 和 step。读取成功、准入拒绝以及取消后生成的跳过结果，都可以按这套关联方式解释：哪一次提议得到了什么结论，结论属于哪个步骤。界面展示和历史查询无需仅凭工具名猜测配对关系。

以模型提出 read 为例，调用事件先进入 Session，之后执行器才继续准备准入和分派。获准且文件存在时，文件服务返回窗口，再登记与原调用相连的结果；拒绝时则形成对应的拒绝结果。Session 的存储监听器另外安排写入文件，appendToolCall 的返回点完成的是调用事实的建立。沿“调用记录—准入与执行—结果记录”观察，就能还原这一次工具请求的进展。

  return event.seq
}

01.5 理解检查与讲解问答

问题 1 · accepted 回执确认了哪个处理阶段？

讲解：accepted 回执确认入口已接纳输入。文件结果要在驱动领取输入、模型提出调用、工具准入和实际读取之后产生。

问题 2 · 如何核对总结与实际读取内容的对应关系？

讲解：先找到 read 的调用记录和成功结果，确认返回的行范围覆盖总结所用的材料，再逐项对照总结与原文。这样才能把总结中的结论追到实际读取结果。

问题 3 · 两次模型请求的上下文有什么差异？

讲解：成功路径中的第二次请求新增了工具读取结果。它依据前一步执行所得的文本生成总结，因此两次请求在数据上存在依赖。

02.1 基本概念

变量是与值绑定的名称，例如 path 保存路径字符串。字符串表示文本，数字可以表示行号，布尔值表示真或假。对象组织相关属性，例如读取请求包含路径、起始行和行数，request.content 访问请求的内容属性。数组按索引保存一组值。数组索引通常从 0 开始，文件行号通常从 1 开始，窗口计算需要区分这两种编号方式。

函数封装可复用的处理逻辑，通过参数接收输入，通过返回值提供结果。方法是对象上的函数，例如 agent.followup(message) 调用 Agent 的消息接纳方法。类定义对象的结构和操作，由类创建的对象称为实例。接口和类型描述数据结构，例如将路径声明为字符串；文件是否存在则由执行时的文件服务检查。

TypeScript 在 JavaScript 的写法上增加类型说明。const 固定变量绑定，let 允许重新赋值；对象内部仍可能变化。冒号后面通常是类型，问号表示可缺省，return 把值返回调用者，throw 使当前路径失败。花括号既可能围住对象，也可能围住一组语句，要看它的位置。模块是单独组织代码的文件；import 引入别的模块，export 让别处能够使用本模块的名称。

Promise 表示异步操作的结果，状态包括等待中、成功和失败。async 函数返回 Promise，await 暂停当前函数的后续执行，等待该结果；JavaScript 运行时在此期间可以处理其他就绪工作。进程由操作系统管理，线程是进程内的执行路径。并发允许多项工作交错推进，并行使用多个执行资源在同一时刻处理工作。操作能否重叠，取决于启动和等待顺序。回调是供其他代码在约定时机调用的函数，例如事件监听器。阅读 () => ... 时，需要定位它的注册位置、调用者和触发条件。

JavaScript 提供执行语义，TypeScript 在其基础上增加静态类型检查，用于发现数据结构和调用方式中的问题。输入合法性、文件权限与资源可用性由运行时代码检查。等待外部 I/O 时，事件循环继续处理就绪任务，结果到达后恢复相应的异步函数。

注册工具时，程序把名称、参数说明和执行函数交给注册表。执行函数此时作为一个值保存，具体调用到来时才运行。箭头函数、对象方法和事件回调都要区分定义与调用。要让两个异步操作重叠，可以先分别启动，再用 Promise.all 汇总结果。全部成功时，它按传入顺序返回结果数组；任一项失败时，汇总的 Promise 就失败，其他已启动操作仍按各自流程收尾。

接纳入口的异步执行顺序

prompt 首先校验请求并解析目标。已识别的 requestId 直接返回回执；新请求构造用户消息，调用 followup 或 steer，随后返回接纳结果。followup 将消息加入 Inbox 并请求唤醒驱动，模型请求与工具执行由驱动继续调度。

调试“提交成功但没有回答”时，沿 Inbox、驱动状态、模型请求和工具结果继续查。await prompt 已经结束，后台驱动仍在运行。

容易混淆的地方

“async 使函数内部所有动作并行”：连续写两个 await 时，第二个操作要等第一个返回后才开始。先启动两个操作、再汇总它们的 Promise，才给它们提供重叠推进的机会。

“类型合法就不会失败”：类型不能证明文件存在、网络可达或权限获准；运行时检查依然必要。

工具定义中的 execute 属性保存执行函数。注册完成后，具体调用仍需经过工具运行时，才能进入函数体。

02.4 源码研读

E02A · async 返回的结果由方法契约决定

阅读任务：节选是 prompt 方法开头的输入校验。request 是入口接收的请求对象，内容不合法时方法抛出错误。时区、附件、消息入队与 accepted 返回位于后续逻辑，其主流程见第 1 章。

实现详解

prompt 是客户端提交任务的异步入口，返回类型 SessionPromptValue 规定调用者拿到接纳回执。方法开头先检查请求是否包含可处理内容。content 是内容块数组，其中的文字块可以包含正文，非文字块承载图像、文件等材料。hasPromptContent 遍历这些块：文字去掉首尾空白后还有内容，或者存在非文字块，便通过这一项检查。

空数组、只含空字符串或只含空白文字的请求会在这里失败。入口构造 gateway/bad-request 类别的 RemoteError，附带“需要非空白文字或附件”的说明，然后终止当前方法。错误类别让远程调用方识别失败性质，说明文字帮助客户端显示原因；本次错误没有额外的结构化详情。因为检查发生在解析 Agent 和创建消息之前，这类请求不会经由后续路径进入 Inbox。

async 把方法结果组织成 Promise。方法中的 throw 会使这个 Promise 失败，客户端 await prompt 时便进入错误处理；合法请求跳过拒绝分支，继续检查时区、目标 Agent 和附件，最终获得接纳结果。入口中的 await 用来等待这些接纳工作。后台驱动处理模型与工具的时间线由后续事件呈现，调用方可在收到回执后继续响应界面操作。

比较两个输入便能看到完整顺序：提交三个空格且没有附件时，内容检查直接返回远程错误；只提交一个文件附件时，这项检查通过，随后还要解析附件凭据、接纳附件并绑定到消息。前者在入口结束，后者能否排队由后续接纳步骤决定。阅读异步方法时，先确定它承诺返回的结果，再沿各个等待点和错误分支观察，就能判断 await 结束时系统已经推进到哪一阶段。

02.5 理解检查与讲解问答

问题 1 · await 一个方法，是否等于等待整个用户任务完成？

讲解：由方法返回契约决定。等待接纳方法只获取回执；等待读取方法才获取读取结果。

问题 2 · 注册对象里写了 execute 函数，为什么没有立即读文件？

讲解：注册只是保存函数值与说明。后来发生具体工具调用时，框架才调用执行函数。

问题 3 · 类型说路径是字符串，是否证明文件存在？

讲解：类型检查确认参数符合字符串类型；文件是否存在、权限是否允许以及读取是否成功，由运行时代码分别验证。

第 3 章｜Agent 循环、Inbox 与工具调度

本章学习任务：追踪输入从 Inbox 进入 turn、step 和 attempt 的过程，解释并发执行与有序提交。

03.1 基本概念

轮次（turn）是驱动围绕一批输入推进的过程，步骤（step）是其中的执行单元，尝试（attempt）对应步骤内的一次模型请求。读取 README 和根据读取结果生成总结，可以构成同一轮次的两个步骤。请求失败后若恢复策略允许重试，新的请求仍属于原步骤，attempt 增加，turn 和 step 保持不变。

状态描述系统在某个时刻保存的信息，例如待处理消息、轮次编号和驱动阶段。状态转换规定事件发生后这些信息如何更新，驱动负责调度转换。取消信号向执行代码传递停止请求；支持取消的路径检查信号、停止后续工作，并处理已启动操作的收尾。

Inbox 分别保存 next-turn 和 next-step 输入。followup 放入前者，steer 放入后者。进入下一步骤时，驱动领取全部 next-step 输入；开启下一轮时，再把一项 next-turn 输入接到这批材料后面。因此，较晚到来的引导可以先被领取，较早排队的另一项普通任务仍在等待。领取以后还要经过前置判断，允许进入本步才发起模型请求。

输入接纳、消息领取、模型请求、工具执行和轮次结束分别对应不同的处理阶段。判断任务进展时，需要把各阶段的事件与结果关联到同一轮次。

03.3 关键机制与设计取舍

三层边界

图 03A 外框是一轮任务，内框是两个步骤。第一步有失败和重试两次尝试，第二步有一次成功尝试，因此这条轨迹包含一个 turn、两个 step、三个 attempt。

turn、step 和 attempt 分别统计任务推进的三个层次。前置拒绝时，一轮没有进入模型步骤；读取后总结可以用两个步骤；某一步请求失败后又可以重试。驱动在成功消息提交后提取工具调用；失败尝试的 partial 是尚未成功完成的输出，先进入失败记录与恢复流程。

Inbox 怎样与驱动合作

Inbox 保存尚未领取的输入。followup 排入下一轮并请求唤醒；steer 排入下一步并请求唤醒；inject 也排入下一步，由后续驱动活动领取。选择哪种入口，决定输入何时进入处理以及是否启动驱动。

空闲时，需要唤醒的输入让驱动启动。已有活跃驱动时，新输入由现有驱动在约定边界领取。维护期间，唤醒请求先记在 wakeRequested 中，由维护任务收尾时检查是否启动驱动。这里把正在进行的一次运行称为活动。若活动已收到取消信号，send 会把需要唤醒的输入改排到 next-turn，等待原活动收尾后再处理。

普通运行路径中，驱动开放轮次，准备下一步，领取消息并组装材料。前置决定可能允许进入或拒绝。进入后发起模型请求，成功消息有工具调用则进入工具批次；工具结果回到 Session 历史。驱动再看停止原因与下一步输入，决定继续或结束。

工具执行能重叠，结果仍按模型顺序提交

把贯穿案例稍作教学扩展：模型在同一消息里先提出读取 README 的调用 A，再提出读取包信息的调用 B。要同时说明三个顺序：提议的排列、真实动作的完成先后，以及结果进入 Session 的顺序。三个顺序不必相同。S02 对照本节执行器。

执行器按模型给出的顺序建立调用计划，保存调用标识、工具名、已解析参数、Agent 和取消信号。允许并发的调用进入有数量上限的执行池；需要独占的调用设置执行屏障，等待池内任务结束后运行。执行池管理正在执行的调用，屏障约束不同批次的启动顺序。

启动每一项时，先记下 tool/call 及其序号，再等待这一项的前置准备。准备可能已经形成拒绝结果，也可能允许分派真实执行；前置准备按顺序推进，实际分派与工具体才可能重叠。拒绝结果同样要在相应位置进入结果链，作为确定的结果记录留存。

假设 A、B 均允许并发且执行池容量足够，B 先完成。执行器将 B 的结果暂存于索引 1 的结果槽，提交游标仍停在 A 对应的索引 0。A 完成后，执行器按 A、B 的顺序运行结果后处理、追加 Session 结果，并把额外上下文传入下一步骤。结果槽按调用位置暂存完成结果，提交游标保证历史顺序与模型提议顺序一致。

队列与状态机的最小基础

队列保存“还有哪些输入等待处理”，状态机记录“当前运行在哪个阶段”。新消息入队后，正在执行的请求继续使用原材料；驱动到下一领取时点，才把待处理输入加入后续请求。

ReactLoopAgent 是核心运行驱动。它管理 Inbox、turn、step、模型请求和取消；网页端的 React 组件负责显示这些运行状态。

E03A · 领取时组合两类待处理输入

阅读任务：本段是 Inbox.claim 完整方法。target 指当前是否是新轮次边界，turn 指领取所属轮次。mutate 在这里移除对应列表项并返回被取出的消息；重点是两类列表的领取差异。

实现详解

Inbox.claim 把待处理输入转成当前步骤要使用的一批消息。调用者是准备步骤的 Agent 驱动，传入 target 表明当前边界是否同时开启新轮次，传入 turn 标明这批输入归属哪一轮。Inbox 内有 next-step 和 next-turn 两个列表：前者承载需要在下一步纳入的引导或注入，后者承载等待下一轮的普通任务。

每次领取先取走 next-step 的全部现有消息，并按列表顺序放入 claimed。mutate 同时更新队列状态和返回取出的消息，因此领取后这些输入从待处理列表中移除。在 next-step 边界，领取到此为止；在 next-turn 边界，再从下一轮列表的头部取一项，接在 claimed 后面。即使下一轮排着多项普通任务，本次也只取其中一项。

这样安排使当前轮次的补充要求能够在下一步骤及时进入，同时让排队的普通任务逐轮推进。例如 next-step 有 B、D，next-turn 有 C、E：在当前轮次准备下一步时得到 B、D，C、E 继续等待；在新轮次边界领取相同队列时得到 B、D、C，E 留给后续轮次。这批结果按目标边界和列表顺序组合，不能用所有消息的提交时间重新排序。

队列更新完成后，方法逐条发出 agent/inbox/claimed 通知，通知携带消息和所属 turn，让界面及其他观察者知道输入已被领取。返回的 claimed 数组交给前置步骤处理，随后才组装模型请求。领取说明消息从队列进入了步骤准备，前置处理仍可以拒绝继续。后到的输入保存在队列中，由下次驱动到达领取边界时处理，已发出的模型请求保持原有材料。

问题 1 · C 先以 followup 排入，B 后以 steer 排入，谁先用于本轮下一步？

讲解：B 在下一步领取，C 留给下一轮。Inbox 先按输入的目标边界分组，再在相应边界领取，所以后到的 B 可以先于 C 进入请求。

问题 2 · 一轮两步，第一步重试一次，一共有几次尝试？

讲解：三次。第一步两次，第二步一次；轮次数仍是一次。

问题 3 · inject 与 steer 的关键差别是什么？

讲解：两者都进入 next-step；inject 不触发唤醒，steer 触发。驱动空闲时，inject 的输入会留在队列中，等待后续唤醒。

第 4 章｜文件读取：参数解析与窗口构造

04.1 基本概念

文件路径标识读取目标，当前工作目录是相对路径的解析基准。Session 与所选文件 Provider 共同确定 README.md 对应的实际位置。后端实现统一文件接口：接口规定读取操作及返回形式，具体后端负责本机、远端等环境中的路径解析和文件访问。

工具参数契约规定可接受的字段、类型和值。schema 描述字段结构，例如字符串路径和数字行号；解析逻辑进一步检查取值、补齐缺省参数，并转换成执行体使用的内部输入。读取窗口保存本次选定的文本行，同时返回总行数与截断信息，供模型判断是否需要续读。

流式文件读取按批次向窗口构造器提供文本，避免在内存中保存整个大文件。模型流式响应则按批次返回生成内容，两者分别作用于文件输入和模型输出。读取结果受行数、单行长度和输出字节上限约束，并明确标示实际保留范围。第 18 章进一步说明结构化结果如何生成模型文本与界面元数据。

字节是存储和传输数据的计量单位。UTF-8 把文字编码成字节序列，一个汉字通常占多个字节。模型的 tokenizer 又把文字编码成 token。文件字节数、文本行数和模型 token 数采用不同计量规则，工具输出上限与模型容量分别控制。

读取前要经过通用工具准入；获准后依次解释参数、选择读取方式并构造窗口。拒绝调用与读取时发现文件不存在，是两个独立阶段的结果。

04.2 沿一个任务看完整流程

假设 README 有五行，工具参数是路径 README.md、offset 为 2、limit 为 2。调用先经过 ToolRuntime 准入；获准后，defineTool 包装函数检查参数的 schema，read 执行体再检查路径不为空、行号与行数为正整数。合法输入变成内部的 filePath、offset 和 limit。文件服务解析目标、获取文件信息，然后依大小信息选择一次读取或流式读取；窗口构造器保留第二、三行，并受其他输出上限限制。

如果不提供 offset，使用第 1 行；不提供 limit，采用本次配置的默认上限。提供 0、负数或超过允许上限的 limit，会走参数错误分支。文件大小未知时采用流式路径，是为了避免无法判断大小的后端先缓存任意大文件。

结果返回后，ToolRuntime 校验并渲染输出，驱动再记录工具结果。下一次请求得到的是这次读取的窗口，窗口中的行号和总行数帮助模型决定是否续读。

E04B · 大小信息决定文本获取方式

阅读任务：位置在 read 的执行体内，参数已经解析。target 保存后端解析的目标，info 保存文件信息，caps 是本次读取限制，exec.signal 是取消信号，ctx 是携带各项服务的 Context 对象。后续 outcome 和结果返回在正文中说明。

实现详解

read 的执行体取得合法参数后，需要解决两个连续问题：怎样获取文件文本，以及怎样从文本中构造本次返回窗口。它先调用 resolveRegularReadTarget，由当前文件 Provider 解析路径并确认目标适合普通文件读取。返回的 target 表示后端可访问的目标，info 提供文件信息，包括可选的大小；target.displayPath 用于在结果中显示路径。

第 5 章｜Session 事件日志、投影与持久化

本章学习任务：追踪事件从内存日志进入存储与派生视图的过程，解释 append、flush 和 Session 恢复。

05.1 基本概念

Session 事件日志按顺序记录消息、工具调用和运行边界。终端调试输出属于另一条输出通道。序号说明事件在 Session 中的位置；时间记录发生时刻，序号决定事件顺序和连续性。

快照保存某个时刻的数据副本，冻结限制对象及其内部数据被修改。派生根据已有事实生成新的数据形式，例如从消息事件形成模型历史；投影按事件规则持续维护可查询状态，例如最新待办列表。三者分别用于保留数据、构造视图和更新业务状态。

可序列化数据可以按约定转换成存储或传输格式。例如包含字符串和数字的对象可表示为 JSON，含任意函数的运行对象需要另行处理。冻结保护内存对象，持久化负责写入存储。缓存复用已经计算的派生结果，原始记录变化时使相关缓存失效。

持久化将内存数据写入程序退出后仍可保留的存储。JSON 是表示对象、数组等值的文本格式，JSONL 按行保存 JSON 记录。Session.append 更新内存日志并通知订阅者，JSONL Provider 将事件加入写入队列，再由 writer.append 完成文件追加。flush 等待存储 Provider 排空缓冲并完成写入。

Session 恢复还原已经记录的对话和运行过程；文件当前内容由文件服务读取，外部进程状态由进程 Provider 查询。

05.2 沿一个任务看完整流程

05.3 关键机制与设计取舍

一份事实，多个消费方

图 05A 由 Session 事件分出三个用途：模型历史按 Surface 派生，界面和状态投影消费过程事件，存储监听器排队写入持久记录。

持久日志保存已追加的底层过程事件，模型消息则由当前 Surface 派生。Surface 是参与组装下次模型请求的消息节点序列，规定哪些消息按什么顺序进入请求。Surface 管理器根据事件维护这份序列。生成途中的流式文本片段仍是临时观察；循环正式提交助手消息后，该消息才成为可交给持久化 Provider 处理的记录。提交使消息进入 Session 内存日志，flush 则等待存储写入完成。

append 怎样建立一个事实

Session.append 先创建可序列化的数据副本，再构造带序号和时间的冻结条目。可序列化表示数据能按约定转换成保存格式。接着，方法校验事件字段，并检查 Surface 约束：这条事件是否符合当前消息序列的更新规则。两项校验通过后，事件进入日志并发布。副本与冻结共同防止调用者后来修改原对象时改变已记录的历史。

随后 Session 发布该事实，消费方依各自接口更新或排队处理。消息派生 deriveMessages 遍历当前 Surface 中的消息节点，生成新的消息数组。状态投影则按注册的事件消费规则维护可查询状态。消息视图处理消息节点，状态投影处理各自关心的过程事件。

DSH 的 JSONL Provider 为每个 Session 管理一条写入通道，称为写入句柄。它监听 session/event，将新条目排入后台缓冲；收到 session/flush 后，先等待缓冲排空，再等待 writer.flush 完成。Session 通过事件通知存储，存储组件负责实际文件读写。

投影和持久化屏障

Session 投影按事件规则更新状态，供不同消费方查询。例如，待办投影根据待办变更事件维护最新列表，运行状态投影根据生命周期事件维护当前阶段。同一份日志可以支持多种投影，各自保留业务所需的数据。

JSONL 的持久化链分为两层：实时监听器先把事件放进缓冲，writer.append 再按序写入文件并调用文件同步。session/flush 先等待 drainLive 排空实时缓冲，再等待 writer.flush；尚未写入事件的空 Session 会在此创建并同步头记录。文件追加或同步失败时，存储层关闭追加句柄，再把文件截回本批写入前的长度并同步，随后抛出原错误。若回退也失败，就用 AggregateError 同时报告写入错误与回退错误。成功回退后，本批可以按未推进的游标重试。

E05B · 后台写入与持久化等待

阅读任务：JSONL 存储组件注册两项事件监听。session/event 到达时将事件排入后台缓冲；session/flush 到达时等待缓冲排空并完成刷新。注册调用保存回调，具体事件触发回调执行。

实现详解

JSONL Provider 通过事件监听接入 Session，为每个受管理的 Session 保存写入句柄。Session 发布新事件时，session/event 回调按 session.id 找到对应 writer，再调用 enqueueLive。这个调用把事件加入实时写入缓冲，由写入通道继续追加到文件；Session 的界面观察者可以在同一时期更新显示。

实时写入在后台推进，发生错误时回调记录警告，并保留尚未完成的缓冲事件。这使调用方可以从日志中看到具体哪个 Session 的写入失败，后续排空流程仍能够处理保留的事件。写入句柄的内部逻辑负责顺序、追加位置与失败回退，监听器本身只负责将 Session 事件路由到相应通道。

session/flush 提供显式等待点。回调找到 writer 后，立即启动并返回一个异步操作：先等待 drainLive，把已经排入的实时事件写完，再等待 writer.flush 完成存储层的刷新工作。Session 的 flush 流程收集并等待这些监听结果，调用方据此获知持久化等待是否成功。找不到写入句柄时，这个 Provider 返回 undefined，表示本次没有对应通道参与等待。

以 read 结果为例，工具结果先进入 Session 内存日志，随后被排入 writer 的缓冲。此时界面可能已经显示文件窗口，文件追加仍在进行；关闭或其他需要保存完成的路径再等待 flush，就会先排空缓冲，再等待刷新。若其中一步失败，等待向调用方报告错误。沿“事件发布—缓冲入队—后台追加—显式排空与刷新”观察，可以准确定位显示与保存之间的进度差。

第 6 章｜提示词组装与项目指令

本章学习任务：理解提示贡献、项目指令与历史的组装规则，追踪作用域选择、去重和请求冻结。

06.1 基本概念

一次模型请求的上下文包含系统规则、当前输入、历史消息和工具说明等材料。提示词向模型描述目标与行为要求，system prompt 承载其中的系统规则。用户消息、项目指令和工具结果以各自的来源进入请求，后续组装依据这些来源选择内容和顺序。

注册阶段保存插件提供的提示段或动态上下文，请求组装阶段读取当前可用的贡献。作用域决定贡献对哪些 Agent 可见，同名选择规则决定采用哪个版本，排序规则决定各项内容的排列顺序。三类规则共同确定本次请求的输入。

项目指令描述工作区和当前文件路径相关的规则。每次模型请求前，项目指令插件先选择规则文件，将内容整理成指令消息，再与待处理输入一起进入本步。历史则从 Session 的 Surface 派生，随后与这些新材料汇合。

请求冻结为当前调用建立独立、稳定的数据副本。新消息、插件变化与压缩影响后续请求的组装；已经提交的请求继续使用原副本。因此运行中到达的引导消息，需要在下一步骤被领取后生效。

06.2 沿一个任务看完整流程

以“总结 README，但保留实验性功能的限制”为例，用户目标是一条来源明确的消息。system prompt 贡献说明行为规则，工具贡献说明 read 怎样调用，历史提供先前已经获取的材料；工作区指令再依据当前范围补充约束。

组装器先决定哪些贡献在当前作用域可见，再解决同名项和顺序问题。前置指令处理会清掉不再需要的待处理指令，并把这次需要的指令放入本步消息批次。用户消息在首次尝试登记，重试不再重复登记它；请求创建后获取独立配置副本。

请求执行期间补充的“只总结正式功能”先进入 next-step 队列。当前请求使用既定副本，下一步骤领取新消息并重新组装上下文。后续压缩可以改变历史 Surface，在途请求则保持原内容。定位材料缺失时，分别检查可见提示贡献、前置消息、历史 Surface 和最终请求。

06.3 关键机制与设计取舍

材料有不同的入口

图 06A 的三路材料汇入本步请求：SystemPrompt 组装提示贡献，项目指令形成前置消息，Session 历史按 Surface 派生。它们分别保留自己的来源和排列规则。

system prompt 通常描述运行方式和工具使用等约束。运行时上下文提供当时环境材料，例如当前时间、工作目录或刚读取过的文件路径。项目指令描述工作区规则。用户消息提出当前目标，工具结果给出已获取事实。知道每类材料从哪里来，才能检查冲突、遗漏与重复。

从贡献到请求冻结

插件用 SystemPrompt.section 注册具名提示段，用 context 注册动态上下文。每项贡献带有作用域。同名项先选择当前 Agent 更近的作用域，再按服务规定的顺序排列。完整提示段另有自己的选择规则。SystemPrompt 服务根据这些规则组装本步提示词。

驱动在步骤准备阶段领取输入，调用 assemble 组装提示，并生成本步运行时上下文，随后进入 agent/pre-step 前置处理链。该链按顺序执行，决定步骤能否继续及其消息批次。项目指令插件先等待相关投影就绪，再根据工作区和触及路径选择规则文件。触及路径是工具调用已经接触的文件路径，用于确定适用的目录规则。选中的规则形成上下文消息，插入本步批次。

进入步骤后，框架准备模型调用，记录需要的系统消息、首次进入的用户消息和请求信息，再派生并冻结请求。冻结确保本次请求的内容不会因共享对象被修改而发生预期外变化，下一步重新组装消息和上下文。

顺序与作用域的基础

每项提示贡献通过名称、作用域和顺序参与组装。名称用于识别同名项并选择有效版本，作用域限制可见范围，顺序确定最终排列。显式定义这些信息，使不同插件提供的材料能够按一致规则组合。

消息同时保存内容与来源。项目指令来自规则文件，用户需求来自提交入口，工具结果来自执行链。框架按这些来源组织消息；一段文字里出现“系统提醒”，不会改变它原有的消息类别。

分析示例：重复材料占了多少空间

教学请求包含工具指导 800 字节、项目规则 600 字节、用户需求 200 字节、历史 2400 字节，共 4000 字节。某插件又加入完全相同的项目规则 600 字节，新总量为 4600 字节，增加 15%。

这个算例的组成量保存在计算输入中，calculations 按“基础组成求和—加入重复规则—除以原总量计算增幅”的顺序复算。计算记录中的 C6_baseline_bytes、C6_augmented_bytes 与 C6_increase_percent 对应这三个结果。

重复规则增加请求体积，也使来源判断更加复杂。项目指令用 sameContextPayload 检查等价消息，SystemPrompt 按名称和作用域选择贡献。定位重复内容后，可以在对应组装入口处理，减少后续压缩需要处理的冗余。

在下一步加入项目约束

图 06B 比较重复材料的体积：基础请求 4000 字节，重复一份 600 字节规则后变成 4600 字节，增加 15%。两侧比较的是内容组成和字节数。

驱动准备模型调用时检查取消信号。工具成功访问文件后，项目指令插件按调用结果收集触及路径。当前步骤结束时，插件排队更新对应指令；下一步前置链等待更新完成，再把本次需要的规则消息加入请求。

常见误解

“所有项目指令都直接变成 system prompt”：项目指令在前置步骤中形成指令消息，再与本步输入组合；SystemPrompt 服务另行组装 system prompt。

“更长的提示词必定更可靠”：长度只描述材料体积。冲突、重复和是否被正确执行仍要检查。

“冻结一次请求就冻结整个 Session”：冻结保护本次材料；下一步可读取新消息、工具结果或新的 Surface 状态。

06.4 源码研读

E06A · 项目指令进入本步消息

阅读任务：位置是前置指令处理已经算出 desired 之后。desired 是这一步要插入的指令消息；pending 是待清理指令，decision 保存准备中的消息批次，messages 是已领取输入。重点观察去重和插入位置；指令文件的发现过程见本章前面的讲解。

实现详解

项目指令插件在 agent/pre-step 链中，把当前工作区规则加入本步消息。进入这一段前，它已经等待相关投影更新，计算出 desired 指令消息，并得到其他前置处理返回的 decision。decision.messages 是目前准备采用的消息数组，messages 保存驱动本次从 Inbox 领取的输入，pending 则是 Inbox 中等待更新的项目指令消息。

拒绝继续的步骤，以及首次进入却没有输入的轮次，前面的分支会保留或更新待处理指令。到达本段意味着当前步骤能够继续，插件先从 Inbox 移除 pending 中的旧指令，让它们不再作为后续重复输入排队。随后检查 desired：没有需要插入的指令，或者批次中已经包含等价指令内容，就返回原 decision。等价判断比较上下文内容，用来避免同一份规则反复进入批次。

需要新指令时，插件在 decision.messages 中找到最后一条属于本次领取批次的消息，将 desired 插在它后面。这样直接输入位于项目规则之前，驱动追加的运行时上下文位于规则之后。假设原批次为“用户要求、运行时上下文”，加入后便成为“用户要求、项目指令、运行时上下文”。若数组中没有本次领取项，查找结果为 -1，插入位置因此是数组开头。

插入使用新数组，返回值也保留 decision 的其他字段，只替换 messages。后续请求组装采用这份更新后的批次，当前代码没有直接发送模型请求。以读取目录下的 README 为例，此前访问文件产生的触及路径可以影响 desired 的规则选择；本段负责把选好的规则去重并安放到确定位置，使下一步模型同时看到任务、目录约束与运行环境资料。

06.5 理解检查与讲解问答

问题 1 · 项目指令一定进入 system prompt 吗？

讲解：项目指令由前置步骤形成消息，并加入本步材料；system prompt 则由 SystemPrompt 服务组装。两条路径在准备请求时汇合。

问题 2 · 引导消息到来后，已经发出的请求会改变吗？

讲解：在途请求使用已冻结的数据副本。新消息在下一次领取边界进入后续请求。

问题 3 · 重试为什么不重复登记用户消息？

讲解：首次尝试登记后已有这份 Session 事实，再次登记会把一个输入变成重复历史。

第 7 章｜Skill 发现与按需加载

本章学习任务：追踪 Skill 的目录发现、入口检查与正文读取，区分工作方法与工具执行权限。

07.1 基本概念

Skill 是封装任务方法的说明及相关资源，例如技术报告的整理流程。目录摘要公开名称和用途，正文解释操作步骤与要求。模型通过摘要发现候选，在需要使用时读取对应正文。

Skill 服务负责发现、列出和读取定义，skill 工具让模型按名称获取正文。调用权限分别声明是否允许用户调用、是否允许模型调用；读取入口按相应标志检查。目录可见性用于发现候选，调用标志决定能否从这一入口加载。

Skill 加载获取正文并将其加入模型上下文。正文指导模型组合已有工具，文件访问、网络调用和发布操作仍由工具注册、准入与执行环境控制。用户显式指定 Skill 和模型调用 skill 工具分别采用对应的读取路径。

需要区分三个观察点：目录是否包含名称，读取是否获取定义，正文是否进入本次请求。排查未按 Skill 步骤执行的故障时，先找这三个证据，再评价正文的方法是否清楚。

07.2 沿一个任务看完整流程

假设目录包含 report-skill，摘要标明其用于整理技术报告。模型先根据摘要匹配任务需求，再调用 Skill 读取工具。工具根据当前工作目录、Agent 范围和取消信号获取目录，找到名称以后检查它是否允许模型调用；通过后再获取完整定义。

若目录里的定义已经移除，查询不到名称就报错；名称仍可见但禁止模型调用时，工具返回入口限制错误。获取正文以后，框架把它整理成模型材料，后续模型请求便能使用其中的方法。

用户显式调用的入口会检查用户可调用条件，符合时才建立 Skill 调用来源的指令消息。未知名称和不符合条件的文字不会都被解释为命令。正文中的方法通过后续模型推理与工具调用落实。

07.3 关键机制与设计取舍

先知道名称，再获取正文

图 07A 沿模型调用路径展开：发现候选、发布摘要、选中名称、检查模型调用许可、获取正文。正文作为工具结果记录，随后进入下一次模型请求。

注册表与 Provider 分别负责什么

SkillRegistry 管理可见 Provider 和候选。文件系统 Provider 负责从相应目录发现 Skill 并读文件内容。list 返回摘要列表；get 按名称选择候选；同名项依次按 Provider 优先级、Provider 顺序和本地顺序取舍，把候选定位信息返回对应 Provider 读取，再校验完整定义。这使消费方不必固定绑定某个文件目录实现。

工具插件在前置步骤把当前 Agent 可调用的 Skill 目录写成持久提示消息。目录包含名称与说明，正文按需读取。目录发生变化时，插件发布替换消息；发现过程不完整时，保留已有目录。模型调用 skill 后，执行体检查名称、可见摘要和模型调用标志，再获取完整定义并返回正文。

用户直接调用走另一条路径。前置步骤检查直接用户消息第一行的 /<name>，名称存在且允许用户调用时，加载正文并注入本步消息。模型调用 skill 工具则把正文记录为工具结果，供后续步骤使用。消息来源与调用标志决定这两条路径各自何时生效。

按需加载与工具权限

按需加载在任务需要时获取 Skill 内容。正文提供工作方法，工具注册决定可调用能力，准入链决定本次调用是否允许，执行环境限制实际资源访问。这些控制机制在加载后继续生效。

目录摘要帮助选择 Skill，正文提供步骤、参数和限制。例如“用于文档整理”只说明用途，具体怎样整理要在加载正文后确定。Provider 读取失败、名称消失或入口禁止调用时，工具返回对应错误。

常见误解

“目录列出一百个 Skill，所以上下文已包含一百份全文”：目录与正文有不同契约，应查看实际获取材料。

“任何页面里出现 /Skill 名 都会触发”：直接调用手势有消息来源与可调用策略限制。

“Skill 加载后可以绕过工具准入”：Skill 改变材料和工作方法，准入仍在第十一章的工具链里。

07.4 源码研读

E07A · 读取正文前的可见性和入口检查

阅读任务：这是 Skill 读取工具执行体中的节选。args.name 是请求的名称，exec 提供 Agent 与取消信号；重点区分目录查询、模型调用条件与获取正文。后续结果构造不在本段。

实现详解

模型调用 skill 工具时，需要把名称解析成当前 Agent 可读取、可调用的完整定义。工具先检查名称格式，随后建立 lookup 查询条件：工作目录来自 Agent 的 Session，scope 使用当前 Agent，signal 传递本次调用的取消信号。目录发现和正文读取都使用这组条件，因而沿当前 Agent 的插件装配与工作区解析候选。

工具先调用 skills.list 获取摘要目录，再查找与 args.name 相同的条目。目录里没有这个名称，就报告未知或已经不可用；找到摘要后，再检查它是否允许模型调用。某个 Skill 可以被发现，却只允许用户显式调用，这种候选在模型入口会被拒绝。摘要在这里同时提供发现信息和入口策略，正文尚未进入结果。

摘要检查通过后，skills.get 才获取完整定义。两次异步查询之间，Provider 的可用状态或文件可能变化，所以 get 返回空时仍要报告不可用。紧接节选的代码还会检查完整定义的模型调用标志，通过后才把名称、Provider、可选资源基址与 content 组织成结果。资源基址为正文引用的相关资源提供定位信息，content 保存实际方法说明。

08.1 基本概念

模型一次请求可容纳的材料有容量限制。token 是模型处理文字时使用的编码单位，tokenizer 把文字编码成 token，词数、汉字数和 token 数分别统计。上下文压力把当前材料的 token 计量与模型容量比较。TokenMeter 分别记录本地估计和可复用的 Provider 用量信息。

压缩（compaction）将选定历史改成较短表示，供后续请求使用。例如，把十次文件调查整理成“已读哪些文件、得到什么结论、还缺什么”。原始事件留在日志中，当前 Surface 则使用摘要表示这段历史。

摘要压缩通过较短表示保留关键内容，细节可能被省略。选区检查保持工具调用与结果配对，保留最近历史，并将尚未关闭的步骤留在选区之外。摘要生成期间，稳定性检查确认相关依赖仍与准备依据一致；通过检查后，提交流程把摘要纳入 Session 的当前视图。

裁剪、compaction 和 spill 分别改变不同的数据表示。裁剪移除可省略内容，compaction 以摘要替换选定历史，spill 将长文本保存到外部存储并提供取回入口。它们都减少当前请求承载的内容，后续恢复原文和访问细节的方式则各不相同。

08.2 沿一个任务看完整流程

假设本轮准备请求时材料接近容量，压缩插件在前置步骤测量压力、选择可处理的历史范围、生成较短表示。若选不到范围，就没有压缩结果；若范围可处理，生成期间仍要保持关联条件，提交前再次检查稳定性。

流程先追加 compaction/start，在请求摘要前建立压缩锁。摘要通过稳定性检查后，代码依次记录 compaction/summary、替换 Surface 的检查点消息和 compaction/end。开始以后的失败会进入收尾分支，尝试追加一次结束事件；结束事件本身失败时，未配对的开始标记继续占用锁。已追加的记录保留在 Session 中，错误按 summary 或 commit 阶段报告。自动压力钩子捕获错误、记录警告后继续前置链；上下文溢出恢复则按策略裁剪、重新计量并选择范围。

用一个小例子检查信息损失：原文写“功能 X 是实验性的，只在某后端提供”，摘要若只保留“有功能 X”，字数更少却改变了约束。比较前后应该检查任务仍需要的结论、来源、未完成事项和调用关联。缩短材料为后续请求腾出容量，摘要中的功能范围则决定模型能否准确回答。

第 9 章｜模型流式响应与请求恢复

本章学习任务：追踪模型路由、请求准备和流式消费，解释失败结算、恢复决定与同一步骤内的重试。

09.1 基本概念

流式响应通过连续到达的数据片段传递模型输出，片段可以包含文本、工具调用信息、用量或结束状态。驱动持续消费片段，直至迭代结束或消费过程抛错，并根据 finish 结算结果。适配器将模型服务的协议转换成统一接口，Provider 与模型路由确定本次请求使用的服务。

限流是服务限制一段时间里可接收的请求数量；超时是等待超过规定边界。它们都可能产生失败，但恢复方式由策略决定。

重试是在某次执行失败后重新尝试。恢复策略决定哪些失败可以重试，以及要作哪些准备；agent/request-error 链返回 retry 时，循环才发起下一次尝试。失败尝试产生的临时内容可以被观察，但不能直接作为成功助手消息执行其中的工具提议。

请求先解析模型路由和配置，再获取流并消费片段。流正常结束后，驱动检查 finish：成功则提交助手消息，错误或中止则记录失败尝试并询问恢复链。消费过程中直接抛出的异常走 catch 分支，结算已开始的尝试后继续抛出；这一分支与 finish 携带失败状态的恢复入口分开。

当 finish.kind 为 max-tokens 时，循环先提交已经生成的助手消息，再返回 max-tokens 结束原因，跳过该消息的工具执行。这里达到的是当前请求的输出上限，与上下文过长触发的压缩恢复分开处理。

09.2 沿一个任务看完整流程

假设第一次尝试返回部分文本后以失败状态结束。界面可以显示临时进展，驱动记录失败，并向恢复链提供失败类型、Provider、重试策略和取消信号。恢复链返回 retry 时进入下一次尝试；没有重试决定时抛出对应模型错误。

到达的内容循环处理能否进入工具执行

重试并没有重新接纳一次用户任务。已经登记的用户输入不应重复追加；请求准备也保持对应的配置语义。每次重试重新准备调用，恢复处理可以改变后续请求配置。turn 和 step 保持不变，attempt 增加。

09.3 关键机制与设计取舍

临时输出与最终事实

图 09A 把临时输出和正式提交分开：片段先更新界面，finish 决定成功、失败或取消，循环再记录助手消息或失败尝试。完成且未达到 max-tokens 的消息才进入工具调用判断。

一次调用怎样绑定 Provider

LLM 服务的 prepareCall 按 provider 标识查找适配器，解析目标模型与配置，返回绑定这次调用的 prepared call。它保存冻结配置与重试策略，且只能分派一次。每次重试重新准备调用，适配器将具体服务的响应转换成统一流。

DeepSeek 适配器把响应转换成异步片段，并组合取消信号。空闲监测统计等待新片段的时间，超出阈值就产生超时错误。超时、取消和传输失败分别分类；结束时停止消费，并尝试关闭逐项提供片段的迭代器。关闭失败作为诊断信息保留。

驱动用 for await 消费片段，逐次检查取消信号并推送临时输出。正常终结生成助手消息并记录；符合请求错误恢复流程的失败先记录尝试，再经 agent/request-error 链决定是否重试。没有 retry 决定时抛出 LlmError；已取消时由取消信号结束等待。

异步迭代与响应消费

Promise 表示一次异步结果，异步可迭代对象表示依次产生的一组值。for await 等待下一项，处理完成后再继续迭代。例如流中依次出现文本甲、文本乙和结束信息，驱动按到达顺序处理各项，并在消费结束后读取终结状态。

for await 每次等待下一个片段，直到迭代器结束。驱动随后读取 finish，确定这次响应怎样结算。取消信号沿驱动和适配器传递，各层在检查到取消后停止后续消费，并进入连接清理。

若用户在退避等待中取消，流程在第二次尝试开始前结束，此时只有一次请求。重试能够重新处理临时故障，也会增加等待和用量；Provider 与恢复插件共同决定重试策略。

README 任务中的首次模型请求若失败，驱动记录该尝试并按恢复决定重试。成功响应提出 read 调用后，流程进入工具执行；读取结果加入下一步骤的上下文，模型据此生成总结。失败输出留在尝试记录中，成功消息中的调用才进入工具阶段。

常见误解

“每个 chunk 都是一条助手消息”：片段属于尝试中的暂态流，最终消息有自己的提交边界。

“重试只是再次发送同一函数，在哪里都一样”：重试位置决定是否重复材料、工具副作用（对外部世界产生的实际影响，例如写文件）或其他提交。

“取消后保留了文本，所以任务成功”：应检查 interrupted 与结束原因，并另做产物判断。

E09B · 失败以后是否再尝试

阅读任务：位置在失败已经登记、恢复链已经返回 action 之后。本段处于尝试循环内；finish 保存本次尝试的失败终结信息。重点是没有 retry 时怎样结束，以及 continue 返回哪个循环。

实现详解

本段位于当前步骤的模型尝试循环。流已消费结束，finish 表明这次尝试失败或中止；驱动已经追加 assistant/attempt，保存本次未成功完成的流状态，并等待 agent/request-error 恢复链处理。恢复链收到 Provider、失败详情、当前重试策略与取消信号，返回 action，说明是否继续尝试。

恢复处理可能等待退避或压缩，等待期间用户仍可取消。驱动在使用 action 前再次检查 signal：已经取消就立即进入取消路径，即使恢复链刚返回 retry，也不会启动下一次请求。这个检查使取消状态在恢复等待之后继续有效。

第 10 章｜插件装配、运行配置与热重载

本章学习任务：理解配置条目、profile 与依赖注入，分析插件装配、字段覆盖和热重载。

10.1 基本概念

插件是一份可装入应用的能力实现，例如注册文件工具的模块。配置给出本次采用的参数，profile 选择整组插件及其设置。启动程序按配置装入插件，插件再注册服务、工具和监听器。

依赖是插件运行所需的外部能力，例如文件工具依赖工具注册表与文件服务。依赖注入由框架向插件提供这些服务。Context 是 Cordis 访问服务、登记资源的接口对象；插件的装入、运行和卸载共同构成生命周期，注册与释放发生在对应阶段。

配置条目保存插件身份及其设置，补丁指定对条目字段的修改。配置合成按既定顺序应用补丁，生成加载器使用的条目树。注册表维护名称与实现的对应关系，供消费方解析所需能力。

启动入口先读取运行选择与配置层，再合成条目、加载插件，满足依赖后执行插件的装入函数。函数执行期间注册工具，不表示文件已经读取。条目补丁按 id 定位插件，对补丁中的每个条目字段直接赋值。

热重载在运行时替换符合条件的部件。内部模块可以局部刷新，外部依赖变化则走完整重载路径。Cordis 在卸载时调用已登记的清理函数，例如撤销工具注册或事件监听；第 19 章展开资源登记与释放的机制。

10.2 沿一个任务看完整流程

以文件工具插件为例：配置给出读取上限，启动程序把合成后的条目交给加载器；依赖可用以后执行 apply。apply 检查参数并注册 read 等工具，使注册表更新。实际的文件操作在用户任务发起合法调用并进入执行函数时发生。

配置层先展平成有序补丁列表。applyEntryPatches 按 id 找条目，再用补丁值覆盖对应字段；config 也是一个整体字段。insert 可以向顶层或指定分组加入条目，新条目随即进入 id 索引，供后续补丁修改。缺少目标、目标不是分组或 name 校验不匹配时，函数记录警告并跳过该补丁。

卸载时，框架处理登记的资源释放。热重载还需分析模块依赖：可替换的内部模块走局部处理，外部依赖变化会设置完整重载并调用退出路径。局部替换先释放旧实例的登记资源，再装入新实例；完整重载交给退出和重启路径处理。

10.3 关键机制与设计取舍

配置层怎样汇合

图 10A 按配置应用顺序排列：bundle、profile patch、用户目录 patch、命令行 patch。最终条目交给加载器，满足依赖的插件完成挂载。

启动到挂载的主链

CLI 是 Command-Line Interface，即通过终端命令与选项操作程序的入口。它解析启动参数，profile 模式进入 runProfile。运行器准备环境，读取组合包和有序补丁，得到 Cordis 配置条目。每个条目保存插件及其设置；多个条目按分组组织成应用树。boot 将树中的插件挂载到应用，插件由此提供服务、工具和事件监听。

消费者通过 Context 访问服务，例如文件工具使用文件服务，循环使用模型服务。Provider 实现服务接口，profile 决定挂载哪一份实现。查看应用树，可以确定当前运行使用哪些包及其配置。

官方架构中的 base 是多种 profile 的共享第一层，而 sdk-minimal 是例外：它的组合包拥有完整显式配置树，不应用 base。不同 profile 对热重载的设置也不同。热重载在可局部替换时使相应变化生效；需要完整重载的情形仍走退出与重新启动路径。

依赖注入与生命周期

依赖注入（dependency injection）让插件声明所需服务，再由配置环境提供。框架在当前作用域解析服务；依赖未满足时，实例等待可用环境，服务注册冲突则进入错误处理。作用域决定插件树中哪些位置可以获取这项服务。

插件从安装到卸载的存续期间称为生命周期。注册产生的副作用通常随插件卸载而撤销，例如移除事件监听或能力声明。事件监听是插件为某类事件登记的响应。撤销这项注册后，插件就不再接收相应通知；插件已发出的网络请求和已写入的文件仍由各自服务处理后续状态。

分析示例：覆盖整个 config

设一个插件条目的 config 是 {timeout: 100, limit: 20}，后续补丁给同一 id 设置 {timeout: 300}。applyEntryPatches 直接替换 config，结果只剩 timeout: 300。

加载插件时，配置 schema 再为缺省字段应用默认值。若要显式保留 limit: 20，后续 config 中也应写出它。条目覆盖和插件配置解析是两个连续阶段。

Provider 替换的含义

图 10B 的三栏是消费者、配置与作用域、Provider。read 调用文件服务接口，配置选出具体实现，Provider 负责路径、读取、取消和错误处理。

读取 README 的 profile 需要装入循环、工具、文件服务和模型 Provider。所选模型路由与工具作用域继续决定本次可用能力。Skill、压缩和 MCP 也按当前配置树启用。

常见误解

“包安装了，能力就启用了”：安装与挂载是不同动作，当前 profile 决定是否进入应用树。

base 是多数 profile 的共享配置层；sdk-minimal 使用独立的显式配置树。

“卸载插件会撤销它做过的一切”：卸载调用已登记的释放函数；文件写入和远端请求由各自服务处理后续状态。

实现详解

composeEntries 把启动阶段读取的配置层合成为加载器采用的插件条目列表。layers 的外层数组表示应用顺序，内层数组保存一层的补丁。函数从空条目集开始，将每层展开成一条有序补丁序列，再交给 applyEntryPatches 逐项处理。基础组合包提供条目，后续 profile、用户或命令行补丁沿既定顺序修改它们。

第 11 章｜工具准入、审批与执行约束

11.1 基本概念

准入决定某次工具调用是否进入执行体。前置策略可以允许、拒绝、取消或要求审批；审批服务取得本次决定；后续守卫检查额外限制。allowed-once 将许可绑定到这一次审批，后来的调用重新进入准入流程。

守卫遵循单调约束：它可以增加拒绝，前置拒绝则继续有效。undefined 表示当前守卫没有提出额外拒绝，调用仍遵循已有准入决定。执行环境限制实际资源访问，操作系统沙箱及文件、网络控制由具体 Provider 和配置决定。

一次调用依次留下调用记录、执行状态和结果。前置拒绝时，框架直接构造拒绝结果；进入执行体后抛错时，已经完成的外部动作按实际情况保留。结果后处理再决定交给模型哪些内容。沿这三个时点，可以分清“没有执行”和“执行后失败”。

准入策略、审批、守卫和执行环境各自提供控制接口，可以独立扩展。故障定位需要确认错误发生在哪一阶段：前置拒绝、审批拒绝、执行失败与结果处理失败分别对应不同记录。

11.2 沿一个任务看完整流程

模型提出读取某路径，循环先登记调用事实。ToolRuntime 建立描述本次调用的执行上下文 exec，进入前置链。拒绝时直接形成拒绝结果；要求审批时，服务记录 asked，等待应答，再记录 decided。允许后继续检查守卫，通过后分派层重新解析执行工具，调用其包装函数。包装函数完成 schema 校验，才进入 read 的读取逻辑。

考虑四项请求：前置拒绝、审批拒绝、允许后成功、允许后抛错。请求数是 4，实际进入执行体是 2，成功结果是 1。最后一项已经进入执行体，失败前发生了哪些动作，要沿执行体内部的调用顺序追踪。

执行体返回后，结果规范化把返回值整理成统一结构，后置策略再决定模型最终收到的内容。若策略替换结果文字，模型会看到替换后的版本；此前完成的读取或修改保留在外部系统中。调用记录、准入决定和执行结果分别解释这次调用怎样推进。

11.3 关键机制与设计取舍

工具执行前后的处理链

图 11A 的主线是调用记录、前置决定、可选审批与守卫、执行、结果处理和记录。拒绝支线跳过 execute，再把拒绝结果交给后续处理。

从调用到最终结果

循环先记录工具调用，ToolRuntime 创建执行上下文并检查取消。tools/pre-execute 链返回允许、拒绝、取消或审批请求，策略插件在这条链上作出决定，链尾默认返回 allow。需要审批时，服务向应答者发出询问、记录事实并回传结论。交互界面通常由用户应答，自动化桥接也可以提供机器应答。前置决定为允许时，ToolRuntime 再检查单调守卫。单调指守卫只能否决或原样放行，不能把应拒绝的调用升级为授权。

进入分派后，注册表重新解析可执行工具，融合来自调用方与外层封装的取消信号，再调用真实 execute。执行体返回的规范对象经过成功结果构造；抛错被转成工具错误。之后还有后置处理、内容约束和最终结果通知，循环再按约定顺序记录模型面对的结果。

审批服务在开放轮次内记录 approval/asked 与 approval/decided。开放轮次指已经开始、尚未结束的 turn，这让询问和应答归属到同一轮任务。allowed-once 允许本次审批对应的调用。要求审批时，若缺少审批服务、调用 Agent 或可用应答通道，serviceAsk 返回拒绝。

三种边界分别回答什么

准入策略为本次调用生成处理决定，审批服务收集确认结果，执行环境约束实际资源访问。沙箱或文件系统守卫在执行层实施范围限制；审批确认与这些资源约束分别配置，并在同一次调用中依次生效。

profile 选择审批策略与执行 Provider，将决策流程和资源限制装配到工具链。分析权限行为时，需要同时检查前置决定、审批结果、后续 guard 与执行后端的配置。

阅读任务：这是 prepareExecution 中创建执行上下文之后的节选。exec 描述本次调用，carrier 确定服务派发范围；观察前置决定与审批分支，后续守卫和实际分派不在本段。

实现详解

ToolRuntime 在执行工具前建立 exec，保存本次调用的 Agent、参数、身份和取消状态。本段发生在执行上下文创建成功且初次取消检查通过之后。scopeTarget 按当前工具服务与调用 Agent 选择派发范围，使准入策略沿这次调用所见的插件环境工作。

tools/pre-execute 是一条可等待的前置处理链。策略处理者接收 exec，结合工具名称、参数及调用环境形成 allow、deny、cancel 或 ask 决定。链尾提供默认 allow，处理者可以据自身规则改变结果或直接返回。waterfall 完成后，gate 保存本次处理链最终给出的决定，真实工具体此时尚未分派。

gate 为 ask 时，ToolRuntime 调用 serviceAsk，等待审批服务并取得决策与审批取消状态。缺少可用审批条件时，这条询问路径会形成拒绝。其他 gate 直接包装成统一结构，approvalCancelled 置为 false，表示这个分支没有经历审批取消。此字段与实际决策分别保存，方便后续代码区分调用取消和询问过程中的取消。

阅读任务：这是审批服务已经获取可记录 Session 之后的正常路径。req 保存工具和调用信息；重点是同一个审批标识怎样关联 asked 和 decided。取消或失败处理还需依 decide 和上层调用契约理解。

实现详解

审批服务为一次需要确认的工具请求记录询问与结论。request 先要求 Session 有尚未结束的 turn，让两条审批事件归属当前任务。进入本段后，它用 randomUUID 建立本次审批 id；这个 id 标识一次询问，工具调用的 callId 则标识被询问的操作，两者分别承担审批配对和调用关联。

第 12 章｜MCP：外部工具与资源接入

本章学习任务：理解 stdio 与 Streamable HTTP 传输，追踪能力发现、注册代次、工具调用与资源读取。

12.1 基本概念

Model Context Protocol（MCP）规定客户端怎样与服务端发现能力并交换请求和结果。客户端发起调用，服务端提供能力。协议处理通信与能力发现，具体服务实现存储、检索或其他动作。

stdio 是 standard input/output 的缩写，通过子进程的标准输入和标准输出传递协议数据。标准输入接收外部数据，标准输出发送程序结果。HTTP（Hypertext Transfer Protocol，超文本传输协议）规定请求与响应的交换方式，URL 标识服务地址。Streamable HTTP 使用服务 URL，支持跨网络连接。连接、能力发现、工具注册和调用完成分别对应不同状态。

名称包装让来自不同服务器的工具能进入同一注册表。公开名称和服务器原工具名可能不同；执行包装保存二者的对应关系，因此模型调用公开名以后，客户端仍向服务器发送原名。

MCP 工具接收参数并执行操作，资源接口按标识读取材料。客户端分别发现并调用这些能力。跨 Session 记忆还需要服务保存信息，并在后续 Session 中提供相应查询。

12.2 沿一个任务看完整流程

假设服务 A 通过 stdio 提供 search 工具。客户端启动配置指定的进程、建立连接、获取完整工具列表，再构造公开名称并更新注册代次。代次标识本次连接及其工具注册结果。模型调用公开名称后，请求经过本地 ToolRuntime；执行包装使用服务器原工具名，将参数、取消信号与超时配置传入远端调用。

服务 B 使用 Streamable HTTP 时，客户端连接它的 URL；服务 A 的 stdio 则由本机子进程承载。两者发现的工具都接入本地 ToolRuntime。更新时先准备完整定义，准备失败保留旧注册；开始交换后若新注册失败，客户端撤销本轮已注册项，结果是该服务器没有工具注册。

远端工具返回内容后，本地包装按输出契约整理，再交给 Session。资源能力通过独立接口发现和读取。检索算法由服务器实现：子字符串查询匹配原文是否含查询词，向量检索则按 embedding 相似度选择材料。

12.3 关键机制与设计取舍

外部工具复用原工具链

图 12A 从 MCP 连接与工具发现开始，经过公开名称包装和本地注册，再进入模型调用与远端执行。本地 ToolRuntime 继续处理准入、取消和结果。

连接、发现与代次交换

MCP 客户端按配置建立连接，并同步该连接代次的工具列表。代次标识一轮连接及其注册结果。同步分两阶段：先获取完整列表并构建所有定义，此时保留旧注册；准备成功后撤销旧注册，再逐项注册新定义。新注册发生冲突时，代码撤销本轮已注册项，使该服务器留下零项工具；严格启动同步继续抛错，普通同步记录错误并返回空注册表。

工具公开名采用 mcp__服务名__原工具名 的命名形式。简单有效名称直接拼接，非法字符和过长名称经过规范化与哈希处理。哈希把输入映射成较短标识，执行包装仍保存服务器原名，用于发送远端调用。

包装定义将远端参数 schema、说明和执行函数接到 ToolRuntime。模型调用公开名，参数经过本地准入与执行链，再由包装层向服务器原名发起调用。返回的模型文本与结构化内容按输出契约处理；资源插件另行提供资源发现和读取。

连接与知识能力的基础区别

客户端发起请求，服务端提供协议能力，远程调用在进程或网络之间传递参数与结果。MCP 规定这层交互协议。RAG（Retrieval-Augmented Generation，检索增强生成）先检索相关材料，再将材料加入模型上下文，例如检索项目文档后生成总结。协议接入和检索生成分别解决通信与信息组织问题。

Memory 服务的存储与查询实现决定是否支持 embedding、语义检索和跨 Session 记忆。embedding 将文本编码为用于相似度比较的向量，第 8 章已有介绍。本项目的 Memory MCP 指南提供可选第三方服务的接入方式，其中 Reference Memory 采用子字符串查询；相关能力通过对应服务配置启用。

继续使用该工具前，还要检查一次实际调用结果、调用许可与结果质量。以协议接入可以复用成熟链路，代价是多了外部可用性、超时、版本和返回契约问题。

“用了 MCP 就做了 RAG”：协议接入与检索生成方法是不同层次。

“服务连上就知道它的全部资料”：需要能力发现和具体读取；连接本身不提供全文。

13.1 基本概念

实现详解

进程内 fork 为子 Agent 选择初始历史，completedTurnPrefix 负责确定这份种子。它先获取父 Session 当前事件数组的快照，再从末尾寻找最近的 turn/end。这个结束标记给出已经完成轮次的边界，使子任务能够从包含完整轮次结算的历史起点开始。

找到结束事件后，函数从数组开头截取到该事件，并把结束事件本身包含在结果中。Session 的追加契约让 seq 与数组下标对应，而 slice 的结束位置不包含在返回范围内，所以使用 lastEnd.seq+1。例如最后一个 turn/end 的 seq 为 20，返回位置 0—20，共 21 项；位置 21 以后的事件全部留在父 Session。

没有 turn/end 时返回空数组，子任务以空历史种子开始。存在完成轮次时，种子包含从位置 0 起的整个事件前缀，涵盖消息、工具调用、结果和边界记录。该函数按位置切片，保留前缀中的历史表示及其关联，后续创建流程再据此建立新的子 Session。

第 14 章｜Web Client：任务提交与状态同步

14.1 基本概念

网页交互至少有两条信息流：用户向宿主提交任务，宿主把后续变化送回页面。远程调用（RPC）让页面请求另一执行环境执行操作；它这次返回的是接纳结果。持续跟随则让页面在任务推进期间获取变化。

本地回显在请求完成前显示用户输入，提供即时交互反馈。输入此时保存在客户端 pending 状态，Host 接纳后生成正式记录。requestId 关联这两种表示，使客户端能够协调状态并避免重复显示。

快照描述某个位置的已知状态，游标指出后续消费从哪个位置推进。持久事件有序号，助手临时流是尚在生成中的变化。跟随过程在准备快照前安装监听与缓冲，可以保留准备期间发生的事件。

Host 的 follow 按序号发送事件：略过旧事件，发送符合预期的下一项，发现缺口则报错并结束这次流。客户端的历史来源管理与控制流重连分别处理历史和状态，下一节说明两条路径。

14.2 沿一个任务看完整流程

用户发送消息后，客户端先创建 pending 记录并显示输入。附件处理完成后，客户端发出带 requestId 的 prompt 请求，Host 接纳后返回回执。后续跟随流提供正式用户消息，客户端根据 requestId 协调 pending 与正式记录，避免重复显示。

基线是已知时点的完整状态，增量是此后发生的变化。订阅登记后续事件的接收关系，缓冲保存尚待处理的事件，监听器响应事件通知。快照与增量结合，持续维护客户端的 Session 镜像。

另一条链路获取快照与后续变化。假设下一预期序号是 41，而缓冲收到 39、41、43：39 为过去的重复记录被略过；41 正常消费后预期更新为 42；43 暴露序号缺口，无法作为 42 消费。Host 跟随生成器因此抛出 gateway/internal 错误。

页面刷新后，客户端重新获取快照，再接收后续变化。已提交的助手消息从 Session 记录恢复；正在生成的文字通过启用的助手临时流观察。页面不更新时，沿提交、接纳、跟随、客户端状态和视图订阅逐项定位。

“提交函数返回成功就是最终回答”：其契约仍然是接纳；连续过程走跟随链。

“刷新会把所有临时片段逐字恢复”：临时流与持久事实的保存方式不同。

“有序号就一定无损恢复”：序号能检查连续性，恢复还要由实际协议与客户端路径完成。

阅读任务：这是跟随消费循环内的节选，item 是当前缓冲事件，nextOffset 是下一个需要的位置。yield 是把一项结果交给流的消费者，后续可再继续生成下一项。

实现详解

Host 的 follow 先提供快照，再从缓冲队列消费后续变化。nextOffset 表示下一个等待的持久事件位置，初始值由快照游标加 1 得到。本段处理缓冲中的 Session 事件；助手临时流使用另一类条目和序号判断，在此前的分支处理。持久历史的连续性由 Session 的 seq 检查。

当前事件比 expectedSeq 小时，说明它位于已知或已消费位置，循环跳过这项。安装监听、准备快照和读取缓冲之间可以覆盖到同一事件，跳过旧项能避免重复交付。当前事件等于 expectedSeq 时，通过连续性检查，nextOffset 先增加 1，再把事件转换成协议条目，通过 yield 交给流的消费方。

当前事件大于 expectedSeq 时，Host 抛出 gateway/internal，错误说明缺少的序号，当前跟随流终止。它没有把较大的序号当成连续事件继续发送，因为消费方可能依赖中间事实才能正确更新状态。外层 finally 撤销事件及临时流监听，移除取消处理，收尾这次订阅。

例如快照游标为 40，预期接收 41。缓冲先给出 39，Host 略过；收到 41 后发送它，预期推进为 42；随后给出 43，就报告缺少 42。客户端用收到的快照和连续增量更新 Session 镜像，再由视图订阅刷新页面。历史来源替换与投影控制流重连各有自己的客户端流程，本段承担的工作是检查并交付这次跟随中的连续持久事件。

15.1 基本概念

桌面版通过 Electron 承载 Web 客户端。Renderer 运行页面，Main 管理窗口与应用生命周期，preload 向页面暴露受控桌面接口。Harness 后端服务运行在独立的 Node Host 子进程中，由 Main 管理其启动与退出。

进程是操作系统管理的一次程序运行，有自己的内存与生命周期。进程间通信（IPC）传递启动和退出等消息；聊天业务继续使用网页客户端的请求与持续流。HTTP 组织请求和响应，WebSocket 提供持续双向通道；它们与启动 IPC 各自解决不同问题。

第 16 章｜测试、模型回放与行为验证

本章学习任务：理解按位置消费的模型回放，区分调用轨迹检查、请求断言与真实任务评价。

16.1 基本概念

测试将预期行为表达为可检查的条件。断言规定必须满足的关系，例如失败模型尝试中的工具提议不得进入执行阶段。替身替代选定依赖，回放则用预录制响应替代模型生成，所选的真实循环和工具链继续处理这些响应。

本项目的 LLM 回放按 Session 绑定响应脚本，再按调用位置选择条目。新 Session 绑定下一份脚本，每次模型调用消费下一项响应。响应选择的依据是调用序号，请求字段的正确性由测试中的独立断言检查。

脚本在本章指一个录制 Session 的响应清单，每个条目对应一次模型调用。消费检查发现脚本没有绑定或条目没有用完；请求次数超出清单时也会报错。消费检查验证调用次数与脚本绑定。请求内容、工具动作和最终产物分别用对应断言检查。

固定模型输出减少一种变化来源，不固定操作系统文件、时间、并发调度和远端工具的全部行为。回放时使用哪些文件和工具，由测试 profile 与替身配置决定。

16.2 沿一个任务看完整流程

设录制脚本有两个响应：第一项提出 read，第二项生成总结。当前 Session 第一次请求获取第 0 项，第二次获取第 1 项，游标变成 2。只发一次请求时有条目未消费；第三次请求时脚本耗尽。消费检查帮助发现轨迹变化。

位置回放按调用序号返回响应，即使请求上下文存在错误，第一次调用仍会消费第 0 项。验证材料组装时，需要同时断言实际请求中的消息、工具定义和参数。

一个故障测试需要给出触发条件与观察点。例如，构造失败 finish，检查驱动是否记录 attempt、是否执行工具。评价模型总结质量则使用任务集和新生成的产物，按相同要求检查遗漏与错误。

E16A · 消费按位置推进

阅读任务：本段在 replay 已依据 Session 找到或建立绑定状态之后。state 保存该 Session 的脚本数组和游标；重点看这次选择响应的依据。后续生成器（可逐个产出值并暂停的函数，配合 yield，见附录）负责脚本耗尽等错误。

实现详解

模型回放为实际运行的每个 Session 绑定一份响应脚本，再按该 Session 的调用位置消费条目。进入这段代码前，replay 已查找绑定状态；首次出现的 Session 领取下一份录制脚本，后续调用沿用自己的 entries 和 cursor。多个 Session 因而分别推进各自的响应序列。

本次调用先保留 boundState，并捕获已绑定脚本数与脚本总数，供后面的错误消息说明录制范围。随后取 cursor 的旧值作为 index，再把 cursor 增加 1，用 index 读取 entries。cursor=0 时选择第 0 项，下一次选择第 1 项。位置在返回生成器之前已经推进，后面的响应消费沿本次选中的 entry 继续。

entry 允许为空，因为实际请求次数可能超过录制条目数。返回的异步生成器检查未录制 Session 和脚本耗尽情况，并给出要求重新录制的错误；合法条目经过必要的标识与消息相关处理，再逐项产出响应。选择哪一项的核心依据仍是调用位置，请求中的完整上下文是否符合预期要由测试断言检查。

例如一份脚本录制“先提出 read，再生成总结”两项响应，实际两次模型调用依次取得这两项；只调用一次时，assertConsumed 发现还有条目未消费；第三次调用时，生成器报告脚本耗尽。即使首次请求漏了项目规则，位置选择仍能取得第 0 项，因此验证提示组装时，还要检查实际 messages、工具定义和参数。响应回放与请求断言合作，分别检查轨迹和输入内容。

第 17 章｜任务评价、TokenMeter 与遥测

本章学习任务：区分 token 估计、Provider 用量和计费口径，联合分析任务质量、耗时与失败。

17.1 基本概念

评价由任务正确性规则和资源统计共同组成。质量描述产物满足要求的程度，耗时记录指定起点至终点的时间，用量统计请求、token 和工具调用等资源，失败记录保存未正常完成样本的原因。先明确任务要求，再按照统一口径采集这些指标。

计量记录或估算资源数量，遥测向观测系统输出运行信息。投影从事件维护用量与上下文状态，导出后端负责传输。TokenMeter 管理用量和容量统计，业务规则判断产物是否正确，费用依据 Provider 报告的计费类别与用量计算。

比较需要保持任务集、版本、模型选择和验收规则一致，再改变一个明确因素。通过率是通过数除以全部样本数；百分点是两个百分比的直接差，区别于相对增幅。平均数反映所有纳入样本的算术平均，中位数反映排序后的中间位置，失败样本怎样处理要先写清。

本章用一组十项任务的示例，说明怎样把质量、耗时和用量放在一起比较。

17.2 沿一个任务看完整流程

假设同一组十项任务，甲通过九项、消耗 20000 token；乙通过八项、消耗 14000 token。乙用量少了 30%，通过率却从 90% 降到 80%，差 10 个百分点。两种方案的取舍是用量下降、通过率也下降。

对每个任务同时记录输入标识、配置、产物、验收、接纳与终态时间、用量来源和失败原因。成功、失败与取消都保留；缺失数据不能填成零。费用按相应计费类别的用量乘单价求和，正式实验时再核验单价与缓存口径。

TokenMeter 注册用量、压力和材料组成投影，Session 遥测汇集事件并传入导出后端。业务评价将这些过程记录与产物检查关联。例如读取失败时，准确说明资料不足可以满足任务要求；读取成功时，再检查用途和功能总结是否有充分依据。

17.3 关键机制与设计取舍

一次任务的三组记录

图 17A 的三栏记录过程时间、用量次数、质量与失败。每条任务记录共用任务身份，成功、失败和取消都进入统计。

TokenMeter 和遥测怎样提供运行数据

TokenMeter 注册三项投影，投影是从事件计算并持续更新的统计视图。tokenUsage 记录请求用量，contextPressure 估算上下文压力，contextBreakdown 展示材料组成。压力计算使用当前 Surface、请求信息和模型路由；符合复用条件时采用 Provider 用量，否则使用本地估计。界面同时展示数值与来源。

Session 遥测协调器观察生命周期、事件和 flush，将选定记录交给导出后端。OTel 即 OpenTelemetry，提供遥测接口；项目后端支持按需捕获和反馈触发等配置。span 记录一段操作的耗时与关联，任务评分则使用产物检查规则。

质量检查是课程另外设计的实验层：README 总结是否准确说明用途、三点是否各有材料依据、是否保留关键限制、是否编造功能。先定义规则，之后才能计算通过率。

比例、单位和控制变量

通过率＝通过任务数÷全部任务数。平均耗时是所有相应样本耗时的算术平均，中位数则是排序后的中间位置。先说明失败时用哪个耗时、是否单独报告，才谈两项统计。

比较配置甲与乙时保持输入任务集、版本、模型选择、验收规则和预算一致，记录变更项、重复次数和实验环境。若模型与任务同时变了，不能把比例变化全部归因于某个提示词。

成本按明确计费类别求和：总成本 = Σ(该类别用量 × 对应单价)。单价、缓存口径和计费单位在真正实验时核验，缓存输入、普通输入和输出各按自己的单价计算。

E17A · 三项计量视图的注册

阅读任务：节选是 TokenMeter 构造时的投影注册。register 保存计算与读取定义，消费者后续查询和事件更新驱动具体统计。三项注册分别对应用量、上下文压力与材料组成。

18.1 基本概念

扩展点是框架允许新增能力的位置，例如工具注册接口。接口契约既规定输入输出，也规定怎样处理生命周期、取消和结果。一个新能力复用这些位置，才能进入现有流程；插件通过 profile 挂载并注入依赖，工具定义才进入运行中的注册表。

规范值是执行体返回的结构化数据，供输出契约检查。schema 定义结构，render 生成模型内容，presentationMeta 提取可持久化的展示元数据。模型使用渲染文本，客户端根据原始事件与 meta 派生卡片数据。

真实 read 工具通过已选文件服务获取有界文本，再构造路径、行范围和总行数等结果。模型从渲染文字获取资料，界面从保存的展示元数据重建读取卡片。持久记录保存模型内容和展示元数据；界面恢复时读取这份记录。

本章将启动装配、参数校验、工具准入、文件读取、结果记录与界面呈现串联为同一条调用链。新增工具通过现有扩展接口接入各环节，复用统一的控制与记录机制。

18.2 沿一个任务看完整流程

read 的接入始于 profile 装载文件工具插件。插件声明依赖并注册工具，模型调用提交 file_path、offset 和 limit。ToolRuntime 创建参数 JSON 快照并完成准入；defineTool 的 execute 包装函数随后检查 schema，read 执行体通过 parseReadArgs 补齐缺省值、校验行范围，再调用文件服务读取目标并构造窗口。

执行结果形成规范对象，输出 schema 检查形状，render 生成模型材料，顶层工具调用的 presentationMeta 提取可保存的窗口资料。通用链处理最终结果，循环将 content 和 meta 写入 tool/result。后续模型请求使用 content，Web Client 从原始调用、结果和 meta 生成卡片。

18.4 源码研读

E18A · 卡片资料从规范值派生

阅读任务：这是 read 输出定义中的 presentationMeta 函数属性。value 已是读取规范值，_args 是这里未使用的参数。观察怎样形成可序列化展示对象；模型文本 render 是同一输出定义的另一项职责。

实现详解

read 执行体读取文件并构造窗口后，返回规范值 value，其中包含显示路径、起始行、逐行文本和总行数。输出定义一方面用 render 将这个值转换成模型文本，另一方面用 presentationMeta 提取界面恢复需要的结构化资料。本段实现后一条路径，读取的数据已经取得，函数只根据结果值组织元数据。

元数据保留 path 和 offset，再遍历 value.lines，为每一行建立只含 number 与 text 的对象，最后保留 totalLines。新的行数组使展示结构明确，消费方能够直接知道每行编号和文字。offset 表示本次请求的窗口起点，实际保留行数由 lines 给出，totalLines 表示完整文件行数；即使窗口被字节上限截断，这几项信息仍能共同描述覆盖范围。

langFromPath 根据路径推断语言，能识别时加入 lang，无法识别时省略这个字段。界面可据此选择语法显示方式，逐行内容始终来自实际读取结果。函数的 _args 参数在这里未使用，展示资料从 value 派生，避免将请求行数直接当成已经返回的行数。

例如请求从 README 第 41 行读取 30 行，但结果只保留到第 60 行，meta 会保存 offset=41、20 项带实际编号的行和文件总行数。ToolRuntime 为顶层调用取得这份元数据，驱动随模型 content 一起写入 tool/result。Web Client 再校验原参数、结果和 meta，派生读取卡片；刷新后可以使用已保存资料重建同一窗口，无须再读当前文件。这样模型文本与可恢复的卡片共享读取事实，并各自保留所需形式。

18.5 理解检查与讲解问答

问题 1 · 规范值、模型文本与展示元数据各自有什么用途？

讲解：规范值供契约检查和内部处理，模型文本供模型推理，展示元数据供保存与卡片重建。

问题 2 · 专用卡片失败是否意味着模型一定没收到文本？

讲解：Host 将规范结果渲染成模型文本，并为顶层调用保存窗口 meta。Web Client 从原始事件派生卡片；readCardModel 不接受当前数据时，工具行显示原始输出，模型仍使用已保存的文本。

问题 3 · 新增工具只写 execute 是否足够？

讲解：不够。还要完成注册、参数与输出契约、准入配合、取消和资源生命周期。

第 19 章｜Cordis 与 Spatiotemporal Composability

本章从资源登记、依赖变化和插件卸载三个问题出发，讲解 Cordis 的 Spatiotemporal Composability。先用定时器和工具注册理解机制，再把它们与论文的定义和生命周期规则对应起来。

论文是 A Programming Paradigm for Spatiotemporal Composability，作者 Yifan Shi、Wei Zhang、Tianyi Cui，本文采用 arXiv:2608.25512 的 v1（2026-08-26）。实现采用固定项目快照里的 @deepseek-ai/cordis 4.0.4。下面先解释论文模型，再说明 Cordis 4.0.4 的实现方式。

19.1 组件替换与资源释放

假设文件工具插件装入时做两件事：注册 read，监听文件观察事件。模型于是能够使用工具，其他组件也能收到观察通知。后来配置改变，要换成另一份实现。如果只把插件名字从列表删除，旧监听器可能继续接收通知，旧工具也可能留在注册表；重新装入又登记一次，便会出现重复响应或旧对象继续被访问。

组件生命周期同时管理能力启用与贡献撤销。effect 是操作对状态产生的改变，例如注册事件监听器；disposer 是释放该贡献的函数，例如移除本次注册的监听器；inverse 描述对应的逆操作，用于恢复操作前的状态。

read 插件还依赖文件服务。提供者撤销服务后，消费者要重新检查依赖，退出当前实例或等待新的服务。服务名称标识可解析的能力，依赖声明列出装入前需要可用的入口。

论文把这两个问题放在一起：时间方向上，组件的贡献怎样撤回；空间方向上，组件怎样在当前 Context 中获取依赖并随环境变化重新装配。这就是 Spatiotemporal Composability：时间方向上的可撤回与空间方向上的依赖组合。空间维度指服务的组织和解析关系。

19.2 可逆操作与恢复见证

设状态 S 表示工具集合，组件 A 装入前为 {read}，操作 f 将其变为 {read, search}。f 同时提供逆操作 g，g 只移除 A 注册的 search，于是 g(f(S)) = S。这个关系要求逆操作恢复本次操作对应的输入状态。

这里的“状态”是数学模型描述的数据，“函数”是从旧状态得到新状态的规则。论文的 witnessed effect function 不仅返回新状态，还返回一项逆操作，并要求逆操作确实恢复其对应输入；Definition 8 给出这项见证条件。witnessed 表示函数附带满足该等式的数学见证。实现中的 ctx.effect 保存 disposer，组件作者负责让它满足恢复条件。

disposer（释放函数）通过闭包保留资源身份。闭包由函数及其引用的外层变量组成，例如清理函数捕获本次创建的 timer 句柄，卸载时据此停止对应定时器。资源创建时登记释放函数，使资源获取与撤销始终保持明确对应。

释放动作由组件作者编写。以定时器为例，disposer 要记住创建时得到的 timer 句柄，并调用 clearInterval 停止它；只打印“已清理”不会停止定时器。论文 §5.1.1 将逆操作的正确性交给组件作者，Cordis 运行时负责登记和调用。文件写入、邮件发送等外部动作，则要由作者按对应服务的实际能力设计后续处理。

图 19A 从左向右展示资源交接：作者获取资源，返回记住这份资源的 disposer；Cordis 将它登记到当前 Fiber，卸载时调用作者提供的动作。

19.3 逆操作的组合与释放顺序

若组件先申请资源 A，再基于 A 创建资源 B，释放时应先清理 B，再释放 A，以保留 B 清理所需的依赖。LIFO（Last-In-First-Out，后进先出）描述这种顺序：后创建的依赖资源先撤销。

论文把每一步返回的逆操作接到已有恢复动作之前，形成反向组合。effect iterator 让装入逐步推进；迭代器每次给出下一项，并说明是否结束。运行时因此可以在步骤之间记录进度、检查目标状态，决定继续装入还是进入撤离。

论文的反向组合、一个 ctx.effect 内的多步恢复、Fiber 上多个 effect 的释放采用不同组织方式。当前 Fiber._unload 用 Promise.all 等待同层释放任务，多个异步 disposer 会重叠运行。有严格依赖的两项清理，应写在同一个 disposer 中依次 await：先撤资源 B，再撤资源 A。

框架捕获并记录单项释放错误，其他释放任务继续推进。排查时，可以从错误记录找到所属实例和释放位置，再检查该项动作停在了哪里。

19.4 环境要求：coeffect、服务键与依赖

coeffect 描述组件执行需要从环境获取什么，例如文件服务；effect 描述执行对状态造成什么改变，例如注册工具。服务 key 是用于识别和解析某项能力的名称或标识。提供者发布该键下的能力，消费者声明自己需要它，Context 根据当前范围解析到实际实现。

理解一个组件时，可以依次查看它声明的依赖、提供的服务和装入行为。插件声明描述依赖，服务提供操作登记能力，Fiber 管理这次装入产生的资源。

例如插件 T 需要 tools 和 fs。tools 让它登记工具，fs 让它实现读取。只有依赖条件成立，运行时才推进该实例的装入。fs 的提供者撤去服务时，运行时通知相关消费者重新评价目标状态；它们需要退出当前装配或等待新的满足条件的环境。

响应式依赖使环境变化触发实例的目标状态更新。依赖注入通过统一接口解析服务提供者。实例创建的连接、监听器和后台任务经资源管理接口登记，对应 disposer 随实例卸载被调用。

19.5 Fiber 与生命周期：目标变化时怎样收尾

Fiber 是组件的一次运行实例及其生命周期管理对象。每个 Fiber 保存自己的配置、依赖状态和释放动作。相同组件装入多次，可以有不同的 Context、配置、资源记录和状态；讨论清理时要指明是哪一个实例。

论文 §4 用抽象状态和转换规则研究装入、已激活、撤离等过程。论文中的 Reloading 包含推进装入的情形；论文用四类抽象状态表达规则；FiberState 枚举进一步区分运行时状态。实现与官方教程还区分 PENDING、FAILED、DISPOSED 等状态，用于表达依赖未满足、装入失败和实例终结。

装入正在等待连接建立时，配置可能改变。惯性原则要求先完成当前这一步，把结果与 disposer 交给框架，再决定继续装入还是撤回。资源由此及时进入清理记录。若外部操作迟迟不返回，这一步就一直等待；组件要在资源操作中配置超时或取消处理。

依赖撤离时还存在提供者与消费者的顺序问题。消费者的清理可能需要向提供者归还资源。论文的守卫演算通过等待关系限制过早回收，形式化讨论“提供者比它的消费者活得更久”的条件。

当前 Reflect.provide 的释放函数先从公共服务存储撤销入口，通知依赖实例，等待相关 Fiber，再清掉本实例保留的服务入口。这项 disposer 内部按上述顺序等待。Fiber 同层的其他 disposer 仍并发运行；需要消费者先退出才能释放的资源，应与该等待组织在同一受控释放流程中。

19.6 操作独立性与安全卸载

交换律表示先做 A 再做 B，与先做 B 再做 A，得到同样结果。设 A 登记自己的键 a，B 登记另一个键 b。若两项操作都只改变自己的独立槽位，最终集合可以相同。若两项都修改一个顺序敏感的中间件（请求依次经过的一串处理环节）列表，先后就可能改变请求经过的规则。

Definition 42 要求正向、撤回以及相关变换都满足独立性，并保持对方返回的逆操作与后续迭代。检查两次注册能否交换，只覆盖其中一部分；还要检查卸载 A 时，B 的贡献和后续运行是否保持。

考虑一种有缺陷的释放方式：A 注册前保存整个工具集合，B 随后注册另一项工具，A 卸载时用旧副本替换当前集合。这样会连同 B 的合法贡献一起删除。释放逻辑应识别并移除本实例注册的条目。存在重名、覆盖、排序或共享资源时，还需检查替换与撤销规则是否保持独立性。

这解释了为什么论文讨论服务提供者的责任：它发布的操作采用怎样的表示，直接影响其他组件能否独立撤回。服务提供者在设计注册和撤销规则时，就要处理这些独立性条件。

19.7 观测等价与证明条件

观测等价表示按指定的合法观察方式，看不到会影响契约的差别。相同工具集合不要求内存地址、分配顺序或运行时缓存逐字节相同。观察关系由模型规定；网络请求和外部设备写入则有它们自己的可观察状态。

论文 §3.3 通过观察关系界定状态相等的用途，§3.4 再讨论独立性与恢复。证明按这样的顺序展开：先规定状态、操作和观察；写下可逆和依赖条件；再证明满足条件的系统可怎样组合与撤回。

Theorem 73 的推进结果假设依赖先行关系无环、迭代长度有统一有限上界、整个序列涉及的实例名称有限，并且每一步遵守生命周期规则。无环意味着依赖箭头不会从某个组件绕回它自己。在这些条件下，论文给出没有规则层死锁以及有限推进到静止状态（不再有待推进的步骤）的结论。

例如 A 等 B、B 又等 A，构成依赖环，已经不满足 Theorem 73 的无环条件。这个例子说明，依赖图和步骤长度是推进定理本身的组成部分。

19.8 服务作用域与模块热重载

ctx.isolate(name, label) 为指定服务名建立新的解析标签，得到派生 Context。默认新标签使该名称在子范围中可以解析到另一项实现；相同标签可以让多个范围共享该服务解析空间。这些 Context 仍处于同一 JavaScript 宿主中，共享进程资源。

图 19B 先看两个 Context，再看右侧服务实现。派生箭头表示建立子 Context，解析箭头表示按服务标签找到实现。Context 乙为指定服务名使用新标签，其他服务继续沿继承关系解析；两个 Context 共用同一个宿主进程。

19.9 源码研读

E19A · 作者提供资源释放逻辑

阅读任务：这是仓库官方 Cordis 教程中 heartbeat 的 effect 片段。观察定时器句柄怎样进入释放函数，以及 Cordis 怎样获得这项动作。

实现详解

官方教程用 heartbeat 插件说明资源获取与释放怎样成对登记。插件装入时调用 ctx.effect，并传入一个获取资源的函数。这个函数创建定时器，每 200 毫秒输出一次 tick，将得到的 timer 句柄保存在当前调用的局部变量中。句柄标识本次创建的定时器，后面的清理函数依靠它定位资源。

获取函数随后返回另一项函数，作为 disposer 交给 Cordis。这个返回动作只交付释放逻辑，定时器继续运行；Cordis 将 disposer 记入所属 Fiber 的资源集合。释放函数通过闭包保留 timer，所以获取函数结束后，后续清理仍能访问正确句柄。

插件卸载时，框架调用已登记的 disposer。它先用 clearInterval(timer) 停止本次定时器，再输出 heartbeat cleaned up，供教程观察清理确已发生。同一插件的其他实例各有自己的 timer 和闭包，卸载一份实例时沿对应登记清理这份资源。热重载使用同样的生命周期路径撤销旧实例贡献，再推进新实例。

这个例子把责任分成两个相连的部分：组件作者提供正确的获取与释放操作，Cordis 保存对应关系并在实例退出时调用。论文中的恢复条件要求逆操作恢复相应输入状态；这里的具体恢复由 clearInterval 实现。注册 read 或事件监听时，也需要保留本次登记的身份，使释放只撤销这份贡献。资源创建、句柄捕获、disposer 登记与卸载调用共同构成可追踪的生命周期。

E19B · 服务名称作用域隔离

阅读任务：Context.isolate 为 name 指定的服务名称设置解析标签。可选 label 用于让多个 Context 共享同一服务作用域，返回值是携带新解析表的派生 Context。

实现详解

Context.isolate 为指定服务名建立派生的解析范围。Context 内的隔离表保存“服务名到 Symbol 标签”的关系，服务读写按标签选择实现。方法接收 name，指定哪项服务使用新的范围；可选 label 决定是否复用已有标签。返回值是派生 Context，调用方随后可在它下面挂载插件或提供服务。

方法先建立继承当前隔离表的新表，再只为 name 设置标签。查找其他服务时，新表仍沿继承关系取得父范围的标签，所以局部改动不影响其他名称。设置新表也不改写原 Context 的隔离表，父范围继续使用原来的服务解析关系。

缺省 label 时，每次 Symbol(name) 都生成新的唯一身份，即使两次的 name 相同，标签仍不同。显式传入同一个 Symbol 时，多个派生 Context 使用同一标签，可以共享这项服务的解析空间。例如为 fs 分别创建两项新标签，可以在两个子范围提供不同文件服务；复用同一 label 则把它们接到同一个 fs 解析范围。

extend 将新表放进派生 Context，服务名称的读取和提供由后续操作沿这张表解析。这个方法自身只建立解析标签，没有创建文件 Provider 或启动子进程。各 Context 仍位于同一宿主中；profile 与插件装配决定每个标签下实际提供的实现，文件与进程服务负责资源访问。把服务名、解析标签和实际实现分开，就能理解插件树为什么可以在局部范围替换同名能力。

代码类型：真实源码摘录。证据编号 E19B；下表的数字是原文件行号。

    return this.extend({ [symbols.isolate]: shadow })
  }

E19C · 同层资源释放并发等待

阅读任务：节选位于 Fiber._unload 的资源释放阶段。_disposables 保存当前 Fiber 的释放函数，Promise.all 等待各项异步清理，每项有独立的异常记录。后续流程清理 store 并更新实例状态。

实现详解

Fiber._unload 负责释放这个插件实例登记的资源，再清理实例存储并推进生命周期状态。本段先从 _disposables 取出整组释放动作，同时清空登记集合，让这次卸载处理明确的一组资源。每个释放动作都由作者或注册 API 提供，框架通过 runDisposable 实际调用它。

代码把每一项映射成异步任务，再用 Promise.all 等待整组收尾。各任务之间能够重叠推进，结束顺序由实际等待决定。例如移除监听器很快完成，关闭网络连接需要等待，前者可以先结束；整个卸载仍等待连接清理返回。若某项释放一直不结束，统一等待也无法完成，因此资源操作内部要具备相应的超时或取消处理。

每项任务有独立的 try/catch，并通过 composeError 组织诊断信息。调用释放动作之前先经过一个异步等待点，再记录本次错误位置；失败时结合外层调用信息写入日志。某项释放报错后，它的处理路径结束，其他释放任务继续收尾。这里使用的 Promise.all 汇总的是这些带独立错误处理的任务。

所有任务结束后，后续代码清空 store，再按目标状态决定保持未激活或重新装入。具有严格依赖的清理应在同一个 disposer 中按顺序等待：例如先停止仍会访问连接的后台任务，再关闭连接。同层两个 disposer 分别启动时，不会因为登记顺序就保证前一项完全结束。实例资源集合、独立错误记录和整组等待共同说明一次卸载怎样从开始走到状态更新。

19.10 理解检查与讲解问答

问题 1：框架能够调用释放函数，为什么不等于保证释放正确？

讲解：登记把 disposer 与当前 Fiber 联系起来，卸载时框架调用它。以定时器为例，作者必须在 disposer 内调用 clearInterval，并传入本次创建的句柄。论文的见证条件要求恢复原状态；运行时的登记与调用实现资源管理，具体恢复动作由作者完成。

问题 2：同层两个异步释放函数，能否只靠登记顺序保证第一个完全结束后第二个才开始？

讲解：_unload 将同层释放函数映射成异步任务，再用 Promise.all 汇总等待。后启动的任务可以先结束。有先后依赖时，在同一个 disposer 中依次 await。

问题 3：把插件放入 ctx.isolate 后，能否运行不可信代码而无须其他隔离？

讲解：ctx.isolate 调整服务名称的解析标签，派生 Context 与原 Context 仍共享宿主进程。不可信组件的运行需要独立设计执行隔离、桥接接口与资源访问限制。

追问：怎样向别人准确讲述 Cordis 的价值？

Cordis 把插件组织成声明依赖、登记资源、响应环境变化并释放贡献的运行实例。Context 解析服务，Fiber 管理实例状态，effect 保存资源与 disposer 的对应关系。论文解释这些机制需要满足的可逆性和独立性条件，源码给出装入、撤离与依赖通知的具体执行方式。
