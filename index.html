第 1 章｜从一句话到一个结果：DeepSeek Harness 究竟做什么

本章学习任务：沿读取 README 的案例，说明谁接纳任务、谁调用模型、谁读取文件、谁保存结果；区分工具提议、接纳回执与任务完成。

01.1 基本概念

计算机程序是一组交给计算机执行的步骤；数据是步骤处理的信息，例如一段任务文字或一份文件内容。大语言模型（Large Language Model，LLM）接收材料、生成文字或工具调用建议。运行模型的服务与管理本地文件的程序是不同的参与者。模型提出读取建议，文件服务实际读取，再把结果交给模型用于后续回答。

Agent 在本书中指能够围绕任务反复获取材料、调用模型并使用工具的运行单元。Harness 组织这些步骤，DeepSeek Harness 是本书研究的具体项目。Tool 是由程序实现的一项操作，像 read 读取文本；模型看到的是工具的名称、用途和参数说明。参数是告诉操作“这次处理什么”的输入，例如文件路径；结果是操作返回的信息，例如第 1—20 行文字。

Session 保存一次持续交互的身份和记录。日志是按发生顺序保存的记录集合；Session 事件日志因此能回答“先发生了什么，随后发生了什么”。消息是供对话使用的内容；事件是“某件事已经发生”的记录，例如开始一次工具调用。消息内容参与对话，轮次开始、工具调用等事件记录运行过程。Inbox 保存已经接纳、尚待领取的输入；它把下一轮输入与下一步输入分开保存，由驱动在对应时点领取。

请求是向另一方提出的操作要求，例如“为这个 Session 接纳一段文字”。请求标识用来识别同一次提交，防止重复排队。客户端发起请求并接收结果，例如网页界面；Host 提供并处理项目能力。入口先返回接纳回执，后台任务随后继续运行。

附件是随文字一同提交的文件或图像等材料；只有文字时不需要附件。后文会解释附件如何进入请求。

上下文是本次请求提供给模型使用的材料，例如任务文字、行为规则和已读到的文件。system prompt 是用于向模型表达系统行为规则的那部分文字；模型根据这段文字生成回答；文件访问由工具链和文件服务控制。

这条流程有六位参与者：用户、接纳入口、Agent 驱动、LLM 服务、ToolRuntime 和 Session。接纳入口收下任务，驱动安排步骤，LLM 服务调用模型，ToolRuntime 组织工具执行，Session 保存过程与结果。

对照短源码还会用到几个基础词：函数封装一组可调用步骤，变量给值取名，对象把相关字段放在一起，属性是对象的一项字段，返回值是函数交给调用者的结果，类型说明值应有什么形状。第 2 章会用真实写法展开它们。

01.2 沿一个任务看完整流程

先看成功路径：用户要求“读取 README，概括项目用途和三项功能”。用户提交一句话，入口建立消息并排入 Inbox，返回“已接纳”。驱动领取输入，组装第一次模型请求；模型提出读取建议。工具服务记录调用，按安全规则判断是否放行，这一步称为准入。获准后，文件服务读取文本。工具结果进入 Session，第二次请求才有这些文字可用。模型生成总结，驱动记录轮次结束，界面显示结果。

入口先检查是否有文字或附件，两者都没有就拒绝接纳。接纳以后若文件不存在，工具返回错误，后续请求可据此解释资料不足或选择其他目标。模型请求失败时，驱动先记录失败，再由恢复策略决定是否重试；工具阶段等待成功响应。这个案例的主循环包含两次相互依赖的请求：第一次提出读取，第二次使用读取结果。主循环就是驱动反复执行“请求模型—执行工具—再请求”的过程。

01.3 关键机制与设计取舍

先看材料怎样流动

图 01A 按箭头展示成功路径：接纳任务、模型提出 read、文件服务返回窗口、下一次请求使用结果，再生成总结。第一次请求负责提出读取，第二次请求负责利用读到的文本。

  1. 用户提交任务，入口把消息放入 Inbox，返回接纳回执。
  2. 驱动组装第一次请求。模型提出 Tool Call，指定 read 和参数 { file_path: "README.md" }。花括号里的“名称—值”组合称为对象，这里保存本次读取的路径。
  3. ToolRuntime 完成准入，执行包装函数检查参数，再由文件服务读取目标。
  4. 工具结果记录到 Session；驱动组装第二次请求，把已获取的文件窗口交给模型。
  5. 模型根据这些文字生成总结，驱动记录轮次结束，界面显示结果。

01.5 理解检查与讲解问答

问题 1 · 入口返回 accepted 后，能说已经读完 README 吗？

讲解：不能。这里只确认输入已接纳。还要经过领取、模型提议、准入与读取，才有文件结果。

问题 2 · 模型给出了三点总结，怎样检查它依据了文件？

讲解：先找到 read 的调用记录和成功结果，确认返回的行范围覆盖总结所用的材料，再逐项对照总结与原文。这样才能把总结中的结论追到实际读取结果。

问题 3 · 第一次模型请求与第二次请求的材料有什么差别？

讲解：成功案例的第二次请求增加了读取结果。它依赖前面的真实执行，不是独立重复同一份输入。

第 2 章｜读懂代码：类型与异步等待

本章学习任务：认出值、对象、函数和类型的基本写法；解释一次 await 等待的结果，并区分注册回调、调用回调和后台完成。

02.1 基本概念

先把程序里的信息和动作拆开。变量是给一项值取的名字，例如 path 保存路径文字。字符串是文字值；数字可以表示起始行号；布尔值只有真和假。对象把相关信息放在一起，例如一份读取请求同时保存路径、起始行和行数。属性是对象中的一项信息，request.content 表示请求的内容属性。数组按位置保存多项值，例如多行文本；位置通常从 0 开始，文件行号却常从 1 开始，两个口径不能混用。

函数把一组步骤包装成可以调用的操作。参数是调用者交给函数的值，返回值是函数返回的值。方法是属于某个对象的函数；agent.followup(message) 表示让这个 Agent 的方法处理消息。类描述一类对象的结构和操作，实际创建出来的对象叫实例。接口和类型说明规定数据形状，例如路径应是字符串。文件是否存在，要等文件服务访问目标时检查。

TypeScript 在 JavaScript 的写法上增加类型说明。const 固定变量绑定，let 允许重新赋值；对象内部仍可能变化。冒号后面通常是类型，问号表示可缺省，return 把值返回调用者，throw 使当前路径失败。花括号既可能围住对象，也可能围住一组语句，要看它的位置。模块是单独组织代码的文件；import 引入别的模块，export 让别处能够使用本模块的名称。

Promise 表示一项异步操作的结果，可以处于等待中、成功或失败状态。async 方法返回 Promise，await 暂停这个方法的后续部分，等待该结果；其他工作可以继续推进。进程是操作系统管理的一次程序运行，线程是进程内一条执行指令的路径。等待期间，JavaScript 运行时可以执行其他已经就绪的工作。并发是多项工作可以交错推进，并行是同一时刻用多个执行资源处理多项工作；多个操作怎样交错，取决于它们的启动与等待顺序。回调是交给别处、等特定时机再调用的函数，例如收到事件后更新记录。以后看到 () => ...，先问谁会在什么时候调用它，而不是把它当成已经执行的结果。

JavaScript 是运行这些步骤的语言；TypeScript 的类型检查帮助在执行前发现写法与数据形状的问题。程序真正运行时，输入是否合法、资源是否可用仍要由实际代码检查。运行时的事件循环会处理已准备的工作并恢复后续执行；等待外部读取时，当前方法暂停，其他已准备工作仍可推进。

await prompt(...) 等待提交回执。接纳方法校验请求内容，把消息交给 Agent，再返回接纳对象。调用方拿到回执后可以继续工作；Agent 驱动继续处理任务，最终总结通过持续观察通道送回界面。

注册工具时，程序把名称、参数说明和执行函数交给注册表。执行函数此时作为一个值保存，具体调用到来时才运行。箭头函数、对象方法和事件回调都要区分定义与调用。要让两个异步操作重叠，可以先分别启动，再用 Promise.all 汇总结果。全部成功时，它按传入顺序返回结果数组；任一项失败时，汇总的 Promise 就失败，其他已启动操作仍按各自流程收尾。

容易混淆的地方

“async 使函数内部所有动作并行”：连续写两个 await 时，第二个操作要等第一个返回后才开始。先启动两个操作、再汇总它们的 Promise，才给它们提供重叠推进的机会。

“类型合法就不会失败”：类型不能证明文件存在、网络可达或权限获准；运行时检查依然必要。

“工具对象里有 execute，所以启动已执行”：对象属性可以是一段尚未调用的函数。要追保存与调用位置。

02.5 理解检查与讲解问答

问题 1 · await 一个方法，是否等于等待整个用户任务完成？

讲解：由方法返回契约决定。等待接纳方法只获取回执；等待读取方法才获取读取结果。

问题 2 · 注册对象里写了 execute 函数，为什么没有立即读文件？

讲解：注册只是保存函数值与说明。后来发生具体工具调用时，框架才调用执行函数。

问题 3 · 类型说路径是字符串，是否证明文件存在？

讲解：没有。类型说明数据形状，文件存在、权限和读取成功需要运行时检查。

第 3 章｜循环与消息队列：一轮任务为什么需要多步

本章学习任务：追踪一个输入怎样被领取、怎样进入轮次和步骤；比较 followup 与 steer，并解释工具执行与结果提交的顺序。

03.1 基本概念

轮次（turn）是驱动围绕一批输入推进的一段过程；步骤（step）是轮次里的一个推进单元；尝试（attempt）是该步骤中一次模型请求的执行。读取 README 后继续总结，可以是同一轮次的两个步骤。第一次请求失败、恢复策略允许再请求，则是同一步骤中的另一次尝试，而不是再收到一次用户任务。

状态是某个时刻保存的信息，例如待处理消息有哪些、当前轮次编号是多少。状态转换说明一件事发生后这些信息怎样改变。驱动是负责持续推进转换的程序。取消信号是可被执行代码检查的停止请求；接到信号后，执行代码停止后续工作，并等待已经启动的操作收尾。

Inbox 分别保存 next-turn 和 next-step 输入。followup 放入前者，steer 放入后者。进入下一步骤时，驱动领取全部 next-step 输入；开启下一轮时，再把一项 next-turn 输入接到这批材料后面。因此，较晚到来的引导可以先被领取，较早排队的另一项普通任务仍在等待。领取以后还要经过前置判断，允许进入本步才发起模型请求。

由此可以分别问：输入有没有接纳、有没有被领取、模型请求是否成功、工具是否执行、轮次以什么原因结束。这些问题各自对应不同记录，不能用一个“成功”替代。

03.3 关键机制与设计取舍

三层边界

图 03A 外框是一轮任务，内框是两个步骤。第一步有失败和重试两次尝试，第二步有一次成功尝试，因此这条轨迹包含一个 turn、两个 step、三个 attempt。

turn、step 和 attempt 分别统计任务推进的三个层次。前置拒绝时，一轮没有进入模型步骤；读取后总结可以用两个步骤；某一步请求失败后又可以重试。驱动在成功消息提交后提取工具调用；失败尝试的 partial 是尚未成功完成的输出，先进入失败记录与恢复流程。

Inbox 怎样与驱动合作

Inbox 保存尚未领取的输入。followup 排入下一轮并请求唤醒；steer 排入下一步并请求唤醒；inject 也排入下一步，由后续驱动活动领取。选择哪种入口，决定输入何时进入处理以及是否启动驱动。

空闲时，需要唤醒的输入让驱动启动。已有活跃驱动时，新输入由现有驱动在约定边界领取。维护期间，唤醒请求先记在 wakeRequested 中，由维护任务收尾时检查是否启动驱动。这里把正在进行的一次运行称为活动。若活动已收到取消信号，send 会把需要唤醒的输入改排到 next-turn，等待原活动收尾后再处理。

普通运行路径中，驱动开放轮次，准备下一步，领取消息并组装材料。前置决定可能允许进入或拒绝。进入后发起模型请求，成功消息有工具调用则进入工具批次；工具结果回到 Session 历史。驱动再看停止原因与下一步输入，决定继续或结束。

工具执行能重叠，结果仍按模型顺序提交

把贯穿案例稍作教学扩展：模型在同一消息里先提出读取 README 的调用 A，再提出读取包信息的调用 B。要同时说明三个顺序：提议的排列、真实动作的完成先后，以及结果进入 Session 的顺序。三个顺序不必相同。S02 对照本节执行器。

执行器先按模型排列建立计划，给每项保存调用身份、工具名、解析后的参数、所属 Agent 和取消信号。然后查询当前工具的执行模式：允许交错执行的调用可以进入有数量上限的池；需要独占的调用形成屏障，让当前池排空后再处理。池是保存正在执行操作的集合，屏障是在这里要求前面的执行先收尾的边界。

启动每一项时，先记下 tool/call 及其序号，再等待这一项的前置准备。准备可能已经形成拒绝结果，也可能允许分派真实执行；前置准备按顺序推进，实际分派与工具体才可能重叠。拒绝结果同样要在相应位置进入结果链，不能把“未执行”理解为“没有结果记录”。

假设 A、B 均允许重叠、数量上限足够，B 较早读完。执行器先把 B 的结果放到自己的结果槽里。槽是按调用位置保存结果的临时位置；B 放在位置 1，A 在位置 0。提交位置仍停在 0，因此不能跳过 A 先把 B 提交到 Session。A 完成后，执行器才依次进行 A、B 的结果后处理，记录各自结果，并把额外上下文交给下一步骤的材料批次。

取消与调度失败又是不同分支。取消会停止启动新动作，让已开始的执行收尾并按顺序交接；未开始的模型调用会得到表示跳过的合成结果。合成结果是框架生成的说明，没有对应真实工具动作。调度失败时，执行器等待已分派动作收尾，再把错误返回当前步骤。

按顺序提交让历史与模型提议容易对应，允许执行重叠则可以利用独立工作的等待时间。执行器为此维护并发池、结果槽和提交位置。B 虽然先完成，仍要等待 A 提交；下一步模型按原提议顺序读取结果。

队列与状态机的最小基础

队列保存“还有哪些输入等待处理”，状态机记录“当前运行在哪个阶段”。新消息入队后，正在执行的请求继续使用原材料；驱动到下一领取时点，才把待处理输入加入后续请求。

事件通知让关注这些变化的观察者（例如界面或记录组件）知道队列或状态变了。DSH（DeepSeek Harness 的缩写）Inbox 变更先更新可观察状态，再通知监听者，因此监听者可以在通知里查询新状态。

ReactLoopAgent 是核心运行驱动。它管理 Inbox、turn、step、模型请求和取消；网页端的 React 组件负责显示这些运行状态。

“下一步输入会立刻打断当前模型流”：next-step 指定下一次领取的位置。当前请求继续执行；取消则通过独立信号要求它停止。

“结果按顺序记录，所以工具肯定串行执行”：工具的实际执行部分（工具体）可能同时跑多个，而准备、后处理和最终提交有顺序约束。

“出现 turn/start 就花费一次模型请求”：前置拒绝或初始空输入可能没有进入步骤。

第 5 章｜Session 与日志：发生过的事怎样保存和还原

本章学习任务：说明事件怎样从当前 Session 进入记录和存储；区别 append、flush、重放与派生视图，判断崩溃时哪些事实已有持久证据。

05.1 基本概念

Session 事件日志按顺序记录消息、工具调用和运行边界。终端调试输出属于另一条输出通道。序号说明事件在 Session 中的位置；时间记录发生时刻，序号决定事件顺序和连续性。

快照是在某个时刻获取的一份数据副本；冻结让已经建立的对象不能再被直接改写。派生是从事实计算另一种数据，例如从消息类事件形成模型历史。投影是按特定问题整理状态，例如当前有哪些待办。快照保留某个时刻的数据，派生生成新的数据形式，投影持续维护某项业务状态。

可序列化表示数据能够按约定转成可保存或传输的形式，例如对象中的字符串与数字可形成 JSON，带任意函数的运行对象则不能直接当作同样的事实数据。冻结是限制对象修改，不是把它写到存储。缓存是保存已经算过的结果供后续复用，例如消息派生结果；原始记录变化后要使相关缓存失效。

持久化把运行内存中的资料交给能够在退出后保留它的存储。JSON 是表示对象、数组等值的文本格式；JSONL 每行保存一个 JSON 记录。追加事件首先改变 Session 内的历史，并通知订阅者；JSONL Provider 把写入排队。flush 等待存储 Provider 排空缓冲并完成写入。Session.append 更新内存日志，存储 writer.append 才执行持久写入。

Session 恢复还原已经记录的对话和运行过程；文件当前内容由文件服务读取，外部进程状态由进程 Provider 查询。

05.3 关键机制与设计取舍

一份事实，多个消费方

图 05A 由 Session 事件分出三个用途：模型历史按 Surface 派生，界面和状态投影消费过程事件，存储监听器排队写入持久记录。

持久日志保存已追加的底层过程事件，模型消息则由当前 Surface 派生。Surface 是参与组装下次模型请求的消息节点序列，规定哪些消息按什么顺序进入请求。Surface 管理器根据事件维护这份序列。生成途中的流式文本片段仍是临时观察；循环正式提交助手消息后，该消息才成为可交给持久化 Provider 处理的记录。提交使消息进入 Session 内存日志，flush 则等待存储写入完成。

append 怎样建立一个事实

Session.append 先创建可序列化的数据副本，再构造带序号和时间的冻结条目。可序列化表示数据能按约定转换成保存格式。接着，方法校验事件字段，并检查 Surface 约束：这条事件是否符合当前消息序列的更新规则。两项校验通过后，事件进入日志并发布。副本与冻结共同防止调用者后来修改原对象时改变已记录的历史。

随后 Session 发布该事实，消费方依各自接口更新或排队处理。消息派生 deriveMessages 遍历当前 Surface 中的消息节点，生成新的消息数组。状态投影则按注册的事件消费规则维护可查询状态。消息视图处理消息节点，状态投影处理各自关心的过程事件。

DSH 的 JSONL Provider 为每个 Session 管理一条写入通道，称为写入句柄。它监听 session/event，将新条目排入后台缓冲；收到 session/flush 后，先等待缓冲排空，再等待 writer.flush 完成。Session 通过事件通知存储，存储组件负责实际文件读写。

投影和持久化屏障

投影可理解为“按用途整理事实”。给定同一份订单记录，可以整理出当前状态，也可以整理出明细清单；软件里同理。Session 投影同样按各自的事件规则更新结果。

JSONL 的持久化链分为两层：实时监听器先把事件放进缓冲，writer.append 再按序写入文件并调用文件同步。session/flush 先等待 drainLive 排空实时缓冲，再等待 writer.flush；尚未写入事件的空 Session 会在此创建并同步头记录。文件追加或同步失败时，存储层关闭追加句柄，再把文件截回本批写入前的长度并同步，随后抛出原错误。若回退也失败，就用 AggregateError 同时报告写入错误与回退错误。成功回退后，本批可以按未推进的游标重试。

教学片段有一条用户消息、两条助手消息和一条工具结果，另有一条工具调用、两项轮次边界和四项步骤边界，共 11 个列出的事件。这里得到的消息数是 4，工具调用数是 1，日志片段事件数是 11；三个值回答不同问题。

写入时间线与故障判断

图 05B 对比 append 返回和 flush 等待。append 完成 Session 内追加与通知，flush 等待存储监听器排空并完成写入；后台写入从接到通知时就可以开始。

回到读取任务：用户输入、助手工具提议、工具调用、工具结果、助手总结和轮次边界依次进入事件序列。消息视图组织后续请求，页面更新显示，存储 Provider 写入文件。页面已经显示而写入失败时，问题出在存储链；刷新后临时文字消失时，先查它是否曾被提交为助手消息，再查对应事件是否写入文件。

常见误解

“日志里每一项都发给模型”：消息派生只处理相应的消息节点，过程边界另有用途。

“可从日志还原，所以视图必须与原日志相同”：派生视图可以按用途选择、组合和更新；压缩会在第八章进一步改变当前 Surface。

“页面显示了，所以已经保存到磁盘”：界面与存储分别消费事件。查看存储写入和 flush 的结果，才能确定对应记录是否已保存。

第 6 章｜提示词与项目指令：下一次模型输入怎样形成

本章学习任务：追踪目录中的指令怎样被发现、组合与加入模型请求；解释指令的适用范围，以及文字规则与执行权限的区别。

06.1 基本概念

一次模型请求不是只发送用户刚打出的那句话。上下文指这一次推理能够使用的材料，包括行为规则、当前输入、历史内容和工具说明。提示词是作为材料发送给模型的文字指示；system prompt 是其中用于表达系统规则的部分，用户消息、项目指令和工具结果各自保留来源。

注册是先把某项贡献交给管理者保存，组装才是在请求需要时取出可见贡献形成材料。作用域回答贡献对谁可见；同名覆盖回答同一位置有多个版本时选择谁；排序回答不同贡献按什么顺序出现。这三件事分别决定请求内容。

项目指令描述工作区和当前文件路径相关的规则。每次模型请求前，项目指令插件先选择规则文件，将内容整理成指令消息，再与待处理输入一起进入本步。历史则从 Session 的 Surface 派生，随后与这些新材料汇合。

请求冻结为正在执行的请求固定数据副本。新输入、插件变化或压缩仍可影响下一次组装，但不能倒回去改已经提交的这一份请求。这解释了为什么引导消息要等下一步骤生效。

06.2 沿一个任务看完整流程

以“总结 README，但保留实验性功能的限制”为例，用户目标是一条来源明确的消息。system prompt 贡献说明行为规则，工具贡献说明 read 怎样调用，历史提供先前已经获取的材料；工作区指令再依据当前范围补充约束。

组装器先决定哪些贡献在当前作用域可见，再解决同名项和顺序问题。前置指令处理会清掉不再需要的待处理指令，并把这次需要的指令放入本步消息批次。用户消息在首次尝试登记，重试不再重复登记它；请求创建后获取独立配置副本。

若请求执行期间用户补充“只总结正式功能”，这句话先进入下一步输入。当前请求仍使用原来的固定材料；下一步骤重新领取并组装，才有新要求。若之后发生压缩，后续历史视图可能变化，但已经在途的请求仍不变。检查材料缺失时，应分别查可见贡献、前置消息、历史 Surface 和实际请求，而不是只在某个大字符串里找一句话。

06.3 关键机制与设计取舍

材料有不同的入口

图 06A 的三路材料汇入本步请求：SystemPrompt 组装提示贡献，项目指令形成前置消息，Session 历史按 Surface 派生。它们分别保留自己的来源和排列规则。

system prompt 通常描述运行方式和工具使用等约束。运行时上下文提供当时环境材料，例如当前时间、工作目录或刚读取过的文件路径。项目指令描述工作区规则。用户消息提出当前目标，工具结果给出已获取事实。知道每类材料从哪里来，才能检查冲突、遗漏与重复。

从贡献到请求冻结

插件用 SystemPrompt.section 注册具名提示段，用 context 注册动态上下文。每项贡献带有作用域。同名项先选择当前 Agent 更近的作用域，再按服务规定的顺序排列。完整提示段另有自己的选择规则。SystemPrompt 服务根据这些规则组装本步提示词。

驱动在前置步骤领取输入，调用 assemble 得到组装结果，并把运行时上下文投影成适合本步的材料。随后进入 agent/pre-step 链。这是一串按顺序执行的前置检查关卡，决定本步是否继续，以及哪些消息进入本次请求。项目指令插件在这条链上等待相关投影就绪，再按工作区与触及路径整理指令。触及路径就是本次任务接触过的文件路径，用来确定要加载哪些目录下的规则文件。插件把选中的指令整理成上下文消息，插入将要进入步骤的批次。

进入步骤后，框架准备模型调用，记录需要的系统消息、首次进入的用户消息和请求信息，再派生并冻结请求。冻结意味着这次请求的内容不能被稍后修改的共享对象悄悄改变，下一步重新组装消息和上下文。

顺序与作用域的基础

贡献类似多个人填写同一份请求资料，但合并规则由系统决定。每项至少要有身份、范围和位置：身份帮助替换或去重，范围决定谁可见，位置决定有序组装。

消息同时保存内容与来源。项目指令来自规则文件，用户需求来自提交入口，工具结果来自执行链。框架按这些来源组织消息；一段文字里出现“系统提醒”，不会改变它原有的消息类别。

分析示例：重复材料占了多少空间

“更长的提示词必定更可靠”：长度只描述材料体积。冲突、重复和是否被正确执行仍要检查。

“冻结一次请求就冻结整个 Session”：冻结保护本次材料；下一步可读取新消息、工具结果或新的 Surface 状态。

第 7 章｜Skill 的按需读取：目录可见为什么不等于正文已加载

本章学习任务：区分 Skill 目录、Skill 正文与已经执行的动作；说明按需加载怎样增加材料，以及为什么加载 Skill 不等于注册新工具。

07.1 基本概念

Skill 把一项做事方法整理成说明和相关资源，例如“如何分析某类项目”。目录摘要帮助模型知道有哪些方法，正文才说明具体步骤。模型先通过摘要选择 Skill，再获取正文。

Skill 服务负责发现、列出和读取定义，skill 工具让模型按名称获取正文。调用权限分别声明是否允许用户调用、是否允许模型调用；读取入口按相应标志检查。目录可见性用于发现候选，调用标志决定能否从这一入口加载。

加载是实际获取正文并形成可供模型使用的内容，不是装上一个新的操作系统权限。正文可以指导模型组合已有工具，但工具仍受自己的注册、准入和执行边界约束。用户显式指定 Skill 与模型主动选择 Skill，进入材料的路径也不同。

需要区分三个观察点：目录是否包含名称，读取是否获取定义，正文是否进入本次请求。排查“它没有按 Skill 做事”时，先找这三个证据，再评价正文的方法是否清楚。

07.2 沿一个任务看完整流程

假设目录里出现 report-skill，摘要说它用于整理技术报告。模型先根据摘要判断有用，再调用 Skill 读取工具。工具根据当前工作目录、Agent 范围和取消信号获取目录，找到名称以后检查它是否允许模型调用；通过后再获取完整定义。

若目录里的定义已经移除，查询不到名称就报错；名称仍可见但禁止模型调用时，工具返回入口限制错误。获取正文以后，框架把它整理成模型材料，后续模型请求便能使用其中的方法。

用户显式调用的入口会检查用户可调用条件，符合时才建立 Skill 调用来源的指令消息。未知名称和不符合条件的文字不会都被解释为命令。正文中的方法通过后续模型推理与工具调用落实。

图 07A 沿模型调用路径展开：发现候选、发布摘要、选中名称、检查模型调用许可、获取正文。正文作为工具结果记录，随后进入下一次模型请求。

注册表与 Provider 分别负责什么

SkillRegistry 管理可见 Provider 和候选。文件系统 Provider 负责从相应目录发现 Skill 并读文件内容。list 返回摘要列表；get 按名称选择候选；同名项依次按 Provider 优先级、Provider 顺序和本地顺序取舍，把候选定位信息返回对应 Provider 读取，再校验完整定义。这使消费方不必固定绑定某个文件目录实现。

工具插件在前置步骤把当前 Agent 可调用的 Skill 目录写成持久提示消息。目录包含名称与说明，正文按需读取。目录发生变化时，插件发布替换消息；发现过程不完整时，保留已有目录。模型调用 skill 后，执行体检查名称、可见摘要和模型调用标志，再获取完整定义并返回正文。

用户直接调用走另一条路径。前置步骤检查直接用户消息第一行的 /<name>，名称存在且允许用户调用时，加载正文并注入本步消息。模型调用 skill 工具则把正文记录为工具结果，供后续步骤使用。消息来源与调用标志决定这两条路径各自何时生效。

按需读取不等于权限授权

按需读取是到需要时再获取内容。Skill 正文是材料，可以指导做事，但读取它不会自动增加文件、网络或发布权限。工具是否可用、动作是否获准和运行环境怎样限制，仍有独立控制层。

目录摘要帮助选择 Skill，正文提供步骤、参数和限制。例如“用于文档整理”只说明用途，具体怎样整理要在加载正文后确定。Provider 读取失败、名称消失或入口禁止调用时，工具返回对应错误。

第 8 章｜上下文压缩：让历史变短需要付出什么

本章学习任务：说明上下文为何有容量限制，哪些历史可被压缩，哪些事实需要保留；比较摘要、检索、token 估计与真正的语义搜索。

08.1 基本概念

模型一次请求可容纳的材料有容量限制。token 是模型处理文字时使用的编码单位，tokenizer 把文字编码成 token，词数、汉字数和 token 数分别统计。上下文压力把当前材料的 token 计量与模型容量比较。TokenMeter 分别记录本地估计和可复用的 Provider 用量信息。

压缩（compaction）将选定历史改成较短表示，供后续请求使用。例如，把十次文件调查整理成“已读哪些文件、得到什么结论、还缺什么”。原始事件留在日志中，当前 Surface 则使用摘要表示这段历史。

压缩不是无损编码：摘要可能遗漏细节。选区要保持工具调用与结果成对，并保留最近一段历史。选择边界时检查配对平衡；仍未关闭的步骤留在选区外，而不是交给摘要补造缺失结果。稳定性检查确认准备摘要期间，相关依赖没有变化到使旧摘要失效。提交是把准备好的结果正式纳入 Session 视图的动作，区别于仍在生成中的草稿。

另有裁剪和 spill：裁剪移除选定可省略内容，spill 把长内容放到存储并返回取回入口。三者都能缩短当前请求，却改变了不同东西，不能用同一个“压缩掉了”概括。

08.2 沿一个任务看完整流程

假设本轮准备请求时材料接近容量，压缩插件在前置步骤测量压力、选择可处理的历史范围、生成较短表示。若选不到范围，就没有压缩结果；若范围可处理，生成期间仍要保持关联条件，提交前再次检查稳定性。

流程先追加 compaction/start，在请求摘要前建立压缩锁。摘要通过稳定性检查后，代码依次记录 compaction/summary、替换 Surface 的检查点消息和 compaction/end。开始以后的失败会进入收尾分支，尝试追加一次结束事件；结束事件本身失败时，未配对的开始标记继续占用锁。已追加的记录保留在 Session 中，错误按 summary 或 commit 阶段报告。自动压力钩子捕获错误、记录警告后继续前置链；上下文溢出恢复则按策略裁剪、重新计量并选择范围。

用一个小例子检查信息损失：原文写“功能 X 是实验性的，只在某后端提供”，摘要若只保留“有功能 X”，字数更少却改变了约束。比较前后应该检查任务仍需要的结论、来源、未完成事项和调用关联。缩短材料为后续请求腾出容量，摘要中的功能范围则决定模型能否准确回答。

08.3 关键机制与设计取舍

同一历史的两种形态

图 08A 左侧保存原始事件，右侧展示当前 Surface。压缩在 Surface 上用摘要替换选中区域；原始消息、调用和压缩过程记录继续留在日志里。

触发条件与压缩主链

基本压缩插件有两个自动入口：前置步骤检测上下文压力，以及请求恢复链处理 Provider 确认的上下文溢出。compactIfNeeded 先检查目标、策略和计量状态。压力入口根据模型容量计算阈值，未达到阈值就返回；选不到安全区域时，也返回而不请求摘要。

选区确定后，流程检查 Surface 范围和压缩事务状态。事务在这里指由开始、摘要、替换消息和结束标记组织的一次压缩流程。开始标记先建立锁，摘要返回后再检查选区稳定性，通过后按顺序追加提交记录。选区发生冲突时，稳定性检查抛错，流程转入失败收尾。

前置压力压缩失败时，插件记录警告，驱动继续原有前置链。上下文溢出恢复由目标策略和次数上限决定是否再尝试。手工压缩通过维护阶段预留驱动，检查空闲状态与取消信号，并在结束标记追加后等待存储 flush。

逻辑视图和信息保留

Surface 可以理解为当前需要呈现给模型的消息节点集合。历史事实记录发生过什么，Surface 选择当前怎样表示这些事实，两者职责不同。摘要以较短文字保留重点，细节和原文措辞会被省略。项目名、限制条件、路径和未完成事项往往比普通叙述更需要保留。

长期记忆通过存取和检索把其他任务的材料带回请求；compaction 调整当前 Session 的历史表示。语义检索中的 embedding 把文字编码为用于相似度比较的数字向量，第 12 章再介绍这类外部服务。

分析示例：长度与额外成本分开算

第 9 章｜流式输出与重试：一次失败怎样留在同一步里

本章学习任务：追踪模型路由、请求准备、流式结果与重试；说明哪些内容能进入后续工具阶段，哪些失败仍需单独处理。

09.1 基本概念

流式响应不是一条立即得到的完整回答，而是一段段到达的数据。一个片段可以是文字、工具调用信息、用量或结束信息，循环持续收集片段，直到收到 finish 或消费抛错。适配器把特定模型服务的交互转成项目统一接口；Provider 指提供这项能力的接入方，Provider 与模型选择决定这次请求实际交给谁。

限流是服务限制一段时间里可接收的请求数量；超时是等待超过规定边界。它们都可能产生失败，但恢复方式由策略决定。

重试是在某次执行失败后重新尝试。恢复策略决定哪些失败可以重试，以及要作哪些准备；agent/request-error 链返回 retry 时，循环才发起下一次尝试。失败尝试产生的临时内容可以被观察，但不能直接作为成功助手消息执行其中的工具提议。

请求先解析模型路由和配置，再获取流并消费片段。流正常结束后，驱动检查 finish：成功则提交助手消息，错误或中止则记录失败尝试并询问恢复链。消费过程中直接抛出的异常走 catch 分支，结算已开始的尝试后继续抛出；这一分支与 finish 携带失败状态的恢复入口分开。

当 finish.kind 为 max-tokens 时，循环先提交已经生成的助手消息，再返回 max-tokens 结束原因，跳过该消息的工具执行。这里达到的是当前请求的输出上限，与上下文过长触发的压缩恢复分开处理。

09.2 沿一个任务看完整流程

假设第一次尝试先到达文字片段，再收到失败终结。临时流可供界面显示进度；循环记录失败事实，向恢复链交出失败类型、模型 Provider、重试策略和取消信号。如果恢复链没有返回 retry，抛出对应模型错误；返回 retry 才进入下一次尝试。

到达的内容循环处理能否进入工具执行
正在生成的片段更新临时流状态先显示临时进展
失败尝试的工具提议记录尝试失败并走恢复不走成功工具阶段
成功终结的助手消息建立消息并提取工具调用再交给通用准入链

重试并没有重新接纳一次用户任务。已经登记的用户输入不应重复追加；请求准备也保持对应的配置语义。每次重试重新准备调用，恢复处理可以改变后续请求配置。turn 和 step 保持不变，attempt 增加。

09.3 关键机制与设计取舍

临时输出与最终事实

图 09A 把临时输出和正式提交分开：片段先更新界面，finish 决定成功、失败或取消，循环再记录助手消息或失败尝试。完成且未达到 max-tokens 的消息才进入工具调用判断。

一次调用怎样绑定 Provider

LLM 服务的 prepareCall 按 provider 标识查找适配器，解析目标模型与配置，返回绑定这次调用的 prepared call。它保存冻结配置与重试策略，且只能分派一次。每次重试重新准备调用，适配器将具体服务的响应转换成统一流。

DeepSeek 适配器把响应转换成异步片段，并组合取消信号。空闲监测统计等待新片段的时间，超出阈值就产生超时错误。超时、取消和传输失败分别分类；结束时停止消费，并尝试关闭逐项提供片段的迭代器。关闭失败作为诊断信息保留。

驱动用 for await 消费片段，逐次检查取消信号并推送临时输出。正常终结生成助手消息并记录；符合请求错误恢复流程的失败先记录尝试，再经 agent/request-error 链决定是否重试。没有 retry 决定时抛出 LlmError；已取消时由取消信号结束等待。

异步迭代的够用基础

Promise 是将来的一次结果，异步可迭代对象则是分次到来的序列：for await 每轮向它索取下一个片段，拿到就处理，取完为止。例如一条流依次交出文字甲、文字乙和结束信息，循环不是一次拿到三项，而是先等待甲并处理，再等待乙并处理，最后依据结束信息判断完成。

for await 每次等待下一个片段，直到迭代器结束。驱动随后读取 finish，确定这次响应怎样结算。取消信号沿驱动和适配器传递，各层在检查到取消后停止后续消费，并进入连接清理。

分析示例：重试等待算在哪里

教学轨迹为第一次尝试用时 400 ms 后失败，退避等待 300 ms（退避：失败后先等待一段时间再重试的策略），第二次尝试用时 700 ms 后成功。不计其他开销，模型阶段共 400＋300＋700＝1400 ms，其中请求尝试时间 1100 ms，等待时间 300 ms，尝试数 2。

若用户在退避等待中取消，流程在第二次尝试开始前结束，此时只有一次请求。重试能够重新处理临时故障，也会增加等待和用量；Provider 与恢复插件共同决定重试策略。

失败、取消与成功走不同出口

图 09B 左侧展示可重试失败的处理，右侧列出成功和取消出口。失败记录 attempt 后等待恢复；取消时，有保留文本就提交 interrupted 消息，无文本就记录 attempt。

回到 README 任务：第一次模型流失败，符合策略则在本步重试；第二次成功给出读取调用，才进入工具执行。文件结果进入下一步，总结成功后再检查产物。这样避免把失败输出的工具提议当成已准备用来执行的动作。

常见误解

“每个 chunk 都是一条助手消息”：片段属于尝试中的暂态流，最终消息有自己的提交边界。

“重试只是再次发送同一函数，在哪里都一样”：重试位置决定是否重复材料、工具副作用（对外部世界产生的实际影响，例如写文件）或其他提交。

“取消后保留了文本，所以任务成功”：应检查 interrupted 与结束原因，并另做产物判断。

第 10 章｜插件框架与运行配置：这些部件怎样装成一个应用

本章学习任务：从配置条目说明插件怎样装配、怎样获取所需服务；区别 profile、条目修改与运行实例，并定位热更新的边界。

10.1 基本概念

插件是一份可装入应用的能力实现，例如注册文件工具的模块。配置给出本次采用的参数，profile 选择整组插件及其设置。启动程序按配置装入插件，插件再注册服务、工具和监听器。

依赖指一个部件运行前需要另一项能力，例如文件工具需要工具注册表与文件服务。依赖注入让框架提供这些能力，而不是让每个插件自行创建一份。Context 是 Cordis 用于访问当前可用服务与登记资源的对象。注册和资源清理属于插件生命周期：装入、运行、卸载各自有动作。

条目是一项插件及其设置的记录，补丁描述这次怎样修改这些记录。配置合成规则决定补丁怎样作用到原条目。注册表保存名称与实现等对应关系，让使用者在需要时找到能力。

启动入口先读取运行选择与配置层，再合成条目、加载插件，满足依赖后执行插件的装入函数。函数执行期间注册工具，不表示文件已经读取。条目补丁按 id 定位插件，对补丁中的每个条目字段直接赋值。

热重载在运行时替换符合条件的部件。内部模块可以局部刷新，外部依赖变化则走完整重载路径。Cordis 在卸载时调用已登记的清理函数，例如撤销工具注册或事件监听；第 19 章展开资源登记与释放的机制。

10.2 沿一个任务看完整流程

以文件工具插件为例：配置给出读取上限，启动程序把合成后的条目交给加载器；依赖可用以后执行 apply。apply 检查参数，再注册 read 等工具。此时注册表变了，但磁盘文件没有因注册而被读取。用户任务中出现合法调用，才进入执行函数。

配置层先展平成有序补丁列表。applyEntryPatches 按 id 找条目，再用补丁值覆盖对应字段；config 也是一个整体字段。insert 可以向顶层或指定分组加入条目，新条目随即进入 id 索引，供后续补丁修改。缺少目标、目标不是分组或 name 校验不匹配时，函数记录警告并跳过该补丁。

卸载时，框架处理登记的资源释放。热重载还需分析模块依赖：可替换的内部模块走局部处理，外部依赖变化会设置完整重载并调用退出路径。局部替换先释放旧实例的登记资源，再装入新实例；完整重载交给退出和重启路径处理。

10.3 关键机制与设计取舍

配置层怎样汇合

图 10A 按配置应用顺序排列：bundle、profile patch、用户目录 patch、命令行 patch。最终条目交给加载器，满足依赖的插件完成挂载。

启动到挂载的主链

CLI 是 Command-Line Interface，即通过终端命令与选项操作程序的入口。它解析启动参数，profile 模式进入 runProfile。运行器准备环境，读取组合包和有序补丁，得到 Cordis 配置条目。每个条目保存插件及其设置；多个条目按分组组织成应用树。boot 将树中的插件挂载到应用，插件由此提供服务、工具和事件监听。

消费者通过 Context 访问服务，例如文件工具使用文件服务，循环使用模型服务。Provider 实现服务接口，profile 决定挂载哪一份实现。查看应用树，可以确定当前运行使用哪些包及其配置。

官方架构中的 base 是多种 profile 的共享第一层，而 sdk-minimal 是例外：它的组合包拥有完整显式配置树，不应用 base。不同 profile 对热重载的设置也不同。热重载在可局部替换时使相应变化生效；需要完整重载的情形仍走退出与重新启动路径。

依赖注入与生命周期

依赖注入（dependency injection）让插件声明所需服务，再由配置环境提供。框架在当前作用域解析服务；依赖未满足时，实例等待可用环境，服务注册冲突则进入错误处理。作用域决定插件树中哪些位置可以获取这项服务。

插件从安装到卸载的存续期间称为生命周期。注册产生的副作用通常随插件卸载而撤销，例如移除事件监听或能力声明。事件监听是插件为某类事件登记的响应。撤销这项注册后，插件就不再接收相应通知；插件已发出的网络请求和已写入的文件仍由各自服务处理后续状态。

加载插件时，配置 schema 再为缺省字段应用默认值。若要显式保留 limit: 20，后续 config 中也应写出它。条目覆盖和插件配置解析是两个连续阶段。

图 10B 的三栏是消费者、配置与作用域、Provider。read 调用文件服务接口，配置选出具体实现，Provider 负责路径、读取、取消和错误处理。

第 11 章｜工具准入与审批：允许执行的决定在哪里发生

本章学习任务：沿工具准入、审批、守卫、参数校验与执行追踪一次请求，解释各阶段怎样放行、拒绝或取消。

11.1 基本概念

准入决定某次工具调用是否进入执行体。前置策略可以允许、拒绝、取消或要求审批；审批服务取得本次决定；后续守卫检查额外限制。allowed-once 将许可绑定到这一次审批，后来的调用重新进入准入流程。

守卫的单调性是它只能增加拒绝，不能推翻前置拒绝而提高权限。undefined 表示该守卫不提出拒绝，不等于拥有批准权限。执行环境限制获准动作实际能访问什么；它是否存在操作系统沙箱，以及限制哪些文件或网络，取决于具体 Provider 和配置。

一次调用依次留下调用记录、执行状态和结果。前置拒绝时，框架直接构造拒绝结果；进入执行体后抛错时，已经完成的外部动作按实际情况保留。结果后处理再决定交给模型哪些内容。沿这三个时点，可以分清“没有执行”和“执行后失败”。

这套分工使策略与工具实现能分别扩展，同时增加了排查层次。发生错误时必须找到作出决定的位置，而不是把所有错误都归为“没权限”。

11.2 沿一个任务看完整流程

模型提出读取某路径，循环先登记调用事实。ToolRuntime 建立描述本次调用的执行上下文 exec，进入前置链。拒绝时直接形成拒绝结果；要求审批时，服务记录 asked，等待应答，再记录 decided。允许后继续检查守卫，通过后分派层重新解析执行工具，调用其包装函数。包装函数完成 schema 校验，才进入 read 的读取逻辑。

考虑四项请求：前置拒绝、审批拒绝、允许后成功、允许后抛错。请求数是 4，实际进入执行体是 2，成功结果是 1。最后一项已经进入执行体，失败前发生了哪些动作，要沿执行体内部的调用顺序追踪。

执行体返回后，结果规范化把返回值整理成统一结构，后置策略再决定模型最终收到的内容。若策略替换结果文字，模型会看到替换后的版本；此前完成的读取或修改保留在外部系统中。调用记录、准入决定和执行结果分别解释这次调用怎样推进。

11.3 关键机制与设计取舍

工具体前后都有处理

图 11A 的主线是调用记录、前置决定、可选审批与守卫、执行、结果处理和记录。拒绝支线跳过 execute，再把拒绝结果交给后续处理。

从调用到最终结果

循环先记录工具调用，ToolRuntime 创建执行上下文并检查取消。tools/pre-execute 链返回允许、拒绝、取消或审批请求，策略插件在这条链上作出决定，链尾默认返回 allow。需要审批时，服务向应答者发出询问、记录事实并回传结论。交互界面通常由用户应答，自动化桥接也可以提供机器应答。前置决定为允许时，ToolRuntime 再检查单调守卫。单调指守卫只能否决或原样放行，不能把应拒绝的调用升级为授权。

进入分派后，注册表重新解析可执行工具，融合来自调用方与外层封装的取消信号，再调用真实 execute。执行体返回的规范对象经过成功结果构造；抛错被转成工具错误。之后还有后置处理、内容约束和最终结果通知，循环再按约定顺序记录模型面对的结果。

审批服务在开放轮次内记录 approval/asked 与 approval/decided。开放轮次指已经开始、尚未结束的 turn，这让询问和应答归属到同一轮任务。allowed-once 允许本次审批对应的调用。要求审批时，若缺少审批服务、调用 Agent 或可用应答通道，serviceAsk 返回拒绝。

三种边界分别回答什么

策略回答“这次调用应怎样判定”；审批回答“这次需要的确认结果是什么”；执行环境回答“实际动作可以访问什么”。沙箱（限制程序能访问哪些资源的执行机制）或文件系统守卫提供具体范围限制，但它们不是审批弹窗的另一种名字。

教学上可把它类比为门口决策、一次通行许可与场地围栏。profile 分别选择审批策略和执行 Provider，把这三类控制接入实际调用。

分析示例：请求数与执行数

教学批次有四项已记录工具请求：一项前置拒绝，一项审批拒绝，一项允许且执行成功，一项允许但执行体抛错。请求数 4，实际进入执行体数 2，成功结果数 1。被拒绝的两项没有进入工具体，但仍可能有错误形式的结果。

isError 是工具结果中的错误标志。前两项在执行前被拒绝，后两项已经进入执行体；最后一项在失败前产生了哪些动作，要查看执行体。准入记录说明是否放行，结果记录说明调用怎样结束。

发生拒绝时查前置决定和审批记录；执行体抛错时查文件服务或进程结果；输出错误则查结果校验与渲染。

第 12 章｜外部服务与能力接入：连接成功不等于拥有知识库

本章学习任务：比较 stdio 和 HTTP 接入的参与者与步骤；将连接、能力发现、注册、调用、资源读取和记忆分别列出证据。

12.1 基本概念

Model Context Protocol（MCP）规定客户端怎样与服务端发现能力并交换请求和结果。客户端发起调用，服务端提供能力。协议处理通信与能力发现，具体服务实现存储、检索或其他动作。

标准输入是程序接收外部数据的一条通道，标准输出是程序交出普通结果的通道。stdio 是 standard input/output 的缩写；它用子进程的这两条通道传递协议数据。HTTP（Hypertext Transfer Protocol，超文本传输协议）规定网页与服务请求怎样交换信息，URL 是定位服务的地址。Streamable HTTP 连接服务 URL，可以跨网络，不是本机子进程的另一种写法。连接、能力发现、工具注册和一次调用成功，是四个不同状态。

名称包装让来自不同服务器的工具能进入同一注册表。公开名称和服务器原工具名可能不同；执行包装保存二者的对应关系，因此模型调用公开名以后，客户端仍向服务器发送原名。

MCP 工具接收参数并执行操作，资源接口按标识读取材料。客户端分别发现并调用这些能力。跨 Session 记忆还需要服务保存信息，并在后续 Session 中提供相应查询。

12.2 沿一个任务看完整流程

假设服务 A 通过 stdio 提供一个 search 工具。客户端启动配置指定的进程并建立通信，获取完整工具列表，为它构造公开名称和定义，再交换注册代次（代次：一次连接及其注册结果的版本标记，详见下一节）。模型看到公开名后，调用仍经过本地通用工具链；包装执行体把参数、取消信号和超时交给服务器原工具名。

服务 B 使用 Streamable HTTP 时，客户端连接它的 URL；服务 A 的 stdio 则由本机子进程承载。两者发现的工具都接入本地 ToolRuntime。更新时先准备完整定义，准备失败保留旧注册；开始交换后若新注册失败，客户端撤销本轮已注册项，结果是该服务器没有工具注册。

远端工具返回内容后，本地包装按输出契约整理，再交给 Session。资源能力通过独立接口发现和读取。检索算法由服务器实现：子字符串查询匹配原文是否含查询词，向量检索则按 embedding 相似度选择材料。

12.3 关键机制与设计取舍

外部工具复用原工具链

图 12A 从 MCP 连接与工具发现开始，经过公开名称包装和本地注册，再进入模型调用与远端执行。本地 ToolRuntime 继续处理准入、取消和结果。

连接、发现与代次交换

MCP 客户端按配置建立连接，并同步该连接代次的工具列表。代次标识一轮连接及其注册结果。同步分两阶段：先获取完整列表并构建所有定义，此时保留旧注册；准备成功后撤销旧注册，再逐项注册新定义。新注册发生冲突时，代码撤销本轮已注册项，使该服务器留下零项工具；严格启动同步继续抛错，普通同步记录错误并返回空注册表。

工具公开名采用 mcp__服务名__原工具名 的命名形式。简单有效名称直接拼接，非法字符和过长名称经过规范化与哈希处理。哈希把输入映射成较短标识，执行包装仍保存服务器原名，用于发送远端调用。

包装定义将远端参数 schema、说明和执行函数接到 ToolRuntime。模型调用公开名，参数经过本地准入与执行链，再由包装层向服务器原名发起调用。返回的模型文本与结构化内容按输出契约处理；资源插件另行提供资源发现和读取。

连接与知识能力的基础区别

客户端是发起请求的一方，服务端是提供协议能力的一方；远程调用把参数与结果跨越进程或网络边界。MCP 规定交互方式。RAG 是 Retrieval-Augmented Generation，检索增强生成：先检索与问题有关的材料，再把材料交给模型生成回答。例如先找出相关文档片段，再作总结；它是一种材料组织方法，和通信协议不是同义词。

一个 Memory 服务是否使用 embedding（第 8 章简介：把文字转成可比较相似度的数字向量）、按语义搜索、保存跨 Session 信息，需要看该服务契约。本项目 Memory MCP 指南介绍可选第三方接入，并非默认内置数据库；其中 Reference Memory 按子字符串查询。

第 13 章｜Subagent：拆分任务前先看上下文起点

本章学习任务：说明子 Session 的来源与继承材料，比较 fresh 和 fork；解释子任务完成、团队消息送达与共享文件冲突是不同问题。

13.1 基本概念

Subagent 是父任务启动的另一运行单元，负责一部分工作。父 Agent 交代目标、材料、可用能力和交付要求，子 Agent 完成分工，父 Agent 再检查并整合结果。

fresh 从不继承父历史的材料起点开始，fork 从已有历史的规定前缀开始。进程内 Provider 的 spawn 创建空历史子 Session，fork 截取父 Session 到最近已完成轮次为止的事件。前缀保留开头到该位置的全部记录；当前轮次新增资料由父 Agent 通过启动输入传给子任务。

Subagent Runtime 选择 Provider，检查选项与最大深度，再交给 Provider 创建运行。进程内 Provider 为子任务建立独立 Agent 和 Session，它们与父任务共享宿主进程。这里的 fork 指历史继承方式，子任务仍有自己的驱动和生命周期。

实验性团队功能再增加成员、任务板和消息投递记录。邮箱机制可以安排投递、确认与恢复，但不会因此给共享工作区加文件锁。两个成员修改同一文件，仍需要实际的协调或冲突检查。

13.3 关键机制与设计取舍

两种起点

图 13A 左侧是进程内 spawn：新建子 Session，任务材料显式传入。右侧是进程内 fork：复制父 Session 到最近 turn/end 为止的前缀；没有 turn/end 时种子为空。

从父工具调用到子运行

父 Agent 调用 Subagent 工具后，执行入口先取得实际调用 Agent，再处理模型选项和 Provider 请求。Runtime 管理启动、Provider 查找和契约检查。一次性任务调用 start；后台任务选用支持持续运行的 Provider 时，可调用 startContinuable 接纳输入并返回子 Session 身份。Runtime 检查能力和最大深度，后者限制子任务继续创建子任务的层数。检查通过后，Runtime 建立运行描述并交给 Provider。fresh 与 fork 选择初始材料，start 与 startContinuable 选择运行和交付方式。

进程内 spawn 将空种子交给 startInProcessRun，fork 则先截取父 Session 到最近 turn/end 为止的事件前缀。两种 Provider 复用这份创建流程，为子任务建立新的 Agent 和 Session；子 Agent 接收自己的任务输入，再运行自己的循环。没有已完成轮次时，fork 的种子为空。运行句柄提供结果、取消传递和资源释放。

持续运行的历史起点在创建时捕获，后续继续运行沿用子 Session 已有历史。Provider 的能力契约列明支持的选项，Runtime 在启动前按该契约检查。

并发、进程与历史

多个 Agent 和 Session 可以在同一进程内分别运行，各自保存 Inbox、历史与生命周期。进程内 spawn 和 fork 通过这些对象组织任务；进程、容器和操作系统资源由宿主与执行 Provider 管理。

拆分任务先确定职责，再准备材料。例如一个子任务提取功能，另一个核对限制，父 Agent 最后整合。当前轮次刚读到的 README 尚未进入 fork 的已完成历史前缀，父 Agent 要在启动输入中把这份材料传给子任务。

分析示例：拆分不只计算工作时间

教学单代理需要 1200 ms。拆成两个子任务，各 700 ms；假设允许重叠且确实同时开始，启动与交代开销 200 ms，汇合检查 250 ms，则简化总时间是 200＋max(700,700)＋250＝1150 ms，只减少 50 ms。

若串行执行，则相同假设下为 1850 ms。若结果不一致还需额外处理。因此比较不仅要计执行区间，还要计材料、请求量与汇合质量。

选择任务起点

图 13B 用三栏列出拆分任务的工作：父任务交代目标和材料，子任务运行并返回结果，父任务检查与汇合。时间分析应把这三段一起计入。

父 Agent 收集子结果，检查材料来源和相互矛盾，再形成最终总结。取消子任务时，Runtime 调用对应 Provider 的取消与清理路径，运行句柄返回收尾结果。

第 14 章｜网页端：提交任务与跟随结果是两条链

本章学习任务：把宿主事实、客户端镜像和界面状态分开；追踪初次历史与后续事件怎样共同形成可观察的任务进展。

14.1 基本概念

网页交互至少有两条信息流：用户向宿主提交任务，宿主把后续变化送回页面。远程调用（RPC）让页面请求另一执行环境执行操作；它这次返回的是接纳结果。持续跟随则让页面在任务推进期间获取变化。

本地回显先显示刚输入的内容，使人知道按钮已经响应。它属于客户端待提交状态，不是宿主已经保存的事实。请求标识用于把提交与后续记录关联起来，避免重试或状态协调时把同一输入显示两次。

快照描述某个位置的已知状态，游标指出后续消费从哪个位置推进。持久事件有序号，助手临时流是尚在生成中的变化。跟随过程在准备快照前安装监听与缓冲，可以保留准备期间发生的事件。

Host 的 follow 按序号发送事件：略过旧事件，发送符合预期的下一项，发现缺口则报错并结束这次流。客户端的历史来源管理与控制流重连分别处理历史和状态，下一节说明两条路径。

14.2 沿一个任务看完整流程

用户点击发送后，页面先建立待提交记录并显示本地输入。附件等处理完成，客户端发送带 requestId 的 prompt 请求；宿主接纳后返回回执。页面还要把这项暂态与随后观察到的用户消息协调，避免重复显示。

这里把已存在的完整状态称为基线，把其后新增的变化称为增量。订阅是登记自己要持续接收哪类变化，缓冲是先保存尚未处理的变化；监听器是收到变化以后调用的处理函数。

另一条链获取快照与后续变化。假设下一预期序号是 41，而缓冲收到 39、41、43：39 是已经过去的重复记录，略过；41 正常消费后预期变成 42；43 暴露缺口，不能当作 42 使用。Host 跟随生成器因此抛出 gateway/internal 错误。

页面刷新后，客户端重新获取快照，再接收后续变化。已提交的助手消息从 Session 记录恢复；正在生成的文字通过启用的助手临时流观察。页面不更新时，沿提交、接纳、跟随、客户端状态和视图订阅逐项定位。

14.3 关键机制与设计取舍

两个方向

图 14A 左侧是上行提交，右侧是下行跟随。prompt 返回输入接纳结果，follow 提供初始快照、持久事件和启用的助手临时流，客户端据此更新页面。

发送路径

Session 交互控制器从编辑器取出内容，用 beginSubmission 创建本地 pending 条目，立即显示用户输入。随后处理附件并发出请求；Host 的接纳与消息记录通过另一条通道返回。

15.1 基本概念

桌面版使用 Electron 承载网页产品。Renderer 是显示页面的运行环境；Main 是管理窗口和桌面生命周期的主进程；preload 是给页面提供有限桌面接口的桥。实际 Harness 服务还有独立 Node Host 子进程，因此理解架构不能停在一个三层图。

进程是操作系统管理的一次程序运行，有自己的内存与生命周期。进程间通信（IPC）传递启动和退出等消息；聊天业务继续使用网页客户端的请求与持续流。HTTP 组织请求和响应，WebSocket 提供持续双向通道；它们与启动 IPC 各自解决不同问题。

第 16 章｜测试与回放：复现通过究竟证明了什么

本章学习任务：比较位置回放、工程测试与真实任务评价；解释回放游标怎样消费固定材料，以及它不能证明哪些实际模型效果。

16.1 基本概念

测试把一个判断写成可检查的条件。断言是必须成立的条件，例如“失败模型尝试不执行其中的工具提议”。替身代替一个依赖；回放使用已有响应脚本代替这次模型输出，同时让所选真实循环和工具链继续运行。

本项目 LLM 回放采用按 Session 绑定、按调用位置消费的方式。新 Session 获取下一份录制脚本，每调用一次前进一个位置。它不是把当前请求的全部内容与录制请求逐字段比较后再匹配响应。

脚本在本章指一个录制 Session 的响应清单，每个条目对应一次模型调用。消费检查发现脚本没有绑定或条目没有用完；请求次数超出清单时也会报错。消费检查验证调用次数与脚本绑定。请求内容、工具动作和最终产物分别用对应断言检查。

固定模型输出减少一种变化来源，不固定操作系统文件、时间、并发调度和远端工具的全部行为。回放时使用哪些文件和工具，由测试 profile 与替身配置决定。

16.2 沿一个任务看完整流程

设录制脚本有两个响应：第一项提出 read，第二项生成总结。当前 Session 第一次请求获取第 0 项，第二次获取第 1 项，游标变成 2。只发一次请求时有条目未消费；第三次请求时脚本耗尽。消费检查帮助发现轨迹变化。

位置回放按请求次数返回脚本条目。即使第一次请求组装错了材料，仍会拿到第 0 项响应。测试要另外检查实际请求的字段，才能发现材料组装错误。

新提示词使模型更少遗漏使用新模型输出和统一任务评价

16.3 关键机制与设计取舍

固定一个依赖，继续执行其他部分

图 16A 从录制日志派生响应脚本，把脚本接到 LLM 边界，再运行循环和工具。测试检查实际行为，同时检查响应清单是否完整消费。

证据层怎样选择

单元测试检查局部函数，例如读取窗口；快照测试比较选定输出；回放让固定模型响应驱动真实循环；API 端到端测试连接实际服务，走完整请求链；性能实验记录规定条件下的时间和用量。选择检查方式时，先明确要观察哪个行为。

deriveReplayScript 从事件中恢复响应条目。遇到缺失终结的录制，需要在 replay.override.json 中明确提供覆盖响应，让回放使用明确指定的响应。整个 ReplayEntry 数组替换完整脚本；{ patches } 则在可成功派生的脚本上修改指定位置。installLlmReplay 加载脚本，按 Session 绑定消费位置；接入有两种方式：配置 providers 时注册 ReplayAdapter，在模型 Provider 层面直接顶替真实模型；否则在 llm/stream 边界拦截，请求即将发出时截获并改由脚本应答。

回放的消费检查确认每份脚本都绑定到实际 Session，并且条目全部用完。少一次请求会留下未消费条目，多一次请求会使脚本耗尽。用固定响应定位工程故障时，这些检查可以发现调用轨迹变化。

断言、替身与覆盖范围

断言（assertion）写出要检查的条件，替身（mock）替代某项依赖。检查数组长度为 2，只验证数量；检查元素中的工具名、参数和结果，才验证这些字段。回放固定响应序列，断言决定测试实际检查什么。

一个故障测试需要给出触发条件与观察点。例如，构造失败 finish，检查驱动是否记录 attempt、是否执行工具。评价模型总结质量则使用任务集和新生成的产物，按相同要求检查遗漏与错误。

分析示例：四个命题选四种检查

“行窗口只返回选定范围”可以用窗口单元测试；“失败尝试没有执行工具”可以用固定失败响应驱动真实循环；“实际服务能够完成协议请求”需要 API 测试；“修改提示词后更少遗漏实验性声明”需要同条件的业务任务评价。

若把最后一项改成固定输出回放，输出内容已经由脚本决定，无法评价提示词对真实模型的影响。回放便于定位工程回归（回归：原本正常的行为在修改后被破坏），真实模型评价则使用新输出。

第 17 章｜量化评价：同时看质量、时间、用量与失败

本章学习任务：区别估计 token、Provider 用量和实际计费；为一次任务选择可解释的评价口径，避免把输入变短等同于质量提高。

17.1 基本概念

评价先定义任务怎样算正确，再记录完成这些任务花了什么。质量是产物满足规则的程度；时间是选定起点到选定终点的耗时；用量是请求、token 或工具等资源数量；失败记录说明哪些样本没有正常完成以及原因。

计量是记录或估算数量，遥测是把运行信息交给观察系统。投影把事件整理成可读取的用量和上下文状态；导出后端决定资料怎样发送。TokenMeter 负责用量和容量状态，业务评分规则负责判断结果，计费按 Provider 报告和对应计费类别计算。

比较需要保持任务集、版本、模型选择和验收规则一致，再改变一个明确因素。通过率是通过数除以全部样本数；百分点是两个百分比的直接差，区别于相对增幅。平均数反映所有纳入样本的算术平均，中位数反映排序后的中间位置，失败样本怎样处理要先写清。

本章用一组十项任务的示例，说明怎样把质量、耗时和用量放在一起比较。

17.2 沿一个任务看完整流程

假设同一组十项任务，甲通过九项、消耗 20000 token；乙通过八项、消耗 14000 token。乙用量少了 30%，通过率却从 90% 降到 80%，差 10 个百分点。两种方案的取舍是用量下降、通过率也下降。

对每个任务同时记录输入标识、配置、产物、验收、接纳与终态时间、用量来源和失败原因。成功、失败与取消都保留；缺失数据不能填成零。费用按相应计费类别的用量乘单价求和，正式实验时再核验单价与缓存口径。

TokenMeter 注册用量、压力和材料组成等投影，供消费者按用途读取；Session 遥测协调事件并交给导出后端。这些过程信息与业务规则一起组成评价记录。例如“如实说明资料不足”可以是读取失败任务的正确产物，而不是要求每个样本都强行生成三点总结。

一次任务的三组记录

图 17A 的三栏记录过程时间、用量次数、质量与失败。每条任务记录共用任务身份，成功、失败和取消都进入统计。

TokenMeter 和遥测怎样提供运行数据

TokenMeter 注册三项投影，投影是从事件计算并持续更新的统计视图。tokenUsage 记录请求用量，contextPressure 估算上下文压力，contextBreakdown 展示材料组成。压力计算使用当前 Surface、请求信息和模型路由；符合复用条件时采用 Provider 用量，否则使用本地估计。界面同时展示数值与来源。

18.1 基本概念

扩展点是框架允许新增能力的位置，例如工具注册接口。接口契约既规定输入输出，也规定怎样处理生命周期、取消和结果。一个新能力复用这些位置，才能进入现有流程；插件通过 profile 挂载并注入依赖，工具定义才进入运行中的注册表。

规范值是执行体返回的结构化结果，供程序检查。schema 规定结构，render 将它转成模型内容，presentationMeta 提取可保存的展示资料。模型读取渲染文字，客户端从原始事件与 meta 派生界面组件数据。

真实 read 工具通过已选文件服务获取有界文本，再构造路径、行范围和总行数等结果。模型从渲染文字获取资料，界面从保存的展示元数据重建读取卡片。持久记录保存模型内容和展示元数据；界面恢复时读取这份记录。

这一章把启动装配、参数检查、工具准入、读取、结果记录和产品呈现连起来。新增能力的价值在于接上已有责任链，而不是再造一套绕开记录与限制的模型循环。

第 19 章｜Cordis 与 Spatiotemporal Composability：论文契约怎样落到 Harness

本章从资源登记、依赖变化和插件卸载三个问题出发，讲解 Cordis 的 Spatiotemporal Composability。先用定时器和工具注册理解机制，再把它们与论文的定义和生命周期规则对应起来。

论文是 A Programming Paradigm for Spatiotemporal Composability，作者 Yifan Shi、Wei Zhang、Tianyi Cui，本文采用 arXiv:2608.25512 的 v1（2026-08-26）。实现采用固定项目快照里的 @deepseek-ai/cordis 4.0.4。下面先解释论文模型，再说明 Cordis 4.0.4 的实现方式。

19.1 先理解问题：装入以后，还要能够撤离

假设文件工具插件装入时做两件事：注册 read，监听文件观察事件。模型于是能够使用工具，其他组件也能收到观察通知。后来配置改变，要换成另一份实现。如果只把插件名字从列表删除，旧监听器可能继续接收通知，旧工具也可能留在注册表；重新装入又登记一次，便会出现重复响应或旧对象继续被访问。

生命周期不仅关心“怎样让它工作”，还要说明“怎样停止并撤去它带来的贡献”。effect 是操作对状态造成的改变，例如增加一个监听器。disposer 是为撤销相应贡献而保存的动作，例如移除刚增加的那个监听器。inverse 在这里指可以撤回该操作的函数，而不是“再运行一次原函数”。

read 插件还依赖文件服务。提供者撤销服务后，消费者要重新检查依赖，退出当前实例或等待新的服务。服务名称标识可解析的能力，依赖声明列出装入前需要可用的入口。

论文把这两个问题放在一起：时间方向上，组件的贡献怎样撤回；空间方向上，组件怎样在当前 Context 中获取依赖并随环境变化重新装配。这就是 Spatiotemporal Composability：时间方向上的可撤回与空间方向上的依赖组合。空间维度指服务的组织和解析关系。

19.2 一个可逆操作需要交出什么

用一个工具集合说明数学记号。设状态 S 保存当前工具集合，装入 A 前为 {read}；执行操作 f 后为 {read, search}。同时保存的撤回动作 g 只移除 A 注册的 search，则 g(f(S)) 回到 {read}。写成关系是：先执行 f，再执行它给出的 g，恢复原状态。

这里的“状态”是数学模型描述的数据，“函数”是从旧状态得到新状态的规则。论文的 witnessed effect function 不仅返回新状态，还返回一项逆操作，并要求逆操作确实恢复其对应输入；Definition 8 给出这项见证条件。witnessed 表示函数附带满足该等式的数学见证。实现中的 ctx.effect 保存 disposer，组件作者负责让它满足恢复条件。

在程序里，disposer（释放函数）通常通过闭包保存所需信息。闭包是一个函数连同它以后仍需使用的外层值：例如清理回调记住本次创建的 timer 句柄，卸载时才能停止这个定时器，而不是误停别人的资源。登记资源时就把获得与释放放在一起，比以后重新寻找“我到底创建过什么”更容易保持对应关系。

释放动作由组件作者编写。以定时器为例，disposer 要记住创建时得到的 timer 句柄，并调用 clearInterval 停止它；只打印“已清理”不会停止定时器。论文 §5.1.1 将逆操作的正确性交给组件作者，Cordis 运行时负责登记和调用。文件写入、邮件发送等外部动作，则要由作者按对应服务的实际能力设计后续处理。

图 19A 从左向右展示资源交接：作者获取资源，返回记住这份资源的 disposer；Cordis 将它登记到当前 Fiber，卸载时调用作者提供的动作。

19.3 怎样把多个操作的撤回连起来

设一个组件先申请资源 A，再用 A 建立资源 B。撤离时先撤 B 再撤 A，才不会在清理 B 时发现基础资源已经消失。LIFO 是 Last-In-First-Out，后进先出；像把纸依次放到一摞的顶部，再从顶部取出。

论文把每一步返回的逆操作接到已有恢复动作之前，形成反向组合。effect iterator 让装入逐步推进；迭代器每次给出下一项，并说明是否结束。运行时因此可以在步骤之间记录进度、检查目标状态，决定继续装入还是进入撤离。

论文的反向组合、一个 ctx.effect 内的多步恢复、Fiber 上多个 effect 的释放采用不同组织方式。当前 Fiber._unload 用 Promise.all 等待同层释放任务，多个异步 disposer 会重叠运行。有严格依赖的两项清理，应写在同一个 disposer 中依次 await：先撤资源 B，再撤资源 A。

框架捕获并记录单项释放错误，其他释放任务继续推进。排查时，可以从错误记录找到所属实例和释放位置，再检查该项动作停在了哪里。

19.4 环境要求：coeffect、服务键与依赖

coeffect 描述组件执行需要从环境获取什么，例如文件服务；effect 描述执行对状态造成什么改变，例如注册工具。服务 key 是用于识别和解析某项能力的名称或标识。提供者发布该键下的能力，消费者声明自己需要它，Context 根据当前范围解析到实际实现。

理解一个组件时，可以依次查看它声明的依赖、提供的服务和装入行为。插件声明描述依赖，服务提供操作登记能力，Fiber 管理这次装入产生的资源。

例如插件 T 需要 tools 和 fs。tools 让它登记工具，fs 让它实现读取。只有依赖条件成立，运行时才推进该实例的装入。fs 的提供者撤去服务时，运行时通知相关消费者重新评价目标状态；它们需要退出当前装配或等待新的满足条件的环境。

响应式依赖意味着环境变化会推动实例重新计算目标状态。依赖注入使插件通过给定接口取能力，而不是自行硬编码每一个提供者。实例持有的连接、监听器和后台工作应通过资源管理接口登记，让卸载路径可以找到对应 disposer。

19.5 Fiber 与生命周期：目标变化时怎样收尾

Fiber 是组件的一次运行实例及其生命周期管理对象。每个 Fiber 保存自己的配置、依赖状态和释放动作。相同组件装入多次，可以有不同的 Context、配置、资源记录和状态；讨论清理时要指明是哪一个实例。

论文 §4 用抽象状态和转换规则研究装入、已激活、撤离等过程。论文中的 Reloading 包含推进装入的情形；论文用四类抽象状态表达规则；FiberState 枚举进一步区分运行时状态。实现与官方教程还区分 PENDING、FAILED、DISPOSED 等状态，用于表达依赖未满足、装入失败和实例终结。

装入正在等待连接建立时，配置可能改变。惯性原则要求先完成当前这一步，把结果与 disposer 交给框架，再决定继续装入还是撤回。资源由此及时进入清理记录。若外部操作迟迟不返回，这一步就一直等待；组件要在资源操作中配置超时或取消处理。

依赖撤离时还存在提供者与消费者的顺序问题。消费者的清理可能需要向提供者归还资源。论文的守卫演算通过等待关系限制过早回收，形式化讨论“提供者比它的消费者活得更久”的条件。

当前 Reflect.provide 的释放函数先从公共服务存储撤销入口，通知依赖实例，等待相关 Fiber，再清掉本实例保留的服务入口。这项 disposer 内部按上述顺序等待。Fiber 同层的其他 disposer 仍并发运行；需要消费者先退出才能释放的资源，应与该等待组织在同一受控释放流程中。

19.6 为什么“正向能交换”还不足以任意卸载

交换律表示先做 A 再做 B，与先做 B 再做 A，得到同样结果。设 A 登记自己的键 a，B 登记另一个键 b。若两项操作都只改变自己的独立槽位，最终集合可以相同。若两项都修改一个顺序敏感的中间件（请求依次经过的一串处理环节）列表，先后就可能改变请求经过的规则。

Definition 42 要求正向、撤回以及相关变换都满足独立性，并保持对方返回的逆操作与后续迭代。检查两次注册能否交换，只覆盖其中一部分；还要检查卸载 A 时，B 的贡献和后续运行是否保持。

一个错误清理例子是：A 注册前保存整个工具集合；B 后来登记自己的工具；A 卸载时把集合整体恢复成旧副本。A 确实记住了一个旧状态，却把 B 的合法贡献也抹掉。正确的撤回应识别并移除自己贡献的条目。遇到重名、覆盖、排序或共享资源时，还要把条目的替换和撤销规则纳入独立性检查。

这解释了为什么论文讨论服务提供者的责任：它发布的操作采用怎样的表示，直接影响其他组件能否独立撤回。服务提供者在设计注册和撤销规则时，就要处理这些独立性条件。

19.7 观测等价与证明条件

观测等价表示按指定的合法观察方式，看不到会影响契约的差别。相同工具集合不要求内存地址、分配顺序或运行时缓存逐字节相同。观察关系由模型规定；网络请求和外部设备写入则有它们自己的可观察状态。

论文 §3.3 通过观察关系界定状态相等的用途，§3.4 再讨论独立性与恢复。证明按这样的顺序展开：先规定状态、操作和观察；写下可逆和依赖条件；再证明满足条件的系统可怎样组合与撤回。

Theorem 73 的推进结果假设依赖先行关系无环、迭代长度有统一有限上界、整个序列涉及的实例名称有限，并且每一步遵守生命周期规则。无环意味着依赖箭头不会从某个组件绕回它自己。在这些条件下，论文给出没有规则层死锁以及有限推进到静止状态（不再有待推进的步骤）的结论。

例如 A 等 B、B 又等 A，构成依赖环，已经不满足 Theorem 73 的无环条件。这个例子说明，依赖图和步骤长度是推进定理本身的组成部分。

19.8 服务作用域与模块热重载

ctx.isolate(name, label) 为指定服务名建立新的解析标签，得到派生 Context。默认新标签使该名称在子范围中可以解析到另一项实现；相同标签可以让多个范围共享该服务解析空间。这些 Context 仍处于同一 JavaScript 宿主中，共享进程资源。

图 19B 先看两个 Context，再看右侧服务实现。派生箭头表示建立子 Context，解析箭头表示按服务标签找到实现。Context 乙为指定服务名使用新标签，其他服务继续沿继承关系解析；两个 Context 共用同一个宿主进程。

第 13 章的子 Session 组织历史与任务，第 11 章的执行环境限制资源访问，Context 的作用域组织服务解析。论文 §6.3 为不可信组件提出独立受限进程或容器等执行隔离，与这里的服务标签分工不同。

HMR 是 Hot Module Replacement，即热模块替换。项目的更新机制根据模块关系决定局部替换还是完整重载。当前 boot/hmr 检测到外部依赖变化时会走 fullReload（完整重载）并调用 loader.exit（结束当前进程以完成重载）。局部替换通过 disposer 释放旧贡献，完整重载则由 loader.exit 交给退出路径。

19.10 理解检查与讲解问答

问题 1：框架能够调用释放函数，为什么不等于保证释放正确？

讲解：登记把 disposer 与当前 Fiber 联系起来，卸载时框架调用它。以定时器为例，作者必须在 disposer 内调用 clearInterval，并传入本次创建的句柄。论文的见证条件要求恢复原状态；运行时的登记与调用实现资源管理，具体恢复动作由作者完成。

问题 2：同层两个异步释放函数，能否只靠登记顺序保证第一个完全结束后第二个才开始？

讲解：_unload 将同层释放函数映射成异步任务，再用 Promise.all 汇总等待。后启动的任务可以先结束。有先后依赖时，在同一个 disposer 中依次 await。

问题 3：把插件放入 ctx.isolate 后，能否运行不可信代码而无须其他隔离？

讲解：不能。它改变指定服务名的解析标签，仍是语言内组织机制。不可信代码的物理执行边界、桥接接口和可访问资源要另行设计。

追问：怎样向别人准确讲述 Cordis 的价值？

Cordis 把插件组织成声明依赖、登记资源、响应环境变化并释放贡献的运行实例。Context 解析服务，Fiber 管理实例状态，effect 保存资源与 disposer 的对应关系。论文解释这些机制需要满足的可逆性和独立性条件，源码给出装入、撤离与依赖通知的具体执行方式。
